AWS Application Migration Service
MGN（现称 AWS Transform MGN）· 服务器 Rehost — SAP-C02

AWS Application Migration Service（MGN，前身 CloudEndure Migration；当前 AWS 文档称 AWS Transform MGN）将兼容的物理、虚拟或云服务器复制到 AWS，并通过测试启动和正式切割支持 Rehost。它负责服务器级复制与启动，不会自动完成应用重构或数据库语义转换。

一、MGN 服务模型

MGN 面向服务器 Rehost：在源服务器安装 Replication Agent，将块级变更持续复制到 AWS 中的 Staging Area；测试或切割时按启动设置创建目标 EC2 实例。

  • 适用于希望尽量少改应用、通过受支持系统与环境快速迁移服务器的场景。先核对源操作系统、内核、磁盘、区域及网络要求是否在当前支持范围。
  • 服务复制的是服务器磁盘数据；仍需设计目标实例类型、启动模板、网络、IAM、DNS、负载均衡、监控和应用依赖。
  • MGN 是迁移工具，不是长期灾难恢复服务，也不负责重写应用、转换数据库 schema 或保证业务无停机。
考试主线：安装 Agent → 连通复制端 → Staging Area 持续复制 → Launch settings → Test launch 验证 → Cutover launch 切换 → Finalize 后停止复制。

二、复制架构与组件

组件 / 设置作用设计检查
Replication Agent读取源服务器块级变化并发送到目标区域的复制基础设施。安装权限、源操作系统/磁盘支持、出站连接、代理版本和凭据生命周期。
Staging Area临时承载复制数据的 AWS 网络与存储资源。子网、路由、实例类型、存储、加密、带宽和成本；与最终生产目标环境分开规划。
Launch settings / 模板定义目标 EC2 的实例、网络、磁盘等启动参数。按应用角色设置实例类型、子网、安全组、密钥、标签和启动顺序；测试后再次核对正式切割设置。
Test instance从已复制数据启动测试目标，验证启动和应用行为。使用隔离测试网络/DNS，验证依赖、数据一致性、性能、安全、代理和业务验收。
Cutover instance启动正式目标实例，配合业务切换流量。冻结或协调源端写入、确认复制延迟和业务窗口，预先定义回退条件。

复制延迟不仅由 MGN 决定，也受源端变更速率、网络吞吐、磁盘 I/O 和目标区域容量影响。持续监控复制状态并验证瓶颈，不能仅凭 Agent 安装成功就判定可切换。

三、迁移生命周期：测试先于切割

  1. 发现并分组：整理服务器、应用依赖、端口、数据持久性、启动顺序、许可和业务负责人。
  2. 准备目标：配置 MGN、Staging Area、IAM、加密、网络连通性、服务配额、启动模板与标签。
  3. 安装与复制：部署 Replication Agent，等待初始同步完成；持续观察复制健康、延迟、错误和资源。
  4. Test launch：在目标环境启动测试实例，执行技术和业务验证；发现问题后调整模板/网络并重新测试。
  5. Cutover launch：选定切换窗口，确认业务冻结/数据策略和复制状态，启动目标并切换 DNS、负载均衡或客户端路由。
  6. 验收与 Finalize：确认业务、监控、备份和安全控制稳定后完成迁移；Finalize 会结束该服务器的迁移流程并停止持续复制，执行前要确认已不需要回退到源端。
把回退设计在切换之前：保留源端和复制状态直到业务验收门槛满足；切换后源端是否仍可写、如何避免双写，必须明确而不能靠临场判断。

四、准备、网络与安全

  • 源服务器需访问所需的 AWS 服务端点/复制服务；核对出站防火墙、代理、DNS、路由、端口和区域端点。不同部署要求应以当前 MGN 文档为准。
  • 目标 VPC 的子网、路由、NACL、安全组、DNS 和应用依赖必须就绪；Staging Area 可达不等于切割后的生产实例可达。
  • 用最小权限 IAM 角色和安全凭据安装/管理 Agent；配置 KMS 加密权限、CloudTrail 审计和 CloudWatch 监控。
  • 检查 EC2 配额、实例类型可用性、EBS 限制、IP 地址、许可证/主机名绑定、启动脚本及系统时钟。
  • 规模化迁移要自动化安装、分组、启动模板和验收步骤；先做端到端试点并记录失败恢复流程。

六、场景题解析

场景一：大量服务器需快速迁至 EC2，尽量不改应用

源环境包含物理机和虚拟机，业务要求先完成迁移再逐步现代化。

方向：评估 AWS Application Migration Service，部署 Agent，持续复制后按测试/切割流程迁移。
场景是服务器级 Rehost，并要求复制和受控启动。
不要把 MGN 描述为自动重构应用或迁移数据库 schema 的服务。

场景二：切换前要证明目标系统能启动且业务正常

迁移团队需要先行验证网络、依赖和性能，避免直接影响生产。

方向：等待初始复制完成后执行 Test launch，在隔离环境验证，再根据发现调整设置。
Test launch 是正式切换前验证目标实例的关键门槛。
仅检查复制状态不能替代应用级验收。

场景三：Agent 已安装，但复制一直落后

源端产生大量写入，且数据中心出口被限速。

方向：检查源端变更率、网络带宽/防火墙、复制组件健康和目标资源，先解决吞吐瓶颈再安排切换。
初始同步完成与持续复制追平是不同状态。
不要仅重装 Agent，也不要在未满足延迟门槛时盲目 Cutover。

场景四：生产目标启动后仍需保留回退可能

业务要求先观察稳定性，确定成功后再结束源端复制。

方向：执行 Cutover 并按预案切换流量；保留源端/复制状态直到业务验收，再决定何时 Finalize。
Finalize 是迁移生命周期的终结动作，应在确认不再需要该复制链路后执行。
不要在验证前 Finalize，也不要让源端和目标端同时无协调地接受写入。

场景五：目标 EC2 启动但无法访问后端服务

Staging Area 状态正常，正式目标应用实例在不同子网。

方向：排查目标生产 VPC 的路由、安全组、NACL、DNS、后端白名单和依赖顺序。
复制网络可用与生产网络可用是两个独立的验证面。
不要把 Staging Area 的连通性当成最终应用网络已经验证。

场景六：迁移后需长期具备跨区域恢复能力

要求持续复制并在灾难时快速恢复，而不是一次性离开源数据中心。

方向：评估 AWS Elastic Disaster Recovery (DRS) 的 DR 设计；MGN 处理迁移任务，两者目标和持续运营模式不同。
工具选择取决于“迁移并切割”还是“持续灾难恢复”这个业务目标。
不要因为两者都涉及复制，就将 MGN 与 DRS 视为相同服务。

九、快速自测

1. MGN 迁移的一般顺序是什么？

安装 Agent 并复制 → Test launch 验证 → Cutover launch 切换 → 验收后 Finalize。

2. 为什么初始同步完成不代表可以立即切换？

仍需确认持续复制延迟、目标启动设置、应用依赖、网络、性能和业务验收。

3. 长期跨区域灾难恢复和一次性 Rehost，工具目标是否相同？

不同。迁移可评估 MGN；持续灾难恢复应评估 DRS 的恢复设计与运营流程。
