一、迁移框架：先业务，后技术

迁移决策的输入包括业务价值、合规要求、依赖关系、停机窗口、性能目标、技能、许可和预算。先建立应用组合清单和依赖图，再制定目标状态与迁移波次。

  • 明确目标：退出数据中心、降低成本、提高弹性、提升创新速度、满足合规或停止低价值应用。
  • 建立事实基线：采集服务器/数据库配置、资源利用率、软件许可、依赖、数据量、网络流量和业务关键性；区分“当前运行状态”与“目标需求”。
  • 选定策略：逐应用确定 7R；一个应用组合可采用不同策略，不必全站统一 Rehost 或 Refactor。
  • 验证执行能力：先用试点验证网络、身份、安全、自动化、运维和回退，再按依赖关系组织波次。
决策原则：“最快离开机房”通常指 Rehost；“最大化云原生收益”常指 Refactor/Re-architect，但需承担更高成本、周期与变更风险。题目目标决定答案。

二、7R 策略对照

策略核心动作典型线索 / 代价
Retire
退役		关闭不再需要的应用或重复资产。低使用率、已被替代；先确认依赖、数据保留和合规要求。
Retain
保留		暂不迁移，继续在原环境运行。近期无迁移价值、法规/依赖未解除、即将淘汰；记录后续复审条件。
Rehost
重新托管		尽量少改动，将服务器迁移到 AWS（Lift and Shift）。时间紧、应用改造空间有限；上线快，但云原生收益有限，旧架构问题可能保留。
Relocate
重新定位		将整套基础设施/工作负载迁移到云端平台，而不改应用架构。常见于 VMware Cloud on AWS 等平台级迁移；与逐机复制的 Rehost 区分。
Replatform
重新平台化		做有限优化以使用托管服务，不重写核心架构。例如自管数据库迁至兼容托管数据库；改造适中，需验证兼容性与运维差异。
Repurchase
重新购买		用 SaaS 或其他商业产品替换现有应用。放弃旧软件转用 SaaS；关注数据迁移、集成、许可和供应商锁定。
Refactor / Re-architect
重构 / 重构架构		大幅修改或重新设计应用以利用云原生能力。需要弹性、敏捷、微服务或持续创新；长期收益潜力高，但工程投入、时间和风险也高。
术语陷阱：有些材料将 Refactor 与 Re-architect 拆开描述；AWS 7R 框架常把它们作为同一策略表述。按题目强调的“重大重写/云原生重设计”识别，不要把简单升级误判为重构。

三、策略选择决策树

  1. 应用还需要吗？不需要 → Retire；需要继续运行但暂时不迁 → Retain。
  2. 是否整体替换为 SaaS/新产品？是 → Repurchase；否则继续。
  3. 是否要把平台/整套环境原样搬到云平台？是 → Relocate；若逐工作负载迁移且尽量不改代码，优先评估 Rehost。
  4. 是否要利用托管平台，只接受有限改造？是 → Replatform；若核心架构需重写以满足长期业务目标 → Refactor/Re-architect。
  5. 约束是否要求最短时间、最小初始改动？若是且风险可接受，Rehost 常是过渡方案；之后可分阶段现代化。

实际方案需要评估应用耦合、数据重力、许可证、目标服务限制和迁移团队能力。依赖紧密的应用应放在同一波次或明确先后顺序；不要只按服务器清单机械分批。

四、商业案例与 TCO

比较的不是“本地硬件账单”与“EC2 单价”，而是相同业务范围、服务级别和分析周期下的总拥有成本与风险。

成本 / 收益维度评估要点
现有环境服务器折旧、机房/电力、维护、人力、软件许可、网络、备份、灾备和容量闲置。
AWS 运行成本计算、存储、数据库、网络传输、日志监控、安全、备份、支持计划及弹性峰值。
一次性迁移投入发现评估、工具、网络、并行运行、数据传输、测试、培训、应用改造和停机窗口。
许可与合同BYOL 条件、订阅模式、操作系统/数据库许可、SaaS 合同和退出成本。
收益与风险退役机房、部署速度、可用性/弹性收益；同时量化宕机、延期、性能不达标与锁定风险。

AWS Migration Evaluator 可帮助盘点和构建迁移商业案例；AWS Pricing Calculator 可基于目标架构估算 AWS 费用。估算必须明确使用率、区域、承诺折扣、增长、数据传输和成本归属假设。

TCO 不是单次报价：用试点和迁移后的实际账单校准假设，检查资源是否过度配置，并将成本归属、预算和优化责任纳入运营模型。

五、迁移阶段与波次

阶段目标产出 / 门槛
Assess 评估确认业务驱动、应用组合、依赖、准备度和商业案例。清单、依赖关系、7R 初判、TCO/业务案例、目标指标。
Mobilize 动员建立 Landing Zone、身份/安全/网络/运维基础及迁移能力。试点经验、运行手册、自动化、波次计划、风险和回退方案。
Migrate & Modernize 迁移与现代化按波次迁移、验证、切换，并在适当时优化架构。测试证据、业务验收、切换决策、稳定运行和后续优化 backlog。
  • 波次依据应用依赖、业务窗口、数据规模、复杂度和团队能力设计；先迁移低风险试点验证通用路径。
  • 每个波次明确负责人、入口条件、目标状态、数据同步、切换窗口、业务验证和回退条件。
  • 迁移成功不等于立即退役源端；完成稳定性观察、数据留存确认和业务签收后，再按治理流程清理。

六、场景题解析

场景一：六个月内退出机房，应用几乎不能改

优先目标是缩短迁移周期，未来再逐步优化。

方向：将适合的工作负载 Rehost，按依赖分波迁移并规划后续现代化。
低改动、速度优先符合 Lift and Shift；并不意味着它是长期最优架构。
不要因为 AWS 有托管服务就把需要重写的 Re-architect 选为短期退出策略。

场景二：不再使用的旧应用仍占用服务器

业务确认功能已由新 SaaS 替代，历史数据留存义务可满足。

方向：Retire 旧应用；若要购买 SaaS 替代仍在使用的旧软件，则该替代决策属于 Repurchase。
先确认下游依赖、数据保留、合同与审计要求，再关闭资源。
Retire 是退役，不是把应用迁到另一个 AWS 服务。

场景三：VMware 整体迁移，尽量不改虚拟机和应用

要求平台级搬迁，并希望减少逐台重新部署工作。

方向：评估 Relocate 路径（例如 VMware Cloud on AWS 的平台级迁移），而不是把术语与逐机 Rehost 混为一谈。
具体可行性取决于源平台、版本、目标架构和现行服务支持。
只看到“虚拟机迁移”不足以判断；要看题目是否强调整个平台/环境 relocation。

场景四：希望停止自管数据库，但暂不重写应用

应用可通过兼容性测试连接托管数据库，允许有限配置调整。

方向：评估 Replatform 到托管数据库；验证引擎兼容性、扩展、驱动、性能和运维差异。
有限优化利用托管能力，符合 Replatform；若必须重写数据层，则要评估 Refactor。
不能仅因目标是托管服务就忽略应用兼容性与迁移工作量。

场景五：成熟商业系统将被 SaaS 产品整体替换

无需在云上继续维护原应用代码，但需迁移数据和重新集成。

方向：Repurchase，并规划数据导入、身份集成、接口改造、许可和供应商退出条款。
替换为不同产品与将旧系统原样搬迁是两种不同决策。
SaaS 产品运行在云上不意味着旧应用采用了 Rehost。

场景六：多年路线图要求事件驱动弹性与快速迭代

核心应用单体架构限制业务扩展，组织愿意投资渐进式重写。

方向：评估 Refactor/Re-architect，拆分路线图并以业务指标、试点和风险门槛推进。
大幅重设计可以获得长期云原生收益，但投入和执行风险更高。
不要仅凭“云原生”口号直接重写；必须以业务目标和可验证收益支撑。

九、快速自测

1. 最短时间将应用迁出机房且尽量不改代码，优先考虑什么？

Rehost。目标是低改动 Lift and Shift；之后可安排 Replatform 或 Refactor。

2. 一个应用已被 SaaS 替代，不再需要旧系统，属于哪种策略？

停止旧系统属于 Retire；采购 SaaS 替代仍在使用的产品属于 Repurchase。

3. 7R 中哪种策略以重大架构改造换取长期云原生收益？

Refactor / Re-architect；需用业务目标证明投入合理，并控制改造风险。
