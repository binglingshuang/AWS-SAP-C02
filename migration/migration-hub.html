AWS Migration Hub 与 ADS
迁移组合发现与进度跟踪 — SAP-C02

Migration Hub 提供迁移组合的集中跟踪视图；AWS Application Discovery Service（ADS）帮助发现本地服务器清单、配置和依赖信息。它们支撑评估、波次规划和状态可视化，本身不搬迁服务器或数据库。

一、服务职责：看清组合，不替你搬迁

Migration Hub 用于集中查看和跟踪迁移项目及应用进度，并接收支持迁移工具的状态；ADS 用于采集或导入源环境发现数据，帮助理解服务器清单和应用依赖。

能力负责什么不负责什么
Migration Hub迁移组合的应用分组、状态跟踪与集中可视化；与受支持迁移工具的状态集成。不是服务器复制引擎、数据库迁移引擎，也不自动完成 cutover。
Application Discovery Service (ADS)收集/导入服务器配置、资源利用率或依赖相关发现数据，为评估和规划提供输入。发现结果不是完整应用架构保证；不能替代业务访谈、验证和迁移测试。
MGN / DMS执行服务器迁移或数据库数据迁移/复制。执行工具不等于组合级治理视图；需将迁移结果与应用、波次和业务验收关联。
记忆句：ADS 帮你发现“有什么、如何关联”；Migration Hub 帮你跟踪“迁到哪一步”；MGN/DMS 等工具才负责实际迁移工作。
当前服务状态（截至 2026-11）：AWS Migration Hub 自 2025-11-07 起不再向新客户开放，ADS 也不再向新客户开放；AWS 建议新客户评估 AWS Transform 的相似能力。SAP-C02 仍可能考查 Migration Hub 的 home Region / 状态跟踪及 ADS 的发现概念；实际部署需先确认账户资格和当前服务文档。

二、ADS：采集清单与依赖信息

发现方式适合情况采集 / 注意事项
Discovery Agent需要从受支持服务器获取更细粒度的系统和进程信息。按支持条件安装并联网；关注凭据、权限、网络、部署规模和数据上传状态。
Agentless Collector对 VMware 环境进行无代理发现。在受支持的 VMware 环境配置采集器和只读访问；核对当前能采集的配置/利用率类型及限制。
数据导入已有 CMDB、盘点表或其他来源的服务器信息。映射字段、统一标识、清理重复记录并标明时间戳/来源；导入清单不等同实时发现。
  • 发现数据用于形成服务器清单、规格/利用率基线和依赖图，支持分组与目标架构规划。
  • 依赖映射是规划线索：周期、协议、权限或未观测到的连接可能导致遗漏；应通过日志、网络数据和应用负责人交叉验证。
  • 发现窗口要覆盖业务高峰和周期性作业，才能避免仅凭短时间低利用率错误估算容量。
发现代理或采集器的部署授权需谨慎：使用最小权限、限定网络访问、保护采集数据，并按组织治理政策管理生命周期。

三、应用分组与迁移进度跟踪

  1. 定义应用边界：把服务器、数据库、共享存储、接口和业务负责人关联到应用；明确应用间依赖。
  2. 构建波次：依据耦合关系、关键路径、风险和维护窗口组织迁移批次，并定义每波目标与验收标准。
  3. 关联执行工具：通过支持的集成或流程更新迁移状态；按服务器、应用和波次核对状态是否一致。
  4. 跟踪异常：发现未启动、复制异常、测试失败、阻塞依赖或状态未同步时，指派负责人和恢复期限。
  5. 完成验收：将工具状态与业务验收、性能/安全检查和源端退役条件关联，不把“迁移工具显示完成”直接等同于业务完成。

Migration Hub 可集中展示集成迁移工具的状态；具体工具、区域、功能和工作流支持可能变化，应以当前 Migration Hub 文档及账户区域可用性为准。

四、从发现到项目闭环

步骤关键动作可检查的产出
1. 发现部署 ADS Agent/Collector 或导入清单，收集并校准数据。服务器台账、利用率基线、依赖和数据质量问题。
2. 组合评估分组应用，确认业务关键性、7R、约束、数据迁移和目标状态。应用所有者、目标策略、风险、商业案例输入。
3. 准备在 Migration Hub 中建立跟踪结构和项目流程，配置区域及权限。统一标识、波次、状态定义、访问控制和报告口径。
4. 执行用 MGN、DMS 或其他适合的工具迁移，更新集中状态。工具执行结果、问题队列、测试与切换计划。
5. 关闭业务验收，稳定观察，处理源端退役和成本治理。验收证据、例外批准、数据保留与资产清理记录。

五、边界、区域与治理

  • 不是迁移引擎：Migration Hub 不能代替 MGN 的服务器复制、DMS 的数据库迁移或 DataSync 的文件传输。
  • 不是 CMDB 自动真相：发现数据存在采集时间、范围和可见性限制，需要持续更新并与权威资产来源对账。
  • 区域设计：Migration Hub 和相关发现/迁移能力的可用区域、home region 或跨区域行为应按现行服务说明规划；团队报告保持一致的区域和标识。
  • 访问治理：为采集、查看、集成和项目管理配置最小权限；使用 CloudTrail 等审计控制面操作，并管理采集数据的保留与访问。
  • 状态治理：定义统一状态映射和更新时间；工具未集成或状态未同步时采用明确的流程更新，不能将缺失状态显示为成功。

跨模块迁移执行内容参见 MGN、DMS/SCT 和 DataSync/Transfer Family 专题。

六、场景题解析

场景一：企业不知道数百台服务器之间的依赖

需要在规划迁移波次前盘点环境和应用关联。

方向：使用 ADS 的 Agent、Agentless Collector 或数据导入等适合方式建立发现基线，再与应用负责人验证依赖和分组。
发现能力为迁移评估提供数据，不代表自动生成可靠的最终波次。
不要仅根据短时间采集结果断言没有依赖。

场景二：管理层需要统一查看多个工具的迁移状态

各团队使用不同受支持的迁移服务，状态分散难以汇总。

方向：评估 Migration Hub 的集中跟踪和支持的工具集成，建立一致的应用/波次标识和状态映射。
Hub 提供可视化和跟踪，底层迁移仍由集成工具执行。
不能要求 Migration Hub 自己复制服务器或迁移数据库。

场景三：已有 CMDB 清单，但部分数据无法安装 Agent

需要快速导入已知服务器，再对关键应用补充发现。

方向：评估 ADS 数据导入路径，清理重复/过期记录并标注来源，再按需要补充代理或无代理发现。
导入可利用现有盘点资料，但仍需验证字段完整性、时效和身份匹配。
不要把静态导入清单视为持续自动发现。

场景四：发现图没有显示夜间批处理对数据库的连接

采集期间没有覆盖作业窗口，团队准备据此拆开应用迁移。

方向：延长/调整发现窗口，检查采集范围，并与作业配置、日志和业务团队交叉验证后再定波次。
遥测覆盖不完整会造成依赖图假阴性。
未观测到依赖不等于不存在依赖。

场景五：MGN 已报告服务器完成，但业务仍无法验收

迁移状态显示成功，应用测试和业务确认尚未结束。

方向：在 Migration Hub 跟踪状态之外，继续完成应用验证、性能/安全检查和业务签收，再满足波次关闭条件。
工具层完成状态与业务迁移完成定义不同。
不要用迁移工具状态代替业务验收。

场景六：采集权限扩大后出现未经批准的服务器访问

发现工具账号被授予过宽权限，且采集数据包含敏感系统信息。

方向：收敛到最小权限、限定网络路径、保护采集数据，并审计访问与配置变更。
资产发现数据同样属于需要治理的运营和安全信息。
不要以“只是盘点”作为广泛凭据和无限期数据保留的理由。

九、快速自测

1. ADS 是否负责迁移服务器数据？

否。ADS 负责发现或导入环境信息；服务器迁移可由 MGN 等工具执行。

2. Migration Hub 的核心价值是什么？

集中跟踪迁移组合和受支持工具的进度，不是底层复制引擎。

3. 依赖图没有显示服务调用，是否能确认不存在依赖？

不能。要检查采集覆盖、时间窗口和权限，并通过日志、配置及业务负责人验证。
