托管内存缓存

一、定位与选型

ElastiCache 是托管的内存数据存储与缓存服务，常用于降低数据库读取负载、缩短重复查询延迟、保存会话或支持实时排行榜等数据结构。缓存通常是可重建的加速层，不应默认当作唯一持久化数据源。

决策顺序：先明确应用所需的数据结构与客户端协议，再判断是否要求复制/故障切换/持久化，然后选引擎和集群拓扑。若需求是跨数据库查询加速，先确认是否应使用 RDS Proxy、DAX 或应用缓存，而非一律加缓存集群。
  • 典型路径：应用 → 缓存命中则返回；未命中则读数据库、回填缓存并返回。
  • 低延迟并不等于持久化；节点故障、过期和淘汰都可能造成缓存未命中。
  • Redis OSS 兼容引擎和 Memcached 的特性、集群模型及客户端方式不同；评估具体版本与 AWS 区域支持。

二、Redis OSS 与 Memcached

维度Redis OSS（含 Valkey 兼容选项，按部署支持）Memcached
数据结构字符串、哈希、列表、集合、有序集合等，适合排行榜、计数器、队列类缓存场景简单键值缓存，适合可拆分的对象缓存
复制与 HA复制组可配置主节点与只读副本，并配合 Multi-AZ 自动故障转移（依配置与模式）节点间不复制；节点丢失的数据需由应用回源重建
分片集群模式启用时可跨分片水平扩展；客户端需支持集群协议通过客户端一致性哈希将键分散到多个节点
持久化/备份支持备份能力（快照与适用配置依引擎/部署模式）；仍应核实恢复目标缓存节点不提供同类数据持久化保障
多线程主要执行模型与版本/引擎实现相关多线程处理请求，简单缓存工作负载可利用多核
常见选择需要复制组、数据结构、备份或 Global Datastore 等能力时优先评估需要简单、可横向扩展的纯缓存且不需要复制/持久化时评估
不要只凭“Redis 功能更多”做决定：选择受可用 API、应用客户端、版本兼容性、成本、故障恢复要求和服务当前支持矩阵约束。

三、拓扑与扩展

集群模式关闭

单个分片可包含主节点和只读副本。适合数据集能够放入单分片、希望用副本扩读并简化客户端路由的工作负载。副本通常承担读取；写入仍到主节点。

集群模式开启

数据键空间划分到多个分片，每个分片可有副本。适用于需要超出单分片容量或写入吞吐的场景；必须采用支持集群发现与重定向的客户端，并为扩缩容和重分片行为做验证。

Memcached 集群

多个节点由客户端分散键，不提供节点间复制。添加或移除节点可能改变键映射，带来短时缓存未命中；数据库仍应能承受回源流量。

需求优先考虑关键限制
更大的 Redis 数据集/写入横向扩展Redis OSS 集群模式开启，多分片客户端需支持集群；分片间查询与事务能力有边界
读扩展与副本故障切换Redis OSS 复制组与只读副本复制存在延迟；副本读不是强一致性读
简单对象缓存，失效可回源Memcached 多节点无复制与持久化；扩缩容可能导致缓存重建

四、高可用与持久化

  • Redis OSS 复制组：主节点处理写入，副本提供读扩展和冗余；Multi-AZ 与自动故障转移可提升节点故障恢复能力。
  • 故障转移：应用使用稳定的主/配置端点并能重连；不要把节点地址硬编码。故障期间可能发生短暂不可用或未复制写入丢失，按业务容忍度验证。
  • 备份：支持的 Redis OSS 部署可创建备份用于恢复/复制；制定保留期、恢复演练及目标区域策略。备份不是实时高可用替代品。
  • Memcached：节点失败即丢失该节点缓存项，应用从权威存储重建；用限流、请求合并和抖动 TTL 避免缓存雪崩压垮数据库。
  • Global Datastore：适用的 Redis OSS 跨区域复制组功能可服务区域级 DR/本地读取；跨区复制是异步的，评估复制延迟、提升流程与写入拓扑。
缓存不是数据库备份：若重建缓存会造成不可接受的数据丢失，就必须把权威数据放在持久化数据库中，并明确缓存恢复策略。

五、缓存模式与失效

模式读写路径适合风险/控制
Lazy Loading / Cache-Aside读：先缓存，未命中回源并填充；写：通常先更新数据库，再失效缓存读多写少、可接受首次未命中冷数据永不缓存；缓存与数据库可能短暂不一致
Write-Through写入数据库时同步更新缓存读频繁且希望热点数据已预热写延迟与缓存写流量增加；需要定义失败补偿
TTL / 过期为键设定有效期，过期后回源允许一定陈旧窗口的数据同一时刻过期可造成惊群；TTL 加随机抖动
请求合并 / 负缓存同键并发只做一次回源；短期缓存不存在结果热点键、重复无效查询负缓存需谨慎设置短 TTL，避免掩盖新创建数据

常见保护：缓存击穿使用请求合并/互斥刷新；缓存雪崩使用 TTL 抖动、分批预热、回源限流；缓存穿透使用输入校验或短期负缓存。根据一致性要求，明确写后失效顺序并处理并发更新。

六、安全与运维

  • 部署在 VPC 子网组中，安全组仅允许应用安全组访问缓存端口；不要把缓存端点暴露到公网。
  • 使用传输中加密、静态加密、认证/访问控制能力（由引擎、版本与部署模式决定）；密钥和凭证按最小权限管理。
  • 监控 CPU、内存、连接数、命中率、淘汰数、复制延迟、网络流量、故障转移和应用端延迟。
  • 命中率下降可能源自键设计、TTL、工作集变大或扩缩容；内存压力可能导致淘汰，需结合数据淘汰策略和实例规格分析。
  • 客户端应具备连接池、超时、重试退避、故障转移重连和缓存不可用时的降级/限流方案。

七、场景题解析

场景一：购物网站用缓存数据库读压力仍高，热点数据需要副本读取与自动故障切换

判断：评估 Redis OSS 复制组，部署只读副本并启用适用的 Multi-AZ 自动故障转移；应用读副本端点，写主端点。

陷阱：Memcached 节点没有复制组式副本故障转移。

场景二：会话/排行榜需要集合、有序集合等数据结构和多节点水平扩展

判断：选 Redis OSS 兼容引擎并评估集群模式开启，采用支持集群的客户端和多分片拓扑。

陷阱：副本解决读扩展/冗余，不等于跨分片扩展写入容量。

场景三：静态商品对象缓存允许丢失，追求简单多核缓存扩展

判断：Memcached 多节点可作为候选；由客户端分散键，缓存丢失时从数据库重建。

陷阱：不可把 Memcached 作为会话或业务数据的唯一存储。

场景四：大量键同一时刻过期后，数据库 CPU 飙升

判断：TTL 加随机抖动，热点刷新采用请求合并/预热，并为回源设置限流与退避。

陷阱：单纯增加缓存节点不能根治同步过期引起的回源风暴。

场景五：要求区域灾难恢复且用户可在另一地区低延迟读取

判断：评估 Redis OSS Global Datastore 跨区复制，并演练提升/切换和应用端点更新。

陷阱：异步复制不等于零 RPO；跨区域缓存也不是权威数据库的 DR 方案。

场景六：缓存短暂不可用时不能让数据库被瞬时流量击垮

判断：缓存客户端配合熔断、请求合并、限流、退避和容量预留；压测冷缓存/节点故障时的回源行为。

陷阱：缓存可用性不能替代后端过载保护。

八、关键词速查

关键词考试速记
Cache-Aside未命中回源；需设计失效与 TTL
Write-Through写路径同步更新缓存；提高命中但增加写成本
Cluster Mode Enabled多分片水平扩展；客户端需支持集群
Replication Group主副本复制组；读副本和故障转移能力依配置
Memcached简单键值、客户端分片；无节点复制/持久化保障
Global Datastore适用的 Redis OSS 跨区域异步复制能力

  • 用途：缓存是加速层，权威数据留在持久化存储
  • 选型：由数据结构、复制、持久化和客户端能力驱动
  • Memcached：简单键值缓存，没有节点间复制
  • Redis OSS：支持丰富数据结构及复制组能力
  • 集群关闭：单分片，可配置副本读
  • 集群开启：多分片扩容，客户端必须支持集群
  • 写入：主节点处理写，副本读可能有复制延迟
  • Multi-AZ：复制组故障转移提高可用性
  • 备份：用于恢复，不等同实时高可用
  • Global Datastore：跨区异步复制，需评估 RPO
  • Lazy Loading：按需回源填充，首次读取未命中
  • Write-Through：同步更新缓存，读命中较好但写路径更重
  • TTL：适配数据新鲜度，随机抖动可减少雪崩
  • 击穿：热点键请求合并或互斥刷新
  • 穿透：校验输入，谨慎使用短期负缓存
  • 安全：VPC 私网、安全组、加密与最小权限
  • 监控：观察命中率、淘汰、内存、连接与复制延迟
  • 韧性：缓存故障时回源限流、退避并进行冷缓存压测

十、快速自测

1. 需要缓存排行榜，并要求数据集水平分片扩展，应优先选择？
正确答案：B。Redis OSS 数据结构适合排行榜，集群模式可分片扩容，客户端必须支持集群协议。
2. Memcached 节点丢失数据后，正确的恢复来源是什么？
正确答案：A。Memcached 没有节点间复制；应用和后端必须能承受冷缓存回源。
