AWS DMS 与 SCT
数据库迁移与 Schema 转换

把迁移拆为结构转换、数据装载、变更捕获、验证和切换。DMS 负责受支持数据库之间的数据迁移/复制；AWS Schema Conversion Tool（SCT）用于异构 schema 与代码转换评估/转换，二者常组合使用而非互相替代。

一、工具职责：SCT 与 DMS 分工

工具主要职责典型输出/组件边界
AWS Schema Conversion Tool (SCT)评估并转换异构数据库 schema 与可转换代码对象目标 schema、转换评估报告、待手工处理项不能保证所有存储过程/应用 SQL 自动转换；报告与人工改造不可省略
AWS Database Migration Service (DMS)在受支持源/目标之间迁移和复制表数据复制实例或 Serverless、源/目标端点、迁移任务不能自动解决全部 schema/语义转换；需核对引擎组合与限制
原生数据库工具按引擎特性导出、导入、备份或恢复备份文件、dump/restore、原生复制能力选择取决于数据规模、停机窗口、目标兼容和迁移架构
一句话记忆：SCT 处理“结构/代码如何变”；DMS 处理“数据如何搬、如何持续复制”。同构迁移通常无需 SCT，异构迁移常用 SCT + DMS，但必须以实际引擎组合和转换报告为准。

二、同构与异构迁移

类型例子Schema 工作方案关注点
同构相同数据库引擎的源到目标结构基本兼容，通常无需 SCTDMS full load/CDC、原生复制或备份恢复；对比停机窗口、数据库版本和数据量
异构Oracle → Aurora PostgreSQL；商业引擎 → 开源引擎类型、函数、SQL、过程语言和索引差异需评估/转换SCT 评估并转换可支持对象，人工改写剩余项；DMS 搬数据并可 CDC

同引擎不代表完全无差异：版本、字符集、排序规则、扩展、权限、时区、LOB、序列和应用行为都可能带来迁移工作。异构迁移更要先处理数据库对象和应用 SQL，而不是只启动数据复制。

三、端到端迁移流程

  1. 发现与评估：盘点源引擎/版本、schema、对象依赖、数据量、写入峰值、网络、加密、RPO/RTO 和停机容忍度。
  2. 选择路径：确定同构/异构，选 DMS、SCT、原生工具或组合；用 DMS 支持矩阵确认源/目标、CDC、LOB 和 Serverless 能力。
  3. 准备目标：建立目标数据库、网络路由、子网组、安全组、DNS、证书、KMS/凭据和监控。
  4. 转换 schema：异构时运行 SCT 评估，转换 schema/代码；处理不支持对象并先部署、测试目标结构。
  5. 全量装载：创建源端点、目标端点与任务，设置表映射、并行度、LOB 和错误处理，监控装载进度。
  6. 持续复制：需要缩短停机时，在支持组合上启用 CDC 或 Full load + CDC，观察源/目标延迟与错误。
  7. 验证与切换：校验行数/抽样/业务总额，冻结写入或短暂停机，等待延迟归零，切换应用连接并持续观察。
  8. 收尾：确认回滚窗口后清理复制资源；保留审计记录并复盘性能与成本。
先做 PoC：迁移工具支持的引擎版本、表类型、LOB、CDC 操作和对象转换都有具体边界，必须用代表性数据验证。

四、Full Load、CDC 与任务类型

任务类型行为适用情况
Migrate existing data / Full load把现有源数据装载到目标，完成后任务结束或停止允许停机窗口、一次性批量迁移
Replicate ongoing changes / CDC复制任务启动后的源端变更（具体起点依配置）目标已初始化、需要持续同步增量
Full load + CDC先装载既有数据，再持续捕获并应用变更大多数低停机迁移的常见组合
  • CDC 基于源数据库日志/变更机制，需满足日志保留、权限、配置和引擎支持要求。
  • Full load 与并发写入期间可能出现装载/变更应用协调问题；按 DMS 文档和任务模式配置并验证一致性。
  • 复制延迟不是零停机保证。切换前仍需规划写入冻结或短暂只读窗口，并确认目标追平。
  • 重试可能重放操作；检查任务错误、目标约束和应用幂等性，避免把“任务 running”当作数据已验证。

五、拓扑、网络与运行设计

  • 复制资源：DMS Replication Instance 或适用的 DMS Serverless 提供迁移计算资源；按数据量、并发、LOB、吞吐和延迟压测选型。
  • 端点：源端点和目标端点分别配置连接信息、凭据、证书、引擎特有参数；凭证使用 Secrets Manager/受支持的安全集成并限制权限。
  • 网络：检查 VPC、子网、路由、VPN/Direct Connect、DNS、安全组、防火墙和源数据库可达性；跨账户/区域时单独验证连接与授权。
  • 任务：表映射筛选需要迁移的 schema/table；配置目标表准备方式、并行加载、错误处理、日志和任务启动模式。
  • LOB：全 LOB 模式可处理较大 LOB，但可能降低性能；有限 LOB 模式需设定最大长度并接受截断风险。按业务验证。
  • 变更控制：避免迁移期间源/目标双向写入，除非专门设计冲突解决；记录切换点和回滚决策。

六、转换报告、验证与切换

SCT 评估报告

使用评估报告识别自动转换率、不可转换对象和目标平台缺失功能。优先处理高风险依赖：存储过程、触发器、函数、专有 SQL、作业和应用侧 SQL。自动转换率高不代表应用端到端已迁移完成。

数据验证

  • 使用 DMS 数据验证（在支持场景下）或自定义校验对比源与目标；对大表采用范围/抽样/校验和策略。
  • 校验行数、主键唯一性、空值、精度/时区/字符集、LOB 内容、业务汇总、序列/自增值和关键查询结果。
  • CDC 期间监控任务延迟、表统计、失败记录和源日志保留；确保源端日志不会在追平前被清理。
  • 切换前确认目标容量、索引、参数、备份、监控、告警、权限、连接池及应用配置。
  • 保留源库只读或回滚窗口，明确回滚条件；切换后若新目标已有写入，回切前必须解决双向数据一致性。
验收门槛：迁移任务成功不是迁移成功的充分条件；结构、数据、应用行为、性能和恢复能力都需要验证。

七、场景题解析

场景一：Oracle 迁移到 Aurora PostgreSQL，要求评估过程/函数并保持低停机

判断：SCT 评估和转换 schema/代码，人工修改不支持对象；DMS 进行 Full load + CDC（确认组合支持）并在验证后切换。

陷阱：DMS 不负责自动改写所有 Oracle PL/SQL 和应用 SQL。

场景二：相同引擎版本间迁移，数据库对象兼容，想持续同步数据

判断：通常无需 SCT；评估 DMS CDC 或原生复制，结合停机窗口、数据量与引擎支持选择。

陷阱：同构迁移仍需测试版本、权限、扩展和数据行为差异。

场景三：一次性迁移，允许较长维护窗口，完成后不再同步

判断：评估 Full Load only 或原生备份/恢复路径；按数据规模和目标引擎能力选择。

陷阱：CDC 是持续变化复制，不是所有迁移都必须启用。

场景四：全量装载完成但源库仍持续写入，切换时目标数据落后

判断：使用支持的 Full load + CDC 持续追平，切换前冻结写入并等待 CDC 延迟归零。

陷阱：不能把任务状态“完成全量”误认为源目标已经一致。

场景五：SCT 报告显示大量专有存储过程无法转换

判断：评估人工重写、应用重构或目标引擎替代方案；完成对象与业务逻辑回归测试。

陷阱：直接忽略转换报告会导致迁移后功能缺失。

场景六：DMS 无法连接本地源数据库

判断：检查复制资源与源端之间的网络连通性、路由、DNS、端口、安全组/防火墙、凭据和数据库权限。

陷阱：仅调整 DMS 表映射无法修复网络连接问题。

八、关键词速查

关键词考试速记
同构迁移同引擎；通常不需 SCT，DMS/原生工具按需选
异构迁移不同引擎；SCT 评估/转换 + DMS 数据迁移常见
SCTSchema、代码对象转换评估；未支持项需人工处理
DMS Full Load迁移既有数据
DMS CDC持续复制变更；依赖源日志与组合支持
Full Load + CDC先全量、后增量追平，支持低停机切换设计
LOB全量完整性与有限长度/性能之间权衡
切换校验目标追平、冻结写入、切连接并预设回滚

十、快速自测

1. 异构迁移时，哪个工具负责 schema 转换评估？
正确答案：A。SCT 评估并转换支持的 schema/代码；DMS 负责数据迁移与复制。
2. 低停机迁移需要先复制现有数据、再持续跟踪源端变更，任务类型是什么？
正确答案：A。切换前还要等待变更追平并完成一致性校验。
