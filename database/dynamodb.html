一、数据模型与主键

DynamoDB 是全托管、无服务器的键值与文档数据库。表中每个 Item 由主键唯一标识，属性可灵活变化；设计先从应用的读写模式出发，而不是先照搬关系型表结构。

主键类型组成查询行为
Partition key only单一分区键，值唯一标识 Item。按分区键精确查找；一个键值不能对应多条表项。
Partition key + sort key复合主键；分区键可重复，组合必须唯一。按分区键定位集合，再对排序键做等值、范围或前缀查询。
Secondary index为替代访问模式建立另一组键。不必为每种字段组合执行全表 Scan；需考虑写入、存储和一致性成本。
  • 单个 Item 最大 400 KB；大对象通常将元数据放 DynamoDB、对象内容放 S3，并保存对象键。
  • 分区键值应有足够基数并均匀分布；时间戳、固定状态或少量租户 ID 作为唯一分区键可能造成热点。
  • Sort Key 可编码实体类型、时间或层级，使一个 Item Collection 支持多种范围访问模式。
  • 复合主键让同一分区键下的多个 Item 按 Sort Key 排序，但主键设计应能回答已知查询，不能指望任意 SQL 式查询。
设计顺序：列出关键访问模式 → 确定每次请求的定位键 → 选择分区键基数/分布 → 设计 Sort Key 范围 → 再决定 GSI/LSI。避免将 Scan 当成日常查询基础。

二、分区设计与访问模式

分区键：吞吐与热点

  • DynamoDB 根据分区键将数据分布到内部物理分区；应用无需管理底层服务器，但仍需设计均匀的访问分布。
  • 高基数键通常更容易均匀分布；如果大量请求集中到单一键，单个热点会限制该键可获得的吞吐。
  • 一个热门活动 ID、当前日期或单一状态字段可产生热点。可考虑复合键、写分片（sharding）、随机后缀或重新组织访问模式。
  • 写分片能分散热键写入，但读取时需查询多个 shard 并合并结果，增加复杂度。

Sort Key：时间序列与层级查询

  • 将用户 ID 作为分区键、时间戳作为排序键，可按用户读取其事件或订单，并通过时间范围限制数据。
  • Sort Key 前缀可表示实体类型或层级，例如 ORDER#...、PROFILE，在单表设计中容纳相关实体。
  • Query 要求分区键等值；Sort Key 可用范围条件、begins_with 等支持的条件限定结果。
  • 不同访问模式需要另一种分区键/排序键组合时，评估 GSI，而不是在主表做无界扫描。
设计问题危险信号改进方向
分区键分布所有写入指向当前日期、单租户或固定枚举值。提高键基数、加入分片键、改用复合键并验证热点。
查询约束常用 API 只能通过 Scan 再过滤。增加合适的索引或重塑 Item，使查询键可直接定位。
大对象接近 400 KB Item 限制或重复存储二进制内容。大对象放 S3，DynamoDB 保存元数据、索引和引用。
跨实体读单表中所有 Item 缺少统一访问约定。规划复合主键、实体前缀与每个查询的键条件。

三、Query、Scan 与索引

操作 / 索引行为重要限制
GetItem / BatchGetItem通过完整主键读取 Item。Batch 操作仍受大小、未处理键与容量限制，应用需处理重试。
Query使用分区键等值条件，可再限制排序键并分页。FilterExpression 在读取后过滤，不减少已读取数据的容量消耗。
Scan遍历表或索引后返回项目，可并行扫描。大表扫描会消耗吞吐并产生延迟；通常不适合高频在线请求。
GSI可使用不同分区键/排序键，创建后可增加；维护独立索引结构。GSI 查询仅支持最终一致性读取；需规划索引容量/投影与写放大。
LSI与基表共用分区键，采用不同排序键；需在创建表时定义。仅适用于复合主键表；Item Collection 大小有约束；可支持强一致性读取。
  • GSI 可投影全部属性、仅键属性或指定属性；只投影查询需要的字段可降低索引存储和写入成本，但投影不足时需回表取数据。
  • Provisioned 模式下，GSI 需要独立配置读写容量；GSI 写入容量不足可能导致基表写入节流。
  • Query 的 FilterExpression 可过滤返回结果，但不是替代索引设计的捷径；读容量按读取的数据量而非过滤后数量计算。
  • 强一致性读取可用于表和 LSI 的适用读取，GSI 与 Global Tables 的读取不提供强一致性保证。
  • 通过 LastEvaluatedKey 分页；单次 Query/Scan 返回大小有限，应用需要正确处理分页与空结果但仍有后续页的情况。
常见陷阱：“FilterExpression 只返回一条”不表示只消耗一条的读取容量；先读取再过滤。在线高频查询应让 KeyConditionExpression 能直接选中目标集合。

四、容量模式与自动扩展

模式容量管理适合负载注意点
On-Demand按请求量自动扩展，不预先指定 RCU/WCU。流量难预测、间歇性或新建应用，优先降低容量规划运维。按请求计费；仍需考虑账户/表配额、突发特性与成本预算。
Provisioned配置读写容量单位，可启用 Application Auto Scaling。流量可预测且稳定，希望优化单位吞吐成本。容量不足会节流；对主表和 GSI 分别监控并设置合理目标。
Reserved Capacity对符合条件的预置容量承诺付费优惠。长期稳定的预置容量。不改变扩缩功能；核对当前购买资格与承诺范围。
  • RCU/WCU 消耗受 Item 大小、读写类型、一致性、事务和索引影响；单次写入的容量估算需按数据大小和操作类型计算。
  • 最终一致性读取通常比强一致性读取的容量消耗低；事务读写需要更多容量，且有事务大小和项目数限制。
  • Provisioned Auto Scaling 根据目标利用率调整容量，但扩容有传播时间；对突发负载仍需合理余量与重试。
  • On-Demand 免除手动配置容量并非“无限且无成本风险”；热点键、限额和高请求成本依然存在。
  • 使用 CloudWatch 监控 Consumed/Provisioned Capacity、Throttled Requests、成功请求延迟、GSI 指标与限额。
模式选择：未知或波动流量 → On-Demand；稳定且可预测、需要精细成本优化 → Provisioned + Auto Scaling；无论模式都要处理重试、热点与限额。

五、一致性、事务与幂等

  • 表和 LSI 的读取可按需求选择最终一致性或强一致性；GSI 读取为最终一致性。强一致性不是跨 Region 全局读写的保证。
  • Conditional Write 可在满足条件时创建/更新项目，适合防止覆盖并发更新、实现去重或幂等状态转换。
  • TransactWriteItems / TransactGetItems 提供多个 Item 操作的 ACID 事务，但受事务容量、项目数、冲突和跨账户/区域限制。
  • 使用幂等键或条件表达式处理客户端重试，避免网络超时后重复扣款、重复创建订单等业务副作用。
  • TTL 删除由服务异步完成，不保证在过期时刻立即删除；不能把 TTL 当作精确计时器或授权到期控制的唯一机制。
一致性判断：读后立即要看到刚写的数据 → 对支持的表/LSI 请求使用强一致性，或读写同一路径；GSI、DAX 与 Global Tables 需接受其一致性边界并进行应用设计。

六、Streams、TTL 与变更处理

能力用途关键限制
DynamoDB Streams按 Item 变更产生近实时记录，可触发 Lambda、审计或派生处理。记录保留时间有限（通常 24 小时）；消费者应幂等并处理重复/重试。
StreamViewType选择仅键、变更前、变更后或前后图像。按消费者需要选字段，避免不必要暴露或传输数据。
TTL为项目设置过期时间戳，服务异步清理已过期项目。删除有延迟；过期项目在删除前仍可能被读取和计费。
Export to S3将表数据导出至 S3，用于分析、归档或离线处理。按支持的备份时间点导出，无需对在线表执行全量 Scan。
  • Streams 与 Lambda 集成时监控 IteratorAge、失败重试与批次行为；毒记录需有隔离或失败处理设计。
  • 若处理要求按分区键顺序，采用适合的事件源映射并避免多消费者造成顺序假设失效。
  • TTL 常用于会话或临时数据清理，不应用作精确到期授权，需在读取路径也校验业务有效期。
  • 全量或增量分析可用导出到 S3、AWS Glue / Athena 等数据分析链路，避免在线 Scan 影响应用吞吐。

七、Global Tables 与 DAX

Global Tables：多区域读写

  • Global Tables 在多个 Region 复制表数据，适合地理分散用户低延迟读写和区域级韧性需求。
  • 复制为异步；不同区域并发更新可能产生冲突，应用必须理解冲突解决和最终一致性。
  • Global Tables 不等于跨区域强一致性。明确主数据归属、冲突策略、区域故障时写入行为与恢复流程。
  • 部署前验证表配置、容量模式、加密密钥、Streams / 备份要求与目标 Region 的服务支持。

DynamoDB Accelerator(DAX)：内存缓存

  • DynamoDB Accelerator 是全托管、与 DynamoDB API 兼容的内存缓存，适合高读、重复访问且可接受最终一致性缓存语义的场景。
  • DAX 可缓存项目与查询结果，降低应用读取延迟和底层读取请求；写入可经 DAX 传递到 DynamoDB 并更新缓存。
  • DAX 不适合需要强一致性读取的场景；若只需简单应用级缓存或多数据源聚合，评估 ElastiCache 等替代方案。
  • 应用需位于可访问 DAX 集群的 VPC 网络中，并配置 IAM、加密、节点规模与故障恢复。
区分题眼：跨区域多活 → Global Tables（接受异步复制）；微秒级重复读、接受最终一致性 → DAX；跨区强一致性不能简单靠 Global Tables 实现。

八、备份、安全与监控

  • Point-in-time recovery：连续备份窗口内可恢复到某个时间点；恢复会创建新表，再由应用切换数据路径。
  • On-demand Backup：按需创建备份，按保留策略管理；适合长期保护和变更前检查点。
  • 恢复测试：定期恢复到隔离表，验证索引、容量、IAM、Streams 与下游消费者配置。
  • 静态加密：默认使用 KMS 管理加密，也可按需求使用客户管理密钥；保护表数据、备份与相关导出路径时分别核对配置。
  • IAM：按表、索引和操作授权最小权限；可结合条件限制 LeadingKeys 或属性级访问，避免只依赖应用端过滤。
  • 网络：DynamoDB 是区域级服务；私有子网访问可使用 Gateway VPC Endpoint，配合路由表与 Endpoint Policy 限定流量。
  • 监控：观察节流、消耗容量、延迟、系统错误、GSI 写入容量、Streams IteratorAge 和 Global Table 复制延迟。
恢复陷阱：备份还原不会覆盖原表，而是产生新表。切换前要同步 IAM、应用配置、索引、TTL、Streams、备份与监控等表级设置。

九、场景题解析

场景一：按用户读取最近一段时间的事件

系统需按用户查询其事件，并快速返回最近 24 小时数据；写入量大，查询通常限定单一用户。

正确方向：以用户标识作为分区键，以时间戳作为排序键，使用 Query 并指定时间范围。

分析思路：访问模式有稳定分区键与时间范围；Query 可避免扫描整表。

排除：只按日期做分区键可能造成热点；每次 Scan 再过滤用户会消耗大量读取容量。

场景二：热门商品分区键导致写入节流

大量写入集中到单个热门商品 ID，表整体利用率不高但该键请求节流。

正确方向：重新设计写入键以分散热点，例如使用写分片或复合键，再在读取时合并结果。

分析思路：问题是单个热键/分区的访问集中，不是总表容量不足。

排除：简单提高总表预置容量不能消除固定分区键的热点；提高全局读容量更无关。

场景三：需要按邮箱查询用户且不改变主键

用户主表以 UserId 为主键，新增 API 需要按 Email 查找用户，并要求可在表创建后增加查询能力。

正确方向：创建以 Email 为索引键的 GSI，按查询需求投影必要属性。

分析思路：访问模式需要不同分区键；GSI 可在表创建后添加，查询为最终一致性。

排除：Scan + FilterExpression 会读取大量数据；LSI 不能在表创建后追加且需沿用主分区键。

场景四：流量可预测且希望成本优化

生产表日常读写稳定，团队愿意设置容量告警，并希望按目标利用率自动扩缩。

正确方向：使用 Provisioned Capacity 配合 Application Auto Scaling，为主表和 GSI 分别规划读写容量与告警。

分析思路：稳定可预测流量适合预置容量，自动扩展降低手动运维。

排除：On-Demand 更适合未知或波动流量，但不一定是长期稳定负载的最低成本模式。

场景五：高读重复数据要求极低延迟

同一批 DynamoDB 项目被大量重复读取，业务允许最终一致性；希望降低读延迟和底层读取请求量。

正确方向：评估 DAX 缓存层，验证缓存命中率、失效策略、VPC 访问和故障行为。

分析思路：DAX 面向 DynamoDB 读取缓存；使用前确认应用不依赖强一致性读取。

排除：Global Tables 面向跨区域复制，不是单区域的内存缓存；提高写容量也不会加速重复读。

场景六：多区域用户都需本地读写

应用在多个 Region 部署，用户应连接本地数据库端点，区域故障时仍可使用其他区域，团队接受异步复制。

正确方向：使用 DynamoDB Global Tables，并明确冲突解决、区域故障写入和恢复流程。

分析思路：Global Tables 提供多区域复制与本地访问，但复制异步且不是强一致性事务数据库。

排除：单 Region Read Replica 不提供多区域多活；跨区备份也不是本地低延迟读写架构。

十二、快速自测

先独立选择，再点击“查看解析”。

1. 表已存在，现需通过不同于主键的新属性快速查找项目，且可接受最终一致性。应使用什么？
正确答案：B。GSI 可定义新的分区键并在建表后添加；查询为最终一致性，需规划索引成本。
2. FilterExpression 后只剩少量项目，但请求仍大量消耗读取容量，应该怎样改进？
正确答案：B。Filter 在读取之后执行，不降低已读取数据的容量；要让键条件选中所需数据集合。
3. 多区域应用需要本地读写，业务可以接受最终一致性，应选择什么？
正确答案：A。Global Tables 提供多区域复制和本地访问，但复制异步，仍需规划冲突与故障恢复。
