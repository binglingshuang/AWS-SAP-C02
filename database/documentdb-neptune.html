Amazon DocumentDB 与 Neptune
文档模型与图关系

DocumentDB 和 Neptune 面向不同数据模型：前者提供 MongoDB API 兼容的托管文档数据库，后者面向高度关联的图数据。迁移题的关键是验证兼容性与语义，而不是把“兼容”误解为完全等同。

一、先按数据关系选模型

服务选择从主要访问模式开始：灵活文档与 MongoDB API 工作负载考虑 DocumentDB；多跳关系、路径遍历和网络关系查询考虑 Neptune；键值访问考虑 DynamoDB；事务与关系联接考虑 RDS/Aurora。

服务数据模型 / 接口适合场景不要混淆
DocumentDB文档数据库，MongoDB API 兼容JSON 文档、应用使用兼容 MongoDB 驱动/查询模式兼容不等于完整 MongoDB 功能/版本一致
Neptune图数据库；Property Graph 与 RDF 图模型/查询接口社交关系、知识图谱、欺诈关系、路径遍历不是泛用文档存储，也不是传统关系型 join 引擎
DynamoDB键值与文档 NoSQL按主键低延迟、大规模可扩展读写复杂多跳关系查询需重新建模或使用图数据库
Aurora/RDS关系型SQL、事务、一致性约束与关系联接不能仅因数据是 JSON 就默认换文档数据库

二、Amazon DocumentDB

  • 托管的文档数据库服务，支持 MongoDB API 兼容；应用可使用兼容驱动访问，但必须根据目标引擎版本核对操作符、聚合、索引、协议与限制。
  • 集群由写入实例和可选读取实例组成；读取端点可分散读负载，集群端点用于写入，实例故障时服务负责恢复/切换机制。
  • 底层存储与计算实例分离；通过实例扩展计算，通过读取实例扩展读能力；集群卷跨多个可用区冗余（具体架构与可用性查当前文档）。
  • 用文档嵌套表达常一起读取且生命周期一致的数据；若关系需要大量跨文档遍历，检查是否应建模为图。
  • 监控连接数、CPU/内存、读写延迟、存储和复制滞后；应用应使用合适连接池、超时和重试策略。
兼容性陷阱：“MongoDB-compatible”不等于可直接替换任意 MongoDB 版本。先做功能清单、驱动兼容、查询语义、索引和性能验证，再规划迁移。

三、Amazon Neptune

  • 全托管图数据库，适合数据实体间关系本身是核心查询对象、需要遍历多跳关联的场景。
  • Property Graph 工作负载可使用 Gremlin 或 openCypher（按引擎版本/接口支持）；RDF 数据使用 SPARQL。选择查询语言时匹配数据模型与现有应用。
  • 典型模型：顶点表示实体，边表示关系；边与顶点可带属性。查询可沿关系寻找路径、共同邻居或网络模式。
  • 集群有写入实例和只读副本，配合读取端点扩展读；存储层跨可用区冗余，高可用仍需配置读副本并设计应用重连。
  • 复杂图遍历需设计索引/键、控制遍历深度与结果规模，避免无边界的全图扫描；图数据库不自动保证所有查询都低延迟。
场景信号：“找出与该账户两层以内相关的账户/设备/交易网络”是图关系遍历信号；若只是通过固定主键读取单条 JSON，通常不是 Neptune 的首选。

四、迁移与兼容性验证

DocumentDB 迁移评估

  1. 盘点源 MongoDB 版本、驱动/API、命令、聚合管道、索引、事务/一致性、Change Streams、扩展和数据量。
  2. 对照 DocumentDB 目标版本支持矩阵识别不兼容行为；改造应用或查询，不能把接口兼容当作语义完全相同。
  3. 选择 AWS DMS、原生导出/导入或其他受支持路径；先做全量装载与校验，再按停机窗口或 CDC 方案同步增量。
  4. 压测读写、索引构建、连接池、故障切换和恢复；演练回滚与 DNS/应用端点切换。

Neptune 迁移评估

关系型源迁移到图模型时，先把表映射为顶点/边与属性，定义稳定 ID、关系方向和重复处理。AWS Neptune Bulk Loader 可从 S3 批量加载支持的图数据格式；持续同步能力须结合 AWS DMS 对源/目标组合的支持矩阵、CDC 语义及目标配置核验。

迁移原则：数据库迁移工具不会自动替你完成数据模型重构、语义适配或所有应用查询改写。先验证工具支持，再设计切换与数据一致性校验。

五、高可用、安全与运维

  • 将集群部署在 VPC 私有子网中，按应用安全组授权访问；使用 TLS、静态加密和 KMS 密钥策略。
  • DocumentDB 与 Neptune 均应通过读取端点/集群端点和应用重试处理节点变更；连接池需能刷新连接。
  • 为备份保留期、时间点恢复能力、快照和跨区域 DR 需求制定策略；定期演练真实恢复时间和数据一致性。
  • 使用 IAM 与数据库身份认证能力时遵循最小权限，密码存入 Secrets Manager 等凭据服务而非代码。
  • 迁移期间同时监控源/目标延迟、失败记录、全量装载进度与数据校验结果。

六、场景题解析

场景一：现有应用使用 MongoDB API，想迁移到 AWS 托管文档数据库

判断：评估 DocumentDB，但先核对 API/驱动/聚合与索引兼容性，通过 PoC 决定迁移方式。

陷阱：API 兼容不是所有 MongoDB 版本与功能都完全相同。

场景二：需要在欺诈调查中遍历账户、设备、地址与交易的多层关联

判断：Neptune 图模型适合关系遍历；用顶点/边建模关系，选择 Gremlin/openCypher 或 RDF/SPARQL 对应接口。

陷阱：把关系塞入文档后反复执行应用层关联会增加复杂性。

场景三：工作负载只是使用主键访问独立 JSON 记录，需要弹性低延迟

判断：评估 DynamoDB，而不是因为“文档”一词就选 DocumentDB。

陷阱：核心访问模式与关系复杂度优先于数据格式。

场景四：迁移后某些 MongoDB 聚合管道结果不同

判断：检查目标 DocumentDB 版本的兼容矩阵和语义差异，改写查询并回归验证。

陷阱：仅更换连接字符串不足以保证业务行为一致。

场景五：关系型数据要进入 Neptune，数据量很大且允许先离线装载

判断：将源数据映射为图格式，使用 Neptune Bulk Loader 从 S3 批量装载并执行数量/关系校验。

陷阱：Bulk Loader 不会自动决定顶点、边和业务 ID 的建模规则。

场景六：文档数据库读取流量增长，写入量不变

判断：评估增加读取实例并使用读取端点分摊负载，同时确保客户端对复制延迟敏感度合适。

陷阱：读取实例扩展读能力，不是写入容量扩展方案。

九、快速自测

1. 要查询账户之间多层关系路径，优先考虑？
正确答案：A。Neptune 是面向关系遍历的图数据库。
2. MongoDB API 兼容能否证明所有现有查询均可直接迁移？
正确答案：B。API 兼容不等于功能、语义和版本完全一致。
