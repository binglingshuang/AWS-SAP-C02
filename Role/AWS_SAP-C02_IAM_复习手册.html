考试重点不是单纯记住 IAM 用户、组和策略，而是判断复杂企业架构中“谁访问什么、通过什么身份、权限由谁授予、又受到什么限制”。

IAM Policy 基本结构

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-bucket/*"
  }]
}
字段含义
EffectAllow 或 Deny
Action允许或拒绝的操作
Resource作用资源 ARN
Principal谁可以访问，常见于资源策略
Condition附加访问条件
SidStatement 标识符

三类常见策略

  • Identity-based Policy：附加到 User、Group 或 Role，定义身份可以执行什么操作。
  • Resource-based Policy：附加到资源，例如 S3 Bucket Policy、SQS Queue Policy、KMS Key Policy。
  • Trust Policy：IAM Role 的信任策略，定义谁可以 AssumeRole；本质上是 Role 的资源型策略。

2. Policy 权限判断：最重要的基础

检查 Explicit Deny→检查有效 Allow→检查所有适用限制→最终决策
Explicit Deny 优先：只要适用的策略中存在显式拒绝，就会拒绝该请求，其他 Allow 不能覆盖它。
  • Implicit Deny：默认拒绝；没有匹配的 Allow 就不能访问。
  • Explicit Deny：显式拒绝，优先级最高。
  • Allow：必须存在有效授权，并满足适用的限制。

常见策略的职责

策略主要作用能否单独授予权限
Identity Policy授予身份权限可以
Resource Policy在资源侧授权访问可以（视服务和访问主体而定）
SCP限制 Organizations 成员账户权限不可以
Permission Boundary限制 User / Role 的权限上限不可以
Session Policy限制当前 STS 会话的权限不可以

SCP：Service Control Policy

SCP 是 AWS Organizations 的组织级权限控制机制，可附加到 Organization Root、OU 或 Account，用于限制成员账户中 IAM 身份可获得的最大权限。

  • 不能授予权限，只能定义权限边界。
  • 成员账户仍需通过 IAM Policy 等方式获得实际权限。
  • 管理账户不受 SCP 限制。
  • 服务关联角色（Service-linked Roles）不受 SCP 限制。
  • 可用于组织范围的安全护栏，例如限制关闭 CloudTrail、限制使用某些 Region。
题干关键词：Organization-wide restriction、centrally enforce、prevent disabling CloudTrail、restrict Regions → 优先想到 SCP。

Permission Boundary：权限边界

Permission Boundary 定义 IAM User 或 Role 可以获得的权限上限。它本身不授予权限，身份还需要适用的 Identity Policy 等授权。

简化理解：最终身份权限受到 Identity Policy 与 Permission Boundary 的交集约束；实际还需考虑显式拒绝、SCP、资源策略等规则。

典型场景：委托开发团队创建 IAM Role，但防止其创建拥有管理员权限的 Role；避免权限提升（Privilege Escalation）。

3. IAM Role、STS 与跨账户访问

典型场景：Account A 的开发人员需要访问 Account B 的生产环境资源。常见方案是目标账户创建 Role，由源账户身份通过 STS AssumeRole 承担该 Role。

跨账户 AssumeRole 流程

  1. Account B 创建 IAM Role，并配置该 Role 的 Trust Policy。
  2. Trust Policy 信任 Account A 中的指定身份或账户。
  3. Account A 的身份策略允许对目标 Role 执行 sts:AssumeRole。
  4. 调用 STS AssumeRole，获取临时凭证。
  5. 使用临时凭证访问 Account B 中由 Role 权限允许的资源。

目标账户 Trust Policy 示例

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::111111111111:root"
    },
    "Action": "sts:AssumeRole"
  }]
}

这里的账户 Root ARN 表示信任该 AWS 账户中的身份主体，并不等于只信任该账户的 Root 用户。实际仍需源身份获得调用 AssumeRole 的权限。

源账户 Identity Policy 示例

{
  "Effect": "Allow",
  "Action": "sts:AssumeRole",
  "Resource": "arn:aws:iam::222222222222:role/ProductionRole"
}
跨账户记忆：检查源身份是否允许 AssumeRole、目标 Role 是否信任源身份、目标 Role 是否拥有目标资源权限，以及 SCP 等其他限制。

STS 常见 API

API用途
AssumeRole承担 IAM Role
AssumeRoleWithSAML使用 SAML 身份联合获取凭证
AssumeRoleWithWebIdentity使用 Web Identity / OIDC 身份联合
GetSessionToken获取临时会话凭证
GetFederationToken获取联合身份临时凭证

临时凭证通常包含 Access Key ID、Secret Access Key 和 Session Token，并具有有效期。

Session Policy

如果 Role 原本允许 S3 读、写、删除，但某次任务只需要读取，可以在 AssumeRole 时传入 Session Policy，进一步缩小该次会话的权限。会话权限不会超过 Role 本身允许的权限。

关键词：Temporarily restrict permissions、limit a specific session、temporary access with reduced permissions → Session Policy。

跨账户访问方式比较

方式适用场景
Cross-account IAM Role人员或应用需要承担目标账户 Role，适用范围广
Resource-based Policy直接在资源侧授权外部账户或主体，例如 S3、SQS
IAM Identity Center企业员工集中访问多个 AWS 账户

5. Federation：身份联合认证

SAML 2.0 Federation

典型场景：企业使用 AD FS 或其他 SAML 2.0 身份提供商，员工先在企业身份系统完成认证，再通过 AWS STS 获得临时凭证并承担 IAM Role。

用户登录企业 IdP→SAML Assertion→STS→临时凭证 / Role

关键词：Corporate directory、SAML 2.0、existing enterprise identity provider、federated users → SAML Federation。

Web Identity Federation / OIDC

适合 Web 或移动应用通过外部身份提供商认证，再获取访问 AWS 资源所需的临时凭证。常见技术包括 OpenID Connect（OIDC）和 Amazon Cognito。

技术 / 服务典型场景
SAML 2.0企业员工使用企业身份系统登录 AWS
OIDCWeb / 移动应用身份认证
IAM Identity Center企业员工集中访问多个 AWS 账户
Amazon Cognito应用终端用户身份管理

6. RBAC 与 ABAC：权限管理模型

RBAC

Role-Based Access Control，基于角色的访问控制。

例如 Developer → 开发权限；Operator → 运维权限；Auditor → 只读审计权限。

适合岗位角色明确、权限模型相对稳定的组织。

ABAC

Attribute-Based Access Control，基于属性的访问控制。

根据身份标签、资源标签等属性动态判断是否允许访问。

适合大量项目、团队或资源需要动态隔离的场景。

ABAC Policy 示例

{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "aws:PrincipalTag/Project": "${aws:ResourceTag/Project}"
    }
  }
}

示例表达的思路是：身份的 Project 标签必须与资源的 Project 标签匹配，才满足该条件。

对比RBACABAC
权限依据角色属性 / 标签
管理方式分配角色标签匹配
灵活性相对固定更灵活、动态
关键词Job functionTags、Attributes、Project、Department
考试技巧：如果题目不希望为每个项目创建大量 Role，而希望依据用户和资源标签自动匹配权限，优先考虑 ABAC。

Condition Key用途题目线索

8. AWS 工作负载访问 IAM Role

EC2 Instance Role

EC2 需要访问 S3 时，推荐为实例关联 IAM Role，通过 Instance Profile 提供角色身份，再由 EC2 的 Instance Metadata Service（IMDS）获取临时凭证。

名称作用
IAM Role定义身份和权限
Instance Profile将 IAM Role 提供给 EC2 实例
IMDSEC2 获取实例元数据和实例角色凭证的机制
STS提供临时安全凭证
考试关键词：EC2 needs S3 access、avoid storing credentials、automatically rotate credentials → IAM Role + Instance Profile。推荐使用 IMDSv2。

Lambda Execution Role

Lambda 通过 Execution Role 访问 DynamoDB、S3、CloudWatch Logs 等资源。如果 Lambda 无法写入 DynamoDB，应检查 Execution Role 是否具有相应 Action，以及是否存在 SCP、Boundary 等限制。

ECS / EKS Role 区分

服务 / 角色用途
EC2 Instance ProfileEC2 实例上的工作负载访问 AWS
Lambda Execution RoleLambda 函数访问 AWS
ECS Task Role容器内应用程序访问 AWS 服务
ECS Task Execution RoleECS 启动任务所需操作，例如拉取 ECR 镜像、写 CloudWatch Logs
EKS Pod Identity / IRSA将 AWS IAM 权限授予 Kubernetes Pod
记忆：ECS 应用程序访问 AWS → Task Role；ECS 启动和基础设施流程所需权限 → Task Execution Role。

10. Root User、MFA 与 Access Key

Root User

  • 不要使用 Root User 进行日常管理操作。
  • 为 Root User 启用 MFA。
  • 避免创建或使用 Root Access Key。
  • 妥善保护 Root 凭证，仅在必须使用 Root 的任务中使用。
  • 日常人员访问优先使用 IAM Identity Center 或合适的 IAM Role。

MFA

为身份认证增加额外验证因素。常见用途包括保护管理员访问、敏感操作，以及在 IAM Policy 中通过 MFA 条件控制访问。

Access Key

Access Key 用于程序化访问 AWS。对于运行在 EC2、Lambda、ECS 等 AWS 环境中的工作负载，优先使用 IAM Role 的临时凭证，而不是在代码或配置文件中硬编码长期密钥。

13. SAP-C02 IAM 快速答题决策树

第一步：谁需要访问 AWS？

  • 企业员工 → IAM Identity Center
  • 外部身份提供商用户 → Federation
  • EC2 / Lambda / ECS → 对应工作负载 IAM Role
  • 其他 AWS 账户 → Cross-account Role 或 Resource Policy

第二步：需要什么权限控制？

  • 限制整个组织 → SCP
  • 限制某个 IAM User / Role 的权限上限 → Permission Boundary
  • 限制单次临时会话 → Session Policy
  • 根据身份和资源标签 → ABAC
  • 根据岗位角色 → RBAC

第三步：需要什么认证方式？

  • 企业统一登录 → SAML / Identity Center
  • Web 或移动应用 → OIDC / Cognito
  • 临时 AWS 凭证 → STS
  • 多因素验证 → MFA

第四步：检查是否存在其他权限限制

身份与信任

Identity Policy、Trust Policy、Resource Policy

权限边界

Explicit Deny、SCP、Permission Boundary、Session Policy

资源加密

KMS IAM 权限、KMS Key Policy

条件限制

IP、Region、MFA、PrincipalTag、ResourceTag

14. 考试中常见的 10 个陷阱

错误说法 / 误区正确理解
SCP 可以授予权限错误。SCP 只限制成员账户权限上限。
Permission Boundary 可以授予权限错误。它只定义身份权限上限。
Role 有权限就一定能 AssumeRole错误。还要满足 Trust Policy 和调用方权限等条件。
跨账户只需要修改一侧策略通常不够。检查源身份授权、目标信任关系及目标权限。
Explicit Deny 可以被 Allow 覆盖错误。适用的显式拒绝优先。
EC2 应该保存 Access Key错误。优先使用 Instance Profile 和临时凭证。
企业所有员工都应该创建 IAM User通常不推荐。多账户人员访问优先考虑 Identity Center。
RBAC 与 ABAC 一样错误。RBAC 基于角色，ABAC 基于属性。
S3 允许访问就一定能读取对象错误。还可能受 KMS 权限等限制。
Access Analyzer 可以替代 IAM Policy错误。它是分析和辅助权限管理工具，不是授权策略的替代品。

16. 复习优先级与考试技巧

第一优先级

必须熟练

  1. IAM Role / Trust Policy
  2. Cross-account Access
  3. STS / AssumeRole
  4. SCP
  5. Permission Boundary
  6. IAM Identity Center
第二优先级

深入理解

  1. SAML / OIDC Federation
  2. RBAC / ABAC
  3. Resource-based Policy
  4. Session Policy
  5. IAM Policy Evaluation
第三优先级

综合应用

  1. EC2 Instance Profile
  2. Lambda Execution Role
  3. ECS Task Role
  4. IAM Access Analyzer
  5. IAM + S3 + KMS
  6. IAM + Organizations

快速排除选项

  • Least operational overhead → 托管服务、集中管理
  • Most secure → 临时凭证、最小权限
  • Prevent privilege escalation → Permission Boundary
  • Across all accounts → SCP（限制权限）
  • No long-term credentials → IAM Role + STS
  • Dynamic access control → ABAC
Professional 考试原则：不要只问哪个选项“能实现功能”，还要判断它是否满足安全要求、跨账户要求、凭证要求、集中管理要求和最小权限原则。能实现不等于最佳答案。
