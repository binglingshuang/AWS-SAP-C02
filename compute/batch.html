一、Batch 调度模型

AWS Batch 根据作业定义、队列策略和计算环境安排批处理作业。Batch 负责编排提交、排队、调度与容量整合；应用仍需实现正确的作业逻辑、数据持久化和安全边界。

对象职责常见误区
Job Definition作业模板：容器、资源、角色、参数、重试等。定义作业如何运行，不代表已经提交或获得容量。
Job Queue承载待运行作业并关联一个或多个计算环境。队列优先级影响调度顺序，不代表无上限吞吐。
Compute Environment提供作业可用计算资源与容量策略。环境资源不足或配置不匹配会导致作业等待。
Job基于定义提交的一次作业实例。支持单作业、数组作业、依赖作业等模式。

二、Job Definition

  • 容器镜像与命令/参数定义程序入口；镜像存放在 ECR 等仓库。
  • vCPU、内存、GPU 等资源需求影响作业可放置的实例类型；请求过大可能长期无法调度。
  • Job Role 供容器内应用访问 S3、DynamoDB 等 AWS API；执行环境所需角色与应用角色分离。
  • 可配置环境变量、挂载、日志、超时与重试；秘密不应以明文环境值或镜像层保存。
  • 作业容器应把中间/最终结果写到持久化存储，不能依赖实例临时盘承载唯一副本。
容量匹配：如果作业需要的 vCPU/内存/GPU 与计算环境允许的实例规格不兼容，队列即使有大量空闲容量也可能无法运行该作业。

三、Job Queue 与优先级

  • 按业务隔离队列，例如高优先级生产队列、低优先级回填队列。
  • 队列可按优先级和关联计算环境顺序调度；多个队列/环境可帮助划分容量和成本策略。
  • Fair-share Scheduling 可按共享标识和策略在多个用户/工作负载间分配公平份额，避免单一提交方长期占满资源。
  • 作业状态、队列积压、最老作业年龄和失败率是扩缩及告警的重要信号。
  • 即使队列优先级高，仍需保证关联环境容量、服务配额和 IAM/网络配置。

四、Compute Environment 与 Spot

环境/容量适合场景注意
Managed EC2通用容器作业；Batch 可管理底层计算资源的容量生命周期。定义实例类型/规格范围、子网、SG、最大 vCPU 和服务角色。
EC2 Spot可重试、可中断且对成本敏感的计算。允许中断；采用多实例类型/容量池、检查点与重试，关键作业保留稳定容量。
Fargate无需管理 EC2 主机、作业资源规模适合服务支持范围。核对 CPU/内存组合、存储、网络和功能限制；不适合所有特殊节点需求。
Unmanaged EC2需要自行控制底层计算集群和容量生命周期。客户承担更多主机、扩缩和可用性运维。

自动扩缩需要配置容量上限和合适的扩缩逻辑；扩大队列不等于立即增加计算资源。子网需有足够 IP、路由可达镜像/日志/数据服务，实例角色与作业角色按职责隔离。

五、依赖、数组与并行

  • Job Dependencies：指定前置 Job 成功后再运行后续作业，适合 DAG 中简单依赖；复杂分支/长流程可评估 Step Functions。
  • Array Jobs：以一个作业定义提交大量同构子任务，每个子任务通过索引区分输入分片。
  • Multi-node Parallel Jobs：用于需要多个节点协同的紧耦合并行计算，需验证调度环境和网络要求。
  • 参数化：将数据分片、运行模式等作为参数传入；避免把所有数据嵌入任务定义或环境变量。
  • 检查点：长作业应周期性将进度写到耐久存储，以便中断后从检查点恢复，而不是从头重算。

六、重试、超时与可观测性

  • 为可恢复故障配置有限重试次数、退避与超时；永久输入错误应尽早失败并进入人工处理流程。
  • Spot 中断应通过检查点、幂等输出与安全重试恢复；不要把“Batch 会重试”当作作业结果恰好一次的保证。
  • 输出采用幂等键/原子发布标记，避免重试产生重复账单、重复文件或重复业务副作用。
  • 使用 CloudWatch Logs 观察容器输出；跟踪作业状态、失败原因、队列年龄、资源利用率和扩缩事件。
  • 网络与权限分别排查：镜像拉取/日志投递、Job Role 数据访问、路由与安全组都可能独立失败。

七、Batch 与 Lambda / ECS 选型

需求优先评估原因
海量、可排队、资源密集、长时或依赖式离线作业AWS Batch提供队列、调度、作业定义和计算容量整合。
短时、事件触发、单次处理工作Lambda事件驱动，无需维护容器作业队列；受执行时间与运行环境约束。
常驻服务、Web/API、持续消费者ECS / EKS服务/任务编排与长期运行副本控制更合适。
复杂状态工作流Step Functions + Batch工作流编排状态、分支与错误处理；Batch 执行计算作业。

八、场景题解析

场景一：夜间运行大批可重试影像处理

作业运行数小时，输入可分片，成本优先，允许实例中断。

方向：使用 AWS Batch 与 Spot 计算环境，设计检查点、幂等输出和失败重试，并保留必要的稳定容量。

排除：把任务做成单个短时 Lambda 会受到时长/并行执行模型限制。

场景二：队列一直积压，作业未启动

计算环境存在，但队列中部分作业长期 RUNNABLE。

方向：核对资源请求与实例规格是否匹配、最大 vCPU、子网 IP、配额、优先级和环境状态。

排除：单纯增加队列数量不会修复不兼容的资源需求。

场景三：Spot 中断后重复写入结果

作业重试后对象存储出现重复业务输出。

方向：设计幂等的输出键/提交标记，利用检查点恢复，并在最终发布时采用原子或条件写入。

排除：作业重试次数不是 exactly-once 处理保证。

场景四：按数据分片并行数千个独立作业

每个输入分片执行相同的容器算法，输出互不冲突。

方向：评估 Array Job，为各子作业传递索引/分片输入并限制总并发保护下游。

排除：为每个相同任务创建不同队列和定义会增加治理复杂度。

场景五：前置预处理完成后才允许聚合

聚合作业必须在多个预处理 Job 成功后启动。

方向：用 Job Dependencies 表达简单前置关系；若需要复杂分支、等待和人工批准，评估 Step Functions。

排除：仅依赖作业提交先后顺序不保证执行顺序。

场景六：多个团队争抢同一计算容量

单一团队提交大量回填作业，挤占其他团队的公平资源。

方向：分离队列/容量策略，评估 Fair-share Scheduling 与各团队份额/权重。

排除：单纯提高全局最大 vCPU 会增加成本但不解决公平性。

十一、快速自测

先独立选择，再点击“查看解析”。

1. 可重试批处理希望使用低成本且可中断容量，应该怎样设计？
正确答案：B。Spot 中断可通过检查点和安全重试恢复；幂等防止重复副作用。
2. 作业长期 RUNNABLE，最应先检查什么？
正确答案：B。队列无法调度常与资源规格不匹配或容量不足有关。
3. 如何表达一个作业必须在另一个作业成功后运行？
正确答案：A。依赖关系明确表达作业调度先后；复杂状态工作流可进一步使用 Step Functions。
