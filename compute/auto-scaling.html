Launch Template vs Launch Configuration

考试要点：任何需要动态更新 AMI、不同实例规格、IMDSv2 强制模式的场景，答案都是 Launch Template，而不是 Launch Configuration。

二、四种扩展策略

扩展策略是 SAP-C02 的最高频考点之一。四种策略对应四种不同的场景，必须精准区分。

策略类型触发方式调整量典型场景
Simple Scaling一个 CloudWatch Alarm每次调整固定数量（如 +2）或指定新容量简单需求、临时扩展
Step Scaling一个 CloudWatch Alarm + 多个调整步骤根据告警超出阈值的幅度不同，调整不同数量CPU 80%→+2，90%→+4
Target Tracking Scaling自动调整按比例自动增减，使指标接近目标值CPU 保持 60%、ALB 请求目标数
Predictive Scaling基于历史数据预测在流量到来前主动扩容周期性流量（如每日 9 点高峰）

四种策略深度对比

Simple Scaling

最原始的策略。告警触发后，执行一次调整（如 +1 实例），然后等待冷却期结束才能再次响应。冷却期内不能扩展是最大缺点——如果 CPU 持续 100%，扩容只能每次 +1。

Step Scaling

克服了 Simple 的缺点——冷却期内可以继续响应新的步骤。告警超出阈值越大，调整量越大。但本质上仍是 CloudWatch Alarm 驱动。

Target Tracking Scaling

最"智能"的手动策略。你只需要告诉 ASG："把 CPU 维持在 60%"，它会自动计算当前需要加/减几个实例。底层有自己的 CloudWatch Alarm，用户看不到。

Predictive Scaling

基于过去 14 天的 CloudWatch 指标，训练一个机器学习模型，在预测到的流量高峰前主动扩容。适合周期性模式（每日、每周、季节性）。

核心区别记忆：
  • Simple vs Step：冷却期内能否继续响应（Step 可以）
  • Step vs Target Tracking：是否需要手动写 CloudWatch Alarm（Target Tracking 不需要）
  • Predictive vs 其他三种：是否需要流量"已经到来"才触发（Predictive 预测未来）
Target Tracking 内置指标：CPU 使用率、网络入/出字节、ALB 请求数/目标/目标组、AppStream 会话、DynamoDB 读/写容量等。自定义指标也支持，但公式必须是"单值输入 → 输出一个比率"。

三、冷却期（Cooldown）

冷却期是防止"抖动"的安全阀——每次扩展动作后，在冷却期结束前不会再触发新的扩展。

冷却期类型

类型作用范围默认值
Default Cooldown整个 ASG300 秒
Scaling Policy Cooldown单个策略（可覆盖默认值）无默认（使用组级）
实例级 Warm-up（预热）Target Tracking 独有，新实例加入后多久才算"就绪"0 秒（立即生效）
Warm-up 的意义：新启动的 EC2 实例需要时间引导（User Data 执行、应用启动），这段时间内它还没有实际分担负载。Target Tracking 策略的 Warm-up 参数告诉 ASG："这个新实例加入后，等 120 秒再把它的 CPU 算进去"，这样计算不会因为"假扩容"而提前缩容。

全局 Cooldown vs 策略级 Cooldown

  • Simple Scaling 使用 ASG 的 Default Cooldown。
  • Step Scaling 的每个调整步骤可以有独立的 Cooldown，但在策略级 Cooldown 内仍然不能触发新步骤。
  • Target Tracking Scaling 忽略 Default Cooldown，使用自己内部的扩展逻辑——这是因为它的调整是连续且自动的，不需要人为的"冷却等待"。
  • Predictive Scaling 也有自己的参数（调度提前时间、容量缓冲）。
考试陷阱：
  • Simple Scaling 冷却期内 CPU 持续 100%，也只能扩到第一次调整，要等冷却期结束才会再次触发——这是 Simple 最大的缺陷。
  • 冷却期只影响自动扩展，手动改 desired capacity 不受影响。

四、混合实例策略（Mixed Instances Policy）

混合实例策略让一个 ASG 同时运行 Spot 实例和 On-Demand 实例，或同时运行不同规格的实例——这是成本优化的核心武器。

基本组成

  • Launch Template（基础）：定义默认规格、AMI、安全组等。
  • Overrides（覆盖）：一个数组，每个元素指定 instanceType + weightedCapacity（权重，默认 1）。
  • Purchase Option：Spot vs On-Demand（On-Demand + Spot + 百分比分配）。

分配策略（Allocation Strategy）

策略On-Demand 行为Spot 行为适用场景
lowestPrice最低价格的实例类型最低价格的 Spot 池成本优先
prioritized按 Overrides 数组顺序，优先用第一个可用的使用 On-Demand 未选中的类型的 Spot有明确的 On-Demand 首选规格
capacityOptimized优先选剩余容量最多的池优先选中断概率最低的池Spot 高可用性优先
capacityOptimizedPrioritized先按优先级，再看容量先按优先级，再看容量平衡成本、可用性、优先级
记忆口诀：
  • lowestPrice = 最便宜
  • prioritized = 我指定了先后顺序
  • capacityOptimized = Spot 要稳

五、生命周期钩子（Lifecycle Hooks）

生命周期钩子让你在实例的启动或终止过程中注入自定义逻辑。默认情况下 ASG 在实例 Ready 或 Terminating 时不等待就继续——钩子让你可以让它等。

两种钩子类型

钩子触发时机默认超时常见用途
Launch Hook实例启动中时（Pending 状态）1 小时注册到配置中心、跑初始化脚本
Terminate Hook实例终止前时（Terminating 状态）1 小时优雅关闭、从服务发现注销、上传日志

钩子执行流程

Launch Hook 触发
→
发送消息到
Lambda / SNS / SQS / Step Functions
→
执行你的逻辑
→ 必须回复
CompleteLifecycleAction
或 RecordLifecycleActionHeartbeat
→
实例进入 InService

关键规则

  • 必须回复：钩子触发后，你必须在超时时间内调用 CompleteLifecycleAction 或 RecordLifecycleActionHeartbeat。超时不回复，ASG 会按 DefaultResult 处理（ABANDON / CONTINUE）。
  • Heartbeat：如果你的初始化脚本超过 1 小时，调用 Heartbeat 可以延长等待时间（每次加 1 小时，最多 6 次）。
  • Terminate Hook 的 DefaultResult=ABANDON 意味着超时不回复→终止会被放弃（实例不终止，钩子失败）。
  • Terminate Hook + Spot 实例：Spot 被中断时不会走 Terminate Hook，Spot 的 2 分钟中断通知通过 IMDS 和 CloudWatch 事件处理。
  • 同一 ASG 可以同时设置 Launch Hook 和 Terminate Hook。
考试陷阱：
  • Lifecycle Hook 发送通知到 SNS/SQS/Lambda 只是通知，真正完成动作的是 CompleteLifecycleAction API 调用。只发 SNS 消息不调用 Complete，钩子永远不会结束。
  • Terminate Hook 在 Spot 中断时不会触发——Spot 中断走的是不同的流程（2 分钟 IMDS 通知）。

六、实例终止保护与缩轮保护

Instance Termination Protection

在 Launch Template 中设置 DisableApiTermination: true，或对现有实例执行修改。ASG 无法终止保护了的实例，缩容时会跳过它。

特性说明
层级实例级（也可在 Launch Template 中配置，新实例自动继承）
缩容行为ASG 跳过受保护实例，缩容到 min size 为止；如果所有实例都被保护且 > min，缩容会卡住并报警
ELB 行为终止保护的实例仍在 ELB 注册，流量继续进入——这通常不是你想要的
实际场景：在数据库主节点、正在跑长作业的节点上启用终止保护，同时使用 Terminate Hook 在缩容前先完成 ELB 注销 + 优雅关闭 + 持久化数据。

Scale-in Protection（缩容保护）

这是另一种保护方式：你可以让 ASG 在缩容时临时保护某些实例（基于 CloudWatch Alarm 触发），等条件满足后再解除。与 Termination Protection 类似，但 Termination Protection 是永久性的，Scale-in Protection 是临时的。

七、暖池（Warm Pool）

暖池解决的痛点：扩容时需要启动新实例，引导 + 应用启动可能需要几分钟——这段时间内新流量进来却没有可用实例。暖池预先把实例启动到 Stopped 状态，需要时几秒就能启动。

关键参数

参数含义
MinSize（暖池级别）暖池中始终保持的最少实例数
StateStopped（默认，省钱）或 Running（最快但花钱）
WarmPoolSize当前暖池实际有多少实例

重要规则

  • 暖池实例使用与 ASG 相同的 Launch Template。
  • 暖池不参与 ELB 健康检查（因为是 Stopped/Running 但还没 InService）。
  • 暖池容量可以超过 ASG 的 max size（这很重要！）。
  • 暖池启动会跳过 User Data 执行（因为首次启动已执行过），适合预引导的 Golden AMI 场景。
  • 暖池实例和 ASG InService 实例合计不能超过 2000 个（单 ASG 限制）。
适用场景：流量"爆发性"突增（电商秒杀、实时分析峰值），需要分钟级扩容而不是小时级。
考试陷阱：暖池不能绕过 ASG 冷却期——冷却期仍然适用，但"从暖池启动的实例"启动速度远快于全新启动，实际效果等同于绕过了冷启动瓶颈。

八、健康检查（Health Check）

ASG 默认使用 EC2 健康检查（只看系统层面），但和 ELB 集成后应该切换到 ELB 健康检查。

类型检查内容实例被替换条件
EC2 健康检查（默认）实例系统状态（system status + instance status）实例变为 impaired 状态
ELB/ALB 健康检查应用层健康检查（TCP/HTTP/HTTPS 目标组健康检查）ELB 返回 unhealthy
核心陷阱：ELB 健康检查下，实例需要同时在目标组注册 + 通过健康检查才算健康。ELB 会自动帮 ASG 注销 unhealthy 实例，然后 ASG 触发替换。但如果目标组的 deregistration_delay 设太长，替换前可能有流量继续打到 unhealthy 实例。

Health Check Grace Period

  • 实例刚启动时的这段时间内，即使健康检查返回 unhealthy，ASG 也不会终止它。
  • 默认值 300 秒（5 分钟）。
  • 必须大于实例实际启动时间——否则新实例刚启动还没准备好就被 ELB 标记 unhealthy，然后被 ASG 杀掉。

Cooldown vs Grace Period

九、场景题解析

场景 1：一个面向最终用户的 Web 应用，流量存在周期性模式（每日上午 9 点开始递增，11 点达到峰值，下午逐渐下降）。需要在流量到来前提前扩容，避免用户等待。应选择哪种扩展策略？
正确答案：D。需要在流量到来之前扩容 → Predictive Scaling。其他三种策略都需要等 CloudWatch 指标（如 CPU）超过阈值才触发，属于"事后响应"。Predictive Scaling 基于 14 天历史数据训练模型，在预测到的高峰前主动扩容。
场景 2：一个后台批处理系统，需要维持大约 50% 的 CPU 使用率以最大化吞吐量。运维团队希望：① CPU 高于 60% 自动扩容，② CPU 低于 40% 自动缩容，③ 不需要手动写 CloudWatch Alarm。应选择哪种策略？
正确答案：C。维持目标值 + 不需要手动 Alarm → Target Tracking Scaling。它内置 CloudWatch Alarm，自动按比例调整。可以设置 Cooldown 和 Warm-up 参数来优化扩容行为。
场景 3：一家金融公司的 Web 应用运行在 Auto Scaling 上，流量不可预测且会突然飙升。同时要最低成本。架构师建议混合 Spot 和 On-Demand。以下哪个参数配置最合适？
正确答案：B。金融公司需要一定稳定性 → On-Demand 保底 + Spot 灵活扩展；最低成本 + Spot 低中断率 → capacityOptimized 分配策略。OnDemandBaseCapacity=2 保证至少 2 个 On-Demand 不被 Spot 中断；OnDemandAbove=25 表示超出基础的部分 25% On-Demand、75% Spot，既省钱又有缓冲。
场景 4：应用使用 Auto Scaling Terminate Hook 来实现优雅关闭（先从服务发现注销，再执行清理脚本）。运维报告：最近有一次缩容，3 个实例被终止，但只有 1 个成功执行了优雅关闭，另外 2 个实例被 ASG 直接 terminate 了。最可能的原因是？
正确答案：C。Terminate Hook 触发后，必须在默认 1 小时内调用 CompleteLifecycleAction 或 RecordLifecycleActionHeartbeat。如果超时未回复，ASG 会按 DefaultResult（通常是 CONTINUE）执行终止，绕过钩子的优雅关闭逻辑。Spot 中断确实不会触发 Terminate Hook，但题目说是"缩容"，不是 Spot 中断。
场景 5：一个基于 ALB 的 Web 应用，开发团队报告新启动的 EC2 实例经常"刚起来就被 ASG 杀掉"，因为健康检查一直是 unhealthy。最可能的原因和修复方案？
正确答案：C。新实例"刚起来就被杀" → Grace Period 太短。Grace Period 是新实例启动后，ASG 容忍它 unhealthy 的窗口期（默认 300 秒）。如果你的应用启动+初始化需要 5 分钟以上，Grace Period 应设为更长（如 600 秒）。Launch Template 安全组问题会导致健康检查"一直"失败而不是"刚起来"被杀；Warm-up 是另一个参数但用于不同场景。
场景 6：电商应用预计在双十一当天流量会激增 10 倍，需要确保系统能够在流量到来前就"预热"好。方案：维护一个 ASG，同时维护一个暖池（Warm Pool）保持 30 个 Stopped 状态的实例。以下关于此方案的描述，哪项是正确的？
正确答案：B。
  • A 错：暖池 Stopped 实例不会注册 ALB，必须启动并 InService 后才参与。
  • B 对：Stopped 实例不收取 vCPU/内存费用，只收 EBS 存储费。
  • C 错：暖池实例首次启动已经执行过 User Data，后续从 Stopped → Running 不会再执行。
  • D 错：暖池容量可以超过 ASG max size——这是设计意图（先准备好，需要时快速启动）。

  • Health Check Grace Period：新实例启动后容忍 unhealthy 的窗口期，默认 300 秒
  • Cooldown vs Grace Period：Cooldown 防 ASG 抖动，Grace Period 防实例误杀
  • Warm Pool + Stopped：不收费 vCPU/内存，省 EBS 存储费，启动跳过 User Data
  • Warm Pool 容量：可以超过 ASG max size
  • Warm Pool：Stopped 实例不注册 ELB，不参与健康检查
  • Termination Protection：实例级保护，缩容跳过被保护实例；如果所有实例都保护且 > min → 卡住
  • ELB 健康检查：ASG 切换后，unhealthy 实例自动被替换
  • Terminate Hook DefaultResult=ABANDON：超时不回复 → 终止被放弃（实例不终止）

十二、快速自测

先独立选择，再点击"查看解析"。

1. ASG 使用 Simple Scaling，CPU > 80% 时 +2 实例。当前 CPU 是 85%，触发扩容 +2。冷却期 300 秒。假设扩容后 CPU 立刻变成 85%（因为冷却期还没过），300 秒后 CPU 又降到 79%，以下说法哪个正确？
正确答案：C。Simple Scaling 在冷却期内完全不响应任何 CloudWatch Alarm 变化——既不扩容也不缩容。只有冷却期结束后才重新评估。如果用 Step Scaling 则冷却期内可以继续响应。CPU 降到 79% 不会自动缩容——必须有一个单独的缩容策略（Simple Scaling 没有内置的，需要另建或用 Step/Target Tracking）。
2. 一个 ASG 使用 Target Tracking Scaling（CPU 目标 60%），实际发现新扩容的实例在启动后 2 分钟内没有被计入 CPU 平均值。这是因为设置了哪个参数？
正确答案：B。Target Tracking Scaling 有一个独有的 Warm-up 参数，告诉 ASG：新实例加入后，等多少秒再把它的指标纳入平均值计算。这是为了防止新实例还没就绪就被"假扩容"导致提前缩容。Grace Period 是另一个概念——它是给健康检查用的容忍窗口，不是 CPU 指标计算。
3. 一个电商 ASG，双十一前你打算启用 Warm Pool 预先准备好 40 个实例。以下哪种状态的暖池实例启动最快、最省钱？
正确答案：B。Stopped 状态不收取 vCPU/内存费用（只收 EBS 存储费），启动速度接近 Running 状态，同时用 Golden AMI 确保启动时不需要再跑 User Data。Running 状态虽然启动最快但持续计费；Pure Predictive Scaling 扩容需要从 AMI 全新启动（分钟级）；Spot Fleet 不是 ASG Warm Pool 的替代方案。
