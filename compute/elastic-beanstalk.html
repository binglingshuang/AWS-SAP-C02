一、应用与环境模型

Elastic Beanstalk 接收应用代码/版本，负责创建和协调承载应用的 AWS 资源。它降低部署与环境管理工作量，但底层 EC2、负载均衡、Auto Scaling、网络和 IAM 仍可见并需治理。

Application应用的逻辑容器，可关联版本、配置和环境。并非运行时实例。
Application Version可部署的源代码包/版本标识。环境部署某版本后，仍需管理版本保留与构建产物。

Configuration实例规格、扩缩、网络、负载均衡、环境属性等环境设置。配置变更可能触发实例替换或环境更新，生产前评估影响。
关键点：Beanstalk 是托管的应用部署编排层，不是抽象掉全部 AWS 基础设施的黑盒。可结合 CloudFormation、EC2、Auto Scaling 与 ELB 进行底层诊断。

二、环境类型与架构

环境类型典型用途设计点
Web Server Environment处理用户 HTTP/HTTPS 请求。可采用单实例或负载均衡/自动扩缩架构；生产通常需多 AZ 和健康检查。
Worker Environment从队列接收并异步处理后台作业。适合将长任务从请求路径解耦；监控队列积压、失败与重试。
Single Instance开发、演示、低成本非生产环境。无多实例冗余，实例/可用区故障会影响服务。
Load Balanced / Scalable生产 Web 流量与弹性工作负载。维护容量、健康检查、部署策略、子网和扩缩指标。

Worker 环境通常与队列处理机制配合，由应用消费作业并在完成后删除消息；应设计幂等处理和失败恢复。需要复杂工作流编排、严格任务依赖或高规模队列治理时，可评估 SQS、Step Functions、ECS 或 AWS Batch。

三、部署策略与回滚

策略容量/中断特征适合与风险
All at once所有实例同时部署，期间可能中断服务。简单快速，适合开发或可容忍短暂中断的环境；失败影响面大。
Rolling分批替换/更新现有实例。减少同时更新范围，但部署期间可用容量可能下降；需保留足够健康容量。
Rolling with additional batch先增加一批额外实例，再分批更新。避免部署时容量下降，代价是临时增加资源。
Immutable在新实例上部署新版本，成功后替换旧实例。隔离新旧版本、回滚路径清晰；临时需额外容量，需检查配额和部署时间。
Traffic splitting新版本在临时环境中接收一部分线上流量。逐步验证真实流量；失败可回退流量，但需为临时容量与观测做好准备。

蓝绿部署可在两个独立环境分别运行稳定版和候选版，验证后交换 CNAME；旧环境保留为回退目标，确认切换与数据兼容后再终止。数据库 schema 变更需向前/向后兼容，不能假设切回旧应用即可逆转数据变化。

选型口诀：低风险/可回滚优先 Immutable 或 Traffic Splitting；追求简单且能接受容量/中断权衡时才考虑 All at once 或 Rolling。先满足健康检查与容量，再谈部署成功。

四、.ebextensions 与平台钩子

  • .ebextensions/*.config 可在应用包中声明环境选项、资源、软件配置及命令等；采用 YAML/JSON 配置时严格检查结构和执行顺序。
  • 配置文件适合可重复环境设置，不应用于保存明文秘密；敏感值从 Secrets Manager / Parameter Store 获取。
  • Amazon Linux 平台可使用适用版本支持的 .platform/hooks/ 生命周期函数，在部署阶段执行自定义脚本。
  • 自定义命令应幂等、可观测、快速失败，并避免长期阻塞部署；脚本失败可能导致环境更新失败。
  • 平台能力、钩子阶段与旧版配置兼容性依操作系统平台版本而异，升级前查阅对应平台文档。
安全注意：将环境属性或配置文件中的秘密值写入源包，可能泄露到代码仓库、日志或部署产物。使用秘密管理服务和最小权限 IAM。

五、数据库与状态

  • 应用实例应尽可能无状态，用户会话和上传文件放入外部共享服务（如 ElastiCache、DynamoDB、S3）。
  • 数据库与应用环境生命周期解耦：生产数据库通常单独创建和管理，避免删除/重建环境时误删持久数据。
  • 若环境关联 RDS，明确数据库是否随环境生命周期删除、备份保留与恢复流程；生产变更需先评估数据保护。
  • 蓝绿/滚动部署期间，新旧版本可能并行访问数据；采用兼容性迁移和分阶段 schema 变更。
  • 通过连接池、超时与限流保护数据库，避免应用扩缩导致连接风暴。

环境健康显示 Green 不替代端到端业务监控。使用 CloudFormation/EC2/ASG/ELB 事件定位底层故障，利用增强型健康报告与 CloudWatch 日志诊断实例、部署和应用问题。

七、服务边界与选型

服务核心抽象适合需求
Elastic Beanstalk应用版本 + 环境标准 Web/Worker 应用，希望平台化部署且保留底层资源可见性。
App Runner源/容器镜像到托管 Web 服务简化 Web 服务构建与部署，较少管理平台环境。
ECS / EKS容器任务/Pod 编排需要细粒度容器调度、服务拓扑、作业或集群控制。
Lambda事件驱动函数短时无服务器处理，而非持续运行的 Web/Worker 进程。

八、场景题解析

场景一：更新时不能失去现有容量

应用需要滚动发布，但业务不能接受更新期间健康实例数下降。

方向：评估 Rolling with additional batch，或采用 Immutable；确认临时容量、配额和健康检查。

排除：普通 Rolling 可能在更新阶段暂时减少可用容量。

场景二：新版本需先小流量验证

上线风险较高，需观察新版本真实请求后再扩大比例。

方向：使用 Traffic Splitting 或蓝绿环境切换，并配置 CloudWatch 告警/回滚指标。

排除：All at once 没有渐进验证窗口。

场景三：Web 请求处理耗时作业

用户请求需要快速返回，后台报表生成可能运行较久。

方向：把后台工作放入队列，在 Worker Environment 或合适的消费者中异步处理。

排除：让 Web 请求同步等待长任务会占用连接并降低前端可用性。

场景四：环境重建后生产数据库丢失风险

Beanstalk 环境需要替换，但 RDS 中的数据必须保留。

方向：将生产数据库与应用环境生命周期分离，明确备份、保留策略和网络接入。

排除：不要依赖默认删除行为；环境销毁不应成为数据库生命周期控制器。

场景五：需自定义系统依赖安装

部署时必须安装系统包并写入环境配置，且每次新实例都应保持一致。

方向：使用版本控制的 .ebextensions 配置或对应平台的生命周期钩子，确保幂等和无秘密泄露。

排除：手工 SSH 修改单个实例不可重复，Auto Scaling 新实例不会继承手工状态。

场景六：回退应用版本后数据库报错

部署改变了数据库 schema，回滚应用版本导致旧代码无法读取新字段。

方向：采用向前/向后兼容的分阶段 schema migration，先扩展、切换代码、再清理旧字段。

排除：流量切回或应用回滚不会自动撤销数据库结构和数据变化。

十一、快速自测

先独立选择，再点击“查看解析”。

1. 更新期间不能降低健康实例容量，哪种部署策略最贴近需求？
正确答案：C。额外批次或新实例组可避免更新时容量下降；同时检查资源配额和成本。
2. 应用环境可重建，但 RDS 生产数据必须保留，应如何设计？
正确答案：B。应用环境更新和销毁不应意外删除持久数据。
3. 哪种配置适合自动化新 EC2 实例的重复初始化？
正确答案：A。版本化、可重复的配置可应用于新实例；秘密应放在秘密管理服务。
