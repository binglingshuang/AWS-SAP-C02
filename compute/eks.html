一、EKS 架构边界

Amazon EKS 是托管 Kubernetes 控制平面，不是自动替客户管理所有工作节点和 Kubernetes 对象的“全托管应用平台”。

AWS 管理
API Server、etcd、控制平面可用性
→

集群访问、工作节点、网络、工作负载
→
Kubernetes API
Deployment、Service、Pod、CRD
组件职责设计检查
控制平面AWS 在多个可用区运行 Kubernetes 控制平面组件并管理其可用性。集群 API Endpoint 可设为公网、私有或两者；用 CIDR、路由和身份策略限制访问。
工作节点运行 Pod 的 EC2 实例或 Fargate 容量。节点 IAM role、子网、节点组容量与 Pod 调度约束都需正确。
集群 IAM role供 EKS 控制平面代表集群调用所需 AWS API。它不同于节点角色，也不是应用 Pod 的通用身份。
集群版本Kubernetes 版本升级需按支持策略规划，并兼容附加组件与工作负载。先检查版本偏差、API 弃用、CoreDNS / VPC CNI / kube-proxy 等附加组件。
关键边界：控制平面托管不等于节点、容器镜像、Pod 安全策略、应用可用性和集群升级规划都由 AWS 自动完成。

二、节点与容量模式

模式谁管理 EC2适合场景 / 注意点
自管理节点客户管理启动模板、Auto Scaling 与节点生命周期。需要高度自定义 AMI、引导流程或特殊节点管理；运维责任较多。
托管节点组EKS 管理节点组生命周期，底层仍是客户账户中的 EC2 / ASG。通用 EC2 工作负载的常用选择；可配多 AZ、实例类型、更新配置和容量类型。
FargateAWS 管理 Pod 所使用的服务器容量。按 Pod 运行，不管理节点；受支持的工作负载和网络/存储能力有边界。
EKS Auto ModeAWS 自动化更多集群计算、网络和存储管理。按需求评估其支持范围、权限和成本；不是现有集群所有运维责任消失的保证。
EKS Anywhere客户在自有基础设施运行 Kubernetes 集群，并使用 EKS 工具链进行管理。面向本地/边缘一致性，不等同于 AWS 托管云端 EKS 控制平面。

托管节点组扩缩通常与 EC2 Auto Scaling 关联：节点级容量和 Pod 副本数是两层控制。Cluster Autoscaler 或 Karpenter 等组件可根据待调度 Pod 增加节点；节点不足时仅提高 Deployment 副本数不会创造计算容量。

成本线索：EC2 节点适合稳定、密集或需 DaemonSet / GPU / 特殊实例的工作负载；Spot 节点可用于可中断且可重试的任务，并需配置多实例类型、冗余和优雅退出。

三、Fargate Profile

Fargate Profile 通过命名空间和可选 Pod 标签选择哪些 Pod 在 Fargate 上运行。匹配规则是调度入口，不是 Kubernetes Deployment 副本管理器。

  • 为每个 Fargate Profile 配置 Pod 执行角色（Pod execution role），供 Fargate Agent 执行拉取镜像等任务。
  • 匹配的 Pod 调度到 Fargate；未匹配 Pod 仍需合适的 EC2 节点或其他调度方式。
  • 一个 Profile 可指定私有子网；为 HA 选择多个可用区子网，并确保镜像仓库、日志和依赖可达。
  • Fargate 不运行 DaemonSet；需要节点级 Agent、特权容器、特定设备或 GPU 时需核对支持边界，通常选 EC2 节点。
  • Fargate Pod 网络与安全组需按 EKS VPC 网络模型规划；无节点不等于无子网、路由或安全组责任。
角色区分：Pod execution role 是 Fargate 基础设施启动 Pod 所需；应用 Pod 访问 S3、DynamoDB 等 AWS 服务，应使用 IRSA 或 EKS Pod Identity 授权，不要把应用权限塞进节点角色。

四、IAM、IRSA 与 Pod Identity

身份层用途最小权限实践
Cluster IAM roleEKS 控制平面调用 AWS 服务。按 EKS 集群要求授予，不承载应用数据权限。
Node IAM role节点注册集群、拉取镜像及节点级组件所需操作。避免让所有 Pod 继承过宽节点权限。
IRSA为集群配置 OIDC 身份提供者，Service Account 通过 AssumeRoleWithWebIdentity 获取 IAM 权限。角色信任策略限制 OIDC Provider、namespace 和 service account 的 subject。
EKS Pod Identity通过 Pod Identity Agent 与关联，将 IAM role 授予指定 Kubernetes Service Account。检查 Agent、关联、信任策略及区域支持；与 IRSA 是可选的 Pod 级身份机制。

Pod 必须使用预期的 Kubernetes Service Account，应用 SDK 需支持相应凭证链。仅创建 IAM Role 或给节点附加策略，不能证明目标 Pod 已获得正确的最小权限身份。

五、网络与入口

  • Amazon VPC CNI 为 Pod 分配 VPC 地址；子网可用 IP、实例 ENI/IP 配额及安全组规则会限制可调度 Pod 数。
  • 控制平面 Endpoint 的公网/私有访问模式需匹配运维人员、CI/CD 与节点到 API Server 的网络路径。
  • 集群内 Service 提供服务发现；面向 HTTP/HTTPS 流量通常通过 Ingress Controller / AWS Load Balancer Controller 管理 ALB。
  • 需要四层负载均衡时可评估 Service type LoadBalancer 与 NLB；核对目标类型、健康检查、安全组和跨 AZ 路径。
  • 私有子网拉取 ECR 镜像、写日志或调用 AWS API，需要 NAT 或相应 VPC Endpoint，并满足 DNS 与 IAM 策略。
排障顺序：先看 Pod Pending 原因与事件，再检查节点资源/标签/污点、子网 IP 与 CNI、IAM 拉镜像权限、路由/DNS、安全组和控制平面 Endpoint。

六、持久化存储

需求常见选择关键区别
Pod 独占块存储EBS CSI Driver + PVC卷通常绑定可用区；Pod 迁移到其他 AZ 时需处理调度与卷可用区，不是跨 AZ 共享文件系统。
多 Pod 共享文件EFS CSI Driver + PVC适合多实例共享文件系统；需规划 Mount Target、安全组和 POSIX 权限。
对象数据与备份S3 API对象存储不等于可挂载 POSIX 文件系统；使用 IAM Pod 身份与网络端点控制访问。

EBS CSI 持久卷适用于 EC2 节点工作负载；EKS Fargate Pod 不支持挂载 EBS 持久卷。CSI 驱动、StorageClass、PVC、IAM 和网络都可能是存储挂载故障原因。不要把容器可写层视为持久数据存储。

七、扩缩、升级与可靠性

  • Horizontal Pod Autoscaler 扩缩 Pod 副本；需提供有效指标并设置合理 requests / limits。
  • Cluster Autoscaler 或 Karpenter 处理节点容量；它们与 HPA 的作用层不同。
  • 多 AZ 工作节点、Pod 反亲和/拓扑分布、PodDisruptionBudget 可改善故障与维护时的可用性，但 PDB 不是故障时强制冗余保证。
  • 升级顺序需兼顾控制平面、节点组、附加组件及 API 兼容；先验证测试环境和弃用 API。
  • 用 CloudWatch Container Insights / Prometheus 等观测节点、Pod、控制面日志和应用指标；告警应覆盖 Pending、重启、不可用副本和容量耗尽。
常见误区：节点 Auto Scaling 不自动保证服务副本分布；HPA 也不自动扩容节点。需验证 Pod 能否放置、节点能否按时加入、负载均衡健康检查是否通过。

八、EKS 与 ECS 选型

优先选 EKS优先选 ECS
组织已有 Kubernetes 技能、工具链、Helm/Operator/CRD 或多云一致性要求。主要运行在 AWS，倾向 AWS 原生编排、较少控制面复杂度和更直接的服务集成。
必须使用 Kubernetes API 兼容工作负载或生态产品。希望用 Task Definition / Service 管理容器，且无需 Kubernetes 生态。

两者均可运行在 EC2 或 Fargate 的相应模式中。不要把“容器”本身作为选择 EKS 的理由：比较的是编排 API、团队运营能力、可移植性与总运维成本。

九、场景题解析

场景一：Pod 需独立读取 S3 权限

多个团队共用节点，但每个应用只能访问自己的 S3 前缀。

方向：用 IRSA 或 EKS Pod Identity 将独立 IAM role 绑定到各应用 Service Account，并限定资源和前缀。

排除：扩大节点角色会让同节点工作负载获得过宽权限；Kubernetes RBAC 不是 AWS S3 授权。

场景二：公司已有 Kubernetes Operator

应用依赖 CRD/Operator，团队要求继续使用标准 Kubernetes 工具链。

方向：选择 EKS，验证所需 Operator、版本与 AWS 集成兼容性。

排除：ECS 提供不同的任务与服务 API，不能直接运行依赖 Kubernetes API 的 Operator。

场景三：无状态服务不想管理节点

少量 Pod 运行简单 Web 服务，无 DaemonSet、GPU 或节点级特权需求。

方向：使用合适的 Fargate Profile，配置执行角色、私有子网、镜像访问与入口。

排除：Fargate 不会自动替应用创建 Service/Ingress 或解决 IAM 与网络问题。

场景四：Pod Pending，节点 CPU 也不足

HPA 已增加副本，但新增 Pod 长时间 Pending。

方向：检查调度事件、节点组容量上限和节点自动扩缩配置，确认实例类型/配额/子网 IP 足够。

排除：仅继续提高 HPA 最大副本数只会制造更多待调度 Pod。

场景五：多个 Pod 共享上传文件

应用副本会在不同节点同时读取写入共享文件。

方向：评估 EFS CSI 与适配的访问模式、POSIX 权限和 Mount Target 网络。

排除：EBS 通常是区级块卷，并非跨 AZ 多 Pod 共享文件方案；容器临时盘不可持久。

场景六：升级后应用 API 不兼容

集群准备升级，部分清单仍使用将移除的 Kubernetes API。

方向：升级前扫描弃用 API，先迁移清单与控制器，再按兼容矩阵升级控制平面、插件和节点。

排除：托管控制平面并不意味着可以跳过工作负载兼容验证。

十二、快速自测

先独立选择，再点击“查看解析”。

1. 同一 EKS 节点上的两个应用需要不同的 S3 权限，最合适的授权方式是什么？
正确答案：B。Pod 级身份可隔离应用权限；节点角色会扩大同节点工作负载的潜在权限。
2. HPA 已增副本，但 Pod Pending，节点无可用 CPU。下一步优先检查什么？
正确答案：B。HPA 扩 Pod，不会自动保证节点容量；检查节点供给和 Pod 放置条件。
3. 哪种情况更支持使用 EKS 而非 ECS？
正确答案：A。Kubernetes API 生态需求是 EKS 的明确选型因素；纯 AWS 容器工作负载也应比较 ECS 的简洁性。
