一、ECS 核心模型

Amazon ECS 是 AWS 原生容器编排服务；它安排容器在哪里运行、维持多少个副本并协调部署。ECS 本身不等于容器镜像仓库，也不决定应用的业务扩缩策略。

Task Definition版本化的任务蓝图，描述一个或多个容器及运行配置。镜像、CPU/内存、端口、角色、环境变量、日志。
TaskTask Definition 的运行实例；可由 Service 维持，也可一次性运行。短期批处理或一次性作业通常直接运行 Task。
Service维护期望 Task 数、调度替换故障任务，并管理服务部署。持续运行的 Web/API、目标组注册、滚动发布。
Capacity Provider将任务需求映射到 EC2 Auto Scaling 容量或 Fargate 容量。需要混合 EC2/Fargate、容量伸缩或 Spot。
先辨别入口：持续服务用 ECS Service；独立、有限时长的容器工作可用 RunTask / Scheduled Task；长时间队列处理也可由 Service 持续消费。ECS 负责编排，应用仍需处理重试、幂等与优雅退出。

二、Task Definition：容器运行蓝图

Task Definition 以修订版本记录任务配置。发布新修订不会自动替换正在运行的 Task；更新 Service 使用新修订后，才会按部署配置替换任务。

配置项作用常见误区
Container definitions镜像位置、命令、端口、环境变量、依赖关系、健康检查与日志。将镜像存放在 ECR；定义引用镜像，不是将镜像上传到 ECS。
CPU / Memory为 Task 和容器声明资源；Fargate Task 的 CPU / 内存组合须符合平台支持的组合。不能把 Fargate 当成可任意超卖的宿主机；资源请求需与实际负载匹配。
Task execution role由 ECS/Fargate Agent 代表任务执行拉取私有 ECR 镜像、写 CloudWatch Logs、注入受支持的密钥等操作。不是应用代码访问 AWS API 的身份。
Task role向任务中的应用提供 AWS 凭证，例如读取 S3 或调用 DynamoDB。不要把应用权限全部塞进执行角色或 EC2 实例角色。
Network modeFargate 使用 awsvpc；EC2 模式还可按场景选择其他网络模式。Fargate 的每个 Task 使用自己的弹性网络接口与安全组。
Volumes定义容器间共享或持久化所需的卷，例如 EFS 挂载。容器可写层 / 临时存储不应被误当作跨 Task 持久卷。
Logging / secrets配置日志驱动，并通过 Secrets Manager / Parameter Store 引用敏感配置。环境变量引用并不自动赋权；Task execution role 仍需相应权限。
修订与部署：Task Definition 修订是不可变的配置快照。生产更新应注册新修订、更新 Service 指向的修订并观察部署；回滚时可将 Service 恢复到已知稳定修订。

三、EC2、Fargate 与容量策略

模式容量与运维责任适合场景注意点
ECS on EC2客户管理 EC2 实例、AMI、补丁、容量与集群扩展；ECS 管理容器调度。需要宿主机控制、特殊硬件/实例、稳定高利用率或特定内核能力。需同时处理实例容量与任务调度；Task 数量扩展不等于 EC2 容量已就绪。
FargateAWS 管理底层服务器；按 Task 声明的 CPU / 内存提供隔离运行环境。希望减少主机管理、负载波动明显、团队想聚焦容器应用。仍要管理镜像、IAM、网络、Task 资源与扩缩策略；不是“无需配置”。
Fargate Spot使用有折扣但可中断的 Fargate 容量。可容忍中断的无状态、可重试、分布式批处理或弹性工作负载。不要承载唯一副本或不可中断关键处理；实现优雅退出、重试和冗余。

Launch type 与 Capacity Provider

  • Launch type 可直接指定 EC2 或 FARGATE，适合简单、明确的启动选择。
  • Capacity Provider Strategy 可组合 Fargate、Fargate Spot 或 EC2 Auto Scaling 容量提供者；base 指定最低基础任务数，weight 决定超出基础数后的相对分配。
  • 使用容量提供者策略时，应在集群中关联相应 Provider，并在 Service/RunTask 的配置中使用策略；不要把 Launch Type 与 Capacity Provider Strategy 当作同一字段同时配置。
  • EC2 Capacity Provider 可与托管扩缩结合，按任务需求调整关联 Auto Scaling Group 的实例容量；这与 Service Auto Scaling 调整 Task 数是不同控制环节。
选型快记：需控制主机 / 利用特定实例能力 → ECS on EC2；不想管理主机 → Fargate；可中断且希望进一步优化成本 → 将部分容量放到 Fargate Spot，并保留足够的稳定容量。

四、Task、Service 与部署

Service 维持期望状态

将 desiredCount 设为期望任务数后，ECS Service Scheduler 会尝试维持该数量。任务因故障退出时，Service 可启动替代任务；这不代表应用数据自动恢复，也不保证替换立即成功，仍受子网 IP、配额、镜像拉取、资源和健康检查影响。

滚动部署与健康检查

  • 更新镜像或 Task Definition 修订时，Service 按部署配置启动新任务、等待其健康，再逐步停止旧任务。
  • 部署百分比参数控制部署期间允许的最小健康任务数与最大运行任务数；为零停机发布留出额外容量，并确认目标组健康检查与容器启动时间相匹配。
  • Deployment circuit breaker 可在部署失败时停止推进，并可配置自动回滚到最近一次成功部署。CloudWatch Alarm 也可用于部署监控与回滚。
  • 应用应处理 SIGTERM 等停止信号，停止接收新请求并完成在途工作；长任务需要设置合理的停止宽限时间。

服务发现和伸缩不是一回事

Service Connect、AWS Cloud Map 或负载均衡可帮助客户端找到任务端点；它们不负责将 Task 数扩到目标值。扩缩由 Service Auto Scaling 管理。

五、网络、负载均衡与服务发现

需求典型配置核对点
Fargate Task 入站awsvpc 模式，每个 Task 获得 ENI 与可单独关联的安全组。子网需有足够 IP；安全组允许负载均衡器到 Task 端口。
HTTP / HTTPS Web 服务常用 ALB；ECS Service 将任务注册进 Target Group。awsvpc 任务通常使用 Target Group 的 ip target type，而不是 instance。
TCP / UDP、静态地址等需求评估 NLB 与对应目标组及客户端协议。按协议、源 IP 保留、健康检查与入口需求选型，不要仅凭“容器”决定负载均衡器。
Task 出站访问公网私有子网通常经 NAT Gateway；也可为 AWS 服务配置相应 VPC Endpoint。Fargate Task 不因放进 public subnet 就自动有公网 IP；需检查任务网络配置、路由、安全组和 DNS。
内部服务寻址Service Connect、Cloud Map 或内部负载均衡器。健康状态、命名空间、端口及跨 VPC / 跨账号连通性仍需设计。
网络排障顺序：先确认 Task ENI 与子网 IP，再核对路由表、NACL、安全组、DNS、目标组类型/端口/健康检查，最后验证应用监听地址与端口。IAM 授权错误和网络超时是不同故障层。

六、Service Auto Scaling

Application Auto Scaling 调整 ECS Service 的期望 Task 数。它扩的是任务副本，不是 Fargate Task 的 vCPU/内存规格；Task 规格需要修改 Task Definition 并部署新修订。

策略如何工作常见用途
Target tracking维持指标在目标附近，自动创建/调整 CloudWatch Alarm。按平均 CPU、内存或 ALB 每目标请求数维持容量。
Step scaling依据 Alarm 超出阈值的幅度，分级增加或减少 Task 数。需要对不同负载区间采取不同幅度的响应。
Scheduled scaling按已知时间表调整最小、最大或期望容量。每日固定业务高峰、批处理窗口或维护时段。
Predictive scaling根据历史模式预测未来容量；需结合支持的服务与指标配置。规律性流量、希望在需求到来前预扩展；不替代实时扩缩机制。

伸缩边界与联动

  • 配置 MinCapacity / MaxCapacity，避免自动扩展突破账户预算或下游服务承载能力。
  • CPU / Memory 指标应采用适合 Service 的平均值；ALB 请求量应使用每目标请求指标，并确认负载均衡器与目标组关联正确。
  • 扩容 Task 后，若它们运行在 EC2 容量上，还要确保集群有足够的实例；使用 Fargate 时底层主机由 AWS 管理，但仍受服务配额和子网 IP 限制。
  • 缩容时确保任务可优雅排空；对队列消费者监控积压年龄与消费速率，不要只盯 CPU。
  • Fargate Spot 中断会造成容量变化；对关键工作保留稳定容量并使用多副本、可重试和持久化队列。
常见陷阱：Service Auto Scaling 调 Task 数；EC2 Capacity Provider / Auto Scaling Group 调宿主机数量。EC2 模式需要两层容量互相配合，Fargate 则不需要管理宿主实例。

七、IAM、密钥与执行访问

身份 / 控制面负责什么设计原则
Task execution roleAgent 拉取 ECR 镜像、写日志或取出配置引用的秘密。仅授予启动任务所需权限；检查信任关系允许 ECS Tasks 使用。
Task role容器应用代码调用 AWS API。按应用/任务拆分最小权限，避免共享过宽权限。
EC2 instance profileECS on EC2 的宿主实例与 Agent 所需权限。不要用宿主机角色代替 Task Role 为应用授权。
Security Group控制 ENI 入站与出站网络流量。Fargate 可针对单个 Task 使用安全组；只开放必要端口和来源。
Secrets Manager / Parameter Store集中保存敏感值并按权限读取。不要将长期凭证写入镜像、源代码或明文环境变量；规划轮换和任务更新。

使用私有 ECR 时，镜像拉取失败应检查 execution role、ECR 仓库策略、镜像 URI / 标签，以及任务到 ECR 的网络路径。应用运行后访问 S3 失败，则优先核对 Task Role 和出站网络，不要只修改执行角色。

八、存储、日志与运维

  • 临时存储：Task 本地临时空间适合缓存与临时文件；任务替换、重新调度或终止后，不应假设文件仍在。
  • 持久共享文件：需要多个任务共享 POSIX 文件时评估 EFS；为 Fargate 配置 EFS 时同时核对挂载目标、网络、安全组与文件系统授权。
  • 对象 / 块数据：共享对象数据常用 S3；需块设备控制时由 EC2 等适配方案承载。不要将容器生命周期与持久数据生命周期绑死。
  • 日志：为容器配置合适的日志驱动与 CloudWatch Logs；区分容器标准输出日志、应用指标和 ECS 平台事件。
  • 诊断：结合 ECS Service Events、Task stopped reason、容器退出码、CloudWatch 日志、目标组健康状态和 CloudTrail 部署事件排查。
  • ECS Exec：适合受控地进入运行中的容器进行诊断；需显式启用并满足 IAM、网络与审计要求，不能作为日常部署或修复配置漂移的替代方案。
数据持久性：将状态写入外部持久服务；容器磁盘应可丢弃。对于队列消费者，先安全提交处理结果或检查点，再确认消息，降低任务被终止时的重复或数据丢失风险。

九、高可用与成本选型

  • Service 跨多个可用区部署任务，并让负载均衡器健康检查与应用健康端点一致。
  • 至少保留足够的任务冗余应对部署、故障和扩缩；关键工作负载不要把唯一副本放在 Spot 容量。
  • 镜像应小而可复现，采用不可变版本标签；Task Definition 修订、部署状态和基础设施变更纳入审计。
  • 通过真实负载压测确定 CPU / Memory 请求与限制；低估会导致 OOM / 性能退化，高估则增加 Fargate 成本或降低 EC2 利用率。
  • Fargate 按配置资源和运行时间计费；EC2 还需综合实例、存储、网络、容量闲置与运维成本比较。Spot 只适用于能承受中断的工作负载。
  • 监控 Task 数、部署失败、重启、CPU / 内存、请求延迟、队列积压、目标组健康和成本，而非只看单一 CPU 指标。
答题框架：托管控制面（ECS）与计算容量模式（EC2/Fargate）分开选择；持续副本选 Service；定义角色和网络边界；最后按负载指标设置 Service Auto Scaling，并为部署失败与中断设计回滚/重试。

十、场景题解析

场景一：不想维护容器宿主机

团队已有 Docker 镜像，希望以 ECS 运行 HTTP 服务，不想管理 EC2 补丁和集群实例容量，并需要根据请求负载自动增减副本。

正确方向：使用 ECS Service + Fargate，并配置 Service Auto Scaling（例如基于 ALB 每目标请求数或合适的 CPU 指标）。

分析思路：ECS Service 维持期望任务数；Fargate 免去宿主实例管理；Application Auto Scaling 调整任务数量。

排除：只改 Task Definition 不会自动扩缩；EC2 Capacity Provider 需要管理宿主容量；Lambda 不适合需要长期容器进程的服务。

场景二：低流量服务仍需一组常驻任务

内部 API 必须持续运行并注册到内部负载均衡器，不是一次性作业。如何确保故障任务自动恢复？

正确方向：创建 ECS Service 并设置 desired count、跨 AZ 子网和健康检查。

分析思路：Service Scheduler 持续协调期望副本数，并在任务退出时尝试替换。

排除：单次 RunTask 不会自动维持副本；容器重启策略不能取代跨任务调度与服务级部署。

场景三：应用访问 S3 被拒绝

Fargate 任务成功拉取镜像并写入日志，但应用调用 S3 收到 AccessDenied。应优先检查什么？

正确方向：Task Role 的信任关系与 S3 最小权限策略；再确认目标 Bucket Policy 和资源 ARN。

分析思路：拉取镜像和日志成功说明 execution role 的启动权限大体正常；应用运行时的 AWS API 权限来自 Task Role。

排除：扩大 Task execution role 或为整个集群授予管理员权限会混淆职责并扩大风险。

场景四：Fargate 服务无法被 ALB 识别

任务已运行，但 ALB Target Group 中目标不健康；任务网络模式是 awsvpc。

正确方向：使用 IP 类型目标组，核对容器端口映射、任务安全组允许 ALB 安全组访问、健康检查路径和应用监听地址。

分析思路：awsvpc 为任务提供独立 ENI，因此目标是任务 IP，而非 EC2 实例 ID。

排除：只重启 Service 不会修正 Target Group 类型或安全组缺口；开放所有来源也不是必要修复。

场景五：高峰前预先增加容器数量

订单服务每个工作日 10 点出现可预测高峰，当前扩容到达较慢。如何在高峰前增加任务，同时保留实时响应能力？

正确方向：使用 Scheduled Scaling 预调容量，并视负载需要叠加 Target Tracking 处理偏离预测的实时流量。

分析思路：时间表针对已知规律预扩；目标跟踪补充实际指标变化。两者都受 Min/Max 容量约束。

排除：只增加最大容量不会主动扩容；修改 Task CPU/内存不能直接增加副本。

场景六：可重试的批处理追求低成本

一组无状态任务处理持久化队列中的可重试作业，允许任务被中断，但不能丢失作业，也不应让关键在线 API 受影响。

正确方向：可评估 Fargate Spot 作为部分容量，保留稳定容量应对关键工作；使用持久化队列、幂等处理、优雅退出与重试。

分析思路：Spot 的折扣以可中断为代价；耐久性应由队列和处理协议提供，而非依赖某个任务一直运行。

排除：把唯一任务副本放在 Spot 或将未完成作业只保存在容器文件系统中，都会造成中断风险。

  • EC2 Capacity Provider：可联动 ASG 扩宿主机容量
  • 修订：新 Task Definition 需更新 Service 才会生效
  • 持久数据：外置到 EFS / S3 / 数据库等持久服务
  • 部署安全：健康检查 + Circuit Breaker / 回滚 + 优雅退出

十三、快速自测

先独立选择，再点击“查看解析”。

1. Fargate 任务需要调用 DynamoDB。应将应用权限授予哪个角色？
正确答案：B。Task Role 提供给应用容器运行时使用；Execution Role 由 Agent 用于拉取镜像、写日志等任务启动操作。
2. 想依据 ALB 负载自动增加 Fargate Web 服务副本，应该配置什么？
正确答案：B。Service Auto Scaling 调整期望 Task 数；修改 Task Definition CPU 会改变每个任务规格，且需重新部署。
3. Fargate 的任务已经运行，但 ALB 目标持续不健康。网络模式为 awsvpc，首先核对哪组设置？
正确答案：A。awsvpc Task 以任务 ENI/IP 作为目标，连接与健康检查需端到端匹配。
