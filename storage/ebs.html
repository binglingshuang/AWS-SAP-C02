一、EBS 基础与边界

Amazon Elastic Block Store（EBS）为 EC2 提供持久化块设备。卷通常在单个 Availability Zone 内创建，并通过网络附加到同一区域/可用区中受支持的实例。

存储形态块存储，操作系统可在其上建立文件系统或裸设备单实例磁盘、启动卷、数据库数据盘常用 EBS
持久性与实例生命周期解耦（取决于卷的删除设置）实例停止/终止后，数据是否保留要看 DeleteOnTermination
可用区范围卷位于单一 AZ不能把一个普通 EBS 卷直接挂到另一个 AZ 的实例
快照范围快照可用于同区域恢复新卷；复制快照可用于其他区域跨 AZ 迁移通常通过快照在目标 AZ 创建卷；跨 Region 需复制快照
生命周期卷可从实例分离再附加给兼容实例；启动卷需按实例状态与操作约束处理卷分离不等于数据删除，卷终止行为要检查配置

EBS、实例存储、EFS 与 S3

需求优先考虑核心区别
单台 EC2 的低延迟持久化块设备EBS卷通常绑定单 AZ，可独立快照、备份与恢复
实例本地临时高速磁盘Instance Store与宿主机生命周期相关；停止、终止或底层故障时数据可能丢失
多台 Linux 实例共享文件系统EFS托管 NFS 文件系统，可跨 AZ 挂载；不是块设备
对象/静态内容、数据湖、归档S3通过对象 API 访问，不是可挂载的通用块设备
删除保护陷阱：实例终止不必然意味着 EBS 数据删除，也不必然意味着保留。根卷和数据卷的 DeleteOnTermination 行为可能不同；关键生产数据应有独立快照/备份策略，不能只依赖实例属性。

二、卷类型选型

先判断工作负载是通用事务型、低延迟高 IOPS，还是大块顺序吞吐，再选 SSD 或 HDD。容量、IOPS、吞吐和实例 EBS 带宽都要一起核对。

卷类型介质 / 性能方式适合场景主要陷阱
gp3通用 SSD；可独立配置 IOPS 与吞吐，不必随容量同比增加大多数启动卷、开发环境、通用应用及常规数据库通常是优先考虑的通用 SSD；性能配置仍有卷/实例配额与额外成本
gp2通用 SSD；基准性能与容量关联，并有突发机制已有 gp2 工作负载、性能需求适中且匹配容量的通用用途不能把 gp2 的容量关联和突发积分规则套给 gp3
io2 Block Express高耐久、高性能 Provisioned IOPS SSD；适用实例和配置可提供极高 IOPS / 吞吐关键 OLTP、对延迟和 IOPS 有严格要求的大型数据库应核对 Region、实例类型、容量与性能的当前限制；不代表所有实例都能达到卷上限
io2 / io1Provisioned IOPS SSD，可明确配置预置 IOPS要求持续、可预测低延迟 I/O 的关键数据库成本高于通用 SSD；容量与 IOPS 比率、实例带宽和支持能力均有限制
st1吞吐优化 HDD；面向大块顺序读写，使用吞吐/突发模型大数据、日志处理、数据仓库、顺序扫描非启动卷；不适合小块随机 I/O 或低延迟事务型数据库
sc1冷 HDD；成本更低，吞吐和突发能力更低很少访问、以顺序访问为主的冷数据非启动卷；不适合需要稳定高 IOPS 或低延迟的工作负载
快速决策：没给特殊要求的通用块存储，先看 gp3；明确要求高且稳定的 IOPS/低延迟，选 io2/io1；大数据顺序吞吐选 st1；极少访问且成本优先的顺序数据选 sc1。若要求多个 AZ 同时访问同一共享文件，选 EFS，而不是普通 EBS。

启动卷限制

启动卷需要使用支持启动的 SSD 卷类型（常见为 gp3/gp2 或 Provisioned IOPS SSD）。st1 和 sc1 面向数据卷，不能作为 EC2 启动卷。不要只根据价格选卷而忽略启动能力和工作负载 I/O 模式。

三、IOPS、吞吐量与延迟

卷性能不是一个数字。IOPS 表示每秒 I/O 操作数，吞吐量表示每秒传输的数据量；实际应用吞吐还受 I/O 大小、队列深度、实例 EBS 带宽和文件系统影响。

指标 / 机制含义排查 / 选型方式
IOPS每秒完成的读写操作数随机、小块数据库 I/O 通常更看重 IOPS 和延迟
Throughput每秒传输的数据量大块顺序扫描、媒体和批处理通常更看重吞吐
Latency单次 I/O 响应时间对 OLTP、交易系统等关键；持续高延迟应查看卷与实例指标
队列深度 / I/O 大小应用并发提交的请求数及单次请求字节数同一 IOPS 在不同 I/O 大小时可能对应不同吞吐；压测要模拟真实请求模式
实例 EBS 带宽实例类型对 EBS 流量的上限卷配置再高，实例通道不足时也无法实现预期性能
突发性能特定卷类型在基准性能之外按机制短时突发持续压测而非短测；gp2、st1、sc1 的突发机制不可混为一谈

性能诊断路径

  1. 确认应用 I/O 模式：随机还是顺序、读写比例、块大小、队列深度、突发或持续负载。
  2. 查看卷的已配置性能与 CloudWatch 指标（如卷队列长度、读写延迟、IOPS、吞吐及突发余额相关指标）。
  3. 确认实例类型的 EBS 优化能力和带宽上限，并检查 CPU、内存、文件系统及应用是否成为瓶颈。
  4. 根据证据调整卷类型/IOPS/吞吐，或更换实例类型；使用代表性工作负载复测成本与尾延迟。
EBS-Optimized：专用 EBS 带宽可减少存储流量与其他实例网络流量之间的竞争。现代实例通常具备默认或增强的 EBS 能力，但实际性能取决于具体实例规格和卷配置。

四、快照与恢复

EBS Snapshot 是卷在某个时间点的备份，后续快照采用增量方式保存变化块。快照由 AWS 管理底层存储，用户通常通过快照创建新卷、复制或共享快照进行恢复与迁移。

能力用途重点
增量快照记录与前一快照相比发生变化的数据块，降低重复存储删除旧快照时，AWS 会保留其他仍引用的数据块；删除快照不等于删掉所有后续恢复点
从快照创建卷恢复数据、创建同区域新卷新卷在指定 AZ 创建；不能直接把卷从一个 AZ 移动到另一个 AZ
复制快照跨区域灾备、隔离备份账户/区域、转换加密状态跨 Region 使用 Copy Snapshot；检查目标区域的 KMS 密钥策略与权限
共享快照与其他账号共享自有快照接收方可基于共享快照复制后创建自己的卷；加密快照还需密钥授权
Fast Snapshot Restore在指定 AZ 创建卷时避免按需初始化带来的性能抖动按快照和 AZ 启用，有额外费用；不是持续复制，也不替代备份
Data Lifecycle Manager按策略自动创建、保留或复制 EBS 快照/AMI（依策略类型）用标签和生命周期策略统一管理；同时评估 AWS Backup 的集中治理需求

应用一致性

崩溃一致性快照类似突然断电后磁盘状态；多卷应用若要求跨卷一致性，需要使用支持的多卷快照/编排能力，并在数据库或应用层采用静默、备份模式或日志恢复流程。单个卷快照不自动保证分布式应用的一致性。

恢复性能陷阱：从快照创建卷后，数据可能在首次读取时按需加载，导致恢复初期 I/O 延迟。关键工作负载可以评估 Fast Snapshot Restore，或在适用场景使用卷初始化/预热手段；快照本身不是已挂载、已预热的备用卷。

五、加密与密钥

  • EBS 加密在卷与快照层面保护静态数据，并对卷与实例之间传输的数据提供加密；底层使用 AWS KMS 管理的密钥。
  • 加密卷创建的快照会保持加密；由加密快照创建的卷也会加密。加密卷挂载到受支持实例后，对应用和操作系统通常透明。
  • 可为账户/区域启用 EBS 默认加密，避免新建卷和快照意外未加密；新旧资源是否加密仍需盘点与审计。
  • 使用客户管理密钥时，必须确保操作者、服务和恢复账户具备正确的 KMS 密钥使用权限；密钥禁用或授权缺失会阻断挂载、复制或恢复。

将现有未加密卷转换为加密卷

  1. 为现有卷创建快照。
  2. 复制该快照，并在复制时选择加密及目标 KMS 密钥。
  3. 从加密快照在所需 AZ 创建新卷。
  4. 停机窗口内替换挂载卷或迁移应用数据，并验证启动、权限和恢复流程。
常见误区：不能把一个现有未加密卷原地切换成加密卷。要通过加密快照副本创建新加密卷，再替换原卷。跨账号/跨区域复制加密快照时，必须同时处理 KMS 密钥共享与目标密钥加密。

六、卷操作与扩容

操作支持的方向 / 方式操作后检查
增加容量对支持的卷使用 Elastic Volumes 在线修改；可调整大小，部分类型还可调整性能配置等待卷状态完成，再扩展分区和文件系统；只改云端卷大小不会自动扩大操作系统文件系统
调整性能在类型允许时修改 IOPS、吞吐或卷类型核对当前状态、变更频率限制、实例带宽和应用表现
减少容量通常不能直接缩小现有 EBS 卷创建更小目标卷、复制/迁移所需数据并切换；先验证文件系统和容量规划
跨 AZ 迁移从源卷创建快照，在目标 AZ 从快照创建新卷新卷需挂载到目标实例并验证数据一致性与启动配置
终止实例依卷的 DeleteOnTermination 属性决定是否删除终止前检查根卷、数据卷与快照；关键数据不能只靠保留卷属性保护

修改卷后，根据操作系统、分区表和文件系统执行相应扩展。Linux 常见流程包括扩展分区（如有）和文件系统；Windows 则需在磁盘管理中扩展卷。遵循操作系统与文件系统文档，避免盲目操作导致数据风险。

考试关键：“卷已扩容但应用看不到容量”通常是操作系统分区/文件系统尚未扩展；“要缩小卷”则需要新建较小卷并迁移，而不是直接执行反向修改。

七、Multi-Attach 与 RAID

EBS Multi-Attach

特定 io1/io2 卷可启用 Multi-Attach，让同一 AZ 内多个支持的 Nitro 实例同时附加同一个卷，适合经过设计的共享块存储集群。

特性Multi-Attach 行为设计要求
支持类型特定 io1/io2 配置，具体 Region、实例和卷配额以服务文档为准卷和实例必须位于同一 AZ，并满足 Nitro/平台约束
共享单位共享同一个块设备，不是文件级共享服务使用集群感知文件系统/集群软件及正确锁管理
一致性多主机并发写有数据损坏风险不能让多个普通主机把卷当作独立本地磁盘并同时写入
可用区范围同一卷的附加实例限定在同一 AZ需要跨 AZ 文件共享时评估 EFS 或其他适用架构
陷阱：Multi-Attach 不会自动提供分布式锁、集群文件系统或跨 AZ 高可用。题干若只是“多实例共享文件”，通常 EFS 更符合需求；只有明确需要共享高性能块设备且应用可集群化时才选 Multi-Attach。

RAID 与条带化

  • RAID 0（Striping）：跨多个卷分散 I/O，可提高聚合吞吐/IOPS，但没有冗余；任一成员卷故障可能导致整个阵列数据不可用。
  • RAID 1（Mirroring）：镜像写入以提高冗余；有效容量降低，且不等同于跨 AZ 备份或灾难恢复。
  • RAID 设计不能突破实例总 EBS 带宽，也不能代替快照、备份与恢复演练。

八、可用性、备份与灾难恢复

同 AZ 实例故障在适当情况下将卷分离并挂载到同 AZ 的恢复实例；排查实例状态、卷附件与文件系统一致性。
同区域跨 AZ从快照在目标 AZ 创建新卷，接入备用实例；准备快照、网络、启动配置和切换流程。
跨区域灾备复制快照到目标区域，处理 KMS 密钥、网络与恢复资源；定期验证 RTO/RPO。
集中治理按标签和策略管理快照保留、加密与删除；对关键系统设置告警并测试恢复。

EBS 卷属于单 AZ 资源，快照是其常见的跨 AZ/跨区域恢复基础。需要高可用时，通常在应用架构层做多 AZ 部署与自动故障切换；不要把“EBS 本身可跨 AZ 同步挂载”作为设计假设。

备份策略检查清单

  • 定义备份频率、保留期、跨账号/跨区域复制和删除保护要求。
  • 使用适当的 AWS Backup 或 Data Lifecycle Manager 策略自动创建恢复点，并确认资源标签、权限和排除项。
  • 监控快照创建失败、复制延迟、KMS 权限和成本；为关键资源保留独立恢复账户/区域时验证访问策略。
  • 定期恢复快照到新卷并执行应用级验证；“有快照”不等于“恢复目标已达到”。

九、场景题解析

场景一：通用应用磁盘需要独立调整 IOPS

应用使用通用 SSD，容量不会显著增加，但 I/O 负载升高，需要提升性能且希望避免按容量同步扩盘。应优先选择什么？

正确方向：使用 gp3 并按实际需求配置 IOPS/吞吐。

分析思路：gp3 的性能配置可与卷容量相对独立，适合大多数通用工作负载的弹性调优。

排除：gp2 的性能与容量关联；io2 面向明确的高性能/低延迟需求，通常成本更高；st1/sc1 是顺序吞吐 HDD，不适合随机通用 I/O。

场景二：关键数据库要求稳定高 IOPS 与低延迟

OLTP 数据库有严格 I/O 延迟和稳定性能目标，团队需要显式配置预置 IOPS，并且愿意为性能付费。

正确方向：评估 io2（适用时包括 io2 Block Express），并核对实例类型与卷配置上限。

分析思路：Provisioned IOPS SSD 面向关键、低延迟且 IOPS 可预测的数据库工作负载。

排除：st1/sc1 面向顺序吞吐/冷数据；仅提高通用卷容量不一定能满足 IOPS；卷性能不能超过实例 EBS 通道能力。

场景三：需要把 EBS 卷迁移到另一个 AZ

源实例所在 AZ 不可用，恢复团队需要在同一区域的另一 AZ 启动新实例并恢复数据。

正确方向：使用可用快照，在目标 AZ 创建新卷并挂载到恢复实例。

分析思路：EBS 卷具有 AZ 作用范围，卷本身不能直接跨 AZ 迁移；快照可作为在目标 AZ 创建新卷的基础。

排除：直接把原卷挂到另一 AZ 实例不可行；Multi-Attach 也不跨 AZ；若目标在另一个 Region，需要先复制快照。

场景四：现有未加密数据卷必须加密

一块已在使用的未加密 EBS 卷需要满足静态加密要求，且允许维护窗口内迁移。

正确方向：创建快照，将快照复制为加密快照，再从加密快照创建新卷并切换。

分析思路：通过快照复制转换加密状态，使用目标 KMS 密钥并验证权限。

排除：不能直接对现有未加密卷执行原地加密；仅启用默认加密不会自动转换既有卷。

场景五：两台 EC2 需要共享并写入同一组文件

多台实例分布在多个 AZ，需要并发访问同一套目录和文件，业务没有集群块存储能力。

正确方向：评估 EFS 等托管共享文件系统，而非普通 EBS 或 Multi-Attach。

分析思路：需求是多实例共享文件语义并跨 AZ 访问，EFS 提供文件系统接口；EBS 是块设备且通常限定单 AZ。

排除：普通 EBS 卷不能跨 AZ 同时挂载；Multi-Attach 不是通用共享文件系统，还需要集群软件并受同 AZ 限制。

场景六：从快照恢复后首次读取变慢

团队从快照快速创建新数据卷并切换流量，但首次访问旧数据时延迟显著升高。如何降低计划内恢复的初始化抖动？

正确方向：在目标 AZ 为快照评估启用 Fast Snapshot Restore，或按支持方式初始化/预热卷，并提前演练。

分析思路：快照创建的卷可能在首次读取时加载数据；Fast Snapshot Restore 可帮助新卷避免按需初始化性能影响，但有额外成本和适用范围。

排除：增加普通卷容量不等于预热；EBS 快照并不是已初始化的在线备用卷；恢复前未验证无法证明 RTO 达标。

十一、考前速记卡

勾选已掌握项目，页面内进度自动更新。

已掌握 0 / 18

  • EBS：持久化块存储，卷通常属于单一 AZ
  • gp3：通用 SSD，IOPS/吞吐可与容量相对独立配置
  • gp2：通用 SSD，性能与容量相关并具有突发机制
  • io2/io1：Provisioned IOPS SSD，适合关键低延迟数据库
  • st1：吞吐优化 HDD，顺序访问；不能作启动卷
  • sc1：冷 HDD，成本更低且性能更低；不能作启动卷
  • 性能瓶颈：卷、实例 EBS 带宽、IO 大小和应用都要检查
  • Snapshot：增量备份，可用于恢复新卷与跨 AZ 迁移
  • 跨 Region：复制快照，并处理目标 KMS 密钥
  • 加密：新卷/快照可用 KMS；既有未加密卷经快照复制转换
  • Fast Snapshot Restore：指定快照/AZ，缓解恢复后首次读初始化影响
  • Elastic Volumes：支持的卷可在线扩容/调整性能
  • 文件系统：卷扩容后还需扩展分区和文件系统
  • 缩容：不能直接缩小现有卷，需迁移到较小新卷
  • Multi-Attach：特定 io1/io2，同 AZ，多主机共享块设备
  • 共享文件：跨 AZ 多实例场景优先考虑 EFS，不是普通 EBS
  • 删除行为：终止实例是否删卷取决于 DeleteOnTermination
  • RAID 0：可提升聚合性能但没有冗余，不能替代备份

十二、快速自测

先独立选择，再点击“查看解析”。

1. 一个常规应用使用通用 SSD，想在不扩大容量的情况下单独提高配置的 IOPS。优先选择哪种卷？
正确答案：C。gp3 可独立配置 IOPS/吞吐，不要求按相同比例增加容量。gp2 性能与容量关联；st1/sc1 为顺序吞吐型 HDD。
2. 一个未加密 EBS 数据卷必须加密，且允许迁移到新卷。以下哪种做法正确？
正确答案：B。现有未加密卷不能原地转换。快照复制时选择加密及 KMS 密钥，再由加密快照创建新卷。
3. 两台位于不同 AZ 的 EC2 需要同时读写同一个共享目录。哪种设计最符合需求？
正确答案：C。EFS 提供共享文件系统语义并支持多 AZ 访问。普通 EBS 卷为块设备且限定单 AZ；Multi-Attach 也不提供跨 AZ 文件共享。
