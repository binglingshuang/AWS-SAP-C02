AWS IoT Core、Greengrass 与 Device Shadow
云端设备管理与边缘计算 — SAP-C02

AWS IoT 架构常由云端消息接入、设备身份与权限、状态同步、规则路由和边缘运行时组成。解题时先判断设备是否持续联网、应用需要的是消息传递还是期望状态管理，以及处理必须发生在云端还是设备本地。

一、IoT 能力地图

IoT Core 接入并路由设备消息；Device Shadow 用文档表达设备期望/报告状态；Greengrass 在设备侧运行组件、处理本地数据并支持离线工作流。它们解决不同层次的问题，可以组合而非互相替代。

需求优先能力核心作用不要混淆
设备通过 MQTT / HTTPS 安全连接 AWSAWS IoT Core设备接入、消息代理、注册表、策略及规则路由。不等于边缘本地计算运行时。
应用和设备需要异步同步状态Device Shadow在云端维护设备状态文档，支持 desired / reported 状态协调。不是设备数据的通用长期时序数据库。
断网时仍要本地处理、控制设备或运行组件AWS IoT Greengrass在受管边缘设备运行组件、处理本地消息和部署软件。云端 IoT Core 连接恢复与否取决于本地能力和设计。
管理海量设备凭证、配置与任务IoT Core / IoT Device Management 能力注册、批量入网、分组、作业和设备生命周期管理。需将每设备身份、策略和作业发布范围分开治理。
决策口诀：设备连接和 MQTT 消息走 IoT Core；跨云/设备异步状态用 Shadow；本地处理和离线能力用 Greengrass；设备级授权依赖唯一身份与最小权限策略。

二、AWS IoT Core 与 MQTT 消息模型

  • MQTT broker：设备和应用通过主题发布/订阅消息。发布者与订阅者解耦，适合遥测、命令和事件交换；QoS、会话与消息保留语义要按实际需求配置。
  • HTTPS：适合设备或后端通过请求/响应方式与 IoT endpoint 通信；协议选择需结合设备网络、连接管理和消息模式。
  • Thing Registry：可为物理设备或逻辑实体建立 Thing 记录，便于关联属性、证书、策略和设备管理操作；注册 Thing 本身不自动授予消息权限。
  • 主题设计：按租户、设备类型、设备 ID 和消息类型规划命名空间，避免所有设备共享过宽的通配订阅权限。
  • 可靠性：设备应实现断线重连、退避、重复消息处理、离线缓存和上报顺序管理；不能假设网络交付天然 exactly-once。
  • 容量：按设备连接数、消息频率、消息大小、规则动作和突发峰值估算配额与费用，并对关键指标设置告警。
陷阱：MQTT QoS 或消息送达不等于业务操作只执行一次；下游消费者仍需幂等键、去重或状态校验。

三、设备身份、证书与最小权限

设备身份应可区分、可轮换、可撤销。常见方案是为设备配置 X.509 客户端证书，并将 IoT policy 绑定到证书或身份关系；在 AWS IoT Core 支持的连接场景中也可使用其他认证方式，但必须验证目标协议与设备能力。

  • 为每台设备或受控设备组使用独立凭证，避免把同一私钥固化到整批设备镜像中。
  • IoT policy 限制可连接的 client ID、可发布/订阅/接收的 topic ARN；topic 变量应正确绑定已认证的设备身份。
  • 证书创建后要激活并关联恰当策略/Thing 关系；禁用或撤销证书后，应验证设备无法重新连接。
  • 证书安全存储在设备硬件/文件系统适当位置，支持安全引导、轮换、丢失处理和供应链可信验证。
  • 设备到后端调用 AWS 服务时，不要把长期 IAM 用户密钥写入固件；通过安全身份流程和最小权限授权。
  • 审计连接、身份变更和策略更新；对不同租户的主题、影子和作业范围实施隔离。
授权链：设备认证确认“是谁”，IoT policy 决定“能连接并操作哪些 MQTT 资源”，Thing Registry 组织设备元数据；三者不能互相替代。

四、Rules Engine 与云服务集成

IoT Core Rules Engine 可筛选、转换 MQTT 消息，并将符合规则的数据送往受支持的 AWS 服务或其他目标。典型路径是传感器发布遥测 → 规则按 SQL 表达式筛选/提取字段 → 发送到 Lambda、S3、DynamoDB、Kinesis、SNS/SQS 等目标。

  • 规则只应匹配必要主题和消息字段；避免把所有原始遥测无差别写入昂贵存储。
  • 规则动作通常以 IAM role 执行目标服务操作；角色信任关系、目标资源策略和 KMS 权限都要正确配置。
  • 配置错误动作/重试策略和监控，处理目标限流、不可用及格式不匹配；消息生产端也应具备缓冲与重试策略。
  • 命令下发可通过受控 topic 发布，限定设备订阅范围并校验命令来源；对不可逆操作设计确认、版本和过期时间。
  • 若要将 IoT 事件接入事件驱动系统，按目标服务的吞吐、持久化、重放和顺序需求选择后续队列/流服务，而非把 IoT topic 当作永久数据存储。

五、Device Shadow：设备期望状态与实际状态

Device Shadow 是设备状态的 JSON 文档，可由应用或设备通过 MQTT/HTTP 读写。设备离线时，应用仍可更新期望状态；设备重新连接后读取差异并按业务逻辑应用，再上报实际状态。

字段/概念含义常见用法
desired应用/云端希望设备达到的状态。设置温度目标、配置版本或控制参数。
reported设备报告当前观察到的状态。上报当前温度、开关状态和已应用配置版本。
deltadesired 与 reported 中不一致的字段。设备订阅变更并决定是否执行更新。
version / timestamp用于跟踪文档更新和状态变化。处理并发更新、陈旧状态和顺序问题。
classic / named shadow设备可使用经典影子，也可用命名影子隔离不同状态域。不同应用/组件分开维护状态，限制权限和避免字段冲突。
  • Shadow 是协调状态的机制，不是“设备已执行命令”的确认；设备必须更新 reported 状态才能表达实际结果。
  • 设备离线期间 desired 可以累积变更，重连后设备需判断版本、有效期和业务安全约束，不应盲目执行过时命令。
  • 为 shadow topic 设置最小权限，按 Thing/命名影子约束访问；限制敏感数据和不必要的大型状态对象。
  • 多个控制端并发更新时，使用版本条件和应用级冲突解决策略，避免最后写入者无意覆盖关键状态。
考试辨析：“应用更新 desired，离线设备稍后同步”选 Shadow；“本地程序在设备断网时仍执行边缘逻辑”选 Greengrass；必要时两者结合。

六、AWS IoT Greengrass：边缘运行时与本地处理

AWS IoT Greengrass 将运行时和组件部署到客户管理的边缘设备，让本地应用执行消息处理、设备交互和工作负载。云端可用于管理和部署；本地可用能力、依赖与断网表现应按组件和具体架构验证。

  • Greengrass nucleus：设备侧核心运行时，承载组件管理、部署和本地服务通信。
  • 组件：将应用逻辑、依赖和生命周期封装为可部署单元；可包含自定义代码或受支持的 AWS 提供组件。
  • 离线工作：将必需组件、模型、配置和数据预先部署到本地；设备可以在无云连接时继续已安装的本地处理，但云端遥测、远程控制或部署管理会受到连接影响。
  • 本地消息：本地 MQTT/设备通信可减少云往返；明确本地设备授权、消息持久化、队列容量和恢复后的同步方式。
  • 资源约束：边缘 CPU、内存、磁盘、操作系统和架构与云实例不同，需进行设备端压测、磁盘保护及组件升级回滚规划。
  • 版本选择：新方案应按当前 Greengrass 主版本文档设计；若迁移旧版运行时/组件，先确认版本支持、API 差异和迁移路径。
不要过度承诺：Greengrass 可让已部署的本地能力在断网时工作，但并不表示所有云端服务或控制操作都离线可用。列出断网时必须保留的功能并做实机演练。

七、设备规模化入网、分组与作业

  • Fleet provisioning：为批量设备自动创建/配置 Thing、证书和策略，配合可信引导凭证及模板限制可注册的资源。
  • 分组和属性：按租户、型号、软件版本和地区组织设备，分组策略不能因此扩大超出预期的资源访问范围。
  • Jobs：向设备或设备组下发固件、配置和操作任务；按批次/分组逐步发布，监控执行状态、失败比例和回滚条件。
  • 版本控制：固件或组件需要签名/校验、兼容性检查、分阶段 rollout 和失败恢复；网络中断设备应在重新连接后安全续传。
  • 生命周期：为设备退役、丢失或转售定义禁用证书、撤销权限、清除本地数据与审计记录的流程。
  • 观测性：使用连接状态、任务状态、规则错误及设备日志识别故障；遥测需限速、采样或聚合，避免监控通道本身压垮设备网络。

大规模设备管理的关键是可重复的入网、可控的更新波次和明确的失败处置，而不是人工逐台复制凭证或远程登录修改。

九、场景题解析

场景一：设备暂时离线，运维人员仍需更新其期望配置

设备联网后应发现配置差异并报告是否已经应用。

方向：使用 Device Shadow 保存 desired 状态，设备重连后读取变化、校验版本并更新 reported 状态。
Shadow 支持云端与设备间的异步状态协调，设备不必持续在线。
Shadow 记录期望状态，不保证设备离线时命令已经执行。

场景二：工厂断开互联网期间仍需本地分析传感器并控制产线

恢复连接后再同步结果，并由云端集中部署软件。

方向：在边缘设备部署 Greengrass 组件和必要数据/依赖，设计本地缓存、容量上限和恢复同步。
边缘运行时可支持已部署的本地工作负载；云端部署与远程管理仍需连接。
不要假设所有 IoT Core 云端功能在断网时仍可用。

场景三：每台设备只能发布自己的遥测主题

设备已通过 TLS 连接，但策略使用 `devices/*` 通配符。

方向：为设备建立独立身份，使用基于 Thing/身份变量的 IoT policy 限定 topic ARN 和允许的操作。
TLS 身份认证与 MQTT 资源授权是不同环节；策略要最小化到设备自身主题。
仅验证证书有效，不代表设备只能访问自己的 topic。

场景四：遥测需按内容过滤后写入数据湖

设备持续发布 MQTT 消息，目标 S3 前需要筛选与转换。

方向：用 IoT Core Rules Engine 筛选/提取消息，再配置规则 IAM role 和目标存储权限。
Rules Engine 将设备消息路由到 AWS 服务；仍需监控动作失败、权限和目标端限流。
不要给设备证书直接赋予对目标 S3 bucket 的宽泛访问权限。

场景五：数万台设备需分批接收固件更新

团队要观察每批成功率，并在失败扩散前暂停。

方向：使用 IoT Device Management Jobs（或适用的 Greengrass 部署能力）按设备组/波次发布并监控状态。
规模化任务避免逐台运维；版本兼容、签名/完整性和失败回滚仍需设计。
一次向整个 fleet 无条件发布会放大错误固件的影响范围。

场景六：设备恢复联网后积压大量遥测，造成云端消息突增

设备本地缓存和重试策略此前没有上限。

方向：限制离线缓存与重试速率，采用退避/分批补传和云端配额监控；按数据价值设置过期/聚合策略。
离线容错需要与恢复后的流量整形共同设计，避免连接恢复引发级联过载。
简单增加重试次数或无界队列会加剧拥塞与成本。

十一、考前速记卡

已掌握 0 / 18

  • IoT Core 提供云端设备接入与 MQTT 消息代理。
  • MQTT topic 是发布/订阅消息的路由命名空间。
  • Thing Registry 保存设备实体和元数据，不等于授权。
  • 每台设备使用可轮换、可撤销的唯一身份凭证。
  • 证书身份认证与 IoT policy 资源授权是两步。
  • IoT policy 限制 client ID、topic 和操作范围。
  • Rules Engine 可将消息筛选后路由到云服务。
  • 规则目标权限由规则 IAM role 等配置决定。
  • Shadow desired 表示期望状态。
  • Shadow reported 表示设备报告的实际状态。
  • Shadow delta 表示期望与报告状态的差异。
  • Shadow 不能证明离线设备已经执行命令。
  • 命名 Shadow 可隔离不同状态域。
  • Greengrass 在边缘设备运行本地组件。
  • 离线能力依赖已部署组件、数据和本地配置。
  • 云端远程管理和部署仍依赖连接恢复。
  • Jobs / 部署按设备分组和波次发布并监控。
  • 网络恢复时要限速补传并避免无界重试。

十二、快速自测

1. 设备离线时云端想更新期望状态，设备上线后自行对账，选什么？

Device Shadow：写入 desired，设备读取差异并更新 reported。

2. 工厂断网期间仍要执行设备本地控制逻辑，优先使用什么？

AWS IoT Greengrass，将所需组件和依赖预部署到边缘设备并验证离线行为。

3. IoT 设备需要按 MQTT 消息内容过滤并写入 S3，怎么实现？

IoT Core Rules Engine 路由消息，并为规则配置最小权限 IAM role 和 S3/KMS 权限。
