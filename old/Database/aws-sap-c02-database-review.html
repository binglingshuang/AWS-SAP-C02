二、RDS 与 Aurora：关系型数据库

2.1 RDS Multi-AZ：高可用

传统 RDS Multi-AZ DB Instance 会在不同 Availability Zone 部署 Primary 和 Standby。

Application → RDS Endpoint → Primary DB → Standby DB
  • Primary 负责正常的数据库读写。
  • Standby 位于另一个 AZ。
  • 传统 DB Instance 模式使用同步复制。
  • Primary 发生故障时可以自动 Failover。
  • Standby 主要用于故障切换，不负责普通只读流量。

2.2 Read Replica：读取扩展

Application → Primary DB（写）
Primary DB → Read Replica 1 + Read Replica 2
  • Primary 负责写入。
  • Read Replica 承担读取请求。
  • 通常采用异步复制。
  • 可能出现 Replication Lag。
  • 适合读取压力较大的场景。

2.3 Multi-AZ 与 Read Replica 区别

对比Multi-AZ DB InstanceRead Replica
主要目的高可用读扩展
复制方式同步异步
自动故障切换支持不能默认认为支持
只读请求传统 Standby 不处理可以处理
关注关键词AvailabilityRead Performance
考试记忆：
Multi-AZ = Availability。
Read Replica = Read Performance。
注意：Multi-AZ DB Cluster 与传统 Multi-AZ DB Instance 不同。 Multi-AZ DB Cluster 包含一个 Writer 和两个 Reader，Reader 可以处理只读请求。

2.4 Aurora 核心架构

Aurora 兼容 MySQL 和 PostgreSQL，采用计算层与分布式存储层分离的架构。

Writer Instance → Aurora Shared Storage ← Reader Instances

经典 Aurora 存储架构：

  • 3 个 Availability Zones。
  • 6 份数据副本。
  • 写入至少需要 4/6 份确认。
  • 读取至少需要 3/6 份确认。

常见 Endpoint：

Endpoint用途
Writer Endpoint连接写入实例
Reader Endpoint分发只读连接到 Aurora Replicas
Instance Endpoint连接指定数据库实例

2.5 Aurora Serverless v2

  • 适合负载波动较大的关系型数据库。
  • 自动调整数据库计算容量。
  • 减少固定容量管理工作。
  • 适合业务量不稳定的应用。

2.6 Aurora Global Database

Primary Region（读写） → Secondary Region（只读）
  • 跨区域复制数据。
  • 辅助区域可以提供只读访问。
  • 适合全球用户读取及跨区域容灾。
  • 重大故障时可以提升辅助区域。

2.7 RDS / Aurora 选型总结

题目需求优先方案
普通 MySQL 托管RDS MySQL
普通 PostgreSQL 托管RDS PostgreSQL
MySQL / PostgreSQL 高性能Aurora
数据库自动故障切换Multi-AZ
增加只读数据库节点Read Replica / Aurora Replicas
跨区域关系型数据库容灾Aurora Global Database
负载波动明显Aurora Serverless v2

三、DynamoDB：NoSQL 数据库

3.1 核心概念

概念作用
Partition Key分区键，决定数据分布
Sort Key排序键，同一分区键下进行排序和查询
GSIGlobal Secondary Index
LSILocal Secondary Index
TTL自动清理过期数据
Streams捕获数据变更
DAXDynamoDB 读取缓存
Global Tables跨区域复制和多区域读写

3.2 Partition Key 与 Sort Key

例如电商订单表：

UserIDOrderIDProduct
U001O001Phone
U001O002Laptop
U002O003Tablet

可以设计：

  • Partition Key：UserID
  • Sort Key：OrderID
如果所有请求集中在同一个 Partition Key，可能导致 Hot Partition。 需要重新设计分区键，使数据及请求分布更加均匀。

3.3 GSI 与 LSI

对比GSILSI
Partition Key可以不同必须与主表相同
Sort Key可以不同可以不同
创建时间创建表后可以添加或删除必须在创建表时定义
强一致性读取不支持支持
记忆方法：
GSI = Global，允许不同的 Partition Key。
LSI = Local，必须沿用原来的 Partition Key。

3.4 DynamoDB 一致性

类型特点
Eventually Consistent Read最终一致性，通常为默认读取方式
Strongly Consistent Read强一致性读取，返回读取时已完成写入的最新数据
注意：
  • GSI 不支持 Strongly Consistent Read。
  • Global Tables 的跨区域复制具有最终一致性特征。
  • 不要将强一致性读取理解成跨区域强一致性。

3.5 容量模式

模式特点适用场景
On-Demand按请求计费，自动适应请求量流量不可预测
Provisioned预先配置读写容量流量稳定
Auto Scaling自动调整配置容量流量周期性变化

3.6 DAX

  • DynamoDB 专用内存缓存。
  • 适合大量重复读取。
  • 减少直接访问 DynamoDB 的次数。
  • 支持微秒级读取响应场景。

3.7 DynamoDB Streams

DynamoDB Table → DynamoDB Streams → Lambda → 业务处理
典型用途：
  • 捕获数据插入、修改和删除事件。
  • 触发 Lambda。
  • 同步搜索索引。
  • 发送业务通知。

3.8 DynamoDB Global Tables

  • 跨多个 Region 部署。
  • 不同区域均可以读写。
  • 数据在多个区域间复制。
  • 适合全球用户访问与多区域容灾。

3.9 Aurora Global 与 DynamoDB Global Tables

对比Aurora GlobalDynamoDB Global Tables
数据库类型关系型NoSQL
多区域写入通常单主写区域多区域可读写
主要用途关系型跨区域容灾和读取全球多区域读写
关系型数据库全球读取：Aurora Global Database。
NoSQL 全球 Active-Active：DynamoDB Global Tables。

四、ElastiCache 与 MemoryDB

4.1 ElastiCache

ElastiCache 是托管内存缓存服务，主要用于减少后端数据库访问压力。

典型用途：
  • 缓存热点商品数据。
  • 缓存查询结果。
  • 用户 Session 管理。
  • 排行榜和实时数据。

4.2 Redis OSS / Valkey 与 Memcached

对比Redis OSS / ValkeyMemcached
数据结构丰富以简单键值缓存为主
复制支持不支持
持久化支持相关持久化机制，依配置而定不支持
用途缓存、Session、排行榜简单对象缓存

4.3 ElastiCache 高可用

Application → Primary Node → Replica Node
可以通过复制组、不同 AZ 的副本、Multi-AZ 和自动故障切换提高可用性。

4.4 ElastiCache 与 MemoryDB

对比ElastiCacheMemoryDB
核心定位缓存持久化内存数据库
主要用途减少数据库访问高性能主数据存储
关键词Cache、Session持久性、内存数据库
缓存需求优先考虑 ElastiCache；需要持久化内存数据库时考虑 MemoryDB。

七、数据库迁移：DMS 与 SCT

7.1 AWS DMS

AWS Database Migration Service 用于数据库数据迁移和持续复制。

主要功能：
  • 同构数据库迁移。
  • 异构数据库迁移中的数据移动。
  • Full Load 全量迁移。
  • CDC 捕获数据变化。
  • 减少迁移时的业务停机时间。

7.2 Full Load 与 CDC

方式作用
Full Load迁移已有数据
CDC持续捕获后续数据变化
Full Load + CDC先迁移历史数据，再持续同步变化

7.3 AWS SCT

AWS Schema Conversion Tool 用于数据库 Schema 和部分代码转换。 例如：
  • Oracle → PostgreSQL。
  • SQL Server → MySQL。
  • 数据类型转换。
  • SQL 语法转换。
  • 存储过程及数据库对象评估。

7.4 DMS 与 SCT 对比

对比DMSSCT
核心作用数据迁移Schema 转换
Full Load支持不负责
CDC支持不支持
异构迁移迁移数据辅助结构转换
考试必背：
SCT 转结构，DMS 迁数据。
异构迁移 = SCT + DMS。
低停机迁移 = Full Load + CDC。

7.5 同构与异构迁移

场景方案
MySQL → MySQLDMS
PostgreSQL → PostgreSQLDMS
Oracle → PostgreSQLSCT + DMS
SQL Server → MySQLSCT + DMS

八、高可用、备份与灾难恢复

8.1 四种保护机制

机制主要解决的问题
Multi-AZ实例或可用区故障
Read Replica读取性能扩展
Backup / Snapshot历史数据恢复
Cross-Region Replication区域级灾难恢复

8.2 RPO 与 RTO

RPO Recovery Point Objective

允许丢失多少时间范围内的数据？

RTO Recovery Time Objective

允许业务中断多长时间？

例如：
  • RPO = 5 分钟：最多接受最近 5 分钟的数据损失。
  • RTO = 15 分钟：业务需要在 15 分钟内恢复。

8.3 数据库容灾方案

方案典型用途
定期备份与恢复宽松 RTO / RPO，成本较低
跨区域 Read Replica部分 RDS 引擎支持的跨区域恢复
Aurora Global Database关系型数据库跨区域容灾
DynamoDB Global TablesNoSQL 多区域读写

8.4 AWS Backup

主要功能：
  • 集中管理多个 AWS 服务的备份。
  • 统一备份策略。
  • 管理备份保留周期。
  • 跨账户备份。
  • 跨区域备份。
  • 满足组织备份合规要求。
备份与复制不是一回事。备份用于恢复历史数据，复制用于持续同步数据。实际 RPO/RTO 还取决于复制延迟、故障切换与恢复流程。

十、数据库综合架构场景

场景 1：高并发电商网站

CloudFront → ALB → Application → ElastiCache → Aurora
| 组件 | 作用 | |---|---| | CloudFront | 静态内容加速 | | ALB | 负载均衡 | | ElastiCache | 商品热点缓存 | | Aurora | 订单和交易 | | Aurora Replicas | 分担只读请求 | 关键词：High Concurrency + Transaction + Read-heavy。

场景 2：全球用户访问数据库

| 需求 | 服务 | |---|---| | 全球关系型数据库读取 | Aurora Global Database | | 全球 NoSQL 多区域读写 | DynamoDB Global Tables | | 区域缓存 | 各区域部署缓存 | | 全球静态文件 | S3 + CloudFront 等 |

场景 3：本地数据库迁移到 AWS

Source Database → SCT → DMS Full Load → CDC → Target Database
步骤：
  1. SCT 评估和转换 Schema。
  2. DMS 创建源和目标 Endpoint。
  3. 执行 Full Load。
  4. 通过 CDC 同步增量变化。
  5. 验证数据后切换应用。

场景 4：物联网设备数据

场景 5：在线交易与数据分析分离

第三步：检查非功能性要求

  1. 可用性：是否要求自动故障切换？
  2. 性能：是否需要读写分离或缓存？
  3. 容灾：是否要求跨区域？RPO / RTO 是多少？

  5. 成本：是否要求最低成本或 Serverless？

十二、数据库高频考试陷阱

容易混淆正确判断
Multi-AZ vs Read Replica高可用 vs 读扩展
Aurora Global vs DynamoDB Global Tables关系型跨区域 vs NoSQL 多区域读写
RDS vs RedshiftOLTP vs OLAP
DMS vs SCT数据迁移 vs Schema 转换
DAX vs ElastiCacheDynamoDB 专用缓存 vs 通用缓存
S3 vs Redshift对象存储 vs 数据仓库
Backup vs Replication历史数据恢复 vs 持续复制
Secrets Manager vs KMS凭证管理 vs 加密密钥管理

典型干扰项

陷阱 1：题目要求提高数据库可用性，选项中出现 Read Replica。

判断：是否要求故障自动切换？如果是，优先考虑 Multi-AZ。

陷阱 2：题目要求提高读取性能，选项中出现 Multi-AZ。

判断：传统 Standby 不承担读请求，应该考虑 Read Replica 或缓存。

陷阱 3：题目要求跨区域灾难恢复，选项中只有快照。

判断：快照用于恢复历史数据，不等于持续复制。

陷阱 4：Oracle 迁移 PostgreSQL，选项只有 DMS。

判断：异构数据库需要检查 SCT 的 Schema 转换要求。

陷阱 5：题目要求真正的多区域 Active-Active 写入，选项出现 Aurora Global。

判断：如果使用 DynamoDB 并要求多区域读写，应重点考虑 Global Tables。

十四、SAP-C02 数据库答题方法

第一步：分析业务类型

  • 事务型？
  • 分析型？
  • 缓存型？
  • NoSQL？
  • 数据迁移？

第二步：识别核心问题

  • 性能？
  • 高可用？
  • 跨区域容灾？
  • 一致性？
  • 成本？
  • 安全？

第三步：确定技术方案

例如题目要求：

A company needs to improve the availability of its RDS database. The solution must automatically fail over to another Availability Zone.
分析：
  1. 现有数据库是 RDS。
  2. 核心要求是 Availability。
  3. 要求自动 Failover。
  4. 没有要求提高读取性能。
  5. 因此优先选择 Multi-AZ，而不是 Read Replica。

第四步：识别题目限制条件

Minimum operational overhead Most cost-effective Least administrative effort Minimal downtime Near-zero RPO Active-active Strong consistency

这些关键词通常会决定最终选项。
