一、CloudFormation 在 SAP-C02 中的定位

SAP-C02 不只是考 CloudFormation 模板语法，更关注如何在多账户、多区域、复杂基础设施、灾难恢复和持续交付场景中使用它。

核心思想：使用基础设施即代码（IaC），实现可重复、可审计、可规模化的基础设施管理。
考试场景对应功能
多账户统一部署StackSets
多区域统一部署StackSets
复杂模板拆分复用Nested Stacks
部署前检查资源变化Change Sets
检测手工修改的资源Drift Detection
保护数据库等关键资源DeletionPolicy、UpdateReplacePolicy、Stack Policy
自动回滚Rollback Triggers
现有资源纳入 IaC 管理Resource Import
CI/CD 自动部署CodePipeline + CloudFormation

二、Stack 和 Template（基础概念）

Template：模板，描述希望创建什么资源。
Stack：堆栈，CloudFormation 根据模板实际创建和管理的一组 AWS 资源。

一个模板可以定义 VPC、Subnet、Internet Gateway、Route Table、EC2、Security Group、RDS 等资源。CloudFormation 会根据资源引用和依赖关系确定创建顺序。

模板常见结构

Section用途重要程度
AWSTemplateFormatVersion模板格式版本低
Description模板说明低
Parameters部署时由用户提供的输入高
Mappings静态键值映射中
Conditions根据条件决定是否创建资源或设置属性高
Resources定义要创建或管理的资源必考
Outputs输出资源信息高
Metadata / Transform辅助元数据 / 模板转换中低
快速记忆：Parameters = 动态输入；Mappings = 静态映射；Conditions = 条件判断；Resources = 资源定义；Outputs = 输出信息。

三、StackSets（重点）

作用：通过一个 StackSet 操作，将 CloudFormation Stack 部署到多个 AWS 账户和多个 Region。

典型场景：企业有多个成员账户和多个区域，需要统一部署 IAM Role、CloudTrail、Config、安全基线或基础网络资源。

Region 1 / 2

两种权限模式

对比Service-managedSelf-managed
角色管理与 Organizations 集成，自动管理相关角色用户自行创建和管理角色
Organizations支持，需启用 Trusted Access不依赖 Organizations
部署目标Organizations 中的账户、OU指定账户
典型场景企业多账户治理、OU 自动部署非 Organizations 环境或自行管理权限
考试关键词：Organizations、OU、新账户自动部署、多账户统一治理 → 优先考虑 Service-managed StackSets。
不使用 Organizations、自己管理执行角色 → 考虑 Self-managed StackSets。

边界：StackSets 解决跨账户、跨区域部署；普通 Stack 管理单个账户、单个 Region 中的一组资源。

作用：将大型模板拆分成多个可复用的小模板，由 Parent Stack 组织和管理 Child Stacks。

记忆口诀：Nested = 一个系统拆成多个模块；StackSets = 一个模板部署到多个账户和区域。

五、Change Sets（变更集）

作用：在更新 Stack 之前，预览 CloudFormation 将要执行的资源变更。

可以帮助检查资源将被新增、修改、删除还是替换。例如修改生产 RDS 配置前，先查看更新是否会导致数据库实例替换。

重要陷阱：Change Sets 只提供变更预览，不保证部署一定成功，也不保证没有运行时错误、权限问题或配额问题。

题目关键词：Preview changes、Review before deployment、检查资源是否被删除或替换 → Change Sets。

六、Drift Detection（漂移检测）

当实际 AWS 资源配置与 CloudFormation 模板中定义的配置不一致时，就产生了配置漂移（Drift）。

例如：模板定义 Security Group 只允许指定网段访问 443 端口，管理员后来直接在控制台增加了其他入站规则。此时模板未变，但实际资源已经变化。

需求选择
发现管理员手工修改资源Drift Detection
比较实际状态与模板Drift Detection
更新前查看即将发生的变化Change Sets
注意：Drift Detection 主要负责检测，不会自动修复所有漂移；并非所有资源属性都支持漂移检测。

七、DeletionPolicy 与 UpdateReplacePolicy

DeletionPolicy

控制资源从 Stack 中删除或 Stack 被删除时，如何处理该资源。

选项含义
Delete删除资源（默认行为因资源类型而异）
Retain保留资源，不随 Stack 删除
Snapshot对支持快照的资源，在删除前创建快照
RetainExceptOnCreate创建操作回滚时可删除新资源，其他删除场景保留

UpdateReplacePolicy

控制更新导致资源必须被替换时，旧资源如何处理。可以选择保留旧资源或对支持快照的资源创建快照。

场景对应属性
删除 Stack 时保留 RDSDeletionPolicy: Retain
资源从模板中移除时保留资源DeletionPolicy: Retain
更新导致资源替换，保留旧资源UpdateReplacePolicy: Retain
更新替换时对旧资源创建快照UpdateReplacePolicy: Snapshot
记忆：Deletion = 删除操作；UpdateReplace = 更新引发的替换操作。

八、Stack Policy（堆栈策略）

Stack Policy 用于限制 CloudFormation 更新 Stack 时，哪些资源可以被更新或删除。例如允许更新 EC2，但禁止更新关键 RDS。

对比IAM PolicyStack Policy
控制对象用户、角色及其 API 操作权限Stack 更新期间的资源操作
典型用途限制用户调用删除 API防止 Stack 更新意外修改关键资源
关键词：Protect critical resources during stack updates、Prevent accidental updates → Stack Policy。它不能替代 IAM 权限控制，也不等于 DeletionPolicy。

九、Rollback Triggers（回滚触发器）

用于在 Stack 更新期间监控指定的 CloudWatch Alarm；如果告警触发，可以让 CloudFormation 回滚此次操作。

典型场景：新版本基础设施部署后，CloudWatch Alarm 检测到应用错误率或资源指标异常，触发回滚。

题目描述对应功能
资源创建或更新失败CloudFormation 回滚机制
CloudWatch Alarm 触发后回滚Rollback Triggers
更新前预览资源变化Change Sets
发现手工修改资源Drift Detection

十、Resource Import（资源导入）

把已经存在、原本不是由 CloudFormation 管理的资源，导入到 CloudFormation Stack 中，纳入 IaC 管理，而不必先删除再重建。

典型流程

  1. 在 Template 中定义现有资源。
  2. 提供资源标识符。
  3. 创建资源导入操作。
  4. 执行导入。
  5. 使用 Drift Detection 检查模板与实际资源是否一致。
考试关键词：Existing resources、Bring existing infrastructure under CloudFormation management、Avoid recreating resources → Resource Import。

十一、Parameters、Mappings、Conditions、Outputs

功能用途例子
Parameters部署时输入参数用户选择实例类型或输入 AMI ID
Mappings静态映射关系根据 Region 选择对应 AMI ID
Conditions条件判断只有生产环境才创建 RDS
Outputs输出资源信息输出 VPC ID、Subnet ID

Outputs + Export + ImportValue

Stack A 创建 VPC，并通过 Outputs / Export 导出 Subnet ID；Stack B 使用 Fn::ImportValue 引用该值。

注意：Export 名称在同一账户、同一 Region 内必须唯一。被其他 Stack 引用的 Export，不能随意删除，也不能随意修改导出值。

考点作用 / 记忆关键词

Dynamic References从 SSM Parameter Store 或 Secrets Manager 引用配置或密钥
cfn-init在 EC2 中安装软件、写入文件和执行初始化配置

Custom Resources通过 Lambda 或 SNS 等实现模板原生资源类型之外的自定义操作
Macros在模板处理阶段转换或扩展模板内容
CloudFormation Registry管理资源类型和扩展
CloudFormation Hooks在资源配置生命周期执行策略检查或拦截
CloudFormation Guard对模板执行策略和合规规则验证

三组重点辨析

cfn-init / cfn-signal / WaitCondition

cfn-init：执行实例初始化。
cfn-signal：报告初始化结果。
WaitCondition：等待条件或信号。

Macro / Custom Resource

Macro：转换模板内容。
Custom Resource：在 Stack 生命周期中执行自定义逻辑。

Termination Protection / DeletionPolicy

Termination Protection：防止整个 Stack 被删除。
DeletionPolicy：控制某个资源被删除时如何处理。

CloudFormation Guard / Hooks

Guard：对模板进行规则验证。
Hooks：在资源操作生命周期执行治理检查。

十六、SAP-C02 架构场景题思考方法

四步答题法
  1. 找核心需求：跨账户、跨区域、自动化、保护资源、减少人工操作。
  2. 找限制条件：不能停机、不能删除数据库、不能重建资源、必须使用 Organizations。
  3. 定位 AWS 功能：将需求映射到 StackSets、Change Sets、Drift Detection 等。
  4. 检查所有约束：核对成本、运维复杂度、自动化程度、可用性和安全性。

综合场景示例

某跨国企业有多个 AWS 账户和多个 Region。公司希望统一管理基础设施，新加入的账户自动部署安全基线；部署通过自动化流水线执行，生产数据库不能因模板更新而被意外替换。

需求对应方案
多账户、多 RegionStackSets
新账户自动部署Service-managed StackSets + Organizations
自动化部署CodePipeline + CloudFormation
禁止更新替换关键数据库Stack Policy（并结合变更审查）
部署前检查变更Change Sets
删除 Stack 时保留数据库DeletionPolicy: Retain
答题关键：不要只看题目出现的名词，要看题目真正要求解决的问题。问跨账户部署选 StackSets；问保护更新选 Stack Policy；问删除时保留资源选 DeletionPolicy；问预览是否替换选 Change Sets。

十九、快速自测

先独立选择，再点击“查看解析”。这些是概念练习题，不代表真实考试题。

1. 管理员手动修改了生产环境 Security Group，要求发现模板与实际资源的差异，应选择什么？
正确答案：C。Drift Detection 检查实际资源配置与模板定义之间的差异。
2. 企业使用 AWS Organizations，希望自动向指定 OU 及未来加入该 OU 的账户部署 IAM Role，应优先选择什么？
正确答案：B。Service-managed StackSets 与 Organizations 集成，适合按 OU 管理多账户部署。
3. 删除 CloudFormation Stack，但必须保留其中的 RDS 数据库，应使用什么？
正确答案：C。DeletionPolicy 控制资源在删除场景中的处理方式；Termination Protection 则会阻止整个 Stack 被删除。
4. 更新 Stack 前，希望查看哪些资源将被新增、修改、删除或替换，应使用什么？
正确答案：A。Change Sets 提供部署前的变更预览，但不保证最终部署一定成功。
5. 一个大型模板需要拆分成网络、计算和数据库等可复用模块，应使用什么？
正确答案：B。Nested Stacks 用于模板模块化和复用；StackSets 用于跨账户、跨区域部署。
