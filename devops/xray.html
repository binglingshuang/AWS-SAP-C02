AWS X-Ray
分布式请求追踪与服务地图 — SAP-C02

X-Ray 将分布式请求中的 trace 与 segment 关联起来，帮助定位跨服务延迟和错误。理解采样减少的数据量、Service Map 的可视化边界、遥测传播与 IAM 写入权限。

一、Trace、Segment 与 Service Map

概念含义使用方式
Trace单个请求跨多个服务组件的端到端追踪。依靠 trace ID 与父子关系关联各段数据。
Segment服务组件处理请求的一段工作记录。包含时间、状态、子段及可选注释/元数据。
SubsegmentSegment 内部调用或工作单元。用于显示数据库、HTTP 下游等依赖耗时。
Service Map从已收集 trace 派生的服务与依赖关系图。辅助发现错误/延迟，不是完整拓扑配置或实时流量保证。

Trace header（常见为 X-Amzn-Trace-Id）传播 trace 上下文；服务必须正确创建/转发上下文，才能形成连贯的跨服务追踪。

数据区分：Annotation 可索引并用于筛选；Metadata 用于附加非索引上下文。不要把敏感个人信息或秘密放入追踪数据。

二、采集方式与上下文传播

  • AWS SDK、Lambda/X-Ray 集成、语言 SDK 或 OpenTelemetry instrumentation 可产生遥测；新项目应根据 AWS 当前推荐评估 OpenTelemetry 与 CloudWatch 可观测性路径。
  • 应用需允许采集器/SDK 将 segment 数据提交至 X-Ray；EC2/ECS 等环境要配置采集组件、网络出口和写入身份。
  • 同步 HTTP 服务之间需传播 trace header；消息队列等异步边界要将上下文写入并随消息传递，才能关联生产者/消费者。
  • 服务地图中下游节点可能来自 AWS 服务集成或远端调用；缺少 instrumentation、header 丢失或采样不一致会造成 trace 不完整。
  • 记录错误、fault、throttle 与响应时间等有助排查；避免把大请求/响应载荷直接写入 trace。

三、采样规则、筛选与告警

  • 采样可减少遥测成本和噪声，但低频错误可能被漏采；关键交易路径可设计适当采样规则并考虑错误请求的观测覆盖。
  • 采样规则可按服务、HTTP method、URL 等条件匹配，并结合固定采样额度/比例；规则优先级及匹配范围需审慎配置。
  • 使用 Annotation 为租户/业务类型等有限维度打标并过滤；高基数数据会增加索引和查询负担。
  • Groups 可按 filter expression 将符合条件的 trace 聚合查看；Insights 可协助发现延迟/错误异常趋势。
  • X-Ray trace 查询是诊断工具之一；运营告警还应结合 CloudWatch metrics/logs、SLO 与业务指标。
易错点：采样率不是准确的业务请求计数器；需要精确流量统计时使用日志、指标或业务事件，不要用采样 trace 推算总量。

四、权限、网络与数据治理

  • 写入角色需要对应 X-Ray/遥测写入权限；读取 trace、分析组和配置采样规则分别授予最小权限。
  • 私有子网采集器需能访问 X-Ray 接入端点，可评估 NAT 或 Interface VPC Endpoint，并配置 DNS、安全组和 endpoint policy。
  • 跨账号观测需规划角色/资源访问方式、账户边界和区域；X-Ray 控制台视图不自动授予底层日志或业务数据权限。
  • 对 trace 注释、URL、异常消息实施数据最小化与脱敏；制定保留、访问审计和跨境数据治理要求。
  • 排障依次核对 SDK/采集器运行、trace header、采样规则、网络连通、IAM 拒绝及区域配置。

五、场景题解析

场景一：请求经过 API、Lambda 和数据库，需找慢点

单看总响应时间无法确定瓶颈。

方向：启用合适的 X-Ray/OpenTelemetry 追踪，关联 trace、segment 和下游 subsegment。
端到端追踪展示请求在各服务/依赖上的耗时。
Service Map 不会自动补全未采集或未传播的 trace。

场景二：异步消息消费者的 trace 与生产者断开

HTTP 请求追踪正常，但队列之后没有关联。

方向：在消息中传播 trace 上下文，并在消费者侧提取后继续创建关联追踪。
异步边界不会像同步 HTTP 那样天然继承请求上下文。
仅安装消费者 SDK 不会自动恢复丢失的上下文。

场景三：trace 费用/数量过高

高流量 API 的每个请求都被记录。

方向：配置按服务/请求条件适用的采样规则，保留关键路径的代表性数据。
采样可降低遥测量，同时仍需监控未采集请求的指标。
过度降低采样会漏掉低频故障。

场景四：生产错误几乎没有被采集到

团队此前统一设置很低的固定采样率。

方向：重新审视采样规则并加强错误/关键路由的采集，同时用 CloudWatch 错误指标保证告警覆盖。
采样与故障可观测性需平衡，不能仅依赖 trace。
trace 采样结果不等于所有请求总体的完整统计。

场景五：私有子网采集器无法提交 trace

应用运行正常，但 Service Map 没有新数据。

方向：检查采集器、写入 IAM 权限、X-Ray endpoint 的网络路由/DNS 和区域。
遥测写入依赖应用采集链路及服务端点可达性。
只调整控制台读取权限不能修复采集器写入失败。

场景六：通过 trace 筛选特定业务请求

团队需要按租户等级找出高延迟请求。

方向：将受控、低基数的业务分类写入 Annotation，再按条件查询/分组。
Annotation 可索引筛选；Metadata 适合不用于索引的上下文。
不要把访问令牌、个人信息或高基数原始内容放进 trace。

八、快速自测

1. 一个请求跨越多个服务时，哪类数据模型可关联各段处理？

Trace 通过 trace ID 和父子 segment/subsegment 关系关联。

2. Annotation 和 Metadata 的筛选能力有何区别？

Annotation 可索引筛选；Metadata 通常用于附加不索引的上下文。

3. 采样后能否把 X-Ray trace 数当成精确请求总量？

不能。采样会排除请求；准确计数应依赖指标或业务事件。
