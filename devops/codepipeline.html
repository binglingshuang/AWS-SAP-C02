持续交付流水线编排 — SAP-C02

CodePipeline 编排源代码、构建、测试、审批和部署阶段。考试重点是理解 stage/action 的职责、制品在阶段间的传递，以及跨账号/跨区域流水线的授权边界。

一、流水线模型与边界

Pipeline 由一个或多个 stage 构成；stage 内的 action 可串行或并行执行。常见链路为 Source → Build/Test → Approval → Deploy。

CodePipeline 负责编排，不负责替代构建引擎、部署控制器或制品仓库：常与 CodeBuild、CodeDeploy、CloudFormation、Lambda 及第三方 action 集成。Stage 是逻辑边界，action 才执行具体任务。

决策口诀：要定义流水线先后顺序选 CodePipeline；要编译测试选 CodeBuild；要逐步发布应用选 CodeDeploy。

二、Action、Artifact 与执行顺序

概念作用架构注意点
Source action从受支持的代码源或对象存储取得变更并输出制品。连接授权、分支/事件过滤及触发方式需与源码平台配置匹配。
Build / Test action调用 CodeBuild 或外部构建服务。输入输出制品名、构建角色、测试失败后的停止行为需明确。
Deploy action将制品交给 CodeDeploy、CloudFormation 等目标。部署服务所需角色与目标环境权限独立配置。
Artifact在 action 间传递的文件/数据引用。通常使用 S3 制品桶；注意加密、区域、保留和访问策略。

stage 内 action 可通过不同 runOrder 分组实现顺序执行；相同顺序可并行。后续 stage 等待当前 stage 完成，action 输入输出连接必须显式定义。

三、跨账号与跨区域部署

  • 常见模式是在工具账号创建流水线，在目标账号创建部署角色；目标角色信任流水线账号的指定角色，调用端再获准 sts:AssumeRole。
  • 流水线的服务角色需有权访问目标角色、制品桶和 KMS 密钥；目标角色仅授予目标环境部署所需权限。
  • 跨区域 action 需要相应区域的制品桶/制品复制配置；检查桶策略、KMS key policy、区域限制与目标服务权限。
  • 部署账号、区域或 stage 变更后，逐项验证角色信任关系和资源策略；单独给 IAM 用户权限不能替代服务角色链路。
  • 生产环境可将手动审批放在部署前 stage，并用通知/审计机制记录审批上下文。

四、触发器、审批与运行治理

  • 按源提供方选择 webhook、连接器事件或轮询等触发能力；过滤分支、文件路径和事件，避免无关提交启动部署。
  • Manual approval action 可暂停流水线等待人工决定；审批可配置通知主题和外部审批链接，拒绝或超时需有明确处理流程。
  • 配置执行模式时考虑是否允许同一流水线并发、排队或只保留最新变更；避免旧构建晚于新构建发布。
  • 使用 CloudTrail、CodePipeline 执行历史及 CloudWatch 指标/事件追踪变更和失败；警报通知不等于自动回滚。
  • 限制流水线修改和制品读取权限；构建产物与部署输入应可追溯、完整且受加密保护。
易错点：审批 action 只提供关卡，不会自动验证变更安全；跨账号部署也不意味着流水线服务角色自动拥有目标账号权限。

五、场景题解析

场景一：提交代码后自动测试并部署

团队要把多个工具串成可视化交付流程。

方向：用 CodePipeline 编排 Source、CodeBuild 测试和部署 action。
流水线负责阶段编排，构建和部署由专用服务执行。
不要把 CodePipeline 当作执行任意构建命令的环境。

场景二：同一 stage 的安全扫描必须先于打包

两项 action 当前并行执行。

方向：为 action 设置不同 runOrder，明确先扫描再打包。
相同 runOrder 可并行；更高顺序在前序 action 成功后执行。
仅调整 stage 名称不会改变执行顺序。

场景三：中央工具账号向生产账号部署

流水线可生成制品，但目标账号调用被拒绝。

方向：为目标账号配置受限部署角色、信任策略和流水线角色 AssumeRole 权限。
跨账号要求调用方身份权限与被调用角色信任策略同时成立。
不要向跨账号角色授予宽泛管理员权限。

场景四：生产发布必须由值班经理确认

测试通过后才允许继续生产部署。

方向：在生产部署前增加 Manual approval action，并配置审批通知。
审批将流水线暂停，等待获授权人员决策。
SNS 通知本身不是审批门禁。

场景五：多个代码提交造成旧版本覆盖新版本

长时间构建完成顺序与提交顺序不同。

方向：调整流水线执行模式与并发策略，避免过期执行继续发布，并校验部署输入版本。
并发执行与部署排序必须与发布一致性要求匹配。
仅增加构建容量不保证生产部署顺序。

场景六：跨区域部署找不到输入制品

目标区域的 action 无法读取源区域 artifact。

方向：配置目标区域制品存储/复制，并检查 S3 与 KMS 跨区域授权。
流水线制品与加密密钥都需可被目标区域 action 访问。
复制流水线定义不代表制品已经复制。

七、考前速记卡

已掌握 0 / 18

  • CodePipeline 是托管 CI/CD 编排服务。
  • Pipeline 由多个 stage 组成。
  • Stage 内包含执行具体任务的 action。
  • Source、Build、Deploy 是常见 action 类型。
  • 相同 runOrder 的 action 可并行运行。
  • 不同 runOrder 可表达 action 顺序。
  • CodePipeline 编排，CodeBuild 执行构建。
  • CodeDeploy 管理应用部署生命周期。
  • 制品通过输入/输出 artifact 在 action 间传递。
  • 制品桶需设计访问策略和加密。
  • 跨账号需配置调用角色与目标角色信任。
  • AssumeRole 需要调用权限和信任策略匹配。
  • 跨区域部署还要准备目标区域制品存储。
  • KMS key policy 也是制品访问链路的一环。
  • Manual approval 可在部署前暂停流水线。
  • 通知不等同于人工审批门禁。
  • 过滤源事件可减少无关执行。
  • 执行模式应防止旧版本覆盖新版本。

八、快速自测

1. 谁负责把 CodeBuild 与 CodeDeploy 按顺序串起来？

CodePipeline。

2. 为什么跨账号部署需要同时配置两侧策略？

调用方要有 AssumeRole 权限，目标角色也必须信任调用方主体。

3. 如何要求生产部署前人工确认？

在生产部署前加入 Manual approval action，并配置通知/审批流程。
