AWS CodeDeploy
自动化应用部署 — SAP-C02

一、平台与部署策略

平台常见策略关键考点
EC2 / On-PremisesIn-place；Blue/Green需安装 CodeDeploy agent、匹配 deployment group 与实例标签/ASG。
Amazon ECSBlue/Green由 CodeDeploy 更新 ECS 服务和负载均衡器 listener/target groups，可逐步转移流量。
AWS LambdaCanary、Linear、All-at-once通过别名与版本进行流量转移，可挂接部署前后验证钩子。

In-place 在现有实例上停止/更新/启动应用，资源利用率高但更新期间容量或可用性受部署配置影响。Blue/Green 在新环境验证后切换流量，回退快但需要额外环境容量。

术语注意：“蓝绿”是部署模型；具体可用配置、流量控制和钩子随 EC2、ECS、Lambda 平台而异，不要把各平台选项混为一谈。

二、AppSpec 与生命周期钩子

  • AppSpec 文件描述部署修订版本中的文件、权限和生命周期事件；EC2/on-premises 与 ECS/Lambda 的文件结构和字段不同。
  • EC2/on-premises 可在 ApplicationStop、BeforeInstall、AfterInstall、ApplicationStart、ValidateService 等事件运行脚本；脚本退出状态影响部署成败。
  • ECS AppSpec 描述 task definition、容器/端口映射及可选生命周期钩子；Lambda AppSpec 指向函数版本并可定义 hook 函数。
  • 部署组绑定目标实例/服务、部署配置、负载均衡器与回滚策略；CloudFormation/CodePipeline 可调用 CodeDeploy action 编排发布。
  • 部署前校验 agent/权限、安装依赖、磁盘空间、健康检查端点、超时与脚本幂等性。
易错点：AppSpec 不是应用构建脚本。构建生成可部署修订版本，CodeDeploy 再按平台解释 AppSpec 执行部署。

三、流量转移、健康检查与回滚

  • EC2 原地部署配置控制并发更新/可用容量；蓝绿可在新实例组健康后切换负载均衡流量，并按配置终止旧实例。
  • ECS 蓝绿可将测试 listener 指向新 task set，验证后按 All-at-once、Canary 或 Linear 类策略转移生产流量（以平台支持为准）。
  • Lambda 部署配置按比例/时间逐步把别名流量转向新版本；CloudWatch alarms 可作为部署失败/回滚信号。
  • 自动回滚可由部署失败、CloudWatch alarm 或手动触发；回滚通常重新部署先前修订版本，并非反向撤销数据库 schema 等外部副作用。
  • 验证负载均衡器健康检查、实例健康状态、部署事件和 CloudWatch 指标；回滚需保留可用旧版本与兼容的数据变更方案。

四、权限、安全与发布治理

  • 部署服务角色允许 CodeDeploy 操作目标资源；EC2 实例配置文件提供下载制品、读取 S3/KMS 等应用部署所需访问。
  • 跨账号制品发布还需配置源桶/目标账户授权、KMS key policy 与角色信任，不以放宽桶为公开访问解决授权问题。
  • 使用蓝绿降低切换风险，但新旧版本需兼容共享数据库、会话和消息格式；必要时采用 expand/contract schema migration。
  • 发布前执行 smoke/integration test；逐步流量策略要配合足够观察窗口、报警阈值和清晰的人工中止流程。
  • 将部署事件、应用日志、负载均衡健康状态和 CloudWatch alarm 纳入统一排障链路。

五、场景题解析

场景一：EC2 更新时不能中断现有流量

可以临时增加一组实例，健康后再切流。

方向：使用 EC2 Blue/Green 部署，经负载均衡器验证新环境后切换流量。
新旧环境并行可避免直接在承载流量的实例上逐个替换应用。
蓝绿部署需要额外实例容量与旧环境清理策略。

场景二：实例需要按受控并发原地更新

成本不允许维持完整的第二套环境。

方向：使用 In-place deployment，并选择满足容量/可用性要求的部署配置。
原地部署复用实例，但更新期间可用容量取决于批次策略。
“原地”不等于零停机，需评估负载均衡摘除和部署批次。

场景三：Lambda 发布需先给 10% 用户试用

新版本稳定一段时间后再扩大流量。

方向：部署 Lambda 新版本并使用 CodeDeploy Canary/Linear 配置控制别名流量。
渐进式流量转移能在扩大影响前观察错误率与延迟。
直接更新函数代码不能替代基于别名的受控发布。

场景四：ECS 服务需验证新 task 后再切生产

应用必须经过独立测试 listener 检查。

方向：配置 ECS Blue/Green deployment group、生产/测试 listener 与验证钩子。
测试 listener 可在生产流量切换前验证新 task set。
不要误用 EC2 agent 的实例部署流程描述 ECS 发布。

场景五：部署成功但错误率快速上升

希望系统自动停止/回退发布。

方向：为部署组关联 CloudWatch alarm 并启用自动回滚。
部署过程可依据告警信号停止或恢复到先前版本。
回滚应用版本不能自动撤销不兼容的数据迁移。

场景六：EC2 部署脚本下载制品被拒绝

CodeDeploy 已能找到实例，但实例无法读取 S3 对象。

方向：检查实例 profile 的 S3 权限、桶策略和 KMS 解密授权。
控制平面部署权限与实例读取制品权限是不同身份链路。
仅给 CodeDeploy 服务角色授权不一定能让实例读取制品。

八、快速自测

1. 原地部署和蓝绿部署最主要的资源/风险差别是什么？

原地复用实例但更新时需管理可用容量；蓝绿保留新旧环境并行，切换更快但需要额外容量。

2. Lambda 如何逐步将生产流量转到新版本？

使用版本与别名，并通过 CodeDeploy Canary/Linear 等部署配置转移流量。

3. 如何在错误率升高时自动回退应用版本？

关联 CloudWatch alarm 并启用部署组自动回滚；同时确保旧版本和数据兼容策略可用。
