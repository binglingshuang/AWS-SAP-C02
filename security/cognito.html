Amazon Cognito
Web 与移动应用用户身份

Cognito 为应用用户提供注册、登录、联合身份和对 AWS 资源的临时访问能力。最重要的区分：User Pool 完成应用用户认证并签发 JWT；Identity Pool 交换身份令牌取得 STS 临时凭证。

一、User Pools 与 Identity Pools

能力User Pool（用户池）Identity Pool（身份池）
核心职责应用用户目录、注册/登录、认证和令牌将已认证/访客身份映射到 AWS IAM role，发放临时凭证
主要输出JWT：ID、Access、Refresh token通过 STS 获得的临时 AWS credentials
用户来源本地用户目录及配置的 SAML/OIDC 社交 IdPUser Pool、外部 IdP 或其他受支持身份提供方
典型用途应用登录、用户资料、MFA、托管 UI移动/Web 客户端安全访问 S3 等 AWS 服务
常见串联：用户通过 User Pool 或外部 IdP 认证 → 得到 token → Identity Pool 校验身份并映射 role → STS 临时凭证按 IAM 权限访问 AWS 资源。只需要应用登录时，Identity Pool 不是必选。

二、JWT 与令牌用途

令牌用途验证/安全提醒
ID token表达用户身份与声明，供客户端/应用识别用户检查签名、issuer、audience、有效期
Access token授权访问 User Pool API 或携带 scope/claims 供 API 验证不是 AWS 凭证；后端必须验证签名、issuer、client/scope 等
Refresh token在有效期/策略允许时刷新用户会话令牌高度敏感，安全存储，考虑撤销与轮换策略
STS 临时凭证对 AWS 服务发起签名 API 请求由 Identity Pool/STS 流程获得，权限来自映射 IAM role

JWT 通常包含 header、payload、signature；payload 可被读取，不应把机密内容放入 token。API Gateway Cognito authorizer 可校验 token；细粒度业务授权仍需应用代码依据 claims/scopes 实施。

三、联合身份与临时凭证

  • User Pool 可通过 SAML/OIDC/社交 IdP 联合用户登录；配置 callback/logout URL、client secret（如适用）和 scopes。
  • Identity Pool 支持已认证身份以及按配置允许的 guest/unauthenticated identities；为两类身份分别映射最小权限 role。
  • 可用规则或 token claims 做 role mapping；高权限角色不能由用户可控字段随意选择。
  • 临时 AWS credentials 有过期时间；不要把长期 IAM access key 放入移动端或浏览器。
  • 多租户应用可用 group/claim 配合后端授权，但不能仅依赖前端隐藏按钮。

四、应用集成与安全

  • API Gateway 可使用 Cognito User Pool authorizer 验证 JWT；HTTP API 也可用 JWT authorizer 配置 issuer/audience。
  • 对外部身份直接发 AWS credentials 时，Identity Pool 的 role trust policy、身份池授权与 IAM permission 都应最小化。
  • 启用 MFA、强密码/风险防护能力、账号恢复策略和审计；保护客户端密钥与 refresh token。
  • 登录成功不代表用户获准访问所有后端资源；后端仍按租户、所有者、角色和资源属性授权。
  • 检查区域、User Pool app client 配置、token 过期/撤销机制、域名与回调 URL。

五、场景题解析（6 题）

1. 移动应用需要用户注册登录，但不访问 AWS API。
方向：User Pool 提供应用目录、认证与 JWT；无需仅为登录引入 Identity Pool。
2. 登录用户需从浏览器直接上传到 S3，不得嵌入密钥。
方向：使用 Identity Pool 将已验证身份映射到受限 IAM role，获取 STS 临时凭证；或采用预签名 URL 的后端签发模式。
排除：不得在客户端放置 IAM user 长期密钥。
3. API Gateway 只允许已登录用户访问 API。
方向：配置 User Pool/JWT authorizer，限制正确的 issuer、audience/client 和 scope；业务资源授权仍由后端执行。
4. Cognito 登录成功，但 AWS 资源调用 AccessDenied。
方向：检查 Identity Pool provider/token 关联、authenticated role mapping、role trust 和 IAM policy，并确认 SCP/资源策略未拒绝。
5. 应用只想显示用户资料，不需要 AWS 服务访问。
方向：校验 User Pool ID token/Access token 并调用相应用户目录能力；Identity Pool 发 AWS 凭证并非登录必需步骤。
6. 未登录访客需要读取少量公开内容。
方向：可使用公开内容/CDN 或 Identity Pool guest role 的严格只读权限；默认优先减少匿名 AWS 凭证暴露面。

八、快速自测

1. 哪种组件主要完成应用用户认证并签发 JWT？
正确答案：A。User Pool 管用户身份与登录令牌。
2. 浏览器需安全获得可访问 S3 的短期 AWS 凭证，应考虑？
正确答案：B。JWT 本身不是签名 AWS API 所用的临时凭证。
3. API Gateway 已验证 JWT，是否足以保证用户只能读自己的订单？
正确答案：B。认证确认身份，业务层仍需执行对象级授权。
