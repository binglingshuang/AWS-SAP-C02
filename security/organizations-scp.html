AWS Organizations / SCP
多账号治理与权限边界

通过 Organizations 组织、OU 和账号建立治理层级，再用 Service Control Policy 限定成员账号内身份可获得的最大权限。牢记 SCP 不授予权限、管理账号不受 SCP 限制，并用显式 Deny / Allow 列表管理策略继承。

一、组织层级与账号

AWS Organizations 将多个 AWS 账号纳入统一组织。通过 Root、OU 和账号层级组织工作负载、隔离账单与权限治理，并集中管理成员账号的策略。

组件作用治理提示
Management Account创建组织并管理账单、组织策略和成员账号。使用专用管理账号；限制登录与日常工作负载，避免用于应用部署。
Root组织中包含 OU 与账号的根容器。挂载到 Root 的策略会沿层级继承至成员账号；管理账号本身不受 SCP 限制。
Organizational Unit (OU)将账号按环境、业务、合规边界分组，OU 可嵌套。保持层级清晰；相同治理要求可通过 OU 集中应用。
Member Account资源和 IAM 身份的隔离边界，账单可集中管理。可使用独立账号分隔生产、开发、安全、日志和共享网络工作负载。
Delegated Administrator将特定组织集成服务的管理任务委派给成员账号。委派管理不会使该账号成为组织管理账号，也不会绕过 SCP。

组织功能集决定可用治理能力。SCP 等组织策略需要启用 Organizations 的 All features；仅 Consolidated Billing 的组织模式不能使用完整的 SCP 管理能力。

二、SCP 能力边界

SCP 定义组织成员账号中 IAM 身份可获得的最大权限边界。最终允许的操作还要经过 IAM Policy、资源策略、权限边界、会话策略、Endpoint Policy 等适用策略评估。

SCP 会做什么SCP 不会做什么记忆点
限制成员账号内 IAM User、IAM Role（含 member account root user）可使用的 AWS 服务和操作。不会向 IAM 身份授予权限；仍需 IAM Policy 等身份授权。“最大权限天花板”，不是 Allow 授权书。
通过 Root/OU/账号层级策略形成组织级边界。不限制 Organizations 管理账号中的身份。管理账号是重要例外，应使用其他控制保护。
限制受支持服务操作，防止成员账号移除必要治理控制。通常不影响服务关联角色执行的操作。服务关联角色是 SCP 的重要例外；另行检查服务权限与资源策略。
结合条件、资源与操作限制多账号环境。不直接配置资源、设置网络或检查合规状态。预防性权限控制，不替代 AWS Config / Security Hub 等检测控制。
  • 只有管理账号有权管理组织级 SCP；成员账号管理员不能自行解除上层 OU 或 Root 施加的限制。
  • SCP 对账号内身份权限设上限；IAM Policy 仍需显式授予动作，二者的有效权限是交集，并受显式 Deny 等其他策略限制。
  • SCP 不是资源共享策略。跨账号访问还需要资源策略、调用方身份策略和组织策略共同允许。
  • 使用 SCP 控制根用户操作时，确认组织功能、策略范围和服务关联角色例外；不能把它当作唯一安全控制。
核心陷阱：在 SCP 中添加 Allow 不会使成员账号用户自动获得该权限；IAM Policy 仍要授权。SCP 中的显式 Deny 则会限制成员账号内身份，即使 IAM Policy 允许。

实际授权
  • 账号的有效 SCP 边界由从 Root 到其所在 OU、再到账号层级适用的策略共同决定。
  • 在 Allow-list 模式下，祖先和子级层级都必须允许某操作；某一层不允许时，成员账号就无法获得该权限。
  • 在 Deny-list 模式下，通常保留默认全面允许，仅在各层添加需要禁止的操作；显式 Deny 沿层级约束成员账号。
  • 移动账号到另一个 OU 会改变继承的 SCP，变更前需检查目标 OU 的有效策略，避免锁死管理员、日志或安全服务。
  • OU 嵌套可表达逐层收紧的控制：组织基础限制 → 环境限制 → 具体账号特殊限制。
安全变更：修改 Root / 核心 OU 的 SCP 前，先在测试 OU 验证；保留紧急恢复路径，并检查管理角色、日志、加密、备份和安全监控所需 API 是否仍允许。

四、允许列表与拒绝列表

策略模型配置方式适合场景 / 风险
Deny list保留组织默认的广泛 Allow，在 Root/OU/账号层添加显式 Deny 限制特定服务/操作。逐步治理现有组织；需防止新服务默认开放，及时补充禁用策略。
Allow list在 Root、OU 和账号路径上明确允许所需服务/操作；通常移除或调整默认 FullAWSAccess 策略。高控制、受监管环境；新工作负载必须明确申请权限，治理配置更严格。

实施注意事项

  • Allow list 要在每个祖先策略层级都保留必要 Allow；只在账号层添加 Allow 无法突破 Root/OU 的上限。
  • 显式 Deny 优先于 Allow；使用 NotAction 构建允许列表前，需仔细检查例外和新增服务的影响。
  • 不要在组织根层直接部署未经验证的 Deny；一个宽泛的 Deny 可能同时阻止成员账号治理、加密、备份与应急响应操作。
  • 用 IAM Access Analyzer、CloudTrail、策略模拟/测试账号和组织变更流程验证影响；SCP 不支持所有 IAM Policy 功能，需核对策略语法和限制。
  • 管理账号不受 SCP 约束，不能依赖成员账号策略保护管理账号里的凭证与资源。

五、管理账号、委派与 Control Tower

  • Management Account：创建组织、管理 Organizations 与集中账单；权限极高，应使用硬件 MFA、最小化人员访问并避免部署普通业务。
  • Delegated Administrator：让指定成员账号管理支持委派的安全/治理服务；按服务注册委派管理员，不等于转移组织所有者权限。
  • Control Tower：基于 Organizations 建立多账号 landing zone，提供 Account Factory、预防性/检测性控制和集中治理工作流。
  • Preventive controls：通常由 SCP 等机制阻止不允许的操作；Detective controls：通常通过 AWS Config 规则等发现偏离。
  • Account Factory：按组织治理要求创建/注册账号并放入指定 OU；账号配置仍需遵从目标 OU 的策略和控制。
  • 治理修复：由 Control Tower 管理的策略或资源应优先通过 Control Tower 工作流修改，避免手工变更导致 drift。
区分角色：Organizations 负责账号与策略层级；SCP 是权限上限；Control Tower 在其上提供 landing zone、账号供应及预防/检测控制工作流。三者不是互相替代的服务。

六、场景题解析

场景一：禁止所有开发账号创建特定昂贵资源

多个开发账号位于同一 OU，组织管理员希望统一阻止创建一类资源，同时仍由账号管理员决定其他具体权限。

正确方向：在开发 OU 附加 SCP 显式 Deny 对应服务操作；账号 IAM Policy 继续负责授予其他允许操作。

分析思路：SCP 可在 OU 层形成成员账号权限上限，适合组织级预防控制。

排除：仅为每个账号添加 IAM Deny 难以集中治理；SCP Allow 也不会自动授予其他权限。

场景二：成员账号策略允许但 API 仍被拒绝

某 IAM Role 的身份策略允许调用操作，但该账号所属 OU 的 SCP 没有允许该操作。

正确方向：由管理账号调整适用 SCP，在 Root 到账号的策略路径上允许该操作，同时保留 IAM 策略授权。

分析思路：SCP 是权限边界，成员账号管理员不能通过 IAM Allow 绕过上层限制。

排除：扩大该 Role 的 IAM 权限或重新创建角色不会突破组织 SCP。

场景三：构建严格的服务允许列表

新组织只允许每个工作负载使用明确批准的服务，并要求子 OU 不能自行放宽根层限制。

正确方向：启用组织 All features，按 Root/OU/账号路径设计 Allow-list SCP，并在每层显式保留所需服务权限。

分析思路：Allow-list 通过祖先与子级策略共同限定可用服务，账号仍需要 IAM 授权。

排除：只在账号层添加允许项不能越过 Root/OU 未允许的边界；删除默认策略前应验证管理员和治理工具访问。

场景四：组织管理员想限制管理账号所有操作

团队在 Root 上附加 SCP，希望该策略也限制 Organizations 管理账号的超级用户。

正确方向：SCP 不会限制管理账号；应通过 MFA、身份中心/受控角色、严格 IAM、CloudTrail 告警和独立审批保护管理账号。

分析思路：组织管理账号是 SCP 的明确作用范围例外。

排除：把管理账号移动到成员 OU 或重复附加 Root SCP 不能让 SCP 限制管理账号。

场景五：创建账号时自动应用治理基线

企业希望以标准化方式创建多账号 landing zone，自动安排 OU，并实施预防性和检测性控制。

正确方向：采用 AWS Control Tower 的 landing zone 与 Account Factory 工作流，并结合 Organizations/SCP 及检测控制。

分析思路：Control Tower 提供多账号治理工作流，底层组织结构和权限策略依赖 Organizations。

排除：只写一条 SCP 不会供应账号、部署 landing zone 或检测资源配置偏差。

场景六：安全服务需要跨账号集中管理

组织希望让安全账号管理成员账号中的某项受支持服务，但不想把管理账号凭证共享给安全团队。

正确方向：对支持的服务注册安全账号为 Delegated Administrator，并按服务文档设置 Organizations 集成与成员账号权限。

分析思路：委派管理员将特定组织级管理工作交给成员账号，不转移管理账号身份。

排除：共享 management account root 凭证或将安全账号提升为组织管理账号都不符合最小权限原则。

九、快速自测

先独立选择，再点击“查看解析”。

1. 成员账号中的 IAM Role 已有 Allow，但调用仍被组织策略拒绝。应由谁检查什么？
正确答案：A。成员账号 IAM Allow 不能越过 SCP 上限；组织管理员检查从 Root 到账号的有效策略。
2. 一个组织 SCP 允许成员账号执行某服务操作。是否足以让所有用户执行？
正确答案：B。SCP 是最大权限边界，不授予 IAM 身份权限。
3. 管理账号管理员试图用 Root SCP 限制管理账号 root 用户。结果会怎样？
正确答案：A。管理账号不受 SCP 限制，应通过独立身份与审计控制保护。
