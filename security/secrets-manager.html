AWS Secrets Manager
秘密存储与自动轮换

把数据库密码、API token 等运行时秘密集中存储、按需取用并轮换。做题时先区分“秘密生命周期与轮换”（Secrets Manager）和“配置/参数存储”（Systems Manager Parameter Store），再检查调用角色、网络与轮换 Lambda。

一、对象与访问模型

Secret 由名称/ARN、加密后的当前值、可选描述与标签构成。值支持字符串或键值 JSON；版本和 staging label（常见 AWSCURRENT、AWSPREVIOUS、AWSPENDING）协助轮换期间的新旧值切换。

组件职责考试提醒
Secrets Manager保存、读取、版本化、复制与轮换秘密调用应用应通过 SDK/API 取值，不把秘密写入镜像或源代码
KMS使用 KMS key 加密 secret value读取跨账号秘密还需 KMS key policy / IAM 允许解密
应用执行角色获得指定 Secret ARN 的 secretsmanager:GetSecretValue按资源 ARN 收窄权限；必要时限定 VPC endpoint
轮换 Lambda生成新凭证、更新目标系统并标记版本需允许 Secrets Manager 调用，且可连通数据库/API
轮换的核心是凭证在秘密存储端与目标数据库端同时更新，并通过版本阶段完成验证和切换；只改 Secret 字符串不会自动改数据库密码。

二、轮换机制

  1. 创建新版本并标记 AWSPENDING。
  2. 轮换函数在目标服务创建/设置新凭证。
  3. 用新凭证验证连接；失败则不把它设为当前版本。
  4. 成功后将新版本切换为 AWSCURRENT，旧值保留为上一版本以支持恢复。
模式适合情况注意点
单用户轮换通常适合开发/测试或支持该模式的数据库更新同一用户密码，轮换窗口内连接池可能需要重连
交替用户轮换需要降低更新密码时连接中断风险的数据库以两套用户交替，需数据库用户/权限模型支持
自定义轮换 Lambda非内置引擎、外部 API 或企业凭证系统自行实现轮换步骤、幂等、超时、回滚与告警

支持的轮换集成与数据库引擎会变化；应以 Secrets Manager 当前轮换文档和目标引擎支持矩阵为准。应用可使用客户端缓存降低 API 调用频率，但必须设计缓存刷新与轮换后的连接恢复。

三、与 Parameter Store 对比

维度Secrets ManagerSystems Manager Parameter Store
主要定位秘密生命周期管理、轮换、审计配置参数与分层参数存储
自动轮换原生轮换工作流，可集成 Lambda/数据库无同等内建秘密轮换工作流；可自行编排
加密KMS 加密 Secret valueSecureString 使用 KMS；普通 String 不加密
层级/参数类型Secret 名称与 JSON 值层级名称、String / StringList / SecureString
成本与选型按 Secret 与 API 使用计费，需评估轮换成本标准参数适合一般配置；高级参数能力与成本另行评估
不要仅因数值“敏感”就忽略生命周期：固定加密配置可考虑 SecureString；数据库密码、需要自动轮换/版本切换和专门审计的凭证优先 Secrets Manager。确认调用频率和费用。

四、架构与安全

  • 通过 IAM role 最小化授权到具体 Secret ARN；运行时读取使用临时凭证。
  • 跨账号消费者：资源账号 secret resource policy 信任消费者角色，消费者 IAM policy 允许读取，KMS key policy 也允许解密；三个授权层都要检查。
  • 复制 Secret 到其他区域可支持区域性应用/灾备；副本加密密钥和区域访问策略需单独核验，复制不是备份数据库。
  • 可用 CloudTrail 记录 API 活动；避免把 secret value 写入应用日志、错误信息、命令行参数或 CI 输出。
  • 私有网络调用可使用 Secrets Manager interface VPC endpoint；轮换 Lambda 还须具备到数据库的路由、DNS 与安全组访问。
  • 限制删除权限，利用恢复窗口避免误删；轮换失败、访问异常和到期/合规事件要有监控告警。

五、场景题解析（6 题）

1. RDS 密码必须定期自动更换。
方向：将数据库凭证托管到 Secrets Manager，配置受支持的自动轮换并让应用运行角色读取 Secret。
判断：确认数据库引擎、轮换方式、Lambda 网络可达性及应用重连逻辑。
2. Lambda 代码里有长期数据库密码。
方向：移除代码/环境变量中的明文，在执行角色上授予单个 Secret 的读取权限；运行时取值并缓存。
排除：把密码放进另一个明文配置文件并未解决秘密暴露。
3. 轮换后应用仍用旧密码。
方向：检查应用缓存、连接池、凭证刷新和轮换版本阶段；确保应用在需要时重新取 AWSCURRENT。
排除：不应手工覆盖 Secret 而跳过目标数据库更新/验证。
4. 另一个账号需要读取共享 Secret。
方向：配置 secret resource policy、消费者角色 IAM policy 和 KMS key policy；使用完整 ARN。
排除：仅允许 GetSecretValue 但未授予 KMS 解密，仍可能失败。
5. 只存一个不需轮换的应用配置，关注成本。
方向：比较 Parameter Store 标准参数或 SecureString 与 Secrets Manager 的功能/成本；按秘密生命周期而非只看数据格式选型。
6. 私有子网中的轮换 Lambda 超时。
方向：验证 Lambda 到 Secrets Manager API 的 VPC endpoint/NAT 路径，以及到数据库的子网路由、DNS、安全组和超时配置。

八、快速自测

1. 要自动轮换受支持的数据库密码，首选哪项？
正确答案：B。轮换工作流可更新并验证目标凭证。
2. 跨账号读取 Secret 时权限已允许，但解密被拒绝，优先检查？
正确答案：A。Secret policy、调用方 IAM 与 KMS 授权必须同时满足。
3. 仅需保存许多普通配置参数、并需要层级组织，优先比较？
正确答案：A。Parameter Store 面向参数与配置；需要秘密轮换生命周期时再选 Secrets Manager。
