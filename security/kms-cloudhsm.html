一、KMS 与 CloudHSM 选型

AWS KMS 提供托管密钥管理 API、授权控制与服务集成；CloudHSM 提供客户控制的单租户 HSM 集群。需要更细的 HSM 管理权并不自动意味着必须放弃 KMS：KMS Custom Key Store 可让 KMS 使用客户 CloudHSM 集群中的密钥材料。

密钥访问通过 KMS API 执行受授权的密码操作；原始 KMS 密钥材料不可导出（除受支持的导入/外部密钥场景）。通过 HSM 客户端及受支持的加密接口访问；客户管理 HSM 用户凭证和密钥操作。

服务集成S3、EBS、RDS 等 AWS 服务可直接集成 KMS。应用或支持的集成需使用 CloudHSM 客户端；不是 KMS API 的通用替代品。
常见选择集中管理密钥、审计、AWS 服务加密和可扩展授权。需专用 HSM、客户自行控制 HSM 用户/加密操作或特定合规要求。
快速判断：“AWS 托管密钥服务 + 服务集成 + IAM/审计” → KMS；“客户必须管理专用 HSM 用户与密钥操作” → CloudHSM；“需要 KMS API 但密钥材料保存在自有 CloudHSM” → 评估 KMS Custom Key Store。

二、KMS Key 类型与材料

类型 / 来源管理方式可见性与用途
AWS owned key由 AWS 服务拥有和管理，客户通常不能查看或直接管理其密钥策略。服务默认加密等场景；没有客户密钥管理与审计控制粒度。
AWS managed key由 AWS 服务在客户账户中管理的 KMS Key，策略和轮换由 AWS 管理。免额外创建客户密钥的服务集成；客户可在 KMS 中查看相关密钥，但控制面有限。
Customer managed key客户创建并管理策略、标签、启用/禁用、轮换和生命周期。适合自定义授权、跨账户共享、审计和精细化密钥管理。
AWS KMS generated material密钥材料由 KMS 生成并保存在 KMS HSM。常见默认；KMS 控制密钥材料生命周期。
Imported key material客户生成密钥材料并导入 KMS。客户控制材料来源；需自行管理过期/重新导入流程，密钥材料不等于可导出 KMS Key。
External key storeKMS 通过外部密钥管理系统使用外部材料。客户保留材料所在系统的控制权，同时引入外部系统可用性、延迟和运维依赖。

对称、非对称与数据密钥

  • 对称 KMS Key 用于加解密或生成数据密钥；AWS 服务的服务器端加密集成通常使用对称客户密钥。
  • 非对称 KMS Key 提供公钥与私钥配对，可用于加密/解密或签名/验签；公钥可公开分发，私钥操作留在 KMS。
  • HMAC KMS Key 用于消息认证码计算与验证；算法和操作类型由密钥规格决定。
  • KMS 对单次 Encrypt 输入大小有限制；加密大文件或大数据集应使用 GenerateDataKey 的信封加密模式，而非把整份数据直接提交 KMS。
成本与控制：AWS managed/owned key 适合简化运维；需要自定义密钥策略、跨账户授权、密钥停用或审计边界时，通常使用 customer managed key，并核对 KMS API 调用费用与配额。

三、密钥策略、IAM 与 Grant

  • 每个 KMS Key 都有 Key Policy，是控制该密钥访问的核心资源策略；若 Key Policy 未授权账户或委托 IAM Policy，单独授予 IAM 权限可能仍不能使用密钥。
  • 典型账户内授权模式：Key Policy 允许账户使用 IAM 策略控制访问；IAM Policy 再授予具体用户/角色的 KMS 操作。
  • 跨账户访问通常需要密钥所在账户的 Key Policy 允许外部账户/角色，同时调用方账户的 IAM Policy 也允许对应 KMS 操作。
  • Grant 是向 AWS 服务或委托方授予有限 KMS 操作的机制，常用于服务集成或短期授权；Grant 约束可限定被授权操作与加密上下文。
  • Encryption Context 是非机密的键值对，作为额外认证数据与密文绑定；解密时需提供匹配上下文。不要把密码或敏感信息放入上下文，因为它可能出现在审计日志中。
  • Key Policy、IAM Policy、Grant 和服务资源策略共同决定请求是否最终获准；还需检查 SCP、权限边界、会话策略、VPC Endpoint Policy 与显式 Deny。
请求被拒绝检查方向典型缺口
同账户角色无权 EncryptKey Policy 是否启用 IAM delegation；角色 IAM Policy 是否授予具体 Key ARN/操作。只给了 IAM Policy，但 Key Policy 没允许账户委托 IAM。
跨账户服务无法解密密钥账户 Key Policy 与调用方 IAM Policy 是否双向授权；检查服务集成支持。只修改了调用方策略；密钥所属账户未授权外部 Principal。
服务可写入密文但读取失败Encrypt/Decrypt 权限、Encryption Context、Grant 与密钥状态。上下文不匹配、密钥已禁用或服务角色缺少 Decrypt。
策略看似允许仍被拒绝显式 Deny、SCP、权限边界、Endpoint Policy、条件键与区域。更高层级策略或条件限制覆盖了 Allow。
最小权限实践：限定 Key ARN、必要操作、可信 Principal 和 Encryption Context 条件；避免向 * 授予宽泛加解密权限。密钥管理员和密钥使用者可分离。

四、信封加密（Envelope Encryption）

信封加密用 KMS 管理高价值密钥加密数据密钥（Data Key），由数据密钥在应用侧加密大数据。这样无需将大文件内容发送给 KMS，也不必让应用长期保存明文主密钥。

1. GenerateDataKey
KMS 返回明文与加密数据密钥
→
2. 本地加密数据
明文数据密钥只在内存短暂使用
→
3. 保存密文
业务密文 + 加密数据密钥
  1. 调用 KMS GenerateDataKey，指定 KMS Key 和必要的 Encryption Context；获得明文 Data Key 与被 KMS 加密的 Data Key。
  2. 应用使用明文 Data Key 在本地加密数据，随后尽快从内存清除明文密钥。
  3. 将业务密文和加密后的 Data Key 一起保存；加密 Data Key 可与密文一起存储，不是明文密钥。
  4. 解密时调用 KMS Decrypt 解开 Data Key，再在应用侧解密业务数据；KMS 权限、上下文与密钥可用性必须满足。
名词作用存储 / 传递原则
KMS Key（Wrapping Key）保护 Data Key，提供授权、审计与密钥生命周期管理。不离开 KMS 的安全边界执行密码操作；不直接用于大数据加密。
Plaintext Data Key对业务数据执行对称加密。只短暂保留在应用内存，完成后清除；不可写日志或持久化。
Encrypted Data Key加密形式保存的 Data Key，供后续经 KMS 解密。可随密文一起保存；不能在没有 KMS 授权与正确上下文时恢复明文。
Encryption Context绑定密文的非机密认证信息，可用于策略条件与审计。解密时必须提供相同上下文；不得放秘密。
一句话记忆：KMS 加密 Data Key，Data Key 加密数据；存储“数据密文 + 加密 Data Key”，不是存储明文 Data Key。

五、密钥轮换与生命周期

密钥材料类型轮换方式注意事项
AWS KMS 生成的对称 customer managed key可按支持的策略启用自动轮换，或手动按需轮换。自动轮换保留同一逻辑 Key ID/ARN；KMS 会保留旧材料以解密旧密文。
AWS managed key由 AWS 管理自动轮换。客户无法像客户管理密钥那样控制轮换周期与策略。
Imported key material由客户生成新材料并按支持流程重新导入，或创建新 KMS Key 并迁移。旧密文仍需相应旧密钥材料可用；材料过期可能导致无法解密。
非对称 / HMAC Key不适用常见的 KMS 自动轮换方式；按需创建新 Key 并更新应用。迁移签名验证、公钥分发和密文兼容需要版本化设计。
Multi-Region Key主密钥轮换会在相关副本间同步相同密钥材料。密钥策略、别名、启用状态等配置仍需按区域管理。
  • 轮换不会自动重新加密所有历史密文；KMS 使用密钥材料版本识别并解密既有密文。
  • 手动创建新 KMS Key 会得到新的 Key ID；别名可帮助应用切换，但旧密文仍需保留旧 Key 可用。
  • 禁用或计划删除密钥会影响所有依赖该密钥的解密流程；计划删除有等待期，关键密钥应设置审批与监控。
  • 轮换周期、密钥规格和跨区域同步能力以当前 KMS 支持矩阵为准；不要将所有 key type 都假设为可自动轮换。

六、跨区域密钥与服务集成

Multi-Region KMS Keys

  • Multi-Region Key 的主键与副本分布在不同 Region，并共享相同密钥材料与 Key ID；适合跨区域应用需要本地区域执行加解密并保持相同密文互操作的场景。
  • 主键与副本仍是各自 Region 的 KMS 资源，需要调用本地区域 KMS Endpoint；副本上的策略、别名与启用状态要分别管理。
  • Multi-Region Keys 不是自动跨区复制应用数据的服务，也不会取代数据复制、灾备切换或 IAM/资源策略授权。
  • 若只需跨区域加密备份，不一定需要 Multi-Region Key；可按服务的快照复制/重新加密能力与灾备要求设计。

AWS 服务加密集成

  • S3 SSE-KMS 由 S3 调用 KMS；检查 S3 Bucket Policy、KMS Key Policy、调用身份及加密上下文。高请求量可评估 S3 Bucket Keys 以减少 KMS 请求。
  • EBS、RDS 等服务通常在创建资源或复制快照时指定 KMS Key；已有未加密资源可能需快照/复制/恢复方式迁移。
  • 服务代客户调用 KMS 时需确认 Grant 或服务角色授权正确；“服务已启用加密”不表示任意身份都能解密数据。
  • KMS 是区域性服务；密钥一般需在使用资源所在区域创建或按支持方式配置 Multi-Region / 跨区域复制密钥。
故障域：KMS Key 被禁用、计划删除、策略变更或配额节流时，依赖它的新加密/解密请求可能失败。密钥治理需包含监控、审批、恢复与服务依赖清单。

七、CloudHSM 架构与责任

  • CloudHSM 在客户 VPC 内提供专用、单租户 HSM 集群；客户管理密码学用户、客户端连接、应用集成和密钥操作权限。
  • 为可用性部署集群时考虑多个 AZ、HSM 节点、客户端自动发现与集群恢复；HSM 集群不可达会影响依赖它执行的加密操作。
  • CloudHSM 不自动提供 KMS 的通用 AWS 服务集成、Key Policy 或同一套 KMS API；需要应用使用兼容客户端/接口。
  • KMS Custom Key Store 可把 KMS Key 的密钥材料放在客户 CloudHSM 集群中，并继续通过 KMS API 管理授权和服务集成；要接受 HSM 集群故障会影响相关 KMS 操作。
  • CloudHSM 与 KMS 都使用 HSM 保护密钥材料，但服务责任、API、授权、集成和客户运维控制粒度不同。
要求建议方向权衡
AWS 服务原生加密、审计、细粒度授权KMS Customer Managed KeyAWS 托管 HSM；需管理 Key Policy、轮换与费用。
专用单租户 HSM 且自管 HSM 用户CloudHSM更直接控制，但承担集群可用性、客户端、用户凭据与应用集成。
KMS API/集成，同时密钥材料留在 CloudHSMKMS Custom Key Store兼得 KMS 控制面与客户 HSM 材料控制；额外依赖 HSM 集群正常。
应用需要任意操作系统级加密软件EC2 自管方案或 CloudHSM 集成评估 OS/应用控制需求、合规边界与运维成本。

八、场景题解析

场景一：跨账户 S3 SSE-KMS 解密失败

外部账号应用可读取加密对象，但 S3 返回 KMS AccessDenied。调用角色 IAM 策略已允许解密。

正确方向：检查密钥所属账号的 Key Policy 是否允许外部角色/账号，并确认调用方 IAM Policy、S3 权限和 Encryption Context 同时满足。

分析思路：跨账户 KMS 请求通常需要密钥资源策略与调用方身份策略共同授权。

排除：只修改 S3 Bucket Policy 或只添加调用方 IAM Allow 不能越过 Key Policy 的拒绝。

场景二：加密大型对象但避免把内容交给 KMS

应用需要使用 KMS 管理主密钥，并在客户端加密大型文件，文件可能远大于 KMS 单次 Encrypt 输入限制。

正确方向：使用 KMS GenerateDataKey 执行信封加密，应用用明文 Data Key 加密文件，并保存加密 Data Key 与数据密文。

分析思路：KMS 只加密小型数据密钥；大对象由应用侧数据密钥加密。

排除：将整个文件直接调用 KMS Encrypt；或将明文 Data Key 写入存储/日志。

场景三：每年自动轮换客户对称密钥

团队使用 KMS 生成的对称 customer managed key，希望降低手工轮换负担，同时继续解密历史密文。

正确方向：对支持的客户管理对称 KMS Key 启用自动轮换，并保留 Key 不被禁用/删除。

分析思路：KMS 保留旧密钥材料版本以解密历史密文；轮换不会自动重加密所有数据。

排除：删除并新建 key 会产生不同 Key ID，若丢失旧 key 则旧密文可能无法解密；所有非对称/导入密钥也不能假设可自动轮换。

场景四：合规要求客户控制专用 HSM 用户

应用需使用专用单租户 HSM，并要求客户直接管理 HSM 密码学用户和密钥操作，不满足于仅管理 KMS IAM 策略。

正确方向：评估 CloudHSM 集群，设计多 AZ 节点、客户端连接、用户/凭证生命周期与应用集成。

分析思路：CloudHSM 提供客户对专用 HSM 集群与用户的更直接控制。

排除：仅创建 KMS Customer Managed Key 不会把 HSM 用户管理权交给客户。

场景五：AWS 服务需集成 KMS API，但材料必须在 CloudHSM

团队要保留 KMS 的授权和服务集成，同时要求 KMS Key 的材料由自有 CloudHSM 集群保护。

正确方向：使用 KMS Custom Key Store 并关联 CloudHSM 集群，验证服务支持、网络、HSM 可用性和恢复流程。

分析思路：Custom Key Store 将 KMS 控制面与 CloudHSM 密钥材料后端连接。

排除：直接使用 CloudHSM API 不会自动获得 KMS 的全部服务集成和策略语义。

场景六：跨区域应用需本地 KMS 操作相同密文

应用在多个 Region 运行，要求各区域使用对应的本地区域密钥执行加解密，并保持密文可在区域间互操作。

正确方向：评估 KMS Multi-Region Key，配置主键和副本，并分别管理各区域策略与别名。

分析思路：Multi-Region Keys 在区域间共享密钥材料，但每个区域仍是独立资源与 API 端点。

排除：单区域 KMS Key ARN 不能被视为全球可用；Multi-Region Key 也不会自动复制业务数据。

  • 轮换 ≠ 重加密：KMS 保留旧材料以解历史密文
  • 导入材料：客户负责材料到期与重新导入
  • Multi-Region Key：区域副本共享材料但各自管理策略
  • KMS 区域性：服务集成按区域配置密钥
  • 禁用密钥：依赖它的解密与服务操作可能失败
  • CloudHSM 可用性：多 AZ 与客户端恢复需客户设计

十一、快速自测

先独立选择，再点击“查看解析”。

1. 应用需要加密大型文件，主密钥由 KMS 管理，但文件内容不应发送给 KMS。应使用什么？
正确答案：A。KMS 加密数据密钥，应用用明文 Data Key 本地加密文件，并只保存加密后的 Data Key。
2. 跨账户角色有 IAM Decrypt 权限，但无法解密另一个账户拥有的 KMS 密文，先检查什么？
正确答案：B。跨账户授权需要密钥资源策略与调用方身份策略共同允许，并核对 Encryption Context 和显式拒绝。
3. 合规要求客户管理专用 HSM 用户，同时保留 KMS API 及服务集成。应评估什么？
正确答案：B。Custom Key Store 通过 KMS API 管理使用 CloudHSM 集群中的密钥材料；需接受对集群可用性的依赖。
