一、身份中心与访问模型

AWS IAM Identity Center（原 AWS Single Sign-On）为员工和其他 workforce users 提供集中身份入口；用户通过一个门户访问获分配的 AWS 账号、Permission Sets 和受支持的业务应用。

Identity Source
内置目录 / AD / 外部 IdP
→
IAM Identity Center
身份、组与分配
→
Permission Set
会话权限模板
→
AWS Account / App
临时角色会话 / 联合访问
  1. 用户在集中身份源完成登录与认证。
  2. 管理员把用户/组分配到一个或多个 AWS 账号和 Permission Sets，或分配到企业应用。
  3. Identity Center 为目标账号配置相应 IAM Role；用户通过访问门户选择账号和角色，获取临时凭证。
  4. CloudTrail、IdP 与 Identity Center 日志用于审计登录、身份分配和会话访问。
核心用途：Identity Center 面向员工 workforce 的集中登录和多账号授权；它不是应用中的终端消费者身份系统（通常考虑 Cognito），也不是 EC2/Lambda 等工作负载的运行时角色服务。

二、身份来源与 SCIM

身份来源认证 / 配置方式适合场景
Identity Center directory在 Identity Center 内创建和管理用户、组；由 Identity Center 处理门户认证。无既有企业目录，或需要独立的轻量 workforce identity store。
Active Directory连接 AWS Managed Microsoft AD，或通过 AD Connector 等支持方式连接现有目录。沿用 AD 用户、组和密码政策；需规划网络、信任和目录可用性。
External identity provider通过 SAML 2.0 联合进行认证；用 SCIM 自动同步支持的用户和组。企业已有 Okta、Entra ID 等 IdP，希望统一登录、MFA 与员工生命周期。

SAML 与 SCIM 的分工

  • SAML 2.0：建立浏览器/门户登录联合，IdP 对用户进行认证并向服务提供断言；用户凭 IdP 身份访问 AWS 门户。
  • SCIM：自动供应/更新/停用用户和组等身份数据；它不是登录认证协议，也不自动授予账号 Permission Set。
  • 组同步：将 IdP 组同步到 Identity Center 后，再把组分配到 AWS 账号/应用和 Permission Sets。
  • 离职处理：在 IdP 停用用户并验证 SCIM 取消供应、会话失效与账号分配撤销行为；设计紧急手动停用路径。
  • 源切换：身份源选择会影响用户、组和登录管理方式；切换前盘点现有身份、分配、应用与回滚计划。
常见混淆：SAML 负责“谁在登录”；SCIM 负责“用户/组如何自动同步”；Permission Set 负责“登录后可以做什么”。三者必须配套但不能互相替代。

三、Permission Sets 与 AWS 账号访问

Permission Set 是一组可复用的权限与会话设置模板。将其分配给用户/组和目标账号后，Identity Center 会在相应账号中配置 IAM Role，并为用户发放短期会话凭证。

配置项作用运维注意
AWS managed policies附加 AWS 管理的 IAM Policy。选择符合职责的最小权限策略，审查托管策略更新的影响。
Customer managed policy reference引用账号中已存在的客户管理策略。目标账号需预先存在同名/符合要求的策略；组织多个账号应统一部署策略。
Inline policy将自定义 IAM Policy 直接嵌入 Permission Set。权限变化后需重新 provision 到目标账号。
Permissions boundary为 Identity Center 创建的账号角色设置权限边界（按所选能力支持）。边界只限制上限，不授予权限；与账号 SCP 和 IAM Policy 一起评估。
Session duration设定用户通过该 Permission Set 获取的会话时长。高权限角色使用较短会话并强化 MFA / 审批。
  • 账号访问分配的单位通常是“用户或组 + AWS Account + Permission Set”；同一用户可获不同账号、不同权限。
  • Permission Set 的权限修改后，需要将更新 provision / 同步到关联账号；排查时确认 provisioning 状态与账号内生成的 IAM Role。
  • Identity Center 生成的角色用于 workforce 会话，不应被当作应用工作负载长期凭证。
  • 账号权限最终仍受 SCP、资源策略、权限边界、会话策略和显式 Deny 等影响；Permission Set 中的 Allow 不能越过组织 SCP。
  • 使用组而非逐用户授权通常更易维护；通过角色职责拆分 ReadOnly、Developer、SecurityAudit、Administrator 等权限集。
管理模型：集中定义权限模板（Permission Set）+ 账号分配 + 自动 provision 角色。人员变化通过用户/组与分配管理，避免在每个成员账号中手工创建 IAM User。

四、应用访问与联合

  • Identity Center 可将用户/组分配到受支持的企业云应用，通过 SAML 或应用目录支持的联合方式实现 SSO。
  • 企业 SaaS 通常仍需在目标应用侧配置租户、属性映射、证书/元数据和用户授权；仅在 Identity Center 启用 SSO 不代表 SaaS 端无需配置。
  • AWS 账号访问与应用访问是不同分配对象；Permission Set 不等于 SaaS 应用角色，应用侧角色/组映射需单独配置。
  • Identity Center 与 AWS CLI 支持基于浏览器 SSO 的临时凭证流程；开发者无需创建长效 IAM User Access Key。
  • 多账号访问依赖 Organizations 集成与组织实例；组织结构变化、账号加入/移除时需核查分配、委派管理员和日志覆盖。
边界提示：IAM Identity Center 为人员提供 AWS 控制台/CLI 与应用 SSO；机器工作负载应使用 IAM Role、STS 或相应服务身份，不要复用员工 SSO 用户凭证。

五、安全、生命周期与审计

  • MFA：优先使用企业 IdP 的 MFA/条件访问；按组织策略配置 Identity Center MFA 并防止弱认证成为单点。
  • 最小权限：按工作职责定义 Permission Sets，使用短会话，并限制管理权限只授予需要的团队。
  • 身份生命周期：通过 SCIM/目录同步用户和组；测试入职、调岗、离职和紧急账号停用全过程。
  • 审计：使用 CloudTrail 跟踪 AWS 账号内 API 操作；结合 Identity Center/IdP 登录日志和组织级日志归档建立完整链路。
  • Break-glass：保留受审批、MFA 保护且定期演练的紧急访问路径；不能让所有管理员依赖同一身份源故障时无法恢复。
  • 多区域/可用性：确认 Identity Center 区域实例、应用门户、IdP 和组织账号的可用性设计；故障恢复方案需覆盖认证与授权依赖。
  • Provisioning：权限集更新或账号分配失败时，检查目标账号状态、服务配额、策略大小和 provision 状态。
撤销访问：从组移除用户只是生命周期流程的一环。还需确认 SCIM 同步、账号分配撤销、活动会话/凭证有效期和应用侧访问均符合预期。

六、与 IAM / Organizations 对比

服务 / 能力主要对象权限/身份用途
IAMAWS 账号内用户、组、角色、策略。为 AWS API 请求授权；创建工作负载 IAM Role 和资源策略。
IAM Identity Center员工/Workforce 用户与组、多账号账号分配、企业应用。集中 SSO 与 Permission Set，向用户发放短期账号角色会话。
AWS Organizations / SCP组织、OU、成员账号。集中治理账号并限制成员账号身份的最大权限；SCP 不授予权限。
Amazon Cognito面向应用终端用户的用户池与身份池。Web/移动应用注册登录、联邦身份与临时 AWS 凭证。
架构组合：员工 SSO 由 Identity Center 管理；账号级最高权限边界由 SCP 约束；账号内资源/API 具体授权由 IAM Policy 等控制；面向客户的应用登录通常由 Cognito 提供。

七、场景题解析

场景一：员工通过一个入口访问多个 AWS 账号

公司已有数十个成员账号，希望员工使用企业目录登录，并依据组角色访问不同账号，不在每个账号创建长期 IAM 用户。

正确方向：部署 IAM Identity Center，连接企业身份源，配置组、Permission Sets 和账号分配。

分析思路：Identity Center 集中管理 workforce SSO，并在目标账号 provision 临时角色权限。

排除：在每个账号复制 IAM User 会增加凭证与离职撤销成本；IAM Role 本身不提供员工身份门户。

场景二：用户登录已工作，但新组成员没有 AWS 权限

外部 IdP 用户可登录 Identity Center，SCIM 已同步组；新用户在账号门户看不到目标账号角色。

正确方向：检查组到 AWS 账号/Permission Set 的分配、账号状态与 Permission Set provisioning。

分析思路：SAML 登录成功只证明认证链路可用；SCIM 同步组也不自动授予账号访问。

排除：重复修改 SAML 证书不会自动创建账号分配或权限集。

场景三：离职用户需自动停止访问所有账号

员工目录是企业 IdP，要求离职停用后自动撤销 Identity Center 和目标账号访问。

正确方向：使用 SCIM 供应/取消供应流程同步用户状态与组变更，测试 Identity Center 分配撤销、会话失效和应用端访问回收。

分析思路：SCIM 管理身份生命周期；SAML 负责登录，权限仍由分配与 Permission Set 管理。

排除：只删除本地 IAM User 不会撤销 SSO 用户；只禁用登录也需评估已有会话和外部应用。

场景四：新 Permission Set 策略没有出现在目标账号

管理员更新了 Permission Set 的 inline policy，目标成员账号仍使用旧权限。

正确方向：检查 Permission Set provisioning 状态并将更新重新 provision 到关联账号，验证生成 IAM Role 的策略。

分析思路：权限模板变更需要同步到目标账号角色。

排除：只刷新门户或重新登录未必能修复未成功 provision 的账号角色。

场景五：员工角色需要管理权限，但不能越过组织限制

Permission Set 为管理员角色授权某操作，成员账号仍因组织策略拒绝该操作。

正确方向：由 Organizations 管理员评估并调整适用 SCP；IAM Identity Center 的权限集 Allow 不能突破 SCP 上限。

分析思路：Identity Center 管账号内角色授权，SCP 在组织层限制成员账号最大权限。

排除：在 Permission Set 中继续添加更多 Allow 不会覆盖上层 SCP Deny。

场景六：开发者在自动化脚本中需要 AWS CLI 访问

员工需使用 CLI 临时访问多个账号，安全团队禁止长期 Access Key。

正确方向：使用 IAM Identity Center 支持的 CLI SSO 登录流程，按分配的 Permission Set 获取短期凭证。

分析思路：CLI SSO 可以复用 workforce 身份与账号角色分配，避免静态用户密钥。

排除：共享员工 Access Key、在脚本硬编码 IAM User 密钥或将 SSO 用户凭证用于长期工作负载。

十、快速自测

先独立选择，再点击“查看解析”。

1. 外部 IdP 用户可以登录，但新同步的用户组没有 AWS 账号访问权限。下一步检查什么？
正确答案：B。SCIM 同步身份不等于授权；必须创建账号与 Permission Set 分配并确认 provision。
2. 企业希望用 SAML 登录并自动同步用户/组，两个能力分别由什么负责？
正确答案：B。SAML 建立登录联合；SCIM 管理用户/组的自动供应和生命周期。
3. Identity Center Permission Set 允许某操作，但成员账号 SCP 显式拒绝，能否执行？
正确答案：B。Identity Center 生成的账号角色仍受组织 SCP 权限边界约束。
