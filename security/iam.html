一、IAM 核心组件

IAM 是 AWS 权限管理的基石，控制"谁能对什么资源做什么操作"。SAP-C02 要求深刻理解各组件的区别与协同。

四大核心实体

实体定义特点常见场景
User（用户）代表一个人或服务，拥有永久凭证有用户名/密码；可有 Access Key；直接绑定策略或加入 Group开发人员、运维账号
Group（组）用户的集合，不能嵌套，不能直接被 AssumeRole策略附加到 Group，Group 中所有 User 继承策略将 Dev 组赋予开发权限
Role（角色）可被 AWS 服务、用户或外部身份扮演的身份，使用临时凭证无永久密码/密钥；通过 STS 获取临时凭证；支持跨账号EC2 实例角色、Lambda 执行角色、跨账号访问
Policy（策略）定义权限的 JSON 文档，描述允许或拒绝的操作附加到 User/Group/Role/Resource；分多种类型赋予 S3 只读权限

根账户（Root Account）

使用邮箱+密码登录的账户，拥有对所有 AWS 资源的完全控制权，无法被 IAM 策略限制。

考试记忆：Root Account 是 AWS 账户中最高权限实体。应立即启用 MFA，禁止日常使用，仅用于少数必须 root 才能完成的操作（如更改账户联系信息、关闭账户、更改支持计划）。

Best Practice 速查表

最佳实践说明重要程度
不使用 Root 日常操作创建 IAM Admin 用户代替，Root 仅用于账户级别操作必须
为 Root 和特权用户启用 MFA防止凭证泄露导致账户被控制必须
使用角色而非长期访问密钥EC2/Lambda 应使用 Instance Profile/执行角色，避免在代码中硬编码 Key必须
最小权限原则（Least Privilege）只授予完成任务所需的最小权限，定期回顾必须

使用 IAM Access Analyzer持续检测外部可访问的资源策略强烈建议
利用 Organizations SCP 设置护栏从组织层面限制账户级别操作，防止成员账户绕过治理策略强烈建议

二、IAM Policy 深度解析

SAP-C02 最高频的 IAM 考点。必须理解 6 种策略类型的作用域，以及策略评估的优先级逻辑。

策略类型对比

#策略类型附加对象作用典型例子
1身份策略（Identity-based）
托管策略 / 内联策略		User / Group / Role定义身份能做什么允许 EC2 读取 S3；AWS 托管策略 AdministratorAccess
2资源策略（Resource-based）资源本身（S3、SNS、KMS…）定义谁能访问该资源，支持跨账号授权S3 Bucket Policy、SNS Topic Policy、KMS Key Policy
3权限边界（Permissions Boundary）User / Role限制身份策略能赋予的最大权限上限，不直接授权委托开发者创建角色，但不能提权超过自身权限
4组织 SCP（Service Control Policy）Organizations 账户 / OU设置组织级护栏，限制成员账户可用的最大权限禁止成员账户创建 IAM User；强制所有 S3 开启加密
5会话策略（Session Policy）AssumeRole / GetFederationToken 调用时传入进一步限制本次会话的权限，不能超过角色自身策略开发者 AssumeRole 时，额外限制只能操作特定 S3 前缀
6ACL（Access Control List）S3 对象/存储桶、VPC 子网（网络 ACL）旧型跨账号访问控制，功能有限S3 Object ACL 授予其他账号读取权限（现已不推荐，推荐 Bucket Policy）

对比AWS 托管策略客户托管策略内联策略（Inline）

🔑 Policy 评估逻辑（重点！）

当一个 API 调用到达 AWS，权限评估按以下顺序进行：

1
默认拒绝（Implicit Deny） — 没有任何策略明确允许时，请求被隐式拒绝
2
SCP 检查 — 如果账户在 Organizations 下，检查 SCP 是否明确拒绝。SCP 拒绝 → 直接拒绝，不再检查后续策略
3
资源策略检查 — 如果资源有 Resource-based Policy，且明确 Deny，则直接拒绝
4
权限边界检查 — 如果身份有权限边界，且操作不在边界允许范围内，则拒绝
5
会话策略检查 — 如果是会话，且会话策略不允许该操作，则拒绝
6
显式拒绝（Explicit Deny） — 身份策略中有明确 Deny → 始终优先，无论是否有 Allow
7
显式允许（Explicit Allow） — 上述所有检查均未拒绝，且有明确 Allow → 请求被允许
核心规则：Explicit Deny 始终优先于 Explicit Allow。只有"有 Allow 且无任何 Deny"时请求才被允许。同账号内，同时有身份策略 Allow 和资源策略 Allow，两者满足其一即可（OR 关系）。跨账号时，必须两者都 Allow（AND 关系）。
SCP + 权限边界 + 身份策略的交集才是最终有效权限。三者的权限集合取交集，即使身份策略 Allow，SCP 或权限边界未 Allow，请求也会被拒绝。

同账号 vs 跨账号权限评估

场景身份策略资源策略结果
同账号访问 S3Allow无（或也 Allow）✅ 允许
同账号访问 S3无 AllowAllow✅ 允许（资源策略可独立授权）
跨账号访问 S3账户 A 中 Allow sts:AssumeRole + s3:GetObject账户 B S3 Bucket Policy Allow 账户 A✅ 允许（两侧都需 Allow）
跨账号访问 S3账户 A Allow账户 B 无 Allow❌ 拒绝（缺少资源侧授权）

三、IAM Roles 与 AssumeRole

Role 是 SAP-C02 中最核心的权限机制，几乎所有跨服务、跨账号、联合身份场景都依赖 Role。

Role 的组成

Trust Policy（信任策略）

定义"谁能扮演这个角色（AssumeRole）"。这是 Role 上的资源策略，Principal 字段声明允许的调用者（AWS Service、账号、用户、角色、SAML/OIDC 提供商）。

权限策略（Permission Policy）

定义"扮演这个角色后能做什么"。一个 Role 可以附加多个托管策略和内联策略，决定角色的有效权限集合。

常见 Role 类型

Role 类型Principal（信任方）用途
EC2 实例角色（Instance Profile）ec2.amazonaws.comEC2 实例通过 IMDS 获取临时凭证，代码无需硬编码密钥
Lambda 执行角色lambda.amazonaws.comLambda 函数调用 AWS 服务所需的权限
跨账号角色（Cross-Account Role）另一个 AWS 账号 ID 或 ARN账户 A 的用户/服务扮演账户 B 中的角色，获取 B 的临时凭证
联合身份角色（Federated Identity）SAML IdP / OIDC Provider企业 AD 用户或 Web 应用用户通过联合身份获取 AWS 访问权限
服务链接角色（Service-Linked Role）特定 AWS 服务由 AWS 服务自动创建，预定义权限，不可修改信任策略

记忆口诀：Trust Policy = 谁能"进门"（AssumeRole）；Permission Policy = 进门后能做什么。两者缺一不可。

四、权限边界（Permissions Boundary）

权限边界是 SAP-C02 的高频难点，考察对"限制上限"与"直接授权"的理解。

核心概念

  • 权限边界是附加到 IAM User 或 Role 上的托管策略，定义该身份最多能被赋予什么权限。
  • 权限边界不直接授予任何权限，它只是设定上限。
  • 有效权限 = 身份策略（Identity-based Policy）∩ 权限边界（Permissions Boundary）
  • 权限边界不影响资源策略（Resource-based Policy）对身份的直接授权。
身份策略
实际被赋予的权限
∩
权限边界
允许的最大权限
=
有效权限
实际可执行的操作

主要用途

委托管理（Delegated Administration）

允许开发团队为自己的应用创建 IAM 角色，但不能创建超出自身权限范围的角色（防止权限提升）。管理员设置权限边界作为约束条件。

防止提权（Privilege Escalation Prevention）

即使开发者有 iam:CreateRole 和 iam:AttachRolePolicy 权限，因为权限边界限制，他们无法创建比自己权限更大的角色，从而无法通过创建新角色来提升自身权限。

实际场景示例

场景配置
开发者拥有 S3、DynamoDB、Lambda 的完整权限身份策略：Allow S3/DynamoDB/Lambda *
管理员希望限制开发者只能操作 S3权限边界：Allow S3 *
有效权限S3（身份策略∩权限边界 = S3）；DynamoDB 和 Lambda 实际不可用
区分两个"限制"概念：
• 权限边界（Permissions Boundary）：附加到 User/Role，长期有效，限制该身份在任何会话中的最大权限上限。
• 会话策略（Session Policy）：在 AssumeRole 时临时传入，仅限制本次会话的权限，不影响 Role 本身的永久配置。
两者都不能扩展权限，只能缩减。

五、STS（Security Token Service）

STS 是 AWS 颁发临时安全凭证的服务。理解各 API 的适用场景是考试重点。

STS 主要 API 对比

API适用场景有效期关键特点
AssumeRole扮演 IAM Role（同账号或跨账号）15 分钟 ~ 12 小时（默认 1 小时）最通用的 STS API；需要 Trust Policy 允许调用方
AssumeRoleWithWebIdentity使用 OIDC Token（如 Cognito、Google、Facebook）15 分钟 ~ 1 小时Web 应用 / 移动端联合；推荐使用 Cognito 封装
AssumeRoleWithSAML使用 SAML 2.0 断言（企业 Active Directory）15 分钟 ~ 12 小时（默认 1 小时）企业联合；需要配置 SAML Identity Provider
GetSessionTokenIAM User 在 MFA 验证后获取临时凭证15 分钟 ~ 36 小时为 IAM User 提供短期凭证；常用于 MFA 保护的 API 调用
GetFederationToken为自定义联合代理（Federation Broker）颁发临时凭证15 分钟 ~ 36 小时旧有联合模式；新场景推荐用 AssumeRole 替代
快速记忆：企业 AD / SAML → AssumeRoleWithSAML；Web/移动端 OIDC / Cognito → AssumeRoleWithWebIdentity；MFA 之后操作 → GetSessionToken；跨账号 / 服务间 → AssumeRole。

临时凭证组成

AccessKeyId

临时访问密钥 ID，以 ASIA 开头（永久密钥以 AKIA 开头，可快速区分）。

SecretAccessKey

临时访问密钥，配合 AccessKeyId 使用，签名 AWS API 请求。

SessionToken

会话令牌，必须随每次 API 请求一起发送，是临时凭证的关键特征。

Expiration

凭证过期时间戳，到期后自动失效，需重新调用 STS 获取新凭证。

考试注意：临时凭证不能手动撤销（Revoke）。若需要提前失效，需要修改 Role 的 Trust Policy 或删除 Role（影响所有使用该 Role 的主体）。AWS 也支持通过向 Role 附加内联策略添加 aws:TokenIssueTime 条件拒绝旧令牌（Revoke Sessions 功能）。

  • IdP 将 SAML Token 发送给 AWS STS（AssumeRoleWithSAML）。

Web Identity Federation

方案流程推荐程度
Amazon Cognito Identity Pool（推荐）用户 → Cognito（聚合 Google/FB/Apple/OIDC）→ Cognito 颁发 Token → STS AssumeRoleWithWebIdentity → 临时凭证强烈推荐，SAP-C02 标准答案

Cognito 提供了用户池（User Pool，认证）和身份池（Identity Pool，授权）：

  • User Pool：负责用户注册、登录、MFA，返回 JWT Token（IdToken、AccessToken、RefreshToken）。
  • Identity Pool：将外部身份（User Pool、Google、Facebook 等）映射到 IAM Role，调用 STS 获取 AWS 临时凭证。

OIDC 联合 — EKS IRSA（Service Account 级别权限）

Kubernetes Pod 通过 OIDC 绑定 IAM Role，实现 Pod 级别的细粒度权限控制：

  • EKS 集群配置 OIDC Provider → IAM 中创建对应 OIDC Identity Provider。
  • 为 Kubernetes Service Account 关联 IAM Role（IRSA：IAM Roles for Service Accounts）。
  • Pod 使用该 Service Account 运行 → 通过 Token 自动获取 IAM Role 临时凭证。
  • 优势：Pod 级别最小权限，不同服务使用不同 Role，无需在 Node 上挂载 Instance Profile。

七、IAM 高级特性

IAM Access Analyzer

持续分析资源策略，识别对外部实体（其他账号、互联网）开放访问路径的资源。

功能说明
外部访问分析发现 S3 Bucket、KMS Key、IAM Role、Lambda、SQS、SNS 等资源是否存在公开或跨账号访问路径
未使用的访问（Unused Access）识别 IAM User/Role 中长期未使用的权限和访问密钥，支持最小权限治理
策略验证在创建/编辑策略时，检查策略语法错误和安全建议
与 Organizations 集成设置信任区（Zone of Trust）为整个 Organizations，跨账号访问视为内部，只有互联网访问才告警

条件键（Condition Keys）— 高频考点

条件键用途示例场景
aws:RequestedRegion限制 API 调用只能发生在指定区域只允许在 us-east-1 创建资源
aws:PrincipalTag/<TagKey>基于调用方身份标签控制权限（ABAC）拥有 Team=backend 标签的 Role 才能访问 backend 资源
aws:ResourceTag/<TagKey>基于资源标签控制访问（ABAC）只允许操作带有 Environment=prod 标签的 EC2
aws:SourceIp限制请求来源 IP 或 CIDR只有公司网络 IP 可以调用 API
aws:SourceVpc限制请求必须来自指定 VPCS3 只能从特定 VPC 访问（配合 VPC Endpoint）
aws:MultiFactorAuthPresent要求调用方已通过 MFA 认证删除 S3 对象必须使用 MFA 凭证
aws:MultiFactorAuthAgeMFA 认证经过的时间（秒）MFA 认证超过 1 小时（3600 秒）拒绝敏感操作
sts:ExternalId跨账号 AssumeRole 时验证外部 ID，防止 Confused Deputy 攻击第三方服务扮演你账号中的 Role 时，要求提供约定的 External ID
aws:CalledVia请求是否通过特定 AWS 服务发起只允许通过 CloudFormation 调用某个 IAM 操作

ABAC vs RBAC

对比ABAC（基于属性的访问控制）RBAC（基于角色的访问控制）
核心机制使用标签（Tag）条件键，匹配主体标签与资源标签使用预定义的 IAM Role 和策略控制权限
优势大规模动态场景；新增资源或用户无需修改策略，只需打标签权限清晰可审计；适合稳定权限结构
典型场景多团队 / 多应用；用户能操作与自己 Team 标签相同的资源固定权限结构；开发者、运维、只读审计等明确角色划分
策略数量少量通用策略，靠标签区分可能需要大量策略，每类权限一个策略
SAP-C02 关键词"基于标签"、"减少策略数量"、"动态权限""预定义角色"、"稳定权限"、"明确职责分离"

Service Control Policies（SCP）补充说明

  • SCP 附加到 Organizations 根、OU 或成员账户，限制成员账户内所有主体（包括 Root User）的最大可用权限。
  • SCP 本身不授予权限，只起"护栏"（Guardrail）作用。成员账户还需要 IAM 策略明确 Allow。
  • 管理账户（Management Account）不受 SCP 限制。
  • SCP 影响成员账户中的 Root User，这是 SCP 与其他策略的重大区别。
SCP 常见误区：SCP 不直接授权，只限制上限。成员账户的用户需要同时满足：SCP 允许 + IAM 身份策略允许，才能执行操作。即使 SCP Allow，没有身份策略也无法操作。

八、IAM Policy 编写规范

理解 Policy JSON 的每个字段含义，是正确分析和编写权限策略的基础。

Policy 结构字段解析

{
  "Version": "2012-10-17",  // 策略语言版本，固定使用 2012-10-17，支持策略变量
  "Statement": [            // 语句数组，一个 Policy 可包含多条语句
    {
      "Sid": "AllowCostQueryWithMFA",  // Statement ID，可选的唯一标识符，便于管理和调试
      "Effect": "Allow",               // 效果：Allow（允许）或 Deny（拒绝）
      "Principal": {                   // 适用主体（资源策略/Trust Policy 中使用，身份策略中省略）
        "AWS": "arn:aws:iam::123456789012:user/Alice"
      },
      "Action": [                      // 操作列表，支持通配符 * 和 ?
        "ce:GetCostAndUsage",
        "ce:GetUsageForecast"
      ],
      "Resource": "*",                 // 资源 ARN；* 表示所有资源；应尽量精确指定
      "Condition": {                   // 条件块（可选），所有条件为 AND 关系，同一键多值为 OR
        "StringEquals": {
          "aws:RequestedRegion": "us-east-1"  // 限制只能访问 us-east-1 区域
        },
        "Bool": {
          "aws:MultiFactorAuthPresent": "true"  // 要求调用方已完成 MFA 认证
        }
      }
    }
  ]
}

字段详解

字段必填说明
Version推荐固定写 "2012-10-17"，不写则默认旧版本，不支持策略变量 ${aws:username} 等
Sid否Statement 标识符，唯一（同一 Policy 内），字母数字，便于调试和审计
Effect是Allow 或 Deny。Deny 始终优先于 Allow
Principal资源策略中必填身份策略（附加到 User/Role）中省略；资源策略中指定 AWS 账号、用户、角色或服务
Action是服务前缀:操作名，如 s3:GetObject；可用 * 通配，如 s3:*
NotAction否指定不在列表中的所有操作（反向匹配），配合 Deny 可实现"除这些操作外全部拒绝"
Resource是（部分服务）AWS 资源 ARN；不支持资源级权限的服务用 *
Condition否条件键+运算符+值，多个键为 AND 关系；同一键多个值为 OR 关系

常用 Condition 运算符

运算符适用类型示例
StringEquals字符串精确匹配{"aws:RequestedRegion": "us-east-1"}
StringLike字符串通配符匹配（* 和 ?）{"s3:prefix": ["home/${aws:username}/*"]}
Bool布尔值{"aws:MultiFactorAuthPresent": "true"}
NumericLessThan数值比较{"aws:MultiFactorAuthAge": "3600"}
IpAddressIP 地址/CIDR{"aws:SourceIp": ["203.0.113.0/24"]}
ArnLikeARN 模式匹配{"aws:SourceArn": "arn:aws:s3:::my-bucket"}
Null检查键是否存在{"aws:TokenIssueTime": "false"}（确认不是临时凭证）

九、场景题解析

以下 6 道典型场景题覆盖 SAP-C02 最常见的 IAM 考察方向，配有分析思路和关键答案。

场景 1：用户能访问 S3 但不能删除对象

某用户有 IAM 策略 Allow s3:*，但 S3 Bucket Policy 中有一条 Deny s3:DeleteObject。用户能删除该 Bucket 中的对象吗？

答案：B。显式 Deny（Explicit Deny）始终优先于任何 Allow，无论 Deny 来自身份策略还是资源策略。只要有任何一条策略 Deny，请求就被拒绝。
场景 2：跨账号 EC2 访问另一账号的 DynamoDB

账户 A 中的 EC2 实例需要读取账户 B 中的 DynamoDB 表。最低权限的正确配置是什么？

答案：B。跨账号访问应使用 IAM Role 和临时凭证，永远不要在 EC2 配置其他账户的长期 Access Key。DynamoDB 不支持资源策略（选项 C 错误）。步骤：账户 B 建 Role + Trust Policy 信任账户 A → 账户 A EC2 实例角色允许 sts:AssumeRole → EC2 代码 AssumeRole 获取临时凭证 → 使用临时凭证访问账户 B 的 DynamoDB。
场景 3：开发者可以创建 IAM 角色但不能提权

公司希望允许开发团队为自己的应用创建 IAM Role 并附加策略，但必须确保他们无法创建权限超过自身的 Role（防止权限提升）。如何实现？

答案：C。权限边界是解决委托管理和防提权的标准方案。管理员预定义一个权限边界策略（如只允许 S3、DynamoDB、Lambda），要求开发者在 iam:CreateRole 条件中必须附加该权限边界（iam:PermissionsBoundary 条件键）。开发者创建的 Role 有效权限 = 角色策略 ∩ 权限边界，无法超越权限边界范围。
场景 4：企业 AD 用户通过 SSO 访问 AWS 多账号

一家拥有 50 个 AWS 账户的企业，希望员工使用企业 Active Directory 账号登录，通过统一门户访问不同账户的控制台，并能以不同角色操作。最佳方案是什么？

答案：B。IAM Identity Center 是多账号 SSO 的现代推荐方案。它与 AWS Organizations 集成，连接一个 AD 源（AD Connector 或 AWS Managed Microsoft AD），通过"权限集合"（Permission Sets）统一配置各账号的角色，提供统一 SSO 门户。50 个账户分别配置 SAML（选项 A）运维复杂度极高，不推荐。
场景 5：Lambda 函数需要访问 S3 和 DynamoDB

一个 Lambda 函数需要读取特定 S3 Bucket 中的文件，并写入特定 DynamoDB 表。如何配置最小权限？

答案：B。Lambda 应使用执行角色（Execution Role），Trust Policy 信任 lambda.amazonaws.com。权限策略应精确到具体操作和资源 ARN（最小权限）："Action": ["s3:GetObject"] + "Resource": "arn:aws:s3:::my-bucket/*"；"Action": ["dynamodb:PutItem"] + "Resource": "arn:aws:dynamodb:region:account:table/my-table"。绝不应硬编码密钥或使用 AdministratorAccess。
场景 6：限制只有来自特定 IP 的请求才能访问

公司要求 IAM 用户只能从公司办公网络（IP CIDR 203.0.113.0/24）调用敏感 API。如何配置？

答案：B。IP 限制要通过 IAM Policy 的 Condition 实现："Condition": {"IpAddress": {"aws:SourceIp": ["203.0.113.0/24"]}}。Security Group 和 NACL 是网络层控制，不能限制 IAM API 调用。注意：若用户通过 VPN/NAT 出口 IP 是动态的，需结合 aws:SourceVpc 或 aws:SourceVpce 使用。

已掌握 0 / 20

  • Root Account：立即启用 MFA，不用于日常操作，SCP 无法限制管理账户的 Root
  • Explicit Deny 优先：任何 Deny 优先于所有 Allow，无论策略类型
  • 有效权限公式：SCP ∩ 权限边界 ∩ 身份策略（取交集）
  • 同账号 S3：身份策略 OR 资源策略，满足其一即允许
  • 跨账号 S3：调用方身份策略 AND 目标资源策略，两者都需 Allow
  • Trust Policy：定义谁能 AssumeRole；Permission Policy：定义扮演后能做什么
  • 权限边界：限制 User/Role 的最大权限上限，不直接授权，有效权限 = 身份策略 ∩ 边界
  • 会话策略：AssumeRole 时临时传入，只限制本次会话，不改变 Role 本身
  • 防提权：权限边界 + iam:PermissionsBoundary 条件，要求创建角色时必须附加边界
  • STS 临时凭证：AccessKeyId（ASIA）+ SecretAccessKey + SessionToken，有 Expiration
  • AssumeRoleWithSAML：企业 AD/SAML IdP 用户获取 AWS 临时凭证
  • AssumeRoleWithWebIdentity：OIDC Token 获取临时凭证，新应用推荐经 Cognito Identity Pool 封装
  • Cognito User Pool vs Identity Pool：认证（JWT）vs 授权（AWS 临时凭证）
  • IAM Identity Center：多账号 SSO + AD/OIDC 集成，权限集合（Permission Sets）统一管理
  • IRSA：EKS Pod 级别权限，Service Account 绑定 IAM Role，通过 OIDC 获取临时凭证
  • IAM Access Analyzer：检测外部可访问资源 + 未使用权限分析
  • SCP 护栏：限制成员账户内所有主体（含 Root）的最大权限，管理账户不受限
  • ABAC 关键词：基于标签、减少策略数量、大规模动态 → aws:PrincipalTag + aws:ResourceTag
  • aws:SourceIp：限制请求来源 IP（用于 IAM Policy Condition，不是 SG/NACL）
  • External ID：跨账号 AssumeRole 防 Confused Deputy 攻击，第三方服务必须提供约定的 ExternalId

十四、快速自测

先独立作答，再点击选项查看解析。概念练习题，不代表真实考题。

1. 一个 IAM User 的身份策略允许 s3:DeleteObject，但其权限边界中没有 s3:DeleteObject。该用户能删除 S3 对象吗？
正确答案：B。有效权限是身份策略与权限边界的交集。权限边界中不包含 s3:DeleteObject，该操作被权限边界排除在外，即使身份策略 Allow 也无法执行。
2. 企业有 30 个 AWS 账户，要求所有账户无法在非 us-east-1 区域创建 EC2 实例。应使用哪种方式？
正确答案：B。SCP 是组织级护栏，一条 SCP 即可覆盖所有成员账户的所有主体（含 Root User）。Config 是检测和修复，而非预防性控制。分别配置各账户（选项 A）运维复杂度极高。
3. 移动 App 用户通过 Google 账号登录，需要获取临时 AWS 凭证访问用户专属的 S3 文件夹。推荐架构是什么？
正确答案：B。Cognito Identity Pool 是 Web/移动端联合的推荐方案，可聚合多个社交 IdP（Google/Facebook/Apple），通过 ABAC 配合 aws:PrincipalTag 实现用户只能访问自己的 S3 路径（如 s3://bucket/users/${cognito:username}/）。为每个用户创建 IAM User 不可扩展。
4. 调试时发现 AccessKeyId 以 ASIA 开头，但 API 调用总是返回 InvalidClientTokenId 错误。最可能的原因是？
正确答案：B。ASIA 开头说明是 STS 临时凭证。临时凭证由 AccessKeyId + SecretAccessKey + SessionToken 三部分组成，缺少 SessionToken 或凭证过期都会导致认证失败。检查 SessionToken 是否一并提交，以及凭证是否在有效期内。
5. 一个第三方安全审计服务需要 AssumeRole 访问你账户中的只读角色。如何防止"困惑的代理人"（Confused Deputy）攻击？
正确答案：B。External ID 是解决 Confused Deputy 攻击的标准方案。只允许账户 ID（选项 A）不足够，因为第三方服务的其他客户可能诱导该服务扮演你的角色。External ID 作为双方约定的秘密令牌，第三方不知道 External ID 就无法 AssumeRole。
