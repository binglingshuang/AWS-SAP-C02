一、首先理解网站分层架构

典型 AWS 网站通常分为 Web / Presentation、Application、Database 三层。考试重点是理解每层职责，以及每层如何避免单点故障。

Web / Presentation Layer

接收用户请求、处理 HTTP 请求。

常见服务：CloudFront、ALB、EC2、ECS

Application Layer

执行业务逻辑，处理应用请求。

常见服务：EC2、Auto Scaling、ECS、Lambda

Database Layer

负责数据持久化、查询和事务。

常见服务：RDS、Aurora、DynamoDB

高可用的基本原则

冗余部署、健康检查、自动替换、数据复制、避免单点故障。

每一层如何实现高可用？

层级设计方式关键服务 / 概念
Web 层多个实例接收流量，故障实例不再接收请求ALB、Health Check、Multi-AZ
Application 层多实例部署，故障后自动补充；尽量无状态Auto Scaling、Stateless
Database 层备用节点、复制、自动故障转移RDS Multi-AZ、Aurora
快速记忆：Web 层故障看 Load Balancer；计算实例故障看 Auto Scaling；数据库故障看 Multi-AZ / Aurora；Region 故障看跨 Region DR。

二、Failover 故障转移：考试核心

Failover 是指某个资源发生故障时，将业务自动或手动切换到健康的备用资源，使业务尽可能持续运行。

三个容易混淆的概念

概念含义理解重点
High Availability高可用尽量减少服务不可用时间
Fault Tolerance容错故障发生时仍能持续提供服务
Disaster Recovery灾难恢复大规模故障后恢复业务

故障转移的三个范围

故障范围典型措施考试关键词
单个 InstanceELB 停止向不健康实例发流量；ASG 替换实例Unhealthy EC2、replace instance
整个 AZ跨 AZ 部署；ELB 转发到健康 AZ；数据库 Multi-AZAvailability Zone failure
整个 Region备用 Region、跨区域数据复制、流量切换Regional outage、DR
重要：Multi-AZ 不等于 Multi-Region。Multi-AZ 主要应对可用区故障；Multi-Region 才用于区域级故障恢复。

三、网站入口层：Route 53、Global Accelerator、CloudFront、ELB

1. Amazon Route 53

Route 53 是 DNS 服务，可根据路由策略和健康检查结果，把用户引导到合适的端点。

路由策略用途 / 题干线索
Simple简单路由，单一资源或简单 DNS 响应
Weighted按权重分配流量；灰度发布、流量比例
Latency-based按网络延迟选择端点；全球用户就近访问
FailoverPrimary / Secondary；主站故障后 DNS 切换
Geolocation按用户地理位置路由
Geoproximity按地理距离及偏移量调整流量
Multivalue Answer返回多个健康资源的 DNS 记录

Route 53 Failover 工作机制

用户
  |
Route 53 DNS + Health Check
  |
  +---- Primary Region（健康）----> 用户访问主站
  |
  +---- Primary 不健康 -----------> 返回 Secondary
                                      |
                                Secondary Region
  • 配置 Primary 主站点和 Secondary 备用站点。
  • 健康检查判断主站点状态。
  • 主站点不健康时，DNS 响应引导用户访问备用站点。
考试关键词：Primary / Secondary、Active-Passive、Health Check、Automatic DNS Failover → 优先考虑 Route 53 Failover Routing。

注意：DNS 切换不代表备用 Region 的数据库已自动提升为主库；应用资源、数据复制和数据库提升也必须设计好。

2. AWS Global Accelerator

Global Accelerator 是全球流量入口，通过 AWS 全球网络将用户流量引导至健康的应用端点。

  • 标准加速器提供两个静态 Anycast IP 地址。
  • 支持跨 Region 的端点组、健康检查和流量切换。
  • 适合强调固定静态 IP、全球网络、低延迟和快速流量切换的场景。
对比Route 53Global Accelerator
主要功能DNS 路由全球网络流量入口
静态 Anycast IP不提供 GA 式静态入口 IP提供两个静态 IP
切换方式DNS 响应变化全球网络端点流量切换
典型线索DNS、主备记录、路由策略静态 IP、低延迟、全球加速

注意：自定义路由加速器与标准加速器能力不同；自定义路由加速器不提供标准加速器的健康检查和自动故障转移能力。

3. CloudFront Origin Failover

CloudFront 可以配置 Origin Group，包括 Primary Origin 和 Secondary Origin。当主源站返回配置的特定故障状态时，CloudFront 可以尝试备用源站。

User → CloudFront → Primary Origin
                         |
                 符合故障转移条件
                         |
                   Secondary Origin
  • 适用于源站级故障转移，例如主 S3 源站或主应用源站不可用。
  • 可配置触发故障转移的 HTTP 状态码。
  • 不是所有请求失败都会触发切换；请求方法和状态码等存在限制。
记忆：CloudFront = CDN / 缓存 / 边缘分发；Origin Failover = 主源站故障时切换备用源站。

4. Elastic Load Balancing（ELB）

类型主要用途
ALBHTTP / HTTPS 应用层负载均衡，支持基于路径、主机名等规则路由
NLB高性能网络层负载均衡，支持 TCP、UDP、TLS 等
GWLB将流量分发到网络虚拟设备，例如防火墙设备

ELB 健康检查可以停止向不健康目标转发流量，但 ELB 本身不会自动创建新的 EC2 实例。自动替换实例通常由 Auto Scaling 负责。

四、计算层：EC2 Auto Scaling 高可用

1. Auto Scaling Group（ASG）

ASG 可自动增加或减少实例，并在实例不健康时进行替换。它可以跨多个 AZ 部署，并与 ELB 集成。

参数含义示例
Minimum Capacity最少实例数2
Desired Capacity期望实例数4
Maximum Capacity最大实例数10
             Users
                |
               ALB
             /     \\
           AZ-A    AZ-B
            |        |
          EC2-1    EC2-2
          EC2-3    EC2-4
              \\    /
          Auto Scaling Group

题干关键词：Automatically replace unhealthy EC2 instances、maintain desired capacity、scale out / scale in、multiple AZs → Auto Scaling Group。

2. Stateless vs Stateful

如果用户 Session 只保存在某台 EC2 本地，该实例故障后，用户会话可能丢失。更可靠的做法是把会话状态放到共享存储中。

问题解决方向
Session 存在 EC2 本地将应用设计为 Stateless，避免单实例状态依赖
多个 Web 实例共享 SessionElastiCache for Redis / DynamoDB 等共享存储
故障实例自动补充Auto Scaling
请求分发到多个实例ALB
考试陷阱：Sticky Sessions（会话粘性）只是尽量把用户请求送回同一目标实例；它不能从根本上解决实例故障后的 Session 丢失问题。

五、数据库层：RDS、Aurora 高可用

1. RDS Multi-AZ

              Application
                   |
              RDS Endpoint
                   |
           Primary Database
                AZ-A
                   |
          Synchronous Replication
                   |
           Standby Database
                AZ-B
  • 主数据库和备用数据库部署在不同 AZ。
  • 传统 Multi-AZ DB Instance 部署使用同步复制维护备用副本。
  • 主数据库故障时，RDS 自动故障转移。
  • 应用通常通过同一个数据库端点连接，切换后端点指向新的主实例。
  • 主要目的是高可用，不是读写扩展。

RDS Multi-AZ vs Read Replica

对比Multi-AZRead Replica
主要目的高可用读扩展
复制方式传统单备用部署为同步复制异步复制
自动故障转移支持通常需要手动提升（具体取决于部署与服务能力）
主要用途主库故障恢复分担读请求、提高读取能力
高频判断：Improve database availability / automatic failover → RDS Multi-AZ；offload read traffic / increase read throughput → Read Replica。

注意：RDS Multi-AZ DB Cluster 与传统 Multi-AZ DB Instance 的架构和读取能力不同，答题时要看题目指定的部署类型。

2. Amazon Aurora

Aurora 使用跨多个 AZ 冗余保存的分布式集群存储，并通过 Writer、Reader 实例提供数据库服务。Writer 故障时，可将 Reader 提升为新的 Writer。

Endpoint用途
Cluster Endpoint连接当前 Writer，主要用于写入
Reader Endpoint将读取请求分配到 Reader 实例
Instance Endpoint连接指定的数据库实例

考试记忆：Writer 故障、Reader Promotion → Aurora Failover；读写分离 → Cluster Endpoint + Reader Endpoint。

3. Aurora Global Database

             Primary Region
                   |
              Aurora Writer
                   |
          Cross-Region Replication
                   |
             Secondary Region
                   |
             Aurora Read-only
  • 一个 Primary Region，可配置多个 Secondary Region。
  • 跨 Region 复制数据。
  • Secondary Region 可提供低延迟全球读取。
  • 发生区域级故障时，可以将 Secondary 提升为 Primary。
题干关键词：Cross-region database、global reads、regional disaster recovery、low RPO → 考虑 Aurora Global Database。

跨 Region 复制和提升涉及独立的恢复机制，不要将其理解成传统 RDS Multi-AZ 的本地自动故障转移。

六、Multi-AZ 与 Multi-Region：核心区别

对比Multi-AZMulti-Region
部署范围一个 Region 内多个 AZ多个 Region
主要解决实例、AZ 故障Region 级故障
网络延迟通常较低跨区域通信延迟更高
成本与复杂度通常较低通常更高
典型组件ALB、ASG、RDS Multi-AZRoute 53、Global Accelerator、Aurora Global DB
答题口诀：一个 AZ 出问题，考虑 Multi-AZ；整个 Region 出问题，考虑 Multi-Region。题目只要求 AZ 级高可用时，不要无故选择昂贵的跨 Region 架构。

七、RTO 和 RPO：灾难恢复关键指标

RTO — Recovery Time Objective

恢复时间目标：业务中断后，允许多长时间恢复服务。

例如 RTO = 1 小时，意味着目标是在 1 小时内恢复。

RPO — Recovery Point Objective

恢复点目标：可以接受丢失多长时间范围内的数据。

例如 RPO = 5 分钟，表示最多接受丢失最近约 5 分钟的数据。

四种灾难恢复策略

策略备用资源状态恢复速度相对成本
Backup and Restore主要依赖备份，故障后重建最慢最低
Pilot Light核心数据和少量基础设施持续运行较慢较低
Warm Standby完整但缩小规模的备用环境持续运行较快较高
Multi-site Active/Active多个站点同时处理业务流量通常最快最高

题干关键词速判

关键词优先考虑
Lowest cost；恢复时间较宽松Backup and Restore
Only core infrastructure runningPilot Light
Reduced capacity environment running continuouslyWarm Standby
Both sites actively serving trafficActive/Active
Very low RTO / RPO通常考虑 Active/Active，或满足指标的 Warm Standby
注意：Active/Active 不一定总是最佳答案。还要检查数据复制、写入冲突、业务一致性、成本和题目要求的 RTO/RPO。

九、SAP-C02 高频题型与快速答题技巧

题型 1：Web 服务器发生故障

场景：EC2 实例失败时，网站仍要可用。

判断：多个 EC2 实例；ALB 分发流量；ASG 自动替换不健康实例；最好跨多个 AZ。

优先答案：ALB + Multi-AZ Auto Scaling Group。

题型 2：整个 AZ 发生故障

场景：一个 Availability Zone 不可用，应用仍需服务。

判断：不能只在一个 AZ 部署；计算层跨 AZ；ELB 转发到健康目标；数据库也要有 AZ 级冗余。

优先答案：Multi-AZ + ELB + Auto Scaling + RDS Multi-AZ。

题型 3：数据库主节点故障

场景：要求数据库自动故障转移并尽量减少停机。

判断：重点是自动切换，不是读扩展，也不是从备份手工恢复。

优先答案：RDS Multi-AZ 或 Aurora Failover，依数据库类型判断。

题型 4：全球用户访问网站

场景：全球用户希望低延迟访问并提高可用性。

判断：需要全球流量分配及多 Region 应用部署。按延迟选 Region 可考虑 Route 53 Latency-based Routing；静态 IP、AWS 全球网络和快速流量切换可考虑 Global Accelerator。

题型 5：主 Region 故障，切换备用 Region

场景：主区域不可用时将用户引导到备用区域。

判断：跨 Region 应用资源、健康检查、流量切换、数据复制和数据库提升缺一不可。

选择方向：Route 53 Failover 或 Global Accelerator + 跨 Region 数据复制（例如 Aurora Global Database）。

题型 6：要求极低 RTO 和 RPO

场景：区域故障后要求近乎无停机、数据损失极少。

判断：Backup and Restore 通常不符合；评估 Warm Standby 或 Active/Active；必须检查复制延迟、切换步骤与数据一致性。

十二、真正考试时的五步解题法

  1. 故障范围是什么？ 单台 EC2、整个 AZ，还是整个 Region？
  2. 故障发生在哪一层？ Web、Application、Database，还是 DNS / Network？
  3. 要求自动还是手动恢复？ Automatic Failover、Manual Failover，还是 Automatic Scaling？
  4. 数据能否丢失？ RPO 是否为 0？是否允许少量数据丢失？是否需要同步复制？
  5. 成本与恢复速度哪个更重要？ 最低成本通常考虑 Backup and Restore；更快恢复考虑 Warm Standby；极低停机时间可考虑 Active/Active。
核心解题逻辑：先确定故障范围，再确定故障层级，然后根据自动化要求、RTO/RPO 和成本筛选服务组合。不要只因为题目出现某个服务名称就直接选它。

十三、模拟练习题

单选题 一家公司在 AWS 上运行一个三层 Web 应用程序。应用部署在一个 Region 中，Web 和 Application 层使用 EC2，数据库使用 Amazon RDS。

公司要求：

  • 如果一个 Availability Zone 发生故障，网站仍然能够正常访问。
  • EC2 实例发生故障时能够自动替换。
  • RDS 主数据库发生故障时能够自动切换。
  • 尽可能减少架构复杂度和额外成本。

哪种架构最符合要求？

正确答案：B。

  • 多个 AZ 部署 EC2：应对 AZ 故障。
  • ALB：将请求分发到健康实例。
  • Auto Scaling：自动替换不健康实例。
  • RDS Multi-AZ：数据库自动故障转移。

C 可以提供更高级别的区域灾难恢复，但题目没有要求 Region 级容灾，增加了不必要的成本和复杂度。
