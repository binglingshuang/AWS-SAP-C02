Amazon EMR
托管大数据框架与集群 — SAP-C02

EMR 运行 Spark、Hadoop、Hive 等大数据框架。选型关键是部署形态、节点角色、Spot 中断容忍度，以及将可重建计算与持久化 S3 数据分离。

一、部署形态与框架

形态适合场景主要权衡
EMR on EC2（集群）需控制实例/引导配置、长期或定制化集群。团队管理容量、节点和集群生命周期。
EMR Serverless按作业运行 Spark/Hive、无需维护集群基础设施。配置作业容量/并发；框架与自定义需求需验证支持。
EMR on EKS在 EKS 上运行 EMR Spark 工作负载，共享 Kubernetes 平台。需 EKS/容器运维能力并规划隔离、调度与权限。

EMR 提供托管框架和集群集成，不意味着应用代码、数据模型、成本和所有底层运维都自动消失。

二、节点角色、Spot 与 S3 数据湖

  • Primary node：协调集群和管理作业；避免将其当作可随意中断的工作节点。
  • Core nodes：运行计算并通常承载 HDFS 存储。移除 core 节点需考虑 HDFS 副本和数据安全。
  • Task nodes：增加计算容量但不存储 HDFS 数据，适合可中断/可替换任务；Spot 常用于可容错的 task capacity。
  • EMRFS 允许 Hadoop 框架访问 S3；将原始/持久化数据放 S3，可让计算集群销毁后数据仍保留。HDFS 更适合临时中间数据/缓存。
  • EMR Managed Scaling 或自动扩缩可调整容量；设置上限、扩缩策略和作业并发以约束成本。
Spot 原则：把可中断 Spot 放在可重试的任务容量上；对必须长期可用的协调/状态或非容错组件保留稳定容量，并设计 checkpoint/重试。

三、容量、高可用与作业生命周期

  • Instance Groups 配置简单；Instance Fleets 可按多种实例类型/采购选项请求容量，提高容量可得性但需要理解 fleet 策略。
  • Primary 节点故障行为取决于集群配置/版本；规划高可用、作业恢复与状态持久化，不要把多节点集群等同于作业无中断。
  • Bootstrap actions 安装定制软件，应用配置控制框架设置；固定 AMI/发行版和版本以保证可重复部署。
  • 长作业应将 checkpoint、输出数据和临时文件放到适当持久化位置；终止保护是防止意外终止的操作护栏，不是备份。
  • 用步骤/作业状态、CloudWatch 指标和日志定位 pending、资源不足、失败及慢任务；按需启用调试信息并管理日志保留成本。

四、安全、网络与费用

  • 集群位于 VPC 子网，安全组和路由决定节点间通信及访问 S3/外部源的路径；私有子网需规划 NAT 或服务端点。
  • EC2 instance profile、EMR service role、作业运行时角色职责不同；按服务角色、节点角色和用户隔离最小权限。
  • 使用安全配置启用静态/传输加密、Kerberos 或访问控制（按发行版与框架支持）；机密凭证由 Secrets Manager 等管理。
  • EC2 计算、EBS、S3、日志和数据传输共同构成费用；临时集群按作业结束终止，S3 负责数据持久化。

五、场景题解析

场景一：Spark 作业负载波动，不想维护常驻集群

作业可拆分提交，框架需求在托管能力范围内。

方向：评估 EMR Serverless，按作业运行并配置并发/容量上限。
无需常驻 EC2 集群，适合间歇作业。
如需复杂底层定制或长驻集群控制，应评估 EMR on EC2。

场景二：批处理可重试但预算需降低

计算任务可被中断，核心数据需稳定。

方向：用 Spot 增加可容错 task 节点，保留可靠的协调/core 容量并实现作业重试。
Spot 适合可替换计算容量，而非无保护地承载唯一数据。
将核心 HDFS 数据全放在易中断节点可能造成作业/数据风险。

场景三：集群终止后分析数据必须保留

当前团队把业务输出写入 HDFS。

方向：将持久化数据和作业输出写入 S3（EMRFS），只将 HDFS 用于临时数据。
计算集群生命周期与数据生命周期解耦。
HDFS 不应被当作集群销毁后的长期数据湖。

场景四：固定实例类型在特定 AZ 经常无法获得

批处理允许不同实例族完成同类工作。

方向：评估 Instance Fleets、多实例类型和采购选项，放宽容量选择。
更丰富的实例/可用区选择可提升获得容量的机会。
不是简单提高期望实例数就能解决容量不足。

场景五：EMR 节点无法访问 S3 私有数据

集群部署在无公网访问的私有子网。

方向：检查 S3 Gateway Endpoint/路由、bucket policy、KMS 与实例/作业角色。
网络、IAM、bucket 与 KMS 策略都可能阻断访问。
开放 SSH 或更换实例类型不会修复 S3 授权。

场景六：希望在现有 Kubernetes 平台运行 Spark

团队已有 EKS 运维和资源隔离体系。

方向：评估 EMR on EKS，将 EMR 工作负载提交至 EKS virtual cluster。
此选项让 EMR Spark 与现有 Kubernetes 平台集成。
若不需要共享 K8s 平台，EMR Serverless/EC2 可能更简单。

七、考前速记卡

已掌握 0 / 18

  • EMR 托管 Hadoop/Spark/Hive 等框架。
  • EC2、Serverless、EKS 是不同部署模型。
  • Primary 节点负责协调管理。
  • Core 节点可承载 HDFS 数据。
  • Task 节点提供计算而不存 HDFS 数据。
  • Spot 更适合可中断 task capacity。
  • Spot 需要重试与容错设计。
  • S3/EMRFS 适合持久化数据湖。
  • 集群 HDFS 适合临时处理中间数据。
  • 集群销毁前将输出落到持久化存储。
  • Managed Scaling 仍需容量上限和策略。
  • Instance Fleets 可混合实例类型/选项。
  • Bootstrap action 用于启动时定制。
  • 终止保护不是备份或高可用机制。
  • EMR service role 与节点/作业角色分工不同。
  • 私有子网需规划 S3 endpoint 或 NAT。
  • 安全配置可管理加密和认证选项。
  • EC2、EBS、S3 和日志都影响成本。

八、快速自测

1. EMR 中哪类节点常用于可中断的纯计算扩容？

Task nodes，常配合 Spot 和作业重试。

2. 如何让集群终止后数据仍保留？

将持久化数据写入 S3，而非仅保留在集群 HDFS。

3. 已有 EKS 并希望在其上运行 EMR Spark，应评估什么？

EMR on EKS。
