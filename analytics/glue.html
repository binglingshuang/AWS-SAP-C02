一、Glue 在数据湖中的位置

AWS Glue 是托管的数据集成服务：Glue Data Catalog 保存数据库、表、分区和 schema 等元数据；ETL Job 读取源数据并转换/写入目标。数据本身通常仍位于 S3、数据库或流服务中。

常见链路：S3 原始区 → Crawler / Catalog → Glue ETL 清洗 → S3 分析区（Parquet）→ Athena 或 Redshift Spectrum 查询。Catalog 可被 Athena、EMR、Redshift Spectrum 等使用。

易错点：删除 Catalog 表通常删除的是元数据，不等同于删除其指向的 S3 对象；资源清理和数据生命周期需分别设计。

二、Data Catalog、Crawler 与 schema

组件职责考试判断
Database / Table在 Catalog 中组织数据集元数据；表描述 location、格式、列和分区。不是存储引擎，也不搬运数据。
Crawler访问数据源、推断格式/schema，并创建或更新 Catalog 定义及分区。需有数据源读取权限和 Catalog 写权限；schema 变化仍需评估兼容性。
手动定义按已知 schema 建表，或由 ETL/基础设施流程维护。对稳定且有契约的数据可减少扫描和不受控推断。

Crawler 可通过配置识别 S3 路径和分区；相似目录可能被组合成表，也可通过分类器扩展格式识别。定期运行 Crawler 是元数据更新策略，不代表它持续实时监控文件。

三、ETL Job、Bookmark 与工作流

  • Job 可使用 Spark、Python shell 等执行环境；选择运行时、worker、并发与超时以匹配转换负载。Glue Studio 可视化编辑不改变底层权限和数据质量责任。
  • Job Bookmark 记录已处理数据的进度，适合增量处理受支持的数据源；需启用并正确设置 transformation context。它不是通用事务日志，也不能保证任意目标写入 exactly-once。
  • 重跑、重置或回退 Bookmark 前先确认目标写入是否幂等；Bookmark 状态与目标数据状态不是一个原子事务。
  • Triggers / Workflows 可编排 Job、Crawler 和条件依赖；事件或计划触发应处理重试、并发和重复运行。
增量设计：Bookmark 减少重复读取；目标端仍应使用幂等写入、分区覆盖或去重键，避免失败重试产生重复结果。

四、权限、网络与治理

  • Glue Job 执行角色需要对源、目标、Catalog、日志以及所用密钥具备最小权限；创建 Job 的操作者权限与 Job 运行角色是不同边界。
  • 访问 VPC 内数据源时配置连接、子网、安全组、DNS/路由和端点；Glue 执行环境能访问 S3 不代表能连通私有数据库。
  • 跨账号共享 Catalog 可结合 Lake Formation 权限和资源共享；消费者仍需具备查询服务、底层数据位置和加密密钥所需权限。
  • 使用 CloudWatch Logs/metrics 诊断失败；Secrets Manager 保存凭证，避免硬编码到脚本。对敏感字段实施分类、脱敏和访问控制。

五、场景题解析

场景一：新 S3 数据到达后，自动发现表结构供 Athena 查询

团队不想手工录入 schema，目录结构会新增分区。

方向：配置有读取权限的 Glue Crawler，将结果写入 Data Catalog；Athena 使用该 Catalog 表。
Crawler 负责推断/更新元数据；数据仍在 S3。
不要把 Glue Catalog 当成数据副本，也不要假设 Crawler 实时触发。

场景二：每天处理新增对象，不重复扫描旧数据

源为支持 Bookmark 的数据源，作业需按日增量运行。

方向：启用 Job Bookmark，配置稳定的 transformation context，并在目标端实现幂等。
Bookmark 追踪读取进度，但不是源到目标的分布式事务。
只启用 Bookmark 不能防止目标端重复写入或处理错误的回放。

场景三：schema 改变后 Athena 仍看不到新列

对象已写入新字段，但表定义未更新。

方向：重新运行/调整 Crawler 或更新 Catalog 表定义，验证兼容性和分区。
查询引擎依据元数据解释数据；新对象不保证自动更新表 schema。
不要先重建 S3 数据；确认实际文件格式和 Catalog 定义。

场景四：ETL Job 需读取私有子网中的关系数据库

作业在默认网络无法连接源数据库。

方向：配置 Glue Connection、正确子网/安全组、路由/DNS，并给 Job 角色相应凭证与数据库权限。
网络可达性、身份授权、数据库授权需分别排查。
仅添加 IAM 数据库权限无法创建网络路径。

场景五：Crawler 运行成功但无法读取加密数据

S3 使用客户管理 KMS 密钥加密。

方向：为 Crawler 执行角色授予 S3 读取和 KMS 解密权限，并检查密钥策略。
IAM 身份策略和 KMS key policy 都可能形成授权边界。
Catalog 写权限不能替代源数据读取或密钥解密权限。

场景六：作业失败后重跑导致目标重复行

源 Bookmark 已推进，但目标写入部分成功。

方向：为目标设计幂等键、去重或可重复执行的分区覆盖，并建立失败恢复流程。
源端增量状态与目标写入不是原子提交。
不要将 Bookmark 误认为端到端 exactly-once 保证。

八、快速自测

1. Glue Catalog 是否保存 S3 表的实际数据？

否；它保存表、schema、分区和位置等元数据。

2. Bookmark 能否保证 ETL 输出 exactly-once？

不能；目标写入应另行设计幂等和恢复策略。

3. Crawler 的作用是什么？

访问数据源并推断/更新 Catalog 元数据，不是 ETL 数据复制器。
