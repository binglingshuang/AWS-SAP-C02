Amazon MSK
托管 Apache Kafka — SAP-C02

MSK 托管 Apache Kafka 集群基础设施，保留 Kafka API、生态和消费模型。常见架构判断：团队已有 Kafka 技能/应用时选择 MSK；若只需 AWS 原生托管流摄取和投递，可比较 Kinesis。

一、MSK 部署模式

选项运维/容量特点适合场景
MSK Provisioned选择 broker 类型/数量并管理集群容量、存储和 Kafka 参数。需要更明确的容量控制、稳定负载或特定 broker 配置。
MSK ServerlessAWS 管理集群容量扩展，按使用量计费；仍需治理主题、分区、生产者/消费者与配额。希望减少 broker 管理、负载变化且能力/配额适配的 Kafka 工作负载。

两者均以 Kafka 兼容 API 为核心；“托管”不意味着应用不需要理解 Kafka 分区、复制、消费者组、延迟和数据保留。

二、Topic、分区、复制与消费者

  • Topic 被拆分为 partitions；partition 是并行和顺序边界。相同 key 通常路由到相同分区，消费者组中一个分区在同一时刻由组内一个消费者处理。
  • Replication factor 决定副本数；ISR/leader 选举和 broker 可用区分布影响可用性。分区过多会增加 broker/控制面开销和恢复时间。
  • Kafka 消费者通过 offset 追踪进度；重放可从保留期内 offset 再读。应用需设计重复、乱序和提交 offset 的处理语义。
  • 跨区域/集群迁移可评估 MSK Replicator 或 Kafka MirrorMaker 等工具；要规划主题、offset、消费者切换、网络和双写一致性。

三、MSK Connect、网络与安全

  • MSK Connect 运行 Kafka Connect connector，将 Kafka 数据与外部系统集成；规划 worker 容量、插件、扩缩、失败处理和目标端限流。
  • 集群部署在 VPC 子网，客户端需路由、安全组、DNS 和匹配的 bootstrap broker endpoint；跨账号/本地数据中心需要网络与身份两侧协同。
  • 按集群配置选择 IAM、SASL/SCRAM 或 TLS 客户端认证，并启用传输/静态加密；认证通过后仍需 Kafka ACL/授权配置（取决于认证模式）。
  • MSK cluster policy 适用于跨账号访问控制；IAM role、资源策略、Kafka ACL、KMS key policy 和网络规则不可互相替代。
  • 监控 broker/分区状态、存储、生产/消费速率、consumer lag 和连接错误；lag 增长时检查消费者吞吐、分区并行度和下游瓶颈。

四、MSK 与 Kinesis 选型

维度Amazon MSKKinesis Data Streams
协议/生态Kafka API、Kafka Connect 和现有 Kafka 工具链。AWS Kinesis API 与原生消费者集成。
运维Provisioned 需管理容量/主题等；Serverless 减少 broker 运维。On-Demand/Provisioned 管理流吞吐；无需管理 Kafka broker。
迁移匹配希望保留 Kafka 应用、客户端、生态和操作模型。新建 AWS 原生流管道、优先托管服务集成。
共同责任分区/键设计、消费进度、错误重试、数据保留、授权和下游容量均需规划。

五、场景题解析

场景一：现有 Kafka 应用需迁入 AWS 且尽量少改代码

大量客户端和 Kafka Connect 插件依赖 Kafka API。

方向：评估 MSK Provisioned 或 Serverless，按集群/应用对配置和容量的要求选型。
保留 Kafka 协议和生态降低迁移改造。
不能仅因 AWS 托管就假设所有客户端配置/插件无需兼容验证。

场景二：希望 Kafka API 但不管理 broker 扩缩

团队负载变化大，且处于 MSK Serverless 配额范围。

方向：评估 MSK Serverless，并验证网络、功能支持、并发与使用成本。
Serverless 减少 broker 容量运维。
仍要设计 Kafka topic、分区、消费者组和访问控制。

场景三：AWS 服务需持续向 S3 写入简单流数据

没有 Kafka 客户端或生态依赖，优先少运维。

方向：比较 Kinesis Data Streams / Amazon Data Firehose，而非为兼容性引入 Kafka 集群。
Kinesis 可能更直接满足原生摄取或托管投递需求。
MSK 并非所有 AWS 流场景的默认最低运维方案。

场景四：消费者落后，consumer lag 持续增长

生产速率高于消费者持续处理能力。

方向：检查消费者吞吐、分区数/并行度、下游限流及重平衡；再决定扩消费者或重构。
Kafka 的并行消费受分区数量约束，瓶颈也可能在下游。
只扩 broker 未必提升消费者处理能力。

场景五：Kafka Connect 把主题数据同步到外部系统

希望托管 connector worker 生命周期。

方向：使用 MSK Connect，配置受支持 connector 插件、worker 容量、权限和目标连接。
MSK Connect 托管 Kafka Connect worker。
connector 本身的 schema、目标限流和失败处理仍需运维。

场景六：本地客户端无法连接私有 MSK cluster

客户端拿到了 broker endpoint，但连接被拒绝。

方向：检查 VPN/Direct Connect 路由、DNS、broker 子网安全组，再确认认证机制与 ACL。
endpoint 可见不代表网络通路和身份授权正确。
仅轮换密码不能修复安全组或路由问题。

七、考前速记卡

已掌握 0 / 18

  • MSK 是托管 Apache Kafka 服务。
  • Provisioned 对容量/配置控制更明确。
  • Serverless 减少 broker 容量运维。
  • Serverless 仍受功能与配额边界约束。
  • Topic 由多个 partition 并行处理。
  • Partition key 决定路由和顺序范围。
  • 消费者组按分区分配消费工作。
  • Offset 追踪消费进度并支持保留期内重放。
  • 分区数量影响消费并行度。
  • 副本和 AZ 分布影响可用性。
  • MSK Connect 托管 Kafka Connect workers。
  • 网络安全组和 DNS 决定 broker 可达性。
  • IAM/SCRAM/TLS 是可选认证方式。
  • 认证和 Kafka 授权是不同检查点。
  • 跨账号还需资源策略及身份授权。
  • Consumer lag 反映消费进度落后。
  • Kafka 迁移要验证客户端和插件兼容性。
  • 无 Kafka 生态依赖时比较 Kinesis 简化架构。

八、快速自测

1. 需要 Kafka API 兼容且沿用现有生态，应评估什么？

Amazon MSK。

2. Consumer lag 上升，优先看什么？

消费者能力、分区并行度、重平衡和下游瓶颈。

3. MSK Connect 提供什么？

托管 Kafka Connect worker 以运行 source/sink connector。
