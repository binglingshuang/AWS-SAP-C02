Amazon Kinesis
实时流摄取、投递与处理 — SAP-C02

一、流服务选型

服务解决的问题控制/运维边界
Kinesis Data Streams (KDS)持久化流摄取；多个消费者独立读取、回放或自定义处理。选择 On-Demand / Provisioned；管理消费者并关注分片/吞吐。
Amazon Data Firehose（原 Kinesis Data Firehose）托管缓冲、可选转换并近实时交付到支持目标。无需管理分片/消费者；配置目标、缓冲、重试和备份。
Amazon Managed Service for Apache Flink连续、有状态的流转换、窗口和事件时间处理。提交 Flink 应用；管理代码、状态、容量和检查点策略。

把“先持久化供多个消费者各自处理”匹配 KDS；把“最少运维直接交付到 S3/分析目标”匹配 Firehose；把“状态化实时计算”匹配托管 Flink。

二、Data Streams：分片、顺序与 EFO

  • 记录由 partition key 映射到 shard；同一分区键记录落在同一分片，可保持该键范围内的顺序。热点键会形成热分片。
  • Provisioned 模式按 shard 配置读写吞吐，扩缩分片需规划；On-Demand 自动适应流量变化，但仍受服务配额、突发能力和账户限制约束。
  • Enhanced Fan-Out 为注册消费者提供专用读取吞吐与较低延迟，适合多个消费者竞争共享读取带宽的场景；会增加消费者成本。
  • 默认保留期为 24 小时，可按需延长（最长范围及费用依当前配额/定价）；消费者需跟上保留窗口，否则记录过期。
  • Lambda 事件源映射可消费 KDS，需配置批处理、重试/失败目的地和并行度，并处理至少一次投递导致的重复。
容量记忆：Provisioned 单 shard 常用考试基线为写入 1 MB/s 或 1,000 records/s、读取共享 2 MB/s；实际上限和模式细节以当前服务配额为准。EFO 是独立消费者读取能力，不是提高分片写入容量。

三、Data Firehose 与 Managed Flink

  • Firehose 可缓冲后投递到 S3、Redshift、OpenSearch Service、受支持的第三方/HTTP 目标等；支持配置转换、压缩、格式转换、失败备份等能力（按目标支持范围配置）。
  • 缓冲按大小/时间触发；增大缓冲可减少小对象但提高可见延迟。Firehose 面向投递，不提供 KDS 那样由多消费者独立读取和长期回放的体验。
  • 托管 Flink 适合窗口聚合、状态维护、事件时间和连续计算；从 KDS/Kafka 取数，再写入流或分析目标。Checkpoint/savepoint 用于状态恢复/维护，端到端语义取决于 source/sink 配置。
  • 原 Kinesis Data Analytics SQL 应用应注意产品迁移/可用性说明；新设计优先按当前托管 Flink 能力和官方迁移文档核实。

四、可靠性、网络与权限

  • 生产者、消费者使用 IAM 最小权限；跨账号使用资源策略/角色授权，并分别检查加密密钥访问。
  • KDS 可启用服务端加密；Firehose 目标需有写入角色、目标资源授权和必要的 KMS 权限。
  • 对重复记录实施幂等处理；消费者使用 checkpoint/offset 进度，设计重试、死信/失败备份和告警。
  • 跨 AZ 高可用不等于跨 Region 灾备；用跨区域复制、双流或托管复制方案时明确顺序、去重、RPO/RTO 和成本。

五、场景题解析

场景一：多套消费者都要独立读取并可回放事件

数据落入 S3 前还要由不同团队各自处理。

方向：用 KDS 保留流，按消费者需求读取；若读吞吐竞争严重，评估 EFO。
KDS 为多消费者读取和回放提供持久化流。
Firehose 面向托管投递，不是通用的多消费者回放总线。

场景二：日志无需自管消费者，直接进入 S3

可接受短暂缓冲，运维团队希望最少。

方向：选 Data Firehose，设置目标、缓冲、格式转换和失败备份。
托管交付降低分片和消费者管理。
Firehose 缓冲会带来可见性延迟，不是逐条同步写入。

场景三：交易流需要按用户做滚动窗口聚合

要维护状态并对事件时间窗口计算。

方向：使用 Managed Service for Apache Flink，并设计状态恢复与输出幂等。
状态化连续计算是 Flink 的匹配点。
Firehose 的格式转换不是有状态窗口计算。

场景四：单个客户键流量突增，延迟飙升

整体分片数增加后该键仍集中在同一分片。

方向：重新设计 partition key，提升基数并均衡热点；评估聚合/拆分键策略。
增加分片不会自动把一个热键拆散。
盲目扩容整体 shard 无法消除单键热点。

场景五：多个低延迟消费者抢同一流读取容量

每个消费者都需稳定读取吞吐。

方向：评估 Enhanced Fan-Out，为消费者提供专用读取吞吐。
EFO 改善读取竞争与延迟，但会产生额外费用。
EFO 不扩充生产者写入吞吐。

场景六：Lambda 重试后下游出现重复业务记录

消费失败会重试同一批次。

方向：为消费处理和目标写入实现幂等，配置批次错误处理和失败目的地。
重试可能重复交付，业务逻辑不能假定 exactly-once。
仅扩大 shard 不解决重复写入或失败恢复问题。

  • Firehose 托管缓冲、转换与目标交付。
  • 托管 Flink 处理状态化连续流计算。
  • Firehose 曾名 Kinesis Data Firehose。

  • 同一分区键在分片内保持顺序。

八、快速自测

1. 需要托管直接把流写入 S3，最少自管组件选什么？

Amazon Data Firehose。

2. 为什么增加总 shard 数未必解决单个 partition key 延迟？

同一 key 仍映射到同一 shard，需均衡 key 分布。

3. 多消费者需低延迟独立读吞吐可评估什么？

Enhanced Fan-Out。
