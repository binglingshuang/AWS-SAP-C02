Amazon QuickSight & AWS Lake Formation
BI 可视化与数据湖权限 — SAP-C02

QuickSight 面向 BI 数据集、分析和仪表板；SPICE 加速内存数据集，Direct Query 保持查询数据源。Lake Formation 集中管理 Glue Catalog 数据湖访问，常与 Athena 及跨账号共享配合使用。

一、QuickSight 数据集与 SPICE

模式/对象行为适合情况
SPICE数据集载入 QuickSight 的内存引擎；需刷新以更新数据。交互快、重复分析、隔离查询负载。
Direct Query可视化请求查询底层数据源（能力依连接器和源服务）。需要较新数据，且源端可承受并发查询。
Analysis / DashboardAnalysis 用于作者构建；发布 Dashboard 供读者消费。分离创作与共享使用。

SPICE 的刷新频率、容量和数据新鲜度需要治理；增量刷新仅适用于满足数据源与数据集条件的配置。Direct Query 并不保证实时，也会将并发和成本传递给数据源。

二、QuickSight 用户与数据权限

  • QuickSight 用户/群组/命名空间控制平台内的共享与访问；数据集权限和底层数据源权限仍需分别配置。
  • 行级安全（RLS）按用户/群组映射过滤记录；列级安全（CLS）限制可见字段。过滤策略需与分析、导出、嵌入等实际使用路径验证。
  • 服务角色需获得访问 Athena、S3、Glue Catalog、Lake Formation 和密钥的权限；只共享 Dashboard 不会自动授予底层数据授权。
  • 分析隔离和多租户访问要测试身份属性、过滤映射、缓存及导出边界，避免仅依赖前端筛选。

三、Lake Formation 数据湖治理

Lake Formation 在 Glue Data Catalog 与底层 S3 数据之上集中管理数据湖权限，可按数据库、表、列以及支持的行/单元格过滤等粒度授权；还支持基于 LF-Tag 的权限治理。

  • 数据湖管理员注册 S3 数据位置，授权主体执行 Catalog 操作和数据读取；注册位置通常涉及 Lake Formation service-linked role 或配置的访问角色。
  • Athena 等查询服务要通过 Lake Formation 授权，同时确保调用者可使用查询服务并能写查询结果。
  • LF 权限与 IAM、S3 bucket policy、KMS key policy 并行生效。混用 IAM-only 与 Lake Formation 模式时需明确权限路径，避免“有 IAM 但无 LF grant”导致拒绝。
  • 为现有数据接入时盘点 Catalog 表、S3 位置、加密方式、跨账号主体和已存在的 bucket 授权，再逐步启用治理。

四、跨账号共享与权限链

  1. 生产者账号在 Lake Formation 授予消费者账号/主体数据权限，并配置需要的跨账号共享机制（常与 AWS RAM 集成）。
  2. 消费者接受共享资源后，在本账号创建/使用资源链接，将共享 Catalog 数据库或表映射到本地查询上下文。
  3. 查询身份仍需获得 Athena/QuickSight 等调用权限、Lake Formation grant、底层 S3/KMS 访问和结果位置写入权限。
  4. 采用 LF-Tag 跨账号授权时确保标签策略、资源共享和接收端解析均按服务当前支持方式配置。
权限链：QuickSight 用户授权 ≠ 数据集可读 ≠ Catalog/Lake Formation grant ≠ S3/KMS 可访问；逐层验证而不是扩大单一 IAM 权限。

五、场景题解析

场景一：仪表板需交互快速，数据每小时刷新可接受

底层查询成本较高，报表不要求实时。

方向：将数据集导入 SPICE，设计计划刷新并监控容量/刷新失败。
SPICE 适合快速重复交互，需接受刷新延迟。
SPICE 不会自动实时同步源数据。

场景二：报表必须从底层获取最新数据

源支持相应 QuickSight connector，容量能承受用户查询。

方向：评估 Direct Query，并对源端并发、延迟和费用压测。
查询由底层数据源执行，可减少导入副本的新鲜度延迟。
Direct Query 不是无成本，也不保证所有源均即时一致。

场景三：每个分析师只能看到自己负责区域的行

共享分析模型，但数据需按用户动态隔离。

方向：配置 QuickSight 行级安全规则并用真实用户身份验证。
RLS 根据身份/群组过滤记录；CLS 可另行隐藏列。
仅在图表中添加筛选条件不是授权边界。

场景四：多个业务账号需用 Athena 读取中央 S3 数据湖

希望在中央账号治理表和列权限。

方向：用 Lake Formation 管理 Catalog/S3 权限，跨账号共享后由消费者侧建立资源链接。
数据仍在拥有者数据位置，元数据和授权通过共享机制传递。
仅共享 Glue 表不会自动赋予 S3、KMS 和查询结果权限。

场景五：Lake Formation 已授权但 Athena AccessDenied

表可以看到，但查询源文件失败。

方向：检查 LF 数据权限、注册位置角色、S3 bucket policy、KMS 解密以及查询结果桶授权。
Catalog 可见不意味着对象可读或结果可写。
不要直接给全账号 S3 管理权限来绕过细粒度治理。

场景六：QuickSight 可打开 Dashboard，但刷新数据集失败

作者有仪表板权限，服务角色未能读 Athena 表。

方向：为 QuickSight 服务角色分别配置数据源、Catalog/LF、S3/KMS 读取和结果位置权限。
Dashboard 分享与 SPICE 刷新服务身份的权限职责不同。
给 Dashboard Reader 加权限不能修复后台刷新角色授权。

六、关键词速查

七、考前速记卡

已掌握 0 / 18

  • SPICE 是 QuickSight 内存数据集引擎。
  • SPICE 数据依刷新更新而非自动实时同步。
  • Direct Query 将查询下推到底层数据源。
  • Direct Query 会占用源端查询容量。
  • Analysis 用于作者构建，Dashboard 用于发布消费。
  • RLS 按主体过滤数据行。
  • CLS 限制可见列。
  • QuickSight 用户共享与源数据授权分开管理。
  • Lake Formation 集中治理数据湖权限。
  • LF 权限可作用于 Catalog 数据集。
  • LF-Tag 支持基于标签的授权模型。
  • 注册 S3 位置以纳入 Lake Formation 管理。
  • Catalog 可见不等于 S3 对象可读。
  • IAM、LF、S3 和 KMS 权限需共同满足。
  • Athena 查询结果桶需要单独写权限。
  • 跨账号共享可使用 AWS RAM 集成。
  • 消费者资源链接映射共享 Catalog 资源。
  • SPICE 刷新角色和 Dashboard Reader 权限不同。

八、快速自测

1. 需要高交互速度且可定时刷新，优先评估什么？

QuickSight SPICE。

2. Lake Formation 授权表后，Athena 是否必然可读底层 S3？

不一定；仍需核查数据位置角色、S3/KMS 和结果桶权限。

3. QuickSight RLS 与 CLS 分别控制什么？

RLS 控制行，CLS 控制列。
