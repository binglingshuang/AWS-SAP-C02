一、 SAP-C02 维度对比矩阵

在 SAP-C02 考试中，系统架构的可靠性 (Reliability) 和 解耦 (Decoupling) 是高频考察点。理解两者机制上的差异是做对选择题的前提。

二、 考试高频架构：SNS + SQS 扇出模式 (Fan-out)

核心应用场景：一次发布，并行异构处理 + 容错削峰

场景描述：某个关键业务事件发生（如“订单生成”），需要同时触发多个逻辑独立的服务（如：库存扣减、发票生成、风控审计、用户通知）。如果下游有服务处理缓慢甚至宕机，不能影响主业务或其他服务。

标准架构解法：

  • 生产者将业务事件发布至 SNS Topic。
  • 为每个下游独立业务模块创建一个专属的 SQS Queue，并将这些 SQS 队列订阅到该 SNS Topic。
  • 各业务服务的 Worker 节点分别从自己的 SQS 队列中 PULL 消息并进行异步处理。
💡 SAP-C02 考点变体：Cross-Account Fan-out（跨账号扇出）
考试常结合 AWS Organizations 考察：允许不同 AWS 账号下的 SQS 队列订阅中央账号下的 SNS Topic。这需要配置 SQS 的 Resource-based Policy（允许 `sns.amazonaws.com` 发送 `sqs:SendMessage` 权限），同时利用 SNS 的 Filter Policy 减少跨账号无效消息传输成本。

三、 SAP-C02 解题关键词与秒杀法则

题干模式 A：削峰与流量平抑
SQS Queue + Auto Scaling Group

当题干提到“Spike in traffic（突发流量）”、“Downstream system cannot handle burst（下游无法处理突增流量）”时，必选基于 SQS 队列长度（Queue Depth/`ApproximateNumberOfMessagesVisible`）扩展 EC2 Worker 的方案。

题干模式 B：广播与解耦
SNS + Multiple SQS (Fan-out)

当题干要求“Publish event to multiple independent applications asynchronously（将事件异步发布给多个独立应用）”，且强调“Message durability for each subscriber（保证各订阅者的消息持久性）”时，首选 SNS + SQS 组合。

题干模式 C：顺序与防重
SQS FIFO + Message Group ID

当题干要求“Strict ordering（严格顺序）”和“Exactly-once processing（仅一次处理/去重）”时，直接排除 Standard SQS，锁定 SQS FIFO 队列。

题干模式 D：降低 API 轮询成本
SQS Long Polling (WaitTimeSeconds > 0)

当题干提到“Reduce API calls / costs for ReceiveMessage（减少接收消息的 API 调用和成本）”或“Reduce empty responses（减少空响应）”时，正确答案必包含长轮询（Long Polling）。

⚠️ SAP-C02 常见坑点与排除策略
  • 处理重试导致的重复消费：如果题干提到“Worker 在处理消息期间，其他 Worker 又收到了相同的消息”，这通常不是因为 FIFO 未开启，而是因为 Visibility Timeout (可见性超时) 设置过短！正确解法是增大 Visibility Timeout 或在代码中调用 `ChangeMessageVisibility`。
  • 处理中毒消息 (Poison Message)：当某些破坏性消息导致 Worker 反复崩溃、反复重试时，正确解法是配置 Dead-Letter Queue (DLQ)，设置 `maxReceiveCount` 阈值。
  • SNS 消息丢失问题：在考察高可用架构时，若直接将 HTTP Endpoint 或 Lambda 作为 SNS 的订阅端，在下游宕机时可能会丢消息。如果题目要求无损 (Zero Data Loss)，必须在 SNS 和下游应用之间插入 SQS 队列作为缓冲。
