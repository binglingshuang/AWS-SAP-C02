Amazon Managed Grafana
全托管的可观测性可视化

Amazon Managed Grafana（AMG）是基于开源 Grafana 的全托管服务，由 AWS 负责扩缩、打补丁、升级与高可用。考试重点是“托管带来的运维优势”、“从自建 Grafana 迁移”、“数据源与认证集成”，以及与 CloudWatch Dashboards、QuickSight、Amazon Managed Service for Prometheus（AMP）的边界。

一、是什么与核心定位

Amazon Managed Grafana 是 AWS 提供的全托管 Grafana，核心价值是“保留 Grafana 的使用体验，去掉自建 Grafana 的运维负担”。

多种数据源
CloudWatch / AMP / X-Ray / 第三方 → Amazon Managed Grafana Workspace
托管的 Grafana 服务器，AWS 负责扩缩与高可用 → Dashboards
统一的可视化与告警 → 用户
SAML / IAM Identity Center 登录
要点说明考试提示
全托管AWS 负责服务器的预置、扩缩、打补丁、版本升级和跨 AZ 高可用。题目强调“最小运维开销 / 不想管理 EC2” 时优先考虑 AMG。
Workspace（工作区）一个逻辑隔离的 Grafana 服务器环境，包含仪表盘、数据源与用户授权。不是“一个 EC2 实例”，而是托管环境；按工作区管理与隔离。
兼容开源 Grafana保留 Grafana 的仪表盘、面板、查询与大量插件生态。现有 Grafana 仪表盘可以导出 JSON 再导入 AMG，无需重建。
高可用服务默认跨多可用区运行，无需自行搭建 ALB + Auto Scaling。自建 Grafana 的 HA 方案（AMI/ASG/ALB/EFS）在有 AMG 时通常是“运维更重”的错误选项。
一句话定位：需要 Grafana 风格的多数据源可视化 + 高可用 + 几乎零运维时，选 Amazon Managed Grafana；它不替你收集指标，只负责展示与告警。

二、托管带来的运维优势

SAP-C02 很喜欢用“现有自建 Grafana 跑在单台 EC2 上”的题干，考你如何在最小运维下实现高可用并保留仪表盘。

维度自建 Grafana（EC2）Amazon Managed Grafana
服务器运维自行安装、打补丁、升级版本AWS 全托管，无需管理底层服务器
高可用需自建 ASG + ALB + 共享存储（如 EFS）默认跨 AZ 高可用，开箱即用
扩缩容手动或自建 Auto Scaling由服务自动处理
认证集成需自行对接 SAML/LDAP原生集成 IAM Identity Center 与 SAML 2.0
数据源权限手动配置凭证通过服务角色托管访问 CloudWatch、AMP、X-Ray 等
高频得分点：题干“把跑在单台 EC2 上的 Grafana 变成高可用且运维最小、同时保留现有仪表盘”，标准答案是创建 Amazon Managed Grafana 工作区 → 配置 CloudWatch 等数据源 → 从旧实例导出仪表盘 JSON 并导入新工作区。
常见干扰项：
  • 做一个预装 Grafana 的 AMI + Auto Scaling + ALB + EFS —— 可用但运维更重，不是“最小开销”。
  • 用 AWS Backup 每小时备份 EC2，故障时恢复 —— 恢复时间长，难以满足“停机不超过 10 分钟”。
  • 把仪表盘全部迁移到 CloudWatch Dashboards 重建 —— 丢弃了现有 Grafana 仪表盘，工作量大。

三、数据源与集成

AMG 的价值在于“一个面板看多来源”。考试重点是它能原生接哪些 AWS 数据源，以及它本身不采集数据。

数据源用途说明
Amazon CloudWatchAWS 资源与应用的指标、日志。最常见的数据源；通过服务角色授予只读访问即可查询指标。
Amazon Managed Service for Prometheus（AMP）容器与微服务的 Prometheus 指标。AMP 负责存储 Prometheus 指标，AMG 负责可视化；两者常搭配出现（EKS/容器监控场景）。
AWS X-Ray分布式追踪数据。用于在 Grafana 中查看调用链与服务地图。
Amazon OpenSearch Service日志检索与分析。作为日志类仪表盘的数据源。
Amazon Timestream / Athena / Redshift时序、数据湖与数仓查询。支持多种 AWS 分析类数据源。
第三方数据源自建 Prometheus、InfluxDB、Elasticsearch、Loki 等。兼容开源 Grafana 的大量数据源插件。
关键边界：AMG 只做“可视化与告警”，不采集也不长期存储指标。采集与存储由 CloudWatch、AMP、X-Ray 等上游服务负责。题目若问“存储 Prometheus 指标”应选 AMP，而不是 AMG。

四、认证与权限

AMG 不维护自己的用户名密码体系，而是对接企业身份源，这也是常见考点。

机制说明考试提示
IAM Identity Center（原 AWS SSO）用 AWS 的集中身份登录 Grafana 工作区。多账号/组织内统一登录时优先考虑。
SAML 2.0对接企业 IdP（如 Okta、Azure AD/Entra ID、ADFS）。企业已有 IdP、要求 SSO 时选 SAML。
Grafana 角色Admin / Editor / Viewer 三类角色，映射到用户或用户组。按最小权限分配：只读干系人用 Viewer，维护仪表盘用 Editor。
数据源访问通过服务管理的 IAM 角色访问 CloudWatch、AMP、X-Ray 等。遵循最小权限；跨账号查询需配置相应角色与权限。
记忆点：登录身份用 IAM Identity Center 或 SAML；Grafana 内部权限用 Admin/Editor/Viewer；访问 AWS 数据源用服务角色。三层各司其职。

五、从自建 Grafana 迁移

迁移题的标准路径很固定，记住步骤即可快速锁定答案。

创建 AMG 工作区 → 配置数据源
如 CloudWatch → 从旧 Grafana 导出仪表盘 JSON → 导入新工作区 → 配置登录与权限
  • 保留仪表盘：Grafana 仪表盘可导出为 JSON，再导入到 AMG 工作区，避免重建。
  • 切换数据源：在新工作区中重新配置数据源（如 CloudWatch），让面板指向托管数据源。
  • 高可用达成：迁移到 AMG 后天然跨 AZ，满足低停机时间要求，无需自建 ASG/ALB。
  • 运维下降：服务器、补丁、升级交给 AWS，团队专注于仪表盘与告警。
对应真题思路：“Grafana 跑在单 EC2，仪表盘要保留，要求高可用且停机 < 10 分钟，运维最小” → 创建 Amazon Managed Grafana 工作区 + 配置 CloudWatch 数据源 + 导出/导入现有仪表盘。

六、与相邻服务的边界

可视化相关服务容易混淆，这张表能解决大多数边界题。

服务擅长与 Managed Grafana 的边界
Amazon Managed Grafana多数据源的运维/可观测性可视化与告警，兼容开源 Grafana 生态。不采集、不长期存储指标；聚合展示多来源数据。
Amazon CloudWatch DashboardsCloudWatch 原生仪表盘，适合纯 AWS 指标的轻量可视化。多来源聚合、复杂面板和 Grafana 生态不如 AMG；无法直接导入 Grafana 仪表盘。
Amazon Managed Service for Prometheus（AMP）托管存储与查询 Prometheus 指标（PromQL）。负责“存指标”，AMG 负责“看指标”；二者常组合用于容器监控。
Amazon QuickSight面向业务的 BI 报表与商业智能分析。偏业务数据分析与报表，不是运维监控/可观测性仪表盘。
AWS X-Ray分布式追踪与调用链分析。作为追踪数据源接入 AMG；本身不提供统一多源仪表盘。
题干关键词映射：“运维/可观测性仪表盘、多数据源、兼容 Grafana” → Managed Grafana；“纯 CloudWatch 指标的简单看板” → CloudWatch Dashboards；“存储 Prometheus 指标” → AMP；“业务 BI 报表” → QuickSight。

七、场景题解析（5 题）

1. 公司的 Grafana 跑在单台 EC2 上，团队投入大量精力做了仪表盘希望保留，要求高可用、停机不超过 10 分钟，且运维最小。最合适的方案是？

A. 迁移到 CloudWatch Dashboards，按现有 Grafana 仪表盘重建
B. 创建 Amazon Managed Grafana 工作区，配置 CloudWatch 数据源，从旧 Grafana 导出仪表盘并导入新工作区
C. 做一个预装 Grafana 的 AMI，用 EFS 存仪表盘，建 min/desired/max=1 的 ASG 加 ALB 覆盖至少两个 AZ
D. 用 AWS Backup 每小时备份 EC2，需要时在另一个 AZ 从最新快照恢复

答案：B。Managed Grafana 全托管、默认跨 AZ 高可用，且可导入现有 Grafana 仪表盘 JSON，运维开销最小。
排除：A 丢弃现有仪表盘需重建；C 可用但要自管 AMI/ASG/ALB/EFS，运维更重；D 快照恢复耗时，难满足 10 分钟停机要求。

2. 团队在 EKS 上用 Prometheus 采集容器指标，希望用托管方案存储指标并用 Grafana 风格仪表盘展示，运维最小。应如何组合？

A. 只用 CloudWatch Dashboards
B. 用 Amazon Managed Service for Prometheus 存储指标，用 Amazon Managed Grafana 可视化
C. 自建 Prometheus + 自建 Grafana on EC2
D. 用 QuickSight 直接查询 Prometheus

答案：B。AMP 托管存储 Prometheus 指标，AMG 托管可视化，二者组合是容器监控的标准托管方案。
排除：A 不适合 Prometheus/PromQL 场景；C 运维重；D QuickSight 是 BI 工具，不用于 Prometheus 运维监控。

3. 企业已有 Okta 作为 IdP，要求用户用企业账号单点登录 Grafana 工作区。应如何配置认证？

A. 在 Grafana 内各自创建本地用户名密码
B. 配置 SAML 2.0，对接企业 IdP（Okta）实现 SSO
C. 把 Okta 凭证硬编码到数据源
D. 必须先迁移到 IAM 用户

答案：B。AMG 原生支持 SAML 2.0，可对接 Okta、Entra ID 等 IdP 实现 SSO；组织内也可用 IAM Identity Center。
排除：A 不是 SSO 且难管理；C 违反安全实践；D 没必要。

4. 运维团队希望在一个面板里同时看 CloudWatch 指标、X-Ray 追踪和自建 Prometheus 的数据，且不想管理 Grafana 服务器。选哪个服务？

A. CloudWatch Dashboards
B. QuickSight
C. Amazon Managed Grafana
D. 自建 Grafana on EC2

答案：C。Managed Grafana 支持多数据源聚合（CloudWatch、X-Ray、Prometheus 等）且全托管，正好满足多源统一可视化且零服务器运维。
排除：A 多为 CloudWatch 单源；B 是 BI 工具；D 需自管服务器。

5. 关于 Amazon Managed Grafana，下列说法正确的是？

A. 它会采集并长期存储应用指标
B. 它是全托管可视化服务，数据由 CloudWatch/AMP/X-Ray 等上游提供
C. 它只能连接 CloudWatch
D. 它要求自行搭建 ALB 才能高可用

答案：B。AMG 负责可视化与告警，指标采集与存储由上游服务负责；支持多种数据源且默认跨 AZ 高可用。
排除：A 职责弄反；C 低估数据源能力；D 高可用由服务提供，无需自建 ALB。

八、关键词速查与高频考点

题目关键词优先考虑
保留现有 Grafana 仪表盘、高可用、运维最小Amazon Managed Grafana（导出/导入 JSON）
多数据源统一可视化、兼容 Grafana 生态Amazon Managed Grafana
存储 Prometheus 指标（PromQL）Amazon Managed Service for Prometheus（AMP）
容器/EKS 指标监控的托管组合AMP 存储 + Managed Grafana 展示
纯 CloudWatch 指标的轻量看板CloudWatch Dashboards
业务 BI 报表与分析QuickSight（不是 AMG）
企业 IdP 单点登录（Okta/Entra ID）SAML 2.0
组织内集中身份登录IAM Identity Center
仪表盘用户权限分级Admin / Editor / Viewer
AMG 会不会采集/存储指标不会；仅可视化与告警，数据来自上游
高频考点总结：
  • 定位：全托管 Grafana，负责可视化与告警，不采集也不存储指标。
  • 运维优势：免管服务器、自动打补丁与升级、默认跨 AZ 高可用。
  • 迁移路径：建工作区 → 配数据源 → 导出/导入仪表盘 JSON。
  • 数据源：CloudWatch、AMP、X-Ray、OpenSearch、Athena/Redshift 及第三方。
  • 认证：IAM Identity Center 或 SAML 2.0；内部角色 Admin/Editor/Viewer。
  • 边界：AMP 存指标、AMG 看指标；CloudWatch Dashboards 轻量单源；QuickSight 做 BI。
