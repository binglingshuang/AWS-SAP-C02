一、模板与 Stack 生命周期

AWS CloudFormation 使用模板声明资源、参数和依赖关系，并将模板实例化为 Stack。它持续记录由 Stack 管理的资源与配置，但不会自动发现并修复所有手工漂移。

操作CloudFormation 行为风险控制
Create Stack按模板创建资源并跟踪 Stack 状态。检查参数、配额、权限、依赖与名称唯一性。
Update Stack比较新模板/参数与当前 Stack，按资源属性执行变更。先创建 Change Set，理解替换、删除和不可变属性影响。
Delete Stack删除 Stack 管理的资源，除非资源配置保留或有其他保护机制。配置 Retain/Snapshot、Termination Protection，并在生产环境走审批。
Rollback创建/更新失败时按配置回退资源到先前状态。回滚可能受权限、不可恢复资源或外部变更影响；需查看事件与失败原因。

模板可以存放在本地、S3 或通过 CI/CD 管理；将模板审查、参数验证、Change Set 审批和 Stack 执行串成可审计发布流程。

二、模板结构与复用

模板部分用途常见考点
Parameters将环境、AMI、实例规格等部署输入外置。配置默认值、允许值、约束和 NoEcho；NoEcho 不是秘密管理服务。
Mappings / Conditions按区域/环境映射值，或条件化创建资源。适合静态映射与有限环境差异；复杂秘密不要写在模板。
Resources声明要创建或管理的 AWS 资源。资源类型及属性要与服务支持矩阵匹配；可用 DependsOn 明确依赖。
Outputs暴露 Stack 输出，或向其他 Stack 导出值。Export/ImportValue 通常受账号、区域范围限制，删除导出前需解除引用。
Metadata / Rules提供模板元数据、参数校验规则或控制台体验配置。参数 Rules 可在部署前验证组合约束。
Transforms / Macros转换模板语法或执行宏展开；SAM 使用 Transform。宏可执行自定义逻辑，部署前审查宏来源和权限。
  • Intrinsic Functions（如 Ref、Fn::GetAtt、Fn::Sub、Fn::Join、Fn::ImportValue）在模板中引用参数、属性和跨栈输出。
  • 用 Outputs 分享稳定标识符；跨 Stack 强耦合会限制更新和删除顺序，复杂层级优先考虑 Nested Stack 或更松耦合的发现机制。
  • 避免把密码、API Key 写入模板、参数默认值或 Outputs；使用 Secrets Manager/Parameter Store 动态引用并限制访问。
  • 模板描述目标状态，实际部署还受执行身份、IAM 权限、服务配额和区域可用性限制。
参数注意：CloudFormation Parameters 便于复用，但参数值可能出现在 Stack 配置或审计路径中；敏感值应使用受支持的秘密引用与 KMS 保护。

三、Change Set 与更新保护

  • Change Set 在执行更新前展示 CloudFormation 预期新增、修改、替换或删除的资源，有助于评审更新影响。
  • Change Set 是变更预览，不是部署成功保证；运行时条件、动态引用、服务配额、资源状态和执行权限仍可能导致失败。
  • 生产发布可创建 Change Set、保存变更记录、审批后执行；监控 Stack Events 并验证应用级健康。
  • 更新可能触发资源替换（Replacement），造成新建资源、数据迁移或中断；检查属性的 Update requires replacement 语义。
  • Stack Policy 可阻止更新对特定资源执行不允许的更新操作；它不是 IAM 权限策略，也不用于阻止所有手工资源更改。
  • Termination Protection 可阻止删除 Stack；删除保护需要先解除，仍不能替代备份、IAM 和资源级保护。
保护机制控制对象不能替代
Change Set执行前审查模板更新的预期资源变更。部署验证、回滚、备份或权限控制。
Stack Policy限制 Stack 更新时可对指定资源执行的操作。IAM Policy；它不授予/撤销用户的 AWS API 权限。
Termination Protection阻止 Stack 被删除。资源数据保护；也不防止所有资源属性更新或手工变更。
Rollback Triggers在部署期监测 CloudWatch Alarm，异常时触发回滚。应用级回归测试；只监控选定指标与时间范围。

四、资源保留、替换与 Drift

属性 / 能力作用典型用途
DeletionPolicy: RetainStack 删除时保留该资源，而不是删除底层资源。保留数据库、S3 Bucket 或需人工处理的资源；需另行管理残留资源。
DeletionPolicy: Snapshot删除 Stack 时对支持的资源创建快照后删除资源。需要在删除前保留可恢复的数据副本；检查资源类型支持。
UpdateReplacePolicy更新导致资源替换时，决定旧资源的处置方式。数据库或有状态资源更新，避免替换后旧数据立即销毁。
Drift Detection比较支持资源的实际配置与 Stack 模板期望配置，报告差异。检测控制台手工改动或配置漂移。
Resource Import将已存在资源纳入 Stack 管理，前提是资源类型与属性支持导入。逐步采用 IaC 管理现存资源，先清点依赖并验证模板。
  • DeletionPolicy 和 UpdateReplacePolicy 是不同生命周期事件的策略：前者针对删除 Stack/资源，后者针对更新替换。
  • Drift Detection 只报告支持资源的配置差异，不会自动回写模板、修复资源或阻止手工变更。
  • Drift 结果可能是 IN_SYNC、MODIFIED、DELETED 或 NOT_CHECKED；并非每种属性/资源都能被检测。
  • 修复漂移应先判断将实际状态纳入模板，还是重新部署模板期望状态；盲目更新可能覆盖合法的生产修复。
  • 对于有状态资源，明确保留策略、备份、资源导入和删除后的所有权；Stack 删除后 Retain 的资源不会自动再次受该 Stack 管理。
数据保护：模板删除一个数据库资源前，评估 DeletionPolicy、UpdateReplacePolicy、快照和恢复演练；不要假设 CloudFormation 自动判断数据价值。

五、Nested Stacks 与跨栈引用

模式组织方式优势 / 注意事项
Nested Stack父模板将子模板作为 AWS::CloudFormation::Stack 资源调用。模块化复用；父 Stack 负责协调子 Stack 生命周期，参数/输出形成接口。
Export / ImportValue在同一账号和区域的不同 Stacks 间导入导出值。适合共享 VPC ID 等标识；强引用会阻止被引用 Export 删除/修改。
StackSets将同一模板部署到多个账号和/或区域。组织级基线、审计和网络资源部署；使用服务管理或自管理权限模型。
  • Nested Stacks 将同一应用或平台划分为可复用模块；对子 Stack 的模板变更需通过父 Stack 更新，注意部署依赖和失败回滚。
  • Outputs/Exports 适合跨 Stack 显式共享少量稳定值；ImportValue 存在引用约束，不适合随意拆除的动态服务发现。
  • StackSets 解决的是多个账号/区域一致部署，Nested Stack 解决的是一个 Stack 内模板模块化，二者目标不同。

六、StackSets 跨账号 / 区域

  • StackSet 保存模板和部署配置；Stack Instance 表示在目标账号与区域中实例化的 Stack。
  • Service-managed permissions：与 Organizations 集成，可按组织、OU 或账号部署；适合新账号自动纳入基线。需启用组织所需功能并配置可信访问。
  • Self-managed permissions：由客户在管理账号和目标账号准备相应 IAM 执行角色；适用于非 Organizations 或自定义跨账号权限路径。
  • 可配置区域顺序、最大并发、失败容忍和部署目标；对大量账号分批滚动部署，避免一次性错误影响全组织。
  • StackSet 与组织 OU 绑定可在成员账号加入/移动时自动部署或移除实例；需要确认自动部署行为不会删除关键资源。
  • 跨区域部署需考虑区域资源支持、配额、名称唯一性、KMS 密钥区域性和资源依赖差异。
选择提示：“Organizations 中所有/指定 OU 的账号自动部署同一基线” → Service-managed StackSets；“手动管理跨账号信任角色或不使用 Organizations” → Self-managed StackSets。

七、执行角色与安全治理

  • CloudFormation 执行角色允许服务代表部署者创建模板声明的资源；限制其资源类型、操作、账号和区域，避免模板成为权限提升通道。
  • Stack 创建者权限与执行角色权限需要分别审查；允许某人传递高权限 Role（iam:PassRole）可能让其通过模板间接获得该角色能力。
  • 为模板使用代码审查、静态检查、预生产部署、Change Set 审批和 CloudTrail 审计。
  • 用 Secrets Manager / Parameter Store 动态引用秘密，避免明文进入模板、Outputs、源代码或 Stack Events。
  • 使用 StackSets 维护组织基线时，保护委派管理员、执行角色、可信访问和策略变更流程。
最小权限：CloudFormation 不是权限隔离边界。执行角色的权限可能被模板部署调用；委派创建 Stack 的能力时，需要同时评估执行角色、PassRole 和模板可修改范围。

八、场景题解析

场景一：更新前查看是否会替换数据库实例

团队修改生产数据库参数，希望在执行前审查 CloudFormation 将新增、修改、替换或删除的资源。

正确方向：先创建 Change Set，检查数据库资源是否 Replacement，再审批执行。

分析思路：Change Set 提供部署前的资源变更预览，适合生产风险评估。

排除：只运行 drift detection 只能比较当前漂移，不能预览新模板更新；Change Set 也不是成功保证。

场景二：统一向多个 Organizations 账号和 Region 部署基线

新账号加入指定 OU 后应自动部署相同的日志与安全资源，覆盖多个区域。

正确方向：使用 Organizations 集成的 Service-managed StackSets，指定 OU/区域并启用相应自动部署能力。

分析思路：StackSets 用于跨账号/区域一致部署；服务管理权限可与 Organizations 目标集成。

排除：Nested Stack 只做模板模块化，不负责组织账号级部署。

场景三：控制台手工改了模板管理的安全组

需要识别资源实际配置与 Stack 模板的差异，但暂时不能自动覆盖生产中的手工修复。

正确方向：运行 Drift Detection，评估 MODIFIED 结果，再决定更新模板或重新部署期望状态。

分析思路：Drift 检测报告差异，不会自动修复。

排除：直接更新 Stack 可能覆盖手工修改；删除/重建安全组可能造成业务中断。

场景四：删除应用 Stack 但保留数据库

应用基础设施可删除重建，数据库需要在 Stack 删除后继续保留并由数据团队单独管理。

正确方向：为数据库配置 DeletionPolicy: Retain，并规划 Stack 删除后的资源移交、备份与后续管理。

分析思路：Retain 使底层资源在 Stack 删除时保留；它不会自动转交给另一个 Stack。

排除：Termination Protection 会阻止整个 Stack 删除，不是“只保留数据库”的精细配置。

场景五：模板按环境拆成可重用模块

一个应用由网络、数据库和应用层组成，多个环境需要复用相同模块，并希望父部署统一管理子模块。

正确方向：使用 Nested Stacks，将模块拆为子模板，由父 Stack 传入参数并导出必要输出。

分析思路：嵌套堆栈用于模板模块化和复用，父 Stack 协调生命周期。

排除：StackSets 面向跨账号/区域部署，而不是单应用模块拆分。

场景六：部署失败需自动回滚

生产环境希望当 CloudWatch 业务告警在部署期间触发时，Stack 更新自动回退到先前状态。

正确方向：为 Stack 配置 CloudWatch Rollback Triggers，并监控相关 Alarm；同时确保资源可回滚且备份可用。

分析思路：Rollback Triggers 根据部署期指标告警触发回滚，减少错误版本持续运行时间。

排除：仅开启 drift detection 不会监控部署指标或执行回滚；回滚也不替代应用验证。

十一、快速自测

先独立选择，再点击“查看解析”。

1. 更新生产 Stack 前，需要查看数据库资源是否会被替换。应使用什么？
正确答案：A。Change Set 可审查更新计划中的资源替换；漂移检测比较的是模板与当前实际状态。
2. 一个组织要向多个 OU 中的账号和区域自动部署安全基线，应选择什么？
正确答案：B。StackSets 可跨账号/区域部署，Service-managed 权限可与 Organizations 目标集成。
3. 手工修改了 CloudFormation 管理的资源，现在需要报告差异但不自动覆盖它。应使用什么？
正确答案：A。Drift Detection 报告支持资源的配置差异，不会自动修复或修改模板。
