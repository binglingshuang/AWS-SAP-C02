AWS CERTIFICATION STUDY NOTES

AWS Config
资源配置与合规治理

AWS Config 持续记录受支持 AWS 资源的配置状态和变化，并依据规则评估资源是否符合要求。它回答“资源现在是什么配置、过去如何变化、是否合规”；需要把记录范围、规则评估、修复执行和跨账号聚合组合起来，形成可验证的治理闭环。

一、Config 能力地图

AWS Config 是资源配置清单、配置历史和合规评估服务。它先通过配置记录器采集配置，再按规则评估；需要时可执行修复，并通过聚合器汇总多个账号和区域的合规与配置数据。

组件职责典型问题
Configuration Recorder指定需要记录的资源类型和记录频率，持续采集资源配置。哪些资源的配置变化进入 Config？
Configuration Item (CI)某资源在某个时间点的配置快照与相关元数据。该资源某一时刻是什么状态？
Config Rule用托管规则或自定义逻辑评估资源配置，产生合规结果。资源是否满足安全/治理要求？
Remediation对不合规结果执行手动或自动修复动作，常用 Systems Manager Automation。检测到偏差后如何纠正？
Aggregator跨账号、跨区域汇总 Config 数据，集中查看和查询，不替代源账号记录器。组织里哪些账号/区域不合规？
Conformance Pack以 YAML 模板组合一组规则及可选修复配置，便于一致部署。如何把一套合规基线部署到多个账户？
记忆主链：记录器决定“看得到什么” → 规则决定“怎样算合规” → 修复决定“怎样纠正” → 聚合器决定“怎样集中观察”。任何一环缺失，治理闭环都会不完整。

二、记录器与记录范围

Configuration Recorder：先采集，才有历史可评估

  • Config Recorder 按所选范围记录资源配置。规则只能评估已纳入记录范围且 Config 能识别的资源；配置规则本身不会自动打开所有类型的记录。
  • 记录器通常按区域配置。要覆盖多个区域，需要在目标区域启用并配置记录；多区域治理还要逐一确认区域范围及新启用区域的策略。
  • 可选择记录所有当前和未来受支持的资源类型，也可限定资源类型；还可按包含/排除范围控制记录对象。考试场景中要识别“所有资源”与“特定关键类型”的范围差别。
  • 资源类型的支持情况会随服务更新；不是每一种 AWS 资源都能被 Config 记录。先核对支持类型，再决定是否需其他 API、日志或清单机制补足。
  • 记录频率可按资源类型支持连续记录或每日记录。连续模式更适合需要及时配置变化和细粒度时间线的场景；每日记录降低变更采集频率，但不适合要求即时发现的控制。
  • 全球资源与区域资源要分别规划。某些全局资源类型的记录范围/区域行为有特殊规则，避免仅凭在单一区域启用就推断组织内所有全球资源都已覆盖。
常见误区：“Config Rule 显示 compliant”不代表全账号所有资源均已被记录。检查记录器状态、记录资源类型、账号/区域覆盖与规则适用范围，再解释合规结果。

交付与权限准备

Config 需要将配置历史和快照交付到指定的 S3 Bucket，并可通过 SNS 通知相关变化。使用集中式 Bucket、客户管理 KMS 密钥或跨账号目标时，必须同时设计 Config 服务角色、Bucket Policy、KMS Key Policy 和组织授权；单独创建规则不能解决交付权限问题。

三、配置项、时间线与交付

概念含义适合用途
Configuration Item资源在特定时间点的配置表示，含资源标识、类型、关系、配置和时间等信息。分析某次评估时资源状态及其上下文。
Configuration History按资源查看 Config 记录到的配置变化序列。回答“什么时候改了安全组规则、改前改后是什么”。
Configuration Timeline在控制台按时间查看配置项和相关变更。追踪单资源配置漂移、回溯事故时间线。
Snapshot / S3 Delivery定期或按需形成配置快照并交付到指定 S3 位置。集中归档、合规留存、与数据分析工作流集成。
SNS Notification将 Config 变更通知发布到 SNS Topic，供订阅者消费。通知系统或触发下游事件处理；需额外设计过滤和幂等。
  • Config 历史关注资源配置状态及变化；CloudTrail 关注发起 API 调用的身份、时间和操作。遇到“改了什么”优先 Config，“谁调用 API 改的”关联 CloudTrail。
  • 配置历史与快照受记录范围、交付状态和保留期影响。若要求长期证据，明确 S3 生命周期、对象访问权限、加密、不可变保留和审计读取角色。
  • 启用 Config 后不代表可追溯启用之前的所有状态。设计调查与合规要求时，先确认采集开始时间、记录频率及资源类型支持。
  • 若资源删除，Config 可能保留资源删除状态/历史线索；应以具体资源和当前产品行为为准，不能把删除理解成审计证据必然消失。
排查时间线：确认资源类型受支持 → 目标区域记录器已启用 → 资源纳入记录范围 → 变更时间在采集开始后 → 检查交付与权限 → 关联 CloudTrail 确认操作者。

四、规则与合规评估

托管规则 vs 自定义规则

类型实现方式适合情况维护重点
AWS Managed Config Rule使用 AWS 提供的规则标识符与参数配置，例如评估 S3 公有访问阻止或加密状态。需求与现有托管规则匹配，想减少自建逻辑。核对规则支持的资源类型、参数、触发方式和区域可用性。
Custom Lambda Rule由 Lambda 函数实现评估逻辑，可采用配置变更触发或定期触发。需要自定义业务标准或检查跨资源条件。函数权限、超时、错误处理、依赖与评估结果合规性。
Custom Policy Rule以 Guard DSL 描述配置策略，不必为每条策略编写 Lambda 评估代码。偏声明式、希望版本化和复用策略表达式。确保策略可表达目标逻辑，并验证参数及资源覆盖。

触发方式与结果解释

  • Configuration change trigger：资源配置发生变化时评估适用规则，适合需要较快发现配置漂移的场景；及时性仍取决于资源变更进入 Config 的时延。
  • Periodic trigger：按指定周期运行评估，适合依赖时间、外部状态或需要定期复核的检查；不是“每次资源变化立即评估”。
  • 规则的评估范围可以通过资源类型、标签、资源 ID 或规则参数限定。范围太窄会漏检，范围太宽可能产生噪声或成本。
  • Compliance 状态包括合规、不合规及评估/数据不足等非最终状态。尚未完成评估、不支持的资源或缺少配置数据，不应错误解释为已通过。
  • 规则只判断声明的条件，不会自动阻止资源创建或变更。若要求预防性阻止，可结合 IAM/SCP 权限边界、服务控制或其他预防控制。
  • Config Rules 的合规结果是检查信号，不等于完整的安全审计或威胁检测；将其与 CloudTrail、Security Hub、GuardDuty 等按职责组合。
评估顺序：资源是否被记录 → 规则是否适用于该资源 → 触发器是否启动评估 → 规则逻辑/参数是否正确 → 结果是 compliant、noncompliant 还是未评估。

五、自动修复与合规包

Remediation：发现问题后执行纠正

  • Config 可为不合规规则配置修复操作，常通过 Systems Manager Automation 文档执行；可先手动触发，也可为支持的规则配置自动修复。
  • 自动修复不是预防控制：资源可能先变为不合规，再由规则评估发现并启动修复。需要“创建时即阻止”时，应另配预防性控制。
  • 修复动作需要正确的 Automation 文档、参数、执行角色和目标资源权限。采用最小权限并限制允许调用的文档与参数，避免给自动化角色过宽管理权限。
  • 幂等性和安全护栏很重要：重复执行不应造成破坏；对有业务影响的动作先在测试账号验证，必要时使用手动批准、变更窗口和失败告警。
  • 评估是否修复成功需要回看资源状态并等待规则重新评估。Automation 执行成功和资源最终合规并非同一件事。

Conformance Pack：一组可复用的治理基线

Conformance Pack 通过模板组合多个 Config Rules，并可包含修复配置，用于将一套控制以一致方式部署到一个或多个账号/区域。组织级 Conformance Pack 适合集中部署；但它仍依赖目标账号的 Config 记录器、服务权限、规则支持范围和区域可用性。

需求优先方案不要混淆
发现资源不符合基线Config Rule / Conformance Pack规则评估不是阻止变更
不合规时自动纠正配置Config Remediation + SSM Automation修复权限不等于规则权限
多个账号部署相同规则集Organization Conformance Pack 或集中部署流程部署规则不自动证明记录器已覆盖全部资源
资源创建前阻止违规操作SCP/IAM/服务端预防控制；视需求结合策略校验自动修复属于事后检测/纠正

六、聚合器与组织治理

Config Aggregator 是组织范围的只读汇总视图，可从多个源账号和区域收集 Config 配置及合规数据，便于集中查看和高级查询。它本身不记录源资源，也不替代每个源账号/区域的 Configuration Recorder。

  • 聚合器可使用 AWS Organizations 集成来纳入组织账号，也可通过授权流程纳入非组织账号；具体源账号授权、组织权限和委派管理员设置必须完成。
  • 显式检查聚合器的账号和区域范围。新增成员账号、新启用区域或规则覆盖变化后，验证聚合视图是否包含预期来源。
  • 源账号必须启用 Config 并有有效记录数据；聚合器无法凭空补录源账号未收集的配置历史。
  • Aggregator 用于集中只读查看与查询，不是把配置记录复制到管理账号，也不是跨账号自动修复编排器。
  • 组织级治理通常分离职责：源账号记录资源与评估规则；管理/委派账号部署聚合器并监控；独立修复角色按需操作资源。
多账号覆盖检查：组织授权有效 + 源账号/区域纳入 + 源端记录器运行 + 目标资源类型已记录 + 聚合器数据已刷新。只看到 Aggregator 资源不代表链路全部正常。

集中治理的推荐闭环

  1. 定义资源类型、区域范围、记录频率、数据保留和例外管理策略。
  2. 在目标账号/区域启用记录器，建立可验证的 S3/SNS 交付与加密权限。
  3. 使用托管规则优先覆盖标准控制，将自定义业务逻辑独立版本化并测试。
  4. 以 Conformance Pack 部署一致规则，对高风险且安全的规则配置 SSM 自动修复。
  5. 在集中治理账号创建 Aggregator，核验组织账号和区域覆盖，并将不合规趋势纳入运营看板。
  6. 用 CloudTrail 记录治理策略、规则、记录器和修复权限的变更，定期复核例外与审计保留。

七、查询、告警与日常运维

查询和事件联动

  • Config Advanced Query 可对 Config 资源配置数据使用类 SQL 语法进行筛选与聚合；跨账号/区域分析时结合 Aggregator，并关注查询支持的数据范围和结果字段。
  • 需要针对特定资源变更通知下游时，可使用 Config/SNS 通知或 EventBridge 的相应事件集成。设计告警时过滤事件类型、资源和严重性，避免把每次配置更新都变成高噪声告警。
  • Config 回答状态和合规，CloudTrail 事件可帮助补充操作者和 API 上下文；将资源标识、时间窗口和账号/区域作为关联键。

成本、保留与故障定位

风险点检查方向治理建议
配置记录与评估费用增长记录资源数量/类型、规则数量与评估频率、区域覆盖。按合规目标选择连续/每日记录和规则触发方式，监测费用趋势。
历史留存不满足审计核对交付 Bucket、S3 生命周期、对象保留与 KMS 权限。定义保留年限、归档层级、删除审批和独立审计读取角色。
规则持续显示未评估检查记录器、资源类型支持、规则触发类型和执行权限。对照单个资源测试，并检查 Config 及 Lambda/SSM 相关错误。
自动修复未执行检查规则修复配置、Automation 文档参数、执行角色与目标权限。查看 Automation 执行记录；将执行成功与合规复评分开验证。
聚合数据不完整核实来源账号授权、区域列表、Config 记录器状态与刷新。从一个源账号/区域逐层验证，不要只看聚合器总体状态。
故障排除顺序：资源支持吗 → 记录器开启了吗 → 资源纳入范围了吗 → 规则触发和逻辑正确吗 → 评估权限有效吗 → 结果是否聚合 → 修复角色/SSM 执行是否成功 → 交付与费用是否符合预期。

八、服务边界与选型

服务核心问题典型职责
AWS Config资源是什么配置、配置如何变化、是否符合规则？资源配置项、历史时间线、规则评估、Aggregator。

九、场景题解析

场景一：发现所有未加密 EBS 卷并持续跟踪

安全团队需要跨账号和区域识别未加密卷，查看其后续状态，并集中呈现合规结果。

正确方向：确保各源账号/区域记录 EBS 资源，配置适用的 Config Rule，再用 Config Aggregator 汇总组织范围的合规数据。

分析思路：规则负责判断，Aggregator 负责集中汇总；两者都依赖源端 Config 记录链路。

排除：只创建 Aggregator 不会自动开启源端记录器；仅靠 CloudTrail 也不能直接提供持续合规状态。

场景二：安全组开放管理端口时自动纠正

组织希望在发现安全组不符合端口基线时自动执行受控修复，同时保留不合规记录。

正确方向：使用 Config Rule 检测，再配置经测试的 SSM Automation remediation；限制执行角色权限并监控修复结果。

分析思路：Config 先评估状态，Systems Manager 执行修复；修复动作应幂等并经过风险评估。

排除：CloudWatch Alarm 是指标告警工具；SCP 可阻止 API，但不能替代事后配置历史与评估。

场景三：某资源变更后立即评估合规规则

团队需要在资源配置发生变化后尽快重新检查规则，而不是固定每天扫描。

正确方向：为适用的 Config Rule 使用 configuration-change trigger，并确保目标资源类型已由 Recorder 连续记录。

分析思路：触发器选择要与规则语义和记录频率相配；数据未进入 Config 时规则无法及时评估。

排除：Periodic trigger 面向周期性评估，不是变更触发；先启用规则但不启用记录也无法补齐配置事件。

场景四：多账号快速部署相同合规规则集

平台团队要把一组标准 Config 规则和修复配置一致部署到组织成员账号。

正确方向：使用组织级 Conformance Pack（按实际支持与权限配置），配合 Organizations 授权和源账号 Config 设置。

分析思路：Conformance Pack 将一组规则作为基线管理；组织部署减少逐账号差异。

排除：Aggregator 只汇总数据，不负责部署规则；CloudFormation StackSets 可部署资源，但不是 Config 规则基线的专用合规视图。

场景五：集中管理账号看不到部分区域的配置

Aggregator 已创建，但某些新账号和新区域没有资源配置数据。

正确方向：逐项核实源账号 Config Recorder 是否启用、资源类型是否被记录、目标区域是否纳入 Aggregator，以及组织授权是否完成。

分析思路：Aggregator 不会替源端采集；新账号/区域需纳入并具备有效 Config 数据。

排除：重复创建规则或扩大聚合器查询范围，不能修复源端未记录的问题。

场景六：确认是谁移除了某个合规 Bucket 的加密配置

Config 时间线显示 Bucket 加密设置已变化，审计方还需要知道发起变更的 IAM 身份和 API。

正确方向：用 Config 确认资源配置变化前后状态和时间，再关联 CloudTrail 中对应时间、区域、资源和 API 事件。

分析思路：两个服务回答不同问题：Config 呈现状态，CloudTrail 记录操作行为。

排除：Config 单独不一定给出完整操作者证据；只看 CloudTrail 也不如 Config 时间线直接比较资源状态。

十一、考前速记卡

已掌握 0 / 18

  • Recorder：决定记录哪些受支持资源及其频率
  • 区域范围：每个目标区域都要验证记录器与覆盖
  • Configuration Item：资源在特定时间点的配置状态
  • Config History：回看资源配置变化
  • Config Rule：评估配置是否符合要求
  • Managed Rule：优先复用 AWS 托管检查
  • Custom Rule：Lambda 或 Guard Policy 实现自定义逻辑
  • Change trigger：配置变化时评估
  • Periodic trigger：按周期评估
  • 未评估：不等于 compliant，检查数据和触发器
  • Remediation：常用 SSM Automation 执行纠正
  • 自动修复：检测后纠正，不是创建前拦截
  • Conformance Pack：将多条规则作为一组基线部署
  • Aggregator：跨账号/区域只读汇总配置与合规数据
  • 聚合器边界：不替源账号开启 Recorder
  • Config + CloudTrail：配置状态 + API 操作者证据
  • Config + SCP：检测合规 + 预防权限控制
  • 费用与留存：记录范围、评估频率、S3 生命周期都要规划

十二、快速自测

先独立选择，再点击“查看解析”。

1. 需要在组织管理账号集中查看多个账号和区域的 Config 合规结果，应使用什么？
正确答案：B。Aggregator 汇总跨账号/区域数据，但源账号和区域仍需产生 Config 记录。
2. 检测到 S3 Bucket 不符合加密要求后自动设置加密，适合的治理链路是什么？
正确答案：B。Config 负责发现不合规，修复操作由已授权的 Automation 执行。
3. Config 合规规则没有评估新建的资源，首先应检查什么？
正确答案：A。规则依赖记录数据；还需验证资源支持情况、记录范围和触发器。
