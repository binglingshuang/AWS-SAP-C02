AWS 成本管理工具
承诺折扣、预算与成本归因

成本治理的目标不是单纯“找最低单价”，而是先看清支出归属和趋势，再用预算预警、选对承诺折扣，并持续优化利用率。考试常考 Savings Plans 与 RI 的适用范围、Budgets 的边界和成本分配标签的启用方式。

一、成本治理能力地图

把成本管理拆成“看见 → 归因 → 预测/告警 → 优化 → 验证”。Cost Explorer 用于交互式分析；Budgets 监控阈值；Savings Plans/RI 降低符合条件的持续用量成本；Cost and Usage Report / Data Exports 供细粒度分析。

工具核心问题不应误解为
Cost Explorer按服务、账号、标签、时间等切分历史支出，查看趋势和预测。实时逐笔账单或强制费用上限。
AWS Budgets监控费用、用量、RI / Savings Plans 利用率与覆盖率并发送通知。达到预算自动停止所有资源。
Cost allocation tags把资源成本归属到团队、应用、环境等维度。自动贴标签或自动修复漏标资源。
Savings Plans以每小时美元承诺换取合格用量折扣。预付账户余额或保证全部承诺都能用完。
Compute Optimizer依据资源配置和利用率指标提供适当规格、类型等优化建议。自动调整资源，或保证建议能直接应用且不影响性能。
CUR / Data Exports导出细粒度成本/用量数据，供 S3、Athena、BI 分析。替代日常交互式成本分析界面。

二、成本可见性、组织账单与标签归因

  • 组织视角：Organizations 合并账单让付款账号集中查看组织成本；成本和折扣是否共享受付款账号设置、服务规则及具体折扣类型影响，不能简单假设所有账号自动共享一切。
  • 成本分配标签：资源标签不会自动成为账单分组维度。先使用一致的键/值策略标记资源，再在 Billing and Cost Management 中激活用户定义标签；激活后才用于后续成本报告，历史数据回填/显示需等待服务处理。
  • AWS 生成标签：与用户定义标签不同，来源于 AWS 的标签须按账单工具支持情况启用。标签键值大小写要规范。
  • Cost Categories：可用规则把账号、标签或其他成本维度归并成业务部门/产品视图；它是成本组织维度，不会修改资源标签。
  • 数据颗粒度：Cost Explorer 适合可视化趋势；需要自定义明细分析、长期留档或跨系统整合时使用 Cost and Usage Report（CUR）/ Data Exports。
标签归因的常见遗漏：标签已附加在资源上，但没有在账单控制台激活；或标签策略只强制格式，却没有覆盖所有可计费资源。

三、Savings Plans：用承诺换取折扣

Savings Plans 是对每小时美元用量作承诺，按承诺覆盖合格的按需用量并提供折扣。常见期限为 1 年或 3 年；可选择不同预付选项。未使用的每小时承诺不会滚到之后小时，因此购买前应基于稳定基线和增长计划建模。

类型覆盖范围概览灵活性与注意点
Compute Savings Plans覆盖较广的合格计算用量，包括 EC2、Fargate、Lambda 等符合规则的用量。不锁定特定 EC2 实例家族/区域，灵活性高；仍有服务、区域、操作系统/租赁等适用规则。
EC2 Instance Savings Plans针对指定区域中的 EC2 实例家族用量。限定家族与区域，通常折扣更深；家族内实例大小等维度具备灵活性，详见适用规则。
SageMaker Savings Plans符合条件的 SageMaker ML 实例用量。适用于 SageMaker 使用，不能当作 EC2 通用承诺。

折扣按 AWS 的适用顺序覆盖符合条件的用量；同时购买多种承诺时，理解其覆盖范围和账单分配，避免重复按总用量过度承诺。Savings Plans 可与按需用量共存，超出承诺的部分仍按适用费率计费。

有持续、可预测用量时从保守的基线承诺开始；新工作负载、周期性峰值和可大幅迁移的用量留出余量，再定期检查利用率、覆盖率和购买建议。

四、Savings Plans、Reserved Instances 与 Spot

方案优先考虑场景关键区别
Savings Plans跨兼容计算服务/实例类型有稳定消费，重视承诺灵活性。承诺的是每小时金额；折扣覆盖满足条件的用量。
EC2 RIEC2 用量稳定且 RI 属性匹配；需要比较区域/可用区、实例家族、平台和租赁等属性。RI 是账单折扣/容量预留模型；区域 RI 通常提供账单折扣，指定可用区的 Zonal RI 可提供容量预留。
特定服务 RI如 RDS 等服务的稳定数据库用量。服务专属，不等同 EC2 容量预留；逐服务核对适用维度。
Spot可中断、容错的批处理/弹性任务。利用空闲容量获得折扣但可能中断；不是长期承诺折扣替代品。

比较时同时考虑可预测性、服务覆盖、可用区容量要求、平台/家族迁移计划、期限、预付现金流、覆盖率和利用率。RI 可售/交换规则因服务和 RI 类型不同，不能一概而论。

五、Budgets：预警而非硬性支出上限

  • 预算类型：成本/用量预算，以及 Savings Plans 或 Reserved Instances 利用率、覆盖率预算；可使用实际值、预测值阈值。
  • 通知：可通过邮件/SNS 等通知目标告警；阈值与周期适合按业务负责人和账期设计。
  • Budgets Actions：可在达到条件时执行受支持的治理动作，例如应用 IAM policy / SCP 或针对特定资源执行动作；需配置授权与目标范围。它不是无条件关停一切资源的费用防火墙。
  • 预测告警：基于预测支出的预算需要历史数据和预测能力；对短期异常费用还应结合 Cost Anomaly Detection 等检测机制。
预算告警与成本硬上限是两回事：服务可能继续运行并产生费用，除非另行设计有明确范围、权限和安全回滚的自动治理动作。

六、优化闭环与工具协同

  1. 建立归因：统一账号、标签、Cost Categories，并指定每个成本中心的负责人。
  2. 观察趋势：Cost Explorer 看服务/区域/账号变化；Cost Anomaly Detection 检测异常；CUR/Data Exports 支持精细分析。
  3. 设置护栏：Budgets 按实际和预测费用通知；为通知设负责人和响应流程。
  4. 优化用量：Compute Optimizer 提供资源规格和闲置资源建议；Savings Plans/RI 覆盖稳定基线；Spot 承载可中断任务；S3 等存储按访问模式分层。
  5. 复核效果：对比优化前后费用、业务性能与承诺覆盖/利用率，避免单纯压成本造成可用性退化。

七、Compute Optimizer：分析利用率并提出规格建议

AWS Compute Optimizer 根据资源配置和历史利用率指标，识别可能过度配置、配置不足或闲置的资源，并提供权衡成本与性能的优化建议。它是决策支持服务，不会因为显示建议就自动修改或停止资源。

能分析哪些资源

除 EC2 实例外，还可为 EC2 Auto Scaling 群组、EBS 卷、Lambda 函数、运行于 Fargate 的 ECS 服务，以及 Aurora/RDS 等多类资源生成建议；当前支持范围还包括 NAT Gateway、DynamoDB、ElastiCache、MemoryDB、DocumentDB、WorkSpaces、SageMaker 和部分商业软件许可。支持的资源类型、建议内容与适用区域会随服务更新，且各资源类型有各自的资格要求。

建议依据与常见输出

  • 指标与窗口：加入（opt in）后，默认分析近期最多 14 天的资源规格和 CloudWatch 利用率指标；部分资源可启用付费的 Enhanced Infrastructure Metrics，将回溯窗口延长至最多 93 天。不同资源所需指标不同，数据不足时可能暂时没有建议。
  • 建议内容按资源类型变化：例如 EC2 可比较实例规格/类型及其利用率图表；EBS 可评估卷配置；Lambda 可分析内存配置；其他受支持资源也会提供对应的规格或配置建议。
  • 成本信息：启用 Cost Explorer 后，服务可用账单数据展示建议相关的价格/节省估算。估算是评估依据，不代表实际账单节省保证。
  • 置信度与风险：结合利用率图表、建议选项及性能风险判断是否调整；需把业务峰值、季节性、扩容策略、延迟/SLO 和未采集的自定义指标纳入审查。

落地流程与考试边界

  1. 先启用并满足前提：对账号选择加入；组织场景可配置组织级访问。核实区域、权限、Cost Explorer（需要价格/节省估算时）和资源所需的指标数据。
  2. 读懂建议再变更：查看 finding、利用率图表、候选配置和预计影响；对生产资源先评审并分批测试，监控性能和可用性后再推广。
  3. 持续复核：部署后确认实际成本和业务指标。工作负载、需求或指标发生变化时重新评估，不把一次建议视为永久结论。
职责区分：Compute Optimizer 侧重资源规格/配置的 rightsizing 建议；Cost Explorer 侧重成本趋势分析，Budgets 负责阈值告警，Savings Plans/RI 负责符合条件用量的折扣。若要综合考虑现有 Savings Plans 或 RI 对 rightsizing 节省的影响，可结合 Cost Optimization Hub 查看。
考试陷阱：Compute Optimizer 不等于自动扩缩容，也不是成本硬上限；建议受数据充分性、资源资格、区域和配置影响。不要只看平均 CPU 就缩小实例，必须验证内存、网络、磁盘、峰值及应用性能。

八、场景题解析（6 题）

1. 多个账号有长期稳定的 EC2、Fargate 和 Lambda 用量，架构仍可能变化，希望承诺尽量灵活。

评估 Compute Savings Plans，并用组织级成本分析确认合格用量与承诺覆盖；不要仅按当前峰值购买。预留可变用量并持续检查利用率。

2. 一个区域内稳定运行指定 EC2 家族，优先追求更高折扣且不要求为某个 AZ 保证容量。

比较 EC2 Instance Savings Plans 与区域 EC2 RI。确认家族、区域、平台/租赁等条件；若题目要求实际容量预留，则应评估 Zonal RI，而非只看折扣。

3. 管理层要求每个部门按团队标签查看成本，但现有 Cost Explorer 中没有该维度。

规范资源打标，并在账单控制台激活对应 user-defined cost allocation tags；等待数据处理后在 Cost Explorer 分组，必要时使用 Cost Categories 归并部门。

4. 预测月末支出将超过预算，希望提前通知财务和服务负责人，但不要自动中断生产。

配置有预测阈值的 AWS Budgets 通知，并向合适的邮件/SNS 目标发送。不要设置 Budgets Action 关停资源，预算本身不会阻止支出。

5. 批处理可被中断且可在稍后重试，需要比按需更低成本。

将任务设计为可恢复/可重试后使用 Spot 容量；Savings Plans 是稳定承诺用量折扣，不能提供可中断弹性容量本身。

6. FinOps 团队需要将账单明细交由 S3/Athena 做自定义分摊和月度审计。

启用 CUR 或 Cost and Usage Data Exports 并导出到受控 S3，结合 Glue/Athena 等分析；Cost Explorer 可用于交互式趋势查看但不替代明细导出需求。

十、快速自测

1. Budgets 达到阈值后，成本一定会停止增长吗？

不会。预算用于监控和告警；如需动作必须单独配置 Budgets Actions 或其他治理流程，仍需考虑范围和误操作风险。

2. 标签已经贴在 EC2 上，但成本报告里没有团队维度，先检查什么？

检查对应 cost allocation tag 是否在 Billing and Cost Management 中激活，并确认数据处理时间及标签覆盖的资源。

3. 用量可随 EC2 家族与区域迁移，仍希望承诺折扣，常先比较哪类 Savings Plans？

Compute Savings Plans；其适用范围通常比 EC2 Instance Savings Plans 更灵活，但仍应逐项核实合格用量规则。

4. Compute Optimizer 建议缩小一批 EC2 实例，能否直接批量应用以节省费用？

不能只凭建议直接套用。先检查回溯指标是否覆盖峰值、实例规格和应用性能要求，评审变更风险并分批测试；Compute Optimizer 提供建议，不会自动替你调整资源。
