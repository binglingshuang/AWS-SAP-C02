AWS Service Catalog
标准化产品与合规自助服务

Service Catalog 让平台团队发布经过批准的云资源产品，并通过 Portfolio、访问权限和约束，允许应用团队在护栏内自助部署。它管理的是“可供部署的产品及其生命周期”，不只是 CloudFormation 模板仓库。

一、Service Catalog 能力地图

平台团队定义允许部署的产品和参数，组织成 Portfolio，并授权用户/组访问。使用者在授权约束内 launch 产品；Service Catalog 跟踪 provisioned product，可按新版本更新或终止。

对象含义典型题目线索
Product可部署的模板/产品版本及其参数。标准化 VPC、应用栈、数据库或开发环境。
Portfolio一组产品及其访问权限、约束。按团队/业务线发布批准产品目录。
Provisioned Product用户从目录部署后由 Service Catalog 跟踪的实例。产品更新、变更、终止和状态跟踪。
Constraint限制如何启动产品、允许哪些参数或如何部署。Launch / Template / Notification / StackSet 等约束。
TagOption可复用的受控标签键值，关联到 Portfolio/产品。强制成本归因和统一标签值。

二、Portfolio、Product 与产品版本

  • Portfolio：把相关产品、访问控制、约束和标签选项组合成面向消费者的目录；同一个产品可由不同 Portfolio 以不同访问/参数约束提供。
  • Product：可由 CloudFormation 模板等定义，包含一个或多个版本。版本可关联不同模板和参数；新版本发布不会自动更新所有现存 provisioned products。
  • Provisioned Product：代表目录产品的一次部署实例，通常由 Service Catalog 与 CloudFormation 生命周期机制协作。可查看状态、更新到新版本或终止；实际底层资源需按服务规则处理。
  • 目录治理：在开发、验证、发布流程中审查模板、默认值、参数限制和权限；不要把“模板出现在目录”理解为天然安全。

三、Portfolio 访问与 Launch Constraint

Portfolio 需要授权用户/组（及其 IAM 身份）访问。Launch Constraint 为产品指定 Service Catalog 可使用的 IAM role 执行 CloudFormation 部署，使终端用户不必拥有创建模板中所有底层资源的权限。

方式实际效果重点检查
Launch Constraint + IAM role通过指定角色创建资源；消费者获得受控的产品启动能力。角色信任 Service Catalog/CloudFormation 所需主体；角色权限覆盖模板资源但不过宽。
无 Launch Constraint通常需由最终用户的身份权限承担部署所需授权。调用者 IAM 与资源策略可能要开放较多底层权限。
Portfolio 授权决定用户/组能否发现并使用 Portfolio 产品。有权限启动不代表能访问所有 Portfolio；账号/组织共享需分别配置。
Launch Constraint 不是绕过权限检查：执行角色必须有实际资源权限，信任关系和 Service Catalog 绑定要正确；限制终端用户的是被授权的产品入口，而不是任意 AWS API。

四、约束类型与受控输入

约束用途例子/边界
Launch Constraint指定 launch 时使用的 IAM role。让用户无需直接拥有底层资源创建权限。
Template Constraint限定 CloudFormation 模板参数的可选值、范围或可见性。仅允许批准的实例类型/网络选项；并非完整的 IAM 授权机制。
Notification Constraint为产品事件配置 SNS 通知。通知生命周期事件；SNS topic 和权限需配置。
StackSet Constraint把产品部署到指定多个账号/区域的 StackSet 目标。检查 StackSets 权限、目标 OU/账号、区域与部署选项。
TagOptions为产品应用受控标签选项。支持一致标记；不能替代标签策略/IAM 对资源标签的强制条件。

若目的是让消费者只能选择批准参数，使用 Template Constraint；若目的是减少调用者对底层资源的直接权限，使用 Launch Constraint；两者职责不同，常需同时使用。

五、产品生命周期与运维

  1. 建立产品：维护模板、参数、支持版本和可识别的产品信息。
  2. 发布 Portfolio：将产品放入 Portfolio，授予相应用户/组访问。
  3. 施加约束：配置 launch role、参数范围、通知、部署目标和标签。
  4. Provision：用户通过 Service Catalog 部署，平台可跟踪 provisioned product 状态。
  5. 更新/终止：发布新版本后按变更流程更新现有产品；终止前评估数据持久性、保留策略和资源依赖。
CloudFormation StackSets 适合跨账号/区域创建；Service Catalog StackSet Constraint 可以将这种多账号部署能力封装成受控产品。

六、共享、身份与治理

  • 跨账号共享：Portfolio 可按支持方式共享给其他账号或组织；接收账号仍需让本地用户/组获得相应访问，并在其环境中满足部署前提。
  • 与 Organizations：可利用组织结构进行集中共享和治理；账号加入组织并不自动代表所有用户有 Portfolio 访问权。
  • 身份：通过 IAM 用户/角色或 IAM Identity Center 身份建立消费者访问；遵循最小权限并区分目录可见性与底层部署权限。
  • 治理对比：Service Catalog 限定可自助部署的产品；SCP 限制组织账号可执行的 API 上限；Config 评估资源状态；Control Tower 编排多账号 Landing Zone 和 controls。
  • 审计：结合 CloudTrail 跟踪谁执行了产品/资源操作，结合 CloudFormation 状态和 Config 评估实际配置合规。

七、场景题解析（6 题）

1. 平台组希望员工只能自助部署批准的 CloudFormation 产品，且不授予员工创建所有底层资源的权限。

用 Portfolio 授权消费者并配置 Launch Constraint 指向最小权限角色；再以 Template Constraint 限制可选参数。

2. 用户可以访问产品，但模板启动时因缺少 EC2/VPC 创建权限失败。

检查 Launch Constraint 是否配置、角色信任关系是否允许服务使用、执行角色是否有资源权限，以及模板引用的角色/资源策略。单有 Portfolio 访问权不足以授权底层部署。

3. 产品参数中必须只允许批准的实例类型和环境值。

对 CloudFormation 产品配置 Template Constraint 限定参数允许值；如需限制用户调用任意 EC2 API，还需 IAM/SCP 等更广治理控制。

4. 同一个标准产品需要一次性部署到多个组织账号和区域。

可使用支持多账号部署的 StackSet 产品及 StackSet Constraint，并配置目标账号/OU、区域和 StackSets 权限；仅发布普通单账号产品并不会自动跨账号部署。

5. 组织要求所有目录产品创建资源时带上统一的成本中心标签。

通过 TagOptions 提供受控标签键值，并审查模板是否将标签传递到底层资源。需要更强强制性时再配合 IAM/SCP 条件或 Organizations 标签策略，不能假设 TagOptions 单独拦截所有漏标资源。

6. 新版本产品已发布，但已部署的环境仍运行旧模板。

产品版本发布不会自动更新现有 provisioned products。评估差异与数据风险后对现有产品执行受控更新，或通过合适的自动化安排升级。

九、快速自测

1. 约束用户只能选择参数值但仍由用户权限创建资源，用什么约束？

Template Constraint 限制参数；若也要避免调用者持有底层资源权限，应另配 Launch Constraint 和执行角色。

2. 哪种对象把一组产品及其访问配置呈现给消费者？

Portfolio。

3. 发布产品新版本后，现存 provisioned products 会自动更新吗？

不会；需要按变更流程显式更新现存产品。
