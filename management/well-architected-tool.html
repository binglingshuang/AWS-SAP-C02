一、先分清 Framework、Tool 与 Review

三个词在题目里经常混用，但含义完全不同。把三者分清，很多选项可以直接排除。

Well-Architected Framework
知识与最佳实践：六支柱 + 设计原则 → Well-Architected Tool
托管服务：问卷、风险台账、改进计划、里程碑 → Well-Architected Review
评审活动：自评 / AWS 主导 / 合作伙伴主导 → Improvement Plan
把结论落成有负责人和截止日期的行动
概念是什么不是什么考试提示
AWS Well-Architected Framework一套架构设计原则、六大支柱、最佳实践与问题集，以白皮书和文档形式发布。不是一个可以“打开就扫描资源”的控制台服务。问“架构应遵循什么原则”时选 Framework。
AWS Well-Architected Tool把 Framework 变成工作负载级的评审工作流：创建 Workload、应用 Lens、回答 Question、登记 Risk、创建 Milestone、维护 Improvement Plan、生成报告。不是自动检测器，不会读取你的资源或配置；答案由评审人填写。问“在哪里记录评审结论、跟踪整改”时选 Tool。
Well-Architected Review一次评审活动，可由客户团队自评，也可由 AWS 团队或 APN 合作伙伴主持；Tool 是承载评审记录的平台。不是一次性的“认证”或“合规审计”。问“如何组织评审、谁来主持”时选 Review；问“用什么工具记录”时选 Tool。
最高频陷阱：Well-Architected Tool 不做自动检测。它不会扫描 VPC、S3、IAM 或 CloudWatch 指标，也不会自动推断风险等级。所有回答、风险和优先级都来自人工评审。需要自动发现时，应该想到 Trusted Advisor、Compute Optimizer、Cost Optimization Hub、AWS Config、Security Hub 等。
工作负载是区域级资源：创建 Workload 时要选择 Region；跨区域或跨账号评审前，先确认 Region、账号范围和共享权限，避免在错误的区域里找不到工作负载。

二、六大支柱与权衡

Well-Architected Framework 用六个维度审视架构。SAP-C02 更关注“在约束下如何取舍”，而不是背定义。

支柱核心问题关键实践常见支撑服务典型权衡
卓越运营
Operational Excellence		如何稳定地交付、监控和持续改进？小步变更、基础设施即代码、可观测性、Runbook、事后复盘、游戏日演练CloudFormation、CodePipeline、CloudWatch、Systems Manager、Config自动化与标准化需要前期投入，换来更低的变更风险和更快的恢复
安全
Security		如何保护身份、数据和系统？最小权限、纵深防御、加密、审计、集中身份、事件响应IAM、KMS、Organizations/SCP、GuardDuty、Security Hub、CloudTrail更强的控制可能增加登录步骤、运维复杂度或成本
可靠性
Reliability		故障发生时能否恢复，如何减少单点？多 AZ/多区域、健康检查、自动扩缩、备份与恢复演练、容量缓冲Auto Scaling、ELB、Route 53、RDS/Aurora、AWS Backup冗余与跨区域复制提高可靠性，也提高成本与一致性复杂度
性能效率
Performance Efficiency		如何在资源约束下获得合适性能？按需选型、缓存、异步解耦、边缘加速、基于数据优化CloudFront、ElastiCache、Lambda、ECS/EKS、Global Accelerator更高性能通常意味着更高成本或更复杂的架构
成本优化
Cost Optimization		如何用合理成本达成业务目标？成本归因、rightsizing、Savings Plans/RI、Spot、生命周期策略、持续审计Cost Explorer、Budgets、Compute Optimizer、Cost Optimization Hub、S3 Lifecycle过度削减成本可能牺牲性能、可靠性或运维余量
可持续性
Sustainability		如何降低能源与资源消耗？提高利用率、减少无效运行、选择托管/高效服务、优化数据生命周期Graviton、托管服务、Auto Scaling、S3 生命周期、按需容量短期改造投入与长期资源效率之间的平衡

六条通用设计原则

  • 停止猜测容量（Stop guessing your capacity needs）：用弹性与按需容量替代静态预测。
  • 频繁测试系统（Test systems frequently）：在生产规模下验证故障恢复与性能。
  • 自动化（Automate）：把重复、易错的动作交给代码与流水线。
  • 允许架构演进（Allow for evolutionary architectures）：为变化预留接口与解耦边界。
  • 用数据驱动架构（Drive architectures using data）：用监控、成本和性能数据做决策。
  • 通过游戏日改进（Improve through game days）：主动演练故障，暴露薄弱环节。
权衡思维：六个支柱不存在“全部满分”的架构。成本与可靠性、安全与用户体验、性能与复杂度经常互相拉扯。题目会给业务约束（预算、RTO/RPO、合规、上线时间），正确选项是满足约束的平衡方案，而不是每个支柱都堆到最强。
延伸阅读：如果题目偏重 DR、HA 与多账号架构模式，可对照本站综合专题 架构设计模式；本文聚焦 Tool 的评审流程与对象关系，不重复展开 DR 策略细节。

三、核心对象模型

Tool 的题目经常考“某个对象的作用”。先记住下面这条主线，再记每个对象的边界。

Workload
顶层容器 → Lens
问卷与最佳实践包 → Question
按支柱分组的问题 → Best Practice
逐条标记是否采纳 → Risk
未采纳项登记 HRI / MRI → Improvement Plan
负责人 / 优先级 / 截止日期 → Milestone
时点快照，用于对比 → Report
PDF 汇报与归档
对象作用关键点 / 陷阱
Workload（工作负载）被评审的系统、应用或业务能力的容器；所有 Lens、风险、里程碑都挂在它下面。按业务边界划分，不是“一个 AWS 账号一个 Workload”，也不是“一个资源一个 Workload”。
Lens（视角/问卷包）一组问题与最佳实践，可叠加到 Workload 上；Framework Lens 是基础，其他 Lens 针对场景或行业补充问题。Lens 不是 Pillar；新增 Lens 不等于新增支柱。
Question（问题）评审的最小主题单元，带编号并归入某个支柱。问题本身不等于风险；只有未采纳的最佳实践才需要登记风险。
Best Practice（最佳实践）问题下的具体实践条目，逐条标记是否已采纳。“不适用”要有业务理由，不能为了让报告好看而全部标记为已采纳。
Risk（风险）记录未采纳实践带来的架构风险，分为 HRI（高风险）与 MRI（中风险）。风险由评审人判断，Tool 不自动推断；风险不等于漏洞扫描结果。
Improvement Plan（改进计划）把风险转成可跟踪的整改项，记录优先级、负责人、截止日期和状态。不是工单系统的替代品；重点是架构整改的责任与节奏。
Milestone（里程碑）记录某一时刻的回答与风险状态，形成只读快照。不做审批、不做自动修复、不回滚配置；价值在“对比”。
Report（报告）把 Workload、Lens、风险和改进计划汇总为可汇报的输出。报告是评审结果，不是合规认证或审计结论。
一句话记忆：Workload 装 Lens，Lens 出 Question，Question 有 Best Practice；没做到的记 Risk，要整改的进 Improvement Plan，阶段性成果用 Milestone 定格，最后用 Report 汇报。

四、Workload 定义与属性

Workload 是评审的起点。属性填得越准确，后续 Lens 推荐、跨账号共享和报告可读性越好。

属性说明题目提示
Name / Description工作负载名称与业务描述，用于在组织内识别评审对象。按业务能力命名，避免“测试1”“临时环境”这类无法追溯的名字。
Environment生产（Production）或预生产（Pre-production）。生产环境的评审结论通常要求更严格的可靠性与安全基线。
Review Owner评审负责人，通常是架构师或技术负责人。负责人不是“背锅人”，而是推进评审与整改的协调人。
AWS Regions工作负载实际运行的一个或多个 AWS 区域。多区域架构要在属性中体现，否则评审会漏掉跨区域一致性、DR 和延迟问题。
Non-AWS Regions本地机房、混合云或其他云所在的区域。混合架构题要记得填写，配合 Hybrid Networking Lens 使用。
Account IDs工作负载涉及的 AWS 账号。多账号架构的关键信息；也便于跨账号评审时确认范围。
Architectural Design架构设计文档或图的链接。放受控访问的链接；不要在描述或备注里写密钥、口令等敏感信息。
Industry / Industry Type行业与业务类型，帮助选择行业 Lens、理解监管背景。金融、医疗、游戏等行业题，先看行业 Lens，而不是只做 Framework Lens。
Notes补充说明、评审范围、假设与例外。把“为什么某些问题不适用”写清楚，比事后口头解释更可靠。

如何划分 Workload

  • 按业务能力或架构边界划分：一个订单系统、一个数据平台、一个面向客户的 API 网关集群。
  • 不要把整个企业所有系统塞进一个 Workload：问题数量巨大、风险无法归责、报告失去可读性。
  • 也不要把一个微服务拆成几十个 Workload：重复回答、跨服务依赖被割裂、评审成本失控。
  • 共享组件（如统一网络、集中身份）可以单独建 Workload，或作为各业务 Workload 的“依赖”在 Notes 中说明。
考试判断：题目说“需要评审一个跨 3 个账号、2 个区域的订单平台”，正确做法是创建一个覆盖该平台范围的 Workload，并在属性中填写 Regions 与 Account IDs；而不是按账号或按区域拆成 6 个互不相关的评审。

五、Lens 全解与 Pillar 的区别

Lens 是 Tool 里最容易被概念混淆的对象。记住：Pillar 是“维度”，Lens 是“视角/问卷包”。

常见 Lens

Lens适用场景关注重点
AWS Well-Architected Framework Lens所有 Workload 的基础 Lens，覆盖六大支柱。通用架构最佳实践；通常作为评审的起点和必做项。
Serverless LensLambda、API Gateway、Step Functions、DynamoDB、EventBridge 等无服务器架构。冷启动、并发与限流、事件源与重试、幂等、可观测性、成本模型。
SaaS Lens多租户 SaaS 产品。租户隔离、噪音邻居、租户 onboarding、计费与配额、数据分区。
Container Build Lens容器镜像构建与运行体系。镜像分层与供应链、构建流水线、运行时安全、可复现性。
IoT Lens设备接入、边缘计算与大规模设备运营。设备身份、连接安全、离线与断网、固件更新、边缘数据处理。
Machine Learning LensML 训练与推理工作负载。数据质量与治理、训练/推理基础设施、模型监控、MLOps 与成本。
Data Analytics Lens数据湖、批流处理与分析平台。数据分区与格式、摄取与转换、查询性能、权限与数据治理。
Hybrid Networking Lens本地与 AWS 混合网络。DX/VPN、路由与故障切换、DNS、网络分段、跨环境可观测性。
行业 Lens
Financial Services / Healthcare / Games 等		受监管或行业特性强的 Workload。行业监管、数据 residency、业务连续性与行业特定风险。以官方 Lens 目录为准。
Custom Lens（自定义 Lens）企业自有架构标准、内部合规问卷。以 JSON 模板定义问题与最佳实践，导入账号后在多个 Workload 复用；可导入/导出。

Lens 与 Pillar 的区别（必考）

对比项Pillar（支柱）Lens（视角）
本质Framework 的六个评审维度：卓越运营、安全、可靠性、性能效率、成本优化、可持续性。可应用到 Workload 的问卷与最佳实践集合，按场景或行业组织。
数量关系固定六个，是分类轴。可多个叠加；Framework Lens 覆盖全部六支柱，其他 Lens 补充特定问题。
题目问法“从哪些维度评审架构？”“评估无服务器/多租户/金融行业架构，应增加什么？”
常见错误把 Lens 当成第七个支柱。以为应用了 Serverless Lens 就可以不做 Framework Lens。
选 Lens 的口诀：Framework Lens 打底；技术形态决定场景 Lens（Serverless / SaaS / Container / IoT / ML / Data Analytics / Hybrid Networking）；行业监管决定行业 Lens；企业内部标准用 Custom Lens。
陷阱：“需要新增一个无服务器支柱来评估”——不存在这种操作，Pillar 固定为六个；正确动作是给 Workload 应用 Serverless Lens。Lens 越多不代表越全面，选择与 Workload 真正相关的 Lens，避免大量“不适用”拉低评审质量。

六、问题、最佳实践与风险等级

评审的核心动作是逐题回答。回答状态决定了是否需要登记风险，风险等级决定了整改优先级。

回答状态

状态含义后续动作注意
已采纳（Applied）该最佳实践已在 Workload 中落地。通常无需登记风险；可在备注中写实现方式与证据。不要为了“零风险”把未落地的实践标成已采纳。
未采纳（Not applied）该最佳实践尚未落地，需要评估影响。登记 Risk，选择 HRI 或 MRI，并进入 Improvement Plan。这是最常见的评审路径，也是改进计划的来源。
不适用（Not applicable）该问题或实践不适用于当前 Workload。在备注中说明理由。“不适用”不是“没做”，滥用会掩盖真实风险。
未回答（Unanswered）尚未评审。继续评审或明确列入下一轮范围。报告中未回答数量过多，说明评审尚未完成。

HRI 与 MRI

等级全称含义处理建议
HRIHigh Risk Issue高风险问题：可能显著影响安全、可靠性、合规或业务连续性。优先整改；设定负责人和明确截止日期；若暂不整改，需要书面的风险接受记录。
MRIMedium Risk Issue中风险问题：有影响但可控，或需要较长周期优化。纳入改进计划批量处理；结合成本与工作量排序。
概览会汇总：Workload 页面通常显示已回答/未回答数量以及 HRI/MRI 计数。这些数字是评审进度和风险态势的快速指标，也是 Milestone 对比的核心数据。
三个常见错误：
  • 把 Risk 当成“漏洞”：HRI/MRI 是架构取舍的风险等级，不是漏洞扫描的严重级别。
  • 认为 Tool 会自动定级：风险等级由评审人根据业务上下文判断；同一个最佳实践在不同 Workload 中可能是 HRI，也可能不适用。
  • 只登记风险、不建改进项：风险台账不产生行动，改进计划才有负责人和截止日期。
风险接受也要留痕：如果业务上决定暂不整改，应把理由、批准人和复审时间写入备注，并把改进项状态标记为“风险已确认（Risk acknowledged，具体选项以控制台为准）”，而不是删除风险或伪装成已采纳。

七、Milestone 里程碑

Milestone 是某一时刻 Workload 评审状态的只读快照。它的核心价值不是“存档”，而是“对比”和“证明改进”。

维度说明
记录内容该时点的 Lens 回答、风险等级与相关评审信息。
创建方式在 Workload 中创建 Milestone，填写名称与备注；一个 Workload 可以有多个 Milestone。
是否可变只读快照。之后修改 Workload 的回答，不会改变已创建的 Milestone。
典型用途建立评审基线、上线前存档、季度复审对比、故障复盘、迁移前后对比、向管理层展示风险下降。
删除影响删除 Workload 会连同其 Milestone 等关联数据一起删除，操作前要确认。
不是什么不是审批流、不是自动修复、不是配置回滚、不是合规认证。

推荐的 Milestone 命名与节奏

  • 基线：2026-Q4 Baseline，第一次完整评审结束时创建。
  • 上线前：Pre-launch 2026-12，确认 HRI 已关闭或有明确接受记录。
  • 季度复审：2027-Q1 Review，对比 HRI/MRI 数量、未回答数和改进项完成情况。
  • 重大变更后：架构迁移、区域扩展、收购整合后创建新快照，便于解释风险变化。
对比看什么：HRI 数量是否下降、MRI 是否被消化、未回答问题是否减少、风险是否从“安全/可靠性”转移到可控的“成本/性能”类别、改进项完成率是否提升。
陷阱：题目问“如何证明六个月前评审后风险确实下降”，答案是创建并对比 Milestone（基线 vs 当前），而不是查 CloudTrail、Config 或 Trusted Advisor。后者能提供证据，但不能替代评审快照的对比。

八、改进计划与优先级排序

Improvement Plan 把“已知风险”变成“有人负责、有期限、有状态”的整改清单。

字段用途排序建议
Title / Description整改动作的简述与验收标准。写成可执行动作，避免“加强安全”这类空泛描述。
Priority优先级（高/中/低）。HRI 通常为高；影响安全、可靠性、合规的优先。
Owner责任人。必须是能推动变更的人，而不是“整个团队”。
Due date截止日期。与发布节奏、审计窗口、季度复审对齐。
Status未开始 / 进行中 / 完成 / 风险已确认（以控制台为准）。“风险已确认”用于业务决定暂不整改的场景，需保留理由与批准人。
Notes依赖、例外、验证方式、工作量估算。工作量可按低/中/高估算，作为排序输入；Tool 不会自动计算工期。

推荐的排序方法

  1. 先 HRI，后 MRI：高风险问题优先，尤其是安全、可靠性与合规相关项。
  2. 同等级看影响与工作量：影响大、工作量小的先做；影响大、工作量大的拆成阶段性里程碑。
  3. 成组处理：同一根因导致的多个 MRI 合并为一个整改项，避免重复工单。
  4. 明确接受风险：业务上不打算整改的项，要有批准人、理由和复审日期，不能静默跳过。
  5. 闭环验证：整改完成后重新回答对应问题（标记为已采纳），更新改进项状态，并创建新的 Milestone 记录结果。
工作量（Effort）怎么考：题目常给“5 个 HRI、40 个 MRI、预算和人力有限”。正确思路是先按风险等级和业务影响排序，再用工作量判断先后与拆分；不是按问题编号顺序全部处理，也不是只做工作量最小的项。Tool 的字段重点是优先级、负责人、截止日期和状态，工作量通常写在描述或备注中。
与工单系统的关系：Improvement Plan 是架构评审的整改台账；复杂项目可以把条目同步到 Jira、ServiceNow 等工单系统（手工或通过 API/自动化），但评审结论仍以 Tool 中的记录为准。

九、报告、共享与跨账号评审

报告与导出

输出内容 / 用途注意
PDF 报告汇总 Workload 元数据、Lens 评审结果、HRI/MRI、问题回答与改进计划，用于归档和管理层汇报。报告是评审快照，不等于合规认证；敏感信息不要写进 Notes。
自定义 Lens 的 JSONCustom Lens 可导入/导出为 JSON，便于跨账号、跨团队复用同一套企业问卷。导入前确认版本与问题编号，避免覆盖或重复。
API 读取可通过 Well-Architected Tool API 读取 Workload、Lens 评审与改进项，用于自动化汇总或与内部平台集成。用 IAM 最小权限；API 调用同样受 Region 与账号范围约束。

共享与跨账号评审

场景常见做法注意
同账号内协作用 IAM 控制谁可以查看或编辑 Workload；按角色分配架构师、评审人、只读干系人。不要让所有用户都有删除 Workload 的权限。
跨账号共享Workload 所有者把 Workload 共享给其他 AWS 账号，可按需授予只读或可编辑权限；对方在自己的 Tool 中访问。共享是访问权限，不是自动汇总或自动扫描对方账号资源。
组织内集中评审由中央架构团队或管理账号建立 Workload，共享给成员账号参与回答；结合 Organizations 统一治理。确认 Region 一致、成员账号范围、共享权限与审计记录。
合作伙伴/AWS 主导评审通过跨账号角色、Workload 共享或由合作伙伴在其环境中记录评审；结束后输出报告与改进计划。遵循最小权限和保密要求；评审结束后回收访问。
跨账号评审的推荐流程：确定评审范围与 Region → 中心团队创建 Workload 并填写账号/区域属性 → 共享给相关账号（只读或可编辑）→ 各账号完成对应问题 → 中心团队汇总风险与改进计划 → 创建 Milestone → 生成 PDF 报告归档。
陷阱：“共享 Workload 后，Tool 会自动收集所有成员账号的资源并生成风险”——错误。共享只解决访问与协作，评审答案仍由人填写；资源层面的自动发现要靠 Trusted Advisor、Config、Security Hub 等工具。

十、与相邻服务的边界

SAP-C02 很喜欢用“应该用哪个服务”制造干扰项。下面这张表决定大多数边界题。

服务擅长解决与 Well-Architected Tool 的边界 / 配合
AWS Trusted Advisor基于 AWS 预建规则的自动检查与建议，覆盖成本、性能、安全、容错、服务配额等类别；能力与支持计划相关。自动发现，不做架构问卷、风险台账和里程碑。评审时把检查结果作为证据，重大问题转为 Risk/Improvement。
AWS Compute Optimizer基于利用率数据给出计算资源规格与配置建议（如 EC2、Auto Scaling、EBS、Lambda）。资源级 rightsizing，不是架构评审。可作为性能效率/成本优化支柱的输入。
Cost Optimization Hub跨账号汇总成本优化机会与建议（闲置资源、承诺折扣、迁移等）。成本专项建议，不替代六支柱评审。可作为成本优化支柱的证据与改进项来源。
AWS Config记录资源配置历史、按托管/自定义规则评估合规、支持自动修复与聚合。回答“资源配置是否符合规则”，不回答“架构是否优秀”。是卓越运营/安全支柱的持续证据。
AWS Audit Manager对照 SOC 2、PCI DSS、ISO 等合规框架自动收集与整理审计证据。合规审计工具，不是架构最佳实践评审；两者可以互相引用证据，但结论不同。
Security Hub / GuardDuty汇总安全发现、标准控制与威胁检测。安全发现是安全支柱的输入；不等于 Well-Architected 的风险等级。
AWS Architecture Center参考架构、最佳实践指南与白皮书。知识库，不提供 Workload 级评审记录与整改跟踪。
Service Catalog / Control Tower标准化产品目录、Landing Zone 与护栏治理。把评审结论落到“可部署的标准”和“组织级控制”，不是评审工具本身。
一句话区分：Trusted Advisor、Compute Optimizer、Cost Optimization Hub、Config 是自动发现与合规检查；Well-Architected Tool 是人工评审 + 风险登记 + 改进跟踪。前者产出证据，后者产出评审结论与行动计划。
题干关键词映射：“自动检查/支持计划/五类检查” → Trusted Advisor；“rightsizing/利用率” → Compute Optimizer；“跨账号节省机会” → Cost Optimization Hub；“配置合规历史/自动修复” → AWS Config；“架构问卷/风险分级/里程碑” → Well-Architected Tool。

十一、场景题解析（7 题）

1. 一家公司要在上线前评审一个基于 Lambda、API Gateway、Step Functions 和 DynamoDB 的订单系统。架构师希望使用 Well-Architected Tool 完成评估。最合适的做法是？

A. 只启用 Trusted Advisor，等待自动检查生成评审报告
B. 创建一个 Workload，应用 Framework Lens 与 Serverless Lens，逐题人工回答并登记风险
C. 为每个 Lambda 函数创建一个 Workload，分别评审
D. 新建一个“Serverless 支柱”，再导入 CloudWatch 指标自动评分

答案：B。Tool 的评审单位是 Workload，先应用覆盖六支柱的 Framework Lens，再叠加针对无服务器架构的 Serverless Lens。
排除：A 把自动检查当成架构评审；C 粒度错误，Workload 应按业务/架构边界划分；D 不存在“新增支柱”的操作，Tool 也不会根据指标自动评分。

2. 六个月前完成了一次 Well-Architected 评审，现在管理层要求证明高风险问题确实减少。应该怎么做？

A. 查看 CloudTrail 事件数量
B. 用 AWS Config 查看资源配置变更
C. 将当前评审与六个月前的 Milestone 对比，展示 HRI/MRI 与未回答问题的变化
D. 重新运行 Trusted Advisor 并导出检查结果

答案：C。Milestone 记录某一时点的回答与风险状态，可与当前状态或其他 Milestone 对比，这是“证明改进”的标准做法。
排除：CloudTrail 记录 API 调用，Config 记录资源配置，Trusted Advisor 提供自动检查；它们能作为证据，但不能替代评审快照的前后对比。

3. 一个组织有 20 个成员账号，中央架构团队要统一评审各账号的核心工作负载，同时让成员账号参与回答。最合适的方案是？

A. 给所有成员账号发放管理账号的 root 凭证，共用一个 Workload
B. 由中央团队创建 Workload，通过 Workload 共享授予相关账号只读或可编辑权限，结合 Organizations 治理
C. 每个账号各自创建 Workload，禁止中央团队访问
D. 用 AWS Config Aggregator 自动生成评审答案

答案：B。跨账号评审的常见做法是 Workload 所有者共享给目标账号，按需授予只读或可编辑权限，并由组织级治理统一范围与审计。
排除：A 严重违反最小权限；C 会形成 20 份互不关联的记录，无法统一对比；D 配置聚合器不产生架构评审答案。

4. 团队认为 Well-Architected Tool 会自动扫描资源，于是把 Trusted Advisor 的检查结果直接当作评审答案提交。这个做法的问题是什么？

A. 没有给 Workload 绑定 KMS 密钥
B. Tool 不自动检测资源，必须人工回答；Trusted Advisor 结果只能作为评审证据
C. 必须先购买 Enterprise Support 才能使用 Tool
D. 必须先创建 Custom Lens，否则无法提交

答案：B。Tool 是问卷式评审平台，不会读取资源或自动推断风险。Trusted Advisor 是自动检查工具，可作为输入证据，但不能代替逐题回答、风险分级和改进计划。
排除：A、C、D 都是与题意无关的条件；Tool 的使用不要求先购买特定支持计划或先建 Custom Lens。

5. 评审发现某条最佳实践尚未落地，但业务负责人认为当前取舍可以接受，短期内不打算整改。应如何记录？

A. 直接标记为“已采纳”，避免报告中出现风险
B. 标记为“不适用”，不写任何理由
C. 登记风险并选择 HRI/MRI，在改进计划中记录“风险已确认”及理由、批准人和复审时间
D. 删除该问题，等下次评审再处理

答案：C。未落地就是风险，应如实登记等级；业务接受并不等于风险消失，需要留痕和复审。改进计划中的“风险已确认”状态（具体名称以控制台为准）用于这种场景。
排除：A 伪造评审结果；B 滥用“不适用”；D 删除问题会掩盖风险，也破坏评审的可追溯性。

6. 一次评审产生 5 个 HRI 和 40 个 MRI，团队人力有限。架构师应如何安排改进计划？

A. 按问题编号顺序处理，保证每个问题都被触碰一次
B. 先处理 5 个 HRI（优先安全/可靠性/合规），再按影响与工作量对 MRI 分组排序；接受风险的项要留痕
C. 只处理工作量最小的 45 项
D. 等所有 HRI 自动修复后再处理 MRI

答案：B。先按风险等级和业务影响排序，再结合工作量决定先后与拆分；MRI 可合并同根因项批量处理。
排除：A 平均用力会拖延关键风险；C 工作量最小不等于影响最小；D Tool 不会自动修复，HRI 必须有人负责推进。

7. 某团队想评估一个金融行业的多租户 SaaS 平台，计划在 Tool 中“新增一个 SaaS 支柱”。正确做法是？

A. 新增 SaaS 支柱，并替换掉安全支柱
B. 只使用 Framework Lens，因为行业属性不影响评审
C. 在 Workload 上应用 SaaS Lens，并按行业监管需要再应用 Financial Services Industry Lens；Framework Lens 仍然保留
D. 创建 6 个 Workload，分别对应 6 个支柱

答案：C。Pillar 固定为六个，不能新增；Lens 才是按场景/行业补充问题的问卷包。多租户 SaaS 用 SaaS Lens，金融行业叠加行业 Lens，Framework Lens 继续作为基础。
排除：A 混淆 Lens 与 Pillar 且破坏基础评审；B 漏掉多租户与行业特定风险；D 把评审维度误当成 Workload 划分依据。

十四、快速自测

先独立作答，再展开查看解析。

1. Well-Architected Tool 能否替代 Trusted Advisor 自动发现资源配置问题？

不能。Tool 是人工问卷式评审，不会扫描资源。Trusted Advisor 提供自动检查，可作为评审证据；两者互补，不是替代关系。

2. 一个 Workload 已回答 60 个问题、还有 20 个未回答，形成了 3 个 HRI 和 12 个 MRI。Milestone 应该记录什么？又该如何解读这些数字？

Milestone 记录该时点的回答与风险快照。解读时应关注：未回答 20 个说明评审未完成；3 个 HRI 应优先整改或有明确的风险接受记录；12 个 MRI 可批量排序处理。不要只看 HRI/MRI 总数而忽略未回答比例。

3. 团队想用企业自己的 30 条架构标准来评审多个账号的系统，并希望在其他账号复用同一套问题。最合适的做法是？

创建 Custom Lens（以 JSON 定义问题与最佳实践），导入到需要使用的账号并应用到各 Workload；Custom Lens 可导入/导出复用。不要为每个账号手工复制 30 条问题，也不要把企业标准伪装成新的 Pillar。
