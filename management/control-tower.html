AWS Control Tower
多账号 Landing Zone 与护栏

Control Tower 在 AWS Organizations 之上帮助建立和治理多账号 Landing Zone。它编排账号结构、集中日志/审计能力、控制项与账号配置流程；不是独立于 Organizations 的另一套账号体系，也不会自动治理所有既有资源。

一、Control Tower 能力地图

Control Tower 将多账号治理的常见搭建工作流产品化：建立 Landing Zone、注册 OU/账号、应用控制项、集中查看治理状态，并通过 Account Factory 建立符合基线的新账号。

组件用途考题关键词
Landing Zone组织级多账号基础环境与治理基线。组织结构、共享审计、日志归档、控制项。
Controls按 OU/账号应用预防性、检测性或主动性控制。SCP、AWS Config、CloudFormation Hooks 等实现方式。
Account Factory按标准配置供应新 AWS 账号。创建账号、加入目标 OU、基线治理与后续定制。
Account enrollment将已有账号纳入 Control Tower 治理。注册前满足先决条件；检查控制项和组织配置。
Control Tower 是治理编排层，底层仍使用 Organizations、IAM Identity Center、CloudFormation、AWS Config 等服务。控制项的实际实现和可用范围以 Control Catalog/区域支持为准。

二、Landing Zone 与多账号结构

  • 管理账号：承载 Organizations 管理能力和 Control Tower 管理操作。应避免在管理账号运行普通工作负载，保护其权限与账单/组织管理边界。
  • Log Archive：集中接收和保存来自治理环境的日志，访问通常严格受限；集中存储不等于已自动满足所有保留、加密和不可变要求。
  • Audit：供安全/审计团队集中查看或执行跨账号审计任务；其角色和可访问范围应依据当前 Landing Zone 版本及部署设置验证。
  • OU：按环境、业务或治理边界组织账号，向 OU 应用控制项。合理分层可减少逐账号配置；不要通过创建过多 OU 替代清晰的策略设计。
  • 区域：Landing Zone 的 home region 与治理启用区域需一致规划。新增区域或更改治理配置可能需要更新 Landing Zone，并验证账号/服务的区域状态。

Landing Zone 的共享账号命名和部分架构随版本可能调整；设计时应以实际控制台、当前文档和组织要求核验，不要把历史默认值当成固定限制。

三、Controls：预防、检测与主动治理

控制类型典型实现何时生效 / 局限
预防性（Preventive）常以 SCP 等组织策略限制 API 行为。在操作发生前拒绝受限动作；不会自动修复已有违规配置，且不授予权限。
检测性（Detective）常以 AWS Config 规则评估资源状态。资源变化/评估后发现不合规；通常不阻止创建，不等同自动修复。
主动性（Proactive）可通过 CloudFormation Hooks 等机制在受支持的部署路径中评估。针对受支持的 CloudFormation 操作进行部署前检查；不保证拦截绕过该路径的所有 API 操作。
  • 控制项可针对 OU/账号启用或停用；继承范围、冲突策略和可选参数要结合组织结构评估。
  • SCP 设置权限上限，不授予 IAM 用户/角色权限；显式拒绝与更高层级策略继承需仔细核对。
  • 检测控制通常需要 Config 记录器、服务关联角色和目标区域配置正常。看到控制项启用不代表所有现存资源立即符合。
考试陷阱：预防性控制 ≠ IAM 授权；检测性控制 ≠ 预防创建；主动控制只对所支持的 CloudFormation 部署路径有效。

四、Account Factory 与账号生命周期

  1. 预备组织：建立 Landing Zone 和 OU 治理结构，配置 Identity Center、共享日志/审计与必需服务权限。
  2. 供应账号：Account Factory 按指定账号信息、邮箱/所有者属性和目标 OU 建立新账号，并纳入预设治理基线。
  3. 配置定制：根据标准流程应用网络、身份、日志和安全基线；可结合 Control Tower 支持的定制机制或组织自己的部署流水线。
  4. 既有账号注册：核对账号所属组织、先决条件、现存资源/角色与目标 OU，再执行 enrollment；检查治理状态及未合规控制项。
  5. 持续治理：账号移动 OU、控制项变更、区域扩展或底层资源手工修改后，重新检查合规与 drift，避免仅凭供应成功判断完成。

Account Factory 负责按治理流程供应账号，不等于应用团队产品目录或任意资源模板。账号自定义与生命周期自动化的实现方式可随 Control Tower 版本演进。

五、治理漂移、修复与协同服务

  • 治理状态：Control Tower 可识别 landing zone/账号层面的配置状态；治理漂移可能来自手动更改底层 Organizations、共享角色、策略或记录器配置。
  • 修复：先明确 drift 来源和影响，再通过 Control Tower 的修复/更新流程恢复治理基线；避免直接删除由服务管理的资源。
  • AWS Config：提供资源配置记录、规则评估和聚合；Control Tower 的检测控制依赖相关配置治理能力，但二者覆盖面与用途不完全相同。
  • Organizations：账号、OU、SCP 和合并账单的基础组织服务；Control Tower 在其上编排标准 landing zone 与护栏。
  • CloudTrail：审计 API 调用；集中日志存储和告警/保留策略仍需按组织需求验证。

七、场景题解析（6 题）

1. 企业从零建立多账号环境，希望自动创建治理基线并标准化新账号配置。

采用 Control Tower 建立 Landing Zone，通过 OU/controls 管理边界，并用 Account Factory 供应新账号；同时规划共享日志/审计、Identity Center 和区域。

2. 新账号上线后必须阻止用户关闭组织要求的安全服务。

选择适用的预防性 control（通常由 SCP 等实现）并作用于目标 OU。SCP 限制最大权限但不授予权限；确认例外和管理账号语义。

3. 管理员希望发现所有已有 S3 bucket 是否缺少加密设置，但不阻断其他资源创建。

使用检测性 control / AWS Config 规则评估现有资源；若需要修复再另配修复流程。主动/预防控制并非此处发现存量违规的主要方案。

4. CloudFormation 部署必须在创建前检查模板是否符合组织约束。

对受支持的 CloudFormation 路径评估主动性 control（如 CloudFormation Hooks 实现）。仍需处理非 CloudFormation 创建路径，不能认为它覆盖所有 API。

5. 组织已有多个 AWS 账号，想纳入 Control Tower 统一治理而不是重新创建。

先检查既有账号的组织归属和 enrollment 先决条件，再将账号注册到符合设计的 OU；随后检查控制项合规、资源角色和可能的 drift。

6. Control Tower 报告 Landing Zone drift，团队准备直接删除相关服务管理的 IAM 角色。

不要直接删除。查明底层变更及受影响服务，通过 Control Tower 推荐的更新/修复流程恢复基线，并验证治理状态与共享账号访问。

九、快速自测

1. 哪种控制更适合在违规 API 操作发生前拒绝它？

预防性 control，通常借助 SCP 等机制；它限制权限上限但不负责授予允许权限。

2. 想发现已经存在的配置违规，应选预防性还是检测性 control？

检测性 control，通常由 AWS Config 规则评估资源当前配置。

3. Account Factory 与 Service Catalog 的主要区别是什么？

Account Factory 供应符合组织治理基线的 AWS 账号；Service Catalog 提供受控的 IT 产品/资源模板自助部署。
