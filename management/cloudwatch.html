一、CloudWatch 能力地图

Amazon CloudWatch 收集指标、日志和部分服务事件，支持查询、可视化、告警与自动化响应。不同遥测类型面向不同问题：Metrics 看数值趋势，Logs 记录文本/结构化事件，Alarms 判断阈值状态并触发动作。

组件核心作用题目线索
Metrics按时间序列保存数值数据点，可创建自定义指标与数学表达式。CPU、延迟、队列长度、业务吞吐和自定义 SLA。
Alarms评估指标或表达式，在 OK / ALARM / INSUFFICIENT_DATA 等状态间变化。超过阈值后通知、扩缩容或触发自动化。
Logs收集并存储日志组/日志流，执行 Insights 查询、指标过滤和订阅转发。应用日志、系统日志、排障分析和日志管道。
Dashboards跨服务/账号/区域可视化指标与告警。集中运维视图，不等同于自动告警。
Events / EventBridge按服务事件或自定义事件匹配规则并路由目标。资源状态变化、计划事件、事件驱动工作流。
告警闭环：产生遥测 → 选择指标/日志/事件 → 设置阈值或规则 → 确认状态变化 → 配置通知/动作 → 验证响应、权限和告警恢复。

二、Metrics 与维度

  • Metric 由 Namespace、Metric Name、零个或多个 Dimensions、时间戳、数值和 Unit 等构成；Dimension 组合会形成不同的指标序列。
  • AWS 服务自动发布许多基础指标；客户可发布 Custom Metrics，应用与 CloudWatch Agent 可发送自定义业务/主机指标。
  • EC2 默认监控指标不等于 OS 内部指标；内存、文件系统使用率、进程等通常需要安装并配置 CloudWatch Agent。
  • 高分辨率自定义指标可提供更细粒度数据与告警评估，但会增加数据点数量和成本；选择满足响应目标的最低分辨率。
  • 指标保留期会随数据聚合粒度变化；细粒度原始数据保留时间较短，长期趋势会被聚合，成本与保留期需纳入设计。
  • Dimensions 用于区分指标维度，但每个唯一组合都会形成单独时间序列；动态 ID 作为维度可能造成高基数和成本增长。
需求指标来源 / 方案注意点
EC2 CPU / 网络EC2 默认 CloudWatch Metrics基础指标粒度通常为分钟级；详细监控可提高报告频率。
EC2 内存与磁盘使用率CloudWatch Agent 收集并发布先配置 Agent、权限和命名空间；默认 EC2 指标不会提供 OS 内部使用率。
应用业务指标PutMetricData / Agent / OpenTelemetry 集成等控制 Dimensions 数量，统一命名、单位和发布间隔。
日志匹配次数告警CloudWatch Logs Metric Filter 生成指标过滤器只处理新写入的日志事件，不是历史日志回算工具。
多个指标组合判定Metric Math / Composite Alarm组合表达式支持范围与告警能力需按当前配置验证。
维度陷阱：把用户 ID、请求 ID 等高基数值作为指标维度，会迅速增加指标时间序列和费用；逐条明细通常适合日志/追踪系统。

三、Alarms 与自动响应

Alarm 配置含义常见误区
Threshold指标统计值在评估窗口内与阈值比较。必须选择正确 Statistic、Period、Unit 和比较方向。
Evaluation Periods / Datapoints to Alarm定义多个评估数据点中需要多少个越界才进入 ALARM（M out of N）。可平滑抖动，但也会增加响应延迟。
Missing data treatment将缺失数据视为 missing、not breaching、breaching 或 ignore。缺数据可能表示服务无流量、监控中断或应用故障，需按语义选择。
Alarm action向 SNS 发布、触发 Auto Scaling、EC2 动作或其他支持的自动化。告警状态本身不会自动修复业务；目标权限、Region 和动作类型须匹配。
Composite Alarm使用多个 Alarm 的状态逻辑组合，减少告警风暴。组合告警依赖基础告警；不要只监控 Composite 而丢掉底层诊断信息。
  • EC2 Alarm Actions 可在支持配置中执行停止、终止、重启或恢复实例等动作；选择动作前确认实例恢复语义和数据持久性。
  • Auto Scaling policy 可由 CloudWatch Alarm 触发，但扩缩容量仍受 ASG Min/Max、冷却/暖机、配额和启动失败影响。
  • 高可用告警应区分症状与原因；例如延迟、错误率与资源利用率分层监控，避免单一 CPU 阈值漏报业务故障。
  • 配置 SNS 通知时，确认 Topic Policy、订阅确认、加密密钥权限和下游通知渠道可达。
  • 对告警做定期演练：模拟阈值、验证通知/动作，再恢复测试资源；防止长期“ALARM 但无人响应”。
阈值判断：短暂毛刺 → M-of-N 或 Composite；需要快速检测 → 缩短 Period/增加分辨率并接受费用；不应把缺失数据一律当作正常。

四、Logs、Agent 与 Insights

能力作用设计点
Log Group / Log Stream按应用/服务组织日志组，在组内按来源组织日志流。设置保留期、加密、资源策略和命名标准；未设保留期的日志可能持续保存并产生成本。
CloudWatch Agent收集 EC2/本地服务器的日志、内存、磁盘等 OS 指标。配置 Agent、执行角色/凭证、日志路径与指标集合；监控 Agent 健康。
Logs Insights交互式查询和分析结构化/非结构化日志。按时间范围与 Log Group 缩小扫描；查询费用与扫描数据量相关。
Metric Filter从进入日志组的新日志匹配模式并生成指标。适合错误计数告警；过滤模式和单位需正确，无法回算历史数据。
Subscription Filter实时将匹配日志转发至 Lambda、Kinesis 或 Firehose 等目标。设计目标权限、重试、背压与跨账号目的地策略。
  • 日志存储、查询和传输均可能产生成本；设置合理保留期、过滤不必要的高频日志并在需要时导出到 S3 长期归档。
  • Logs Insights 使用类似查询语言分析日志字段；先选对账号/区域/日志组与时间范围，再进行聚合、过滤和排序。
  • 跨账号日志集中可以通过 CloudWatch Logs 的目标/资源策略、订阅与集中日志架构实现；确保源/目标策略、KMS 密钥与区域配置正确。
  • 日志内容可能包含凭证、个人信息或业务机密；在应用侧脱敏并严格控制 Log Group 读取权限。
  • 需要对所有 API 调用进行审计时用 CloudTrail；CloudWatch Logs 可接收/查询日志，但不是 CloudTrail 的替代品。

五、事件、仪表板与跨账号

  • Dashboards：汇总图表、指标、文本和告警状态，可用于跨服务/账号/区域的运维视图；Dashboard 本身不触发扩缩或修复。
  • EventBridge：基于服务事件与自定义事件匹配规则，路由到 Lambda、SNS、Step Functions 等；适合事件状态驱动工作流。
  • CloudWatch Alarm：基于指标阈值/统计结果的状态评估，适合阈值告警与扩缩动作。
  • Cross-account observability：通过 CloudWatch Observability Access Manager（OAM）等机制让监控账号查看来源账号的指标、日志和追踪数据；配置 Sink/Link 与组织信任策略。
  • 跨账号 IAM：旧式跨账号 Dashboard/Alarm 设计可使用角色委派；应采用当前推荐的观测配置并明确数据可见范围。
  • 跨区域：CloudWatch 数据按区域组织；Dashboard 可引用受支持的跨区域数据，但 Alarm 和源指标区域要配置正确。
场景优先使用关键区别
CPU 持续高于阈值时扩容Metric Alarm + Auto Scaling Policy数值评估驱动动作。
EC2 状态变化时触发运维流程EventBridge rule事件匹配，不要求指标越界。
多账号统一运维看板CloudWatch Dashboard / OAM配置账号间数据共享和观测权限。
跨账号日志实时转发Logs Subscription Filter + 目标策略重点是日志数据管道与权限。

六、应用与容器可观测性

  • Container Insights：收集 ECS/EKS 等容器环境的集群、服务、任务/Pod 和节点指标；启用后会产生指标与日志费用。
  • Application Signals / ServiceLens：关联应用服务、依赖、指标与追踪，定位端到端延迟和错误；按应用支持和配置启用。
  • Synthetics：Canary 定期模拟用户请求，检测公网或内部端点的可用性、延迟和功能路径。
  • CloudWatch RUM：从真实用户浏览器收集前端体验数据，补足合成探测无法代表实际用户网络的部分。
  • Trace / X-Ray：分布式追踪用于跨服务请求链路；和指标、日志关联可缩短根因定位时间。
  • 异常检测：CloudWatch Anomaly Detection 可基于历史模式生成动态阈值；季节性变化、冷启动或异常历史需评估模型效果。
指标闭环：基础设施可用性、应用 SLI、日志错误和分布式追踪应互相补充。启用容器或高基数细粒度遥测前，先评估采集量、保留期、查询费用与告警责任人。

八、场景题解析

场景一：EC2 内存不足导致应用错误

CloudWatch 已有 EC2 CPU 指标，但团队看不到内存和磁盘利用率，希望配置告警。

正确方向：安装并配置 CloudWatch Agent 收集 OS 内存/磁盘指标，再创建 Metric Alarm 与通知/动作。

分析思路：EC2 默认指标不含所有 OS 内部数据；Agent 需有日志/指标发布权限。

排除：仅开启 EC2 Detailed Monitoring 不会自动产生内存使用率。

场景二：错误日志出现时立即触发通知

应用日志写入 CloudWatch Logs，希望根据新日志中的特定错误关键字统计并告警。

正确方向：创建 Logs Metric Filter 生成错误计数指标，再为该指标创建 Alarm 并通知 SNS。

分析思路：Metric Filter 把新日志匹配结果转换为数值指标，Alarm 负责阈值评估与响应。

排除：Logs Insights 是交互式查询，不会自动替代 Alarm；过滤器也不会回算历史日志。

场景三：多账号运维团队集中查看指标和日志

多个成员账号分别运行应用，运维团队需要在监控账号查看来源账号的指标、日志与追踪数据。

正确方向：评估 CloudWatch Cross-account observability / OAM，建立 Sink 与 Source Links 并限制可共享数据。

分析思路：OAM 提供跨账号观测数据共享，减少逐账号手工复制指标的维护。

排除：单纯创建一个 Dashboard 不会自动授权访问其他账号数据。

场景四：CPU 告警触发 ASG 扩容但没有新实例

Alarm 进入 ALARM 状态，但 ASG 没有启动实例。

正确方向：检查 Alarm Action 与扩缩策略绑定、ASG Min/Max、扩缩活动记录、实例启动模板、配额及 IAM/服务角色。

分析思路：Alarm 状态只是触发条件；ASG 扩缩策略和底层启动必须都成功。

排除：反复调低阈值不会解决 MaxSize 已满、启动模板无效或配额不足。

场景五：定位请求跨多个服务的延迟根因

用户请求经 API、Lambda、队列和数据库，需观察每个服务的耗时与失败位置。

正确方向：结合分布式追踪（X-Ray/受支持的追踪集成）、CloudWatch Metrics、Logs 和 Application Signals/ServiceLens。

分析思路：追踪串联请求路径，指标显示整体趋势，日志提供错误上下文。

排除：单一 CPU Dashboard 无法显示跨服务调用链路与具体慢操作。

场景六：区分 API 审计和资源配置漂移

合规人员既要知道谁修改了安全组，又要判断现有安全组是否符合规则。

正确方向：CloudTrail 记录 API 操作主体与事件；AWS Config 记录资源配置并评估规则；CloudWatch 可监控指标/日志告警。

分析思路：三个服务的数据用途不同，应关联而非互相替代。

排除：仅依赖 CloudWatch CPU 或应用日志无法构成完整的配置变更审计。

1. 需要监控 EC2 主机的内存使用率，默认 CloudWatch 指标中没有该数据。应怎么做？
