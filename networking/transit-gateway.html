一、Transit Gateway 的定位

AWS Transit Gateway（TGW）是区域级的托管路由中枢：VPC、VPN、Direct Connect、其他 TGW 都作为"附件"挂到它上面，由它在一张或多张路由表中完成转发。它解决的是 N 个 VPC 全互联带来的 N×N 条 Peering 问题。

三个必须记住的属性

  • 区域级资源：TGW 属于某个 Region，不能直接挂载另一个 Region 的 VPC；跨 Region 需要 TGW Peering。
  • 转发是"传递"的：同一个 TGW 内，A → B、B → C 的流量可以由 TGW 中转，不需要 A、C 建 Peering。这是它和 VPC Peering 的本质区别。
  • 路由可控：通过多张路由表把"全互通"切成多个路由域，实现生产/测试隔离、共享服务访问等设计。
一句话选型：2–3 个 VPC 点对点 → VPC Peering 够用；10+ VPC、多账号、混合云、需要集中出口 → Transit Gateway。

TGW 能做什么、不能做什么

二、附件（Attachments）类型

TGW 的所有连接都以"附件"形式存在。考试只要看到"什么资源挂到 TGW"，先定位附件类型，再判断路由与配额。

附件类型连接对象典型用途路由来源
VPC Attachment同 Region 的 VPC（指定一个或多个子网）VPC 互联、集中出口VPC CIDR（静态）
VPN AttachmentSite-to-Site VPN Connection本地/分支通过 IPsec 接入静态路由或 BGP
DX Attachment（Transit VIF）Direct Connect Gateway专线接入多 VPC、专线加密叠加BGP
TGW Peering Attachment另一个 Region 的 TGW跨 Region 组网对端 TGW 的路由
Connect Attachment支持 GRE + BGP 的 SD-WAN / 网络设备替代 IPsec，接入第三方 SD-WANBGP

VPC Attachment 的细节

  • 一个 VPC 在同一 TGW 上通常只有一个附件，可在附件中指定多个子网（不必整个 VPC）。
  • 附件创建后会生成一块 TGW 侧的 ENI 所在子网路由；VPC 路由表需把目标网段指向 TGW。
  • Appliance Mode 是 VPC 附件的一个选项：让同一流量始终落在同一个 AZ，供防火墙/NAT 等有状态设备使用，避免跨 AZ 造成会话中断。
易错点：TGW 附件创建成功不代表业务可达。VPC 内还需要路由表指向 TGW，TGW 路由表还需要有目标网段并关联到该附件，两个方向都成立才通。
与 DX 的衔接：Direct Connect 通过 Transit VIF + Direct Connect Gateway 关联到 TGW，而不是像 VPC 那样直接建附件。这样一条专线可服务多个 Region 的多个 VPC。

三、路由表、关联与传播

TGW 的路由模型只有两个动作：Association（关联）决定某个附件"使用哪张路由表"；Propagation（传播）决定某个附件的路由"进入哪张路由表"。隔离与互通都靠这两个动作组合。

概念含义类比
Transit Gateway Route Table一张路由表，包含目标网段与下一跳附件路由器的路由表
Association把附件绑定到某张路由表，决定它"按哪张表转发"接口加入某个路由域
Propagation把附件的路由注入某张路由表，决定别人"能不能看到它"路由重分发
Blackhole Route黑洞路由，命中即丢弃流量，用于阻断路由层面的拒绝
Default Route Table创建 TGW 时自动生成，新附件默认关联并传播到它默认全互通域

默认行为：一张表 = 全互通

如果不做任何额外配置，所有附件都关联到 Default Route Table，并把各自网段传播进去，结果是"挂上就能通"。这也是考试中最常见的默认前提。

  • 隔离做法：生产附件只关联生产表、只向生产表传播；测试附件同理。两张表互不传播对方路由，天然不可达。
  • 共享服务做法：把共享服务 VPC 同时关联/传播到两张表，实现"共享一个服务、隔离其余流量"。
  • 阻断特定网段：在某张表中加入指向 Blackhole 的静态路由，优先级覆盖更宽泛的默认路由。
设计顺序不能反：先确定"谁和谁能通"（路由域），再创建附件。先建附件、后拆路由表，容易出现生产流量已经跑在默认表上、无法无损切换的情况。
路由选择：TGW 按最长前缀匹配选路；默认路由 0.0.0.0/0 只会在没有更具体匹配时生效。排查时先确认目标网段是否真的出现在对应路由表里，而不是只看 VPC 路由表。

四、与 VPC Peering / VGW / DX Gateway 对比

这四个组件经常在同一道题里同时出现，混淆会导致选错拓扑。抓住"是否为路由器、是否传递、是否跨 Region"三点即可。

对比项VPC PeeringTransit GatewayVirtual Private GatewayDirect Connect Gateway
本质两个 VPC 点对点连接区域级路由中枢单个 VPC 的 VPN 终点DX 的全球逻辑汇聚点
是否传递❌ 非传递（A-B、B-C 不代表 A-C）✅ 同 TGW 内可传递—（不是路由器）—（汇聚，不做 VPC 间路由）
规模VPC 数量少、点对点大量 VPC、Hub-Spoke单 VPC + 少量 VPN多条 DX + 多 VPC/TGW

ECMP不适用✅ 多 VPN/DX 连接可聚合❌ 只能主备由下层连接与 TGW 决定
跨 Region✅ 支持跨 Region Peering需 TGW Peering❌ 单 VPC✅ 全球资源

记忆口诀：Peering 是"两点连线"，TGW 是"交换机 + 路由表"，VGW 是"单个 VPC 的 VPN 插口"，DXGW 是"专线的全球分发器"。
不要用 Peering 拼大规模网络：N 个 VPC 全互联需要 N×(N-1)/2 条 Peering，且每条都要维护路由与接受请求；TGW 只需 N 个附件，是 SAP-C02 "减少运维复杂度"的标准答案。

TGW 与 VPC Peering 能否共存

可以。已有 Peering 的 VPC 仍可再挂到 TGW；但要注意路由优先级与流量路径——同一目标可能同时存在 Peering 路由与 TGW 路由，需明确哪条是主路径，否则会出现非预期绕行。考试中若题目强调"逐步迁移、保留现有 Peering"，通常允许共存，再逐条下线 Peering。

五、多账号与 RAM 共享

多账号场景不需要在每个账号各建一套 TGW。通过 AWS Resource Access Manager（RAM）把 TGW 共享给其他账号或整个 OU，参与账号即可把自己的 VPC、VPN 作为附件挂上来。

共享模型

  • Owner（拥有者）：创建 TGW、定义路由表、审批/管理附件，通常放在网络账号（Network Account）。
  • Participant（参与者）：接受 RAM 共享后，用自己的 VPC 创建附件；附件仍归参与者账号所有与管理。
  • 共享范围：可共享到具体账号 ID，或通过 Organizations 共享给整个 OU，新加入账号自动获得。
  • 权限边界：参与者默认只能管理自己的附件，不能改 Owner 的路由表；需要跨账号改路由时由 Owner 操作。
标准多账号网络架构：网络账号建 TGW 并用 RAM 共享 → 各业务账号挂自己的 VPC → 网络账号统一设计路由表与集中出口。这是 SAP-C02 多账号网络题的高频答案。
常见错误选项："每个账号各建一个 TGW 再互相 Peering"——成本高、路由域难统一、跨账号 Peering 仍需逐对建立；"用 VPC Peering 全互联"——运维复杂度随 VPC 数量平方增长。

共享后仍需注意

事项说明
CIDR 不重叠所有参与账号的 VPC/本地网段必须统一规划，重叠会导致路由冲突
路由审批参与者传播路由到共享路由表时，Owner 需确认不会破坏隔离设计
计费TGW 附件与流量费用计入附件所在账号，需提前约定分摊
删除顺序先删除参与者附件，再停止共享，最后删除 TGW，否则会产生残留附件

六、跨 Region：TGW Peering

TGW 是区域级资源，无法直接把 us-east-1 的 VPC 挂到 ap-southeast-1 的 TGW 上。跨 Region 组网的标准做法是：每个 Region 各建一个 TGW，再用 TGW Peering Attachment 把它们连起来。

Region A TGW
VPC A1 / A2
⇄ Peering ⇄
Region B TGW
VPC B1 / B2

关键行为

  • Peering 连接的两个 TGW 各自保留自己的路由表；对端 TGW 的路由通过 Peering 附件传播进来。
  • 流量走 AWS 全球骨干网，不经过公网 VPN，延迟与稳定性优于跨 Region 公网连接。
  • 不自动传递第三跳：A—B、B—C 两条 Peering 不会让 A 自动访问 C；需要逐段建立 Peering 并在每张路由表中配置路由。
  • 需要确认目标 Region 组合支持 TGW Peering；并非所有 Region 对都可用。
与 DX Gateway 的区别：DX Gateway 是全球级逻辑资源，可把一条专线关联到多个 Region 的 VGW/TGW；TGW Peering 是两个 TGW 之间的网络互联。题目说"一条专线访问多 Region"→ DXGW；"两个 Region 的 VPC 互访、无专线"→ TGW Peering。

跨 Region 方案对比

方案流量路径适用场景缺点
TGW PeeringAWS 骨干网多 VPC 跨 Region 互访需逐 Region 建 TGW 与 Peering，路由管理有成本
跨 Region VPC PeeringAWS 骨干网少量 VPC 点对点VPC 多时呈平方增长
公网 Site-to-Site VPN公共互联网临时、低成本延迟抖动、带宽受限
Direct Connect + DXGW专线 + AWS 骨干网合规、稳定低延迟成本高、开通周期长

七、Multicast 组播

TGW 是少数支持组播的 AWS 网络组件之一，用于"一份数据同时发给多个订阅者"的场景，如行情推送、媒体分发、集群配置同步。

三个概念

Multicast Domain

组播域，是组播流量的逻辑边界；一个 TGW 可建多个域。

VPC Attachment 关联

把 VPC 附件加入组播域，该 VPC 内的实例才能收发组播。

IGMP

实例通过 IGMP 加入/退出组播组，TGW 据此决定哪些子网接收流量。

组播地址

使用 224.0.0.0/4 范围内的地址；需应用与网络设备同时支持。

使用前提

  • 必须在 TGW 上创建 Multicast Domain，并把 VPC 附件关联进去；只建 TGW 不会自动支持组播。
  • 实例所在子网需启用组播，ENI 需支持组播；应用侧要加入同一个组播组。
  • 组播目前以 VPC 附件为主，不能指望它跨 VPN、DX 或 Peering 自动延伸。
  • 安全组/NACL 仍需放行组播流量；不要假设"组播域内自动全通"。
关键词映射："一份行情同时广播给多个 VPC"、"组播"、"IGMP" → TGW Multicast Domain。若题目只是"把同一份数据分发给很多用户"，也可能是 CloudFront/SNS，需看是否要求网络层组播。
组播不是广播：组播只发给加入该组的成员；没有加入组的子网不会收到流量。排查时先确认 IGMP 加入状态与组播域关联，而不是先查路由表。

八、TGW Connect 与 SD-WAN 接入

分支或第三方 SD-WAN 设备不一定支持 IPsec。TGW 提供 Connect Attachment：用 GRE 隧道 + BGP 把这类设备接入 TGW，而不必走 Site-to-Site VPN。

Connect 与 VPN 的差别

对比项VPN AttachmentConnect Attachment
封装协议IPsec（IKEv1/v2）GRE
路由静态或 BGPBGP
对端设备支持 IPsec 的路由器/防火墙支持 GRE + BGP 的 SD-WAN / 网络设备
加密✅ IPsec 加密❌ GRE 本身不加密，需要另叠加加密
典型场景传统分支、DX 加密叠加SD-WAN 厂商设备接入、替代多条 VPN
安全提醒：GRE 不提供加密。若题目同时要求"SD-WAN 接入 + 传输加密"，需要在 GRE 之上叠加 IPsec，或改用 VPN Attachment；不要只答 TGW Connect。
与 VPN 的共存：同一个 TGW 可同时挂 VPN Attachment 和 Connect Attachment，由路由表决定各自可见的网段；迁移期可以让 SD-WAN 与传统 VPN 并存，逐步切换。

九、集中出口与集中检查

TGW 最常见的架构用途之一，是把几十个 VPC 的互联网出口收敛到 一个 Egress VPC，统一做 NAT、日志与安全检查，而不是每个 VPC 都建 IGW/NAT Gateway。

集中出口架构

Spoke VPC A
0.0.0.0/0 → TGW
Spoke VPC B
0.0.0.0/0 → TGW
→
TGW
0.0.0.0/0 → Egress 附件
→
Egress VPC
NAT Gateway / 防火墙
→
Internet
IGW

配置要点

  1. Spoke VPC 路由表：0.0.0.0/0 指向 TGW 附件。
  2. TGW 路由表：0.0.0.0/0 指向 Egress VPC 附件（仅此一条出口，避免多出口混乱）。
  3. Egress VPC：部署 NAT Gateway 与 Internet Gateway，子网路由指向 IGW。
  4. 回程流量：NAT Gateway 保持会话，返回流量经 TGW 回到 Spoke VPC，需确保路由表有回程条目。

集中检查（Inspection）

  • 用 Gateway Load Balancer（GWLB） + 第三方防火墙做集中流量检查，Spoke 的流量先经 GWLB 再出网。
  • Egress VPC 附件启用 Appliance Mode，让同一流量的往返都落在同一 AZ，避免有状态设备会话断裂。
  • 检查架构中 TGW 仍然只做转发，不承担过滤；安全策略在防火墙/GWLB 与安全组上实现。
成本陷阱：集中出口不等于"零成本"。TGW 附件与流量、Egress VPC 的 NAT Gateway、GWLB 都单独计费。题目要求"最低成本"且 VPC 只有 2–3 个时，可能直接每个 VPC 建 NAT Gateway 更便宜。
别把 NAT 写进 TGW：TGW 不做 NAT、不做安全组、不做 DNS。所有需要"地址转换/内容检查/域名解析"的答案，都必须落到 VPC 内的具体服务上。

十、高可用、ECMP 与排错

TGW 本身是托管的多可用区服务，不需要像 EC2 那样自己搭主备。设计中真正需要关注的是附件侧的冗余、路由收敛与监控。

冗余与带宽

需求做法说明
VPN 带宽聚合TGW + 多条 VPN Attachment + ECMP单条 VPN 连接约 2.5 Gbps，需多连接叠加
DX 带宽聚合多条 DX + Transit VIF + ECMPBGP 动态路由让流量分散到多条专线
专线备份公网DX 主 + VPN 备（都挂 TGW）AS-PATH Prepend / MED 控制优先级
跨 Region 冗余双 TGW Peering（不同路径）需确认 Region 对与路由设计支持
集中出口高可用Egress VPC 多 AZ + 多 NAT Gateway避免单 NAT Gateway 成为出口瓶颈

排错顺序

  1. 附件状态：VPC/VPN/DX 附件是否 available；是否被删除或处于 pending。
  2. 关联：源附件是否关联到预期路由表；目标网段是否在该表中。
  3. 传播：目标附件是否把网段传播进该表；跨账号共享时 Owner 是否允许。
  4. VPC 侧：VPC 路由表是否有指向 TGW 的路由；子网是否与附件关联。
  5. 策略：安全组、NACL、实例防火墙；集中出口时再看 NAT/防火墙回程。
常见"不通"根因：只看 VPC 路由表、忽略 TGW 路由表；路由表未关联；跨账号附件已建但未传播；DX/VPN 的 BGP 路由未宣告；集中出口只有去程没有回程。

监控与配额

  • 用 CloudWatch 监控 TGW 的流量与附件相关指标，并为关键附件建立告警。
  • 附件数、路由表数、静态路由数、Peering 数都有配额；大规模设计前先核对配额，必要时申请提升。
  • 变更前记录路由表快照，变更后逐条比对，避免"以为传播了其实没有"。

十一、场景题解析

先独立判断，再查看解析与错误选项排除。

场景 1：公司有 25 个 VPC，需要彼此互通，同时通过 Direct Connect 访问本地数据中心，要求运维简单、避免逐对建 Peering。最优方案是？
正确答案：C。25 个 VPC 全互联若用 Peering 需要 300 条连接，运维不可行；TGW 只需 25 个附件，并可通过 Transit VIF + DX Gateway 接入本地。B 的 VGW 面向单 VPC 与 VPN，不是多 VPC 中枢；D 的 PrivateLink 用于私有访问特定服务，不做 VPC 间全网互通。
场景 2：集团有 12 个业务账号，每个账号有自己的 VPC，希望共享一套 Transit Gateway 并由网络账号统一管理路由。应采用？
正确答案：B。RAM 可以把 TGW 共享给账号或整个 OU，参与账号自行创建附件，Owner 统一维护路由表，是标准的多账号网络架构。A 成本与路由复杂度高；C 破坏账号隔离与计费边界；D 的跨账号 Peering 仍需逐对建立，规模不可控。
场景 3：生产与测试 VPC 都挂在同一个 TGW 上，要求测试环境绝对不能访问生产网段，但两者都能访问共享服务 VPC。应如何设计？
正确答案：C。多路由表 + 关联/传播控制可实现"生产与测试互不可见、但都能到共享服务"。A 的默认表全互通，安全组不能替代路由隔离；B 成本高且共享服务需重复接入；D 的 SCP 管 IAM 权限，管不了网络路由。
场景 4：企业在 us-east-1 与 eu-west-1 各有一套 TGW 和多个 VPC，要求跨 Region 互访且流量走 AWS 骨干网。最合适的做法是？
正确答案：B。TGW 是区域级资源，无法跨 Region 直挂 VPC；TGW Peering 让两个 TGW 通过 AWS 骨干网互联。A 不成立；C 走公网且 VPN 带宽有限；D 的 CloudFront 是内容分发，不是 VPC 间私有网络。
场景 5：30 个业务 VPC 需要统一经一个 Egress VPC 访问互联网，并在此处做集中流量检查，同时避免有状态防火墙会话中断。应如何组合？
正确答案：C。Spoke 默认路由指向 TGW，TGW 默认路由指向 Egress 附件，检查由 GWLB/防火墙完成；Appliance Mode 保证同一流量的往返落在同一 AZ。A 成本高且无法集中检查；B 的 TGW 不做安全检查；D 的 TGW 不具备 NAT/过滤能力。
场景 6：交易所需要把同一份行情数据同时推送给 8 个 VPC 内的订阅应用，要求网络层一份数据多播、由应用按需加入。应选择？
正确答案：C。要求网络层组播 → TGW Multicast Domain，VPC 附件关联组播域，应用通过 IGMP 加入。A 仍是多份复制，浪费带宽；B 是应用层消息推送，不是组播；D 面向 HTTP 内容分发，不适合组播行情。

十四、快速自测

先独立选择，再点击"查看解析"。

1. 新建一个 Transit Gateway 并挂上两个 VPC 附件后，默认情况下两个 VPC 能否互通？
正确答案：A。TGW 创建时自带 Default Route Table，新附件默认关联到该表并传播路由，因此默认全互通。需要隔离时才创建额外路由表并调整关联/传播。B、C 都把默认行为说反；D 与 AZ 无关。
2. 某企业把 TGW 共享给 8 个业务账号，其中一个账号报告"附件已创建，但访问不了其他账号的 VPC"。最应先检查？
正确答案：B。跨账号共享场景最常见的根因是附件关联到了错误的路由表，或路由未传播到共享表。IAM 权限通常影响"能否创建附件"而不是转发；C、D 与现象无关。
3. 以下哪种需求 Transit Gateway 本身无法满足？
正确答案：C。TGW 只负责路由转发，NAT 需在 VPC 内用 NAT Gateway，过滤需安全组/NACL 或 GWLB/防火墙。A、B、D 都是 TGW 的原生能力。
