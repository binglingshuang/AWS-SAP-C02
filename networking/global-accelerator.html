一、服务定位与流量路径

AWS Global Accelerator 是全球网络层服务。它为应用提供固定的 Anycast 入口 IP，将用户流量从就近的 AWS 边缘接入点送入 AWS 全球网络，再转发到一个或多个区域中的应用端点，改善全球访问的网络路径稳定性与可用性。

核心价值：用户使用稳定的静态 IP；流量更早进入 AWS 全球网络；Standard Accelerator 可根据端点健康状态和配置将新连接导向可用端点。它不会缓存应用内容，也不会替代应用自身的区域级容错和数据复制。
组件职责考试中的关键词
Accelerator提供静态入口 IP 与全球流量路由能力。稳定 IP、Anycast、跨区域入口。
Listener定义客户端流量使用的协议与端口或端口范围。TCP / UDP 流量入口。
Endpoint Group按 AWS Region 建立端点组，设置区域级流量拨盘和健康检查参数。区域端点、Traffic Dial。
Endpoint实际承载应用流量的区域资源；Standard 与 Custom Routing 支持不同。ALB / NLB / EC2 / EIP 或 VPC 子网。

二、核心组件与静态 IP

静态 Anycast IP

  • 默认 IPv4 Accelerator 分配两个静态 IPv4 地址；双栈 Accelerator 使用两个静态 IPv4 和两个静态 IPv6 地址。
  • 同一组入口地址可用于全球用户访问多个区域端点，不必让客户端跟随区域负载均衡器地址变化。
  • IPv4 场景可按服务支持条件使用 BYOIP 地址范围；需核对具体配置限制。
  • 只要 Accelerator 仍存在，分配给它的静态 IP 就保留；停用 Accelerator 会停止接收 / 路由流量，但不会仅因停用而释放地址。删除 Accelerator 后地址会失去关联，不能假设可重新取回。

Standard 与 Custom Routing 的端点

Accelerator 类型端点类型目标选择方式
StandardNetwork Load Balancer、Application Load Balancer、EC2 实例、Elastic IP 地址。Global Accelerator 按客户端位置、端点健康和配置策略选择区域及健康端点。
Custom RoutingVPC 子网。仅支持 IPv4；通过 Accelerator 静态 IP 与 Listener 端口映射到子网中的特定私有 IP / EC2 端口。
边界：端点类型、双栈要求、客户端 IP 保留和协议支持取决于 Accelerator 类型及端点配置。设计前按官方 endpoint requirements 核实，不要把一种端点的能力推广到所有端点。

三、Standard Accelerator：多区域应用的常用模式

Standard Accelerator 适用于需要稳定全球入口、智能路由和区域故障切换的互联网应用。一个 Accelerator 可以设置 Listener，每个 Listener 可关联多个区域 Endpoint Group，每个端点组可包含一个或多个受支持端点。

工作机制

  1. 客户端连接 Accelerator 静态 IP 和 Listener 支持的端口。
  2. Global Accelerator 根据客户端位置、端点组配置与健康状态，选择目标区域。
  3. 端点组中的权重影响端点间流量分配；Traffic Dial 控制发往该区域端点组的流量比例。
  4. 标准端点组持续执行健康检查；端点不健康时，新的流量连接会转向其他健康端点 / 区域（需有可用且符合配置的目标）。
适合：全球用户访问多区域 API / 游戏 / 实时应用；需要稳定 IP 白名单；想用区域级流量切换做蓝绿发布、演练或灾备。
不要误解：Global Accelerator 不复制数据库、不同步文件，也不自动保证两个 Region 的应用数据一致。跨区域状态复制、写入冲突和恢复策略仍由应用及数据服务架构解决。

四、Custom Routing Accelerator：定向到特定目的地

Custom Routing 面向需要由客户端连接信息或应用逻辑选定具体后端的场景。端点是 VPC 子网，Global Accelerator 将指定 Listener 端口映射到子网内私有地址和端口；典型用例是多人游戏、媒体会话等，需要把用户分配到特定服务器。

能力Custom Routing 行为设计影响
流量映射外部静态 IP + Listener 端口映射至具体子网目的地 IP / 端口。应用需要了解端口映射并将分配结果提供给客户端。
端点类型VPC 子网。与 Standard 的 ALB / NLB / EC2 / EIP 端点模型不同。
健康检查不使用 Standard 端点组的健康检查机制。需由应用或自有控制面判断目的地可用性，不要依赖 GA 自动健康故障切换。
目标选择按端口映射定向，不由 GA 在多个健康后端间做普通负载均衡。调用方需选择可用的目标与端口。
选型判断：题目若要求“用户 A 必须连到指定游戏服务器及其 UDP 端口”，考虑 Custom Routing；若只要求 GA 在多个区域的负载均衡器 / 实例间按健康度分配，使用 Standard。

五、健康检查与故障切换

Standard Accelerator 的健康判定

  • Standard Accelerator 默认自动执行健康检查。EC2 / EIP 端点的相关设置在 Global Accelerator 配置；ALB / NLB 端点则通过负载均衡器的健康检查设置管理。
  • 需保证目标实际监听并允许探测流量；新加入的 Standard 端点需通过健康检查后才会被视为健康。
  • 端点健康会影响 Global Accelerator 是否把新的连接路由到该端点。已有连接是否存续还取决于协议、连接状态和故障本身。
  • 健康检查失败时，要同时检查端点的服务状态、负载均衡器目标健康、网络 ACL / 安全组和探测端口配置。
  • 为区域故障切换准备真正可承载流量的备用端点及足够容量；只创建空的 Endpoint Group 并不构成灾备。

Custom Routing 的故障处理

Custom Routing 不使用 Standard 的端点健康检查，也没有由 GA 根据健康检查自动切换目的地的同类机制。若业务要避免分配到故障服务器，需在应用分配逻辑或外部控制面中维护目的地健康状态。

连接空闲超时

Global Accelerator 的连接空闲超时不可自定义：TCP 为 340 秒，UDP 为 30 秒。超时窗口内需要有至少 1 字节的业务数据进出；仅发送 TCP keep-alive 不能维持连接。既有连接可在端点标记为不健康或被移除后继续指向原端点，直到空闲超时；因此故障切换主要影响新连接，长连接应用应设计重连与会话恢复。

全端点不健康：若 Standard Accelerator 没有任何健康端点可供路由，Global Accelerator 会将流量路由到所有端点。健康检查不是“无健康目标时绝不发送流量”的绝对安全闸门。
考试排障顺序：检查 Accelerator / Listener 状态 → Endpoint Group 与区域流量拨盘 → 端点健康检查 → 后端目标与容量 → 安全组及监听端口 → 应用与数据层区域容灾。

六、流量调度、蓝绿发布与客户端 IP

控制项作用典型用途
Traffic Dial限制已经被选中发往该区域 Endpoint Group 的流量百分比；未被该组接受的流量会转向其他区域端点组。区域级蓝绿发布、演练、维护或灾备切换。
Endpoint Weight控制同一端点组内不同端点之间的相对流量分配。同 Region 的端点权重路由和渐进迁移。
健康状态Standard Accelerator 对不健康端点停止新流量路由，选择其他可用端点。区域 / 端点故障切换。
客户端 IP 保留部分 Standard 端点类型与配置支持保留客户端源 IP；Custom Routing 会保留客户端 IP。源 IP 访问控制、审计或应用层策略。
  • Traffic Dial 是区域级比例控制，应用在基于其他因素（如用户位置）已被导向该区域组的流量上，不是对 Listener 全部流量的绝对百分比；Endpoint Weight 控制的是端点组内端点的相对分配。
  • 客户端 IP 保留有适用条件，且会影响源地址呈现、安全组和连接行为；逐个验证端点类型、区域与资源配置支持。
  • 对于安全组规则，要根据应用看到的源 IP / 代理路径准确设计；不要无条件假定目标一定看到客户端原始地址。
  • 流量调低到 0 不等于删除资源或完成数据切换；确认应用、依赖服务、缓存和连接排空策略。

七、Global Accelerator vs CloudFront vs Route 53

维度Global AcceleratorCloudFrontRoute 53
主要层次 / 目标网络层全球流量加速与区域端点可用性。HTTP(S) 内容分发、边缘缓存与应用层处理。权威 DNS 与 DNS 路由策略。
入口固定 Anycast 静态 IP；支持 TCP / UDP Listener（按配置）。CloudFront 分发域名及自定义域名，面向 Web 内容 / HTTP(S)。DNS 名称解析为目标记录。
缓存不缓存应用内容。可在边缘缓存静态 / 动态内容，按 Cache Policy 控制。不缓存应用响应；DNS 记录有 TTL。
客户端连接与路径连接到稳定 IP，流量从就近边缘进入 AWS 全球网络，转至区域端点。在边缘处理请求并可从缓存响应；未命中时访问 Origin。客户端解析 DNS 后直接连接所解析的服务端点；故障切换受 DNS 缓存和 TTL 等因素影响。
典型场景非 HTTP 应用、实时 TCP / UDP、静态 IP 白名单、多区域快速切换。网站、API 加速与缓存、边缘认证 / 请求处理。域名路由、基于 DNS 的区域选择、健康检查集成。
是否互斥不互斥。可按需组合 DNS 与 GA 固定入口，或将 CloudFront 用于 Web 内容分发、GA 用于其他实时流量；避免为缓存场景误选纯网络加速。
记忆口诀：“要固定 IP、TCP/UDP、迅速切区域”→ Global Accelerator；“要 HTTP(S) 缓存、边缘函数、WAF / 内容分发”→ CloudFront；“要域名解析和 DNS 策略”→ Route 53。

八、架构设计与常见陷阱

多区域入口设计

  1. 按客户端协议和端口定义 Listener，确认端点资源支持这些流量。
  2. 在需要承载业务的每个 Region 创建 Endpoint Group，并配置该区域的负载均衡器 / 实例端点。
  3. 为端点组配置健康检查，确保探测路径能反映业务服务而非仅仅主机存活。
  4. 通过 Traffic Dial 和 Endpoint Weight 执行区域级与区域内的流量管理。
  5. 验证备用 Region 的数据就绪、容量、依赖项和客户端 IP / 安全组要求，再做故障演练。
常见误区正确理解
Global Accelerator 是全球 CDN。不是。它不提供 CloudFront 式的内容缓存。
静态 Anycast IP 保证应用必然可用。静态入口稳定，但后端健康、应用容量、数据复制仍需自行设计。
GA 会在创建 Accelerator 后自动复制应用和数据库。不会。GA 负责流量入口与路由，不负责跨区域数据复制。
Custom Routing 自动检测服务器健康并避开故障服务器。Custom Routing 不使用 Standard 的健康检查 / 自动故障切换机制。
只把主区域的流量拨盘调低就完成灾备。备用区域必须有健康端点、足够容量和可用数据；并验证连接及依赖。
所有后端都一定看到客户端源 IP。客户端 IP 保留依端点类型与配置而异，需查对应 endpoint requirements。

九、场景题解析

场景 1：全球 TCP 游戏服务需要固定 IP 和快速区域切换

玩家使用 TCP 连接游戏服务，客户端网络策略只允许固定 IP；应用部署在两个 Region，需在一个区域故障时尽快将新连接导向另一区域。

正确方向：使用 Standard Global Accelerator，为区域端点配置 Listener、Endpoint Group 与健康检查。
分析：GA 提供静态 Anycast 入口并按端点健康在区域间路由，适合 TCP 实时服务和固定 IP 需求。确认备用 Region 端点和应用数据已就绪。
排除：CloudFront 面向 HTTP(S) 内容分发，不是通用 TCP 入口；Route 53 DNS 故障切换会受 DNS 缓存与 TTL 影响，也不提供同类固定 Anycast IP 入口。
场景 2：网站需要全球静态资源缓存并降低源站负载

企业网站以图片、脚本和可缓存页面为主，目标是由全球边缘节点缓存内容，并可使用缓存策略控制命中率。

正确方向：使用 CloudFront。
分析：CloudFront 是 CDN，可缓存对象并在缓存命中时直接响应用户。若另有非 HTTP 流量或固定 IP 需求，再评估与 GA 组合。
排除：GA 优化网络路径但不缓存内容；只使用 GA 不会减少静态对象回源请求。
场景 3：多区域发布需要逐步把用户流量切到新 Region

新 Region 已准备好应用端点，团队希望先少量放量，再逐步提高流量，期间可快速回切。

正确方向：使用 Standard Accelerator 的区域 Endpoint Group Traffic Dial 进行区域级流量调整；端点组内需要细分时配置 endpoint weights。
分析：Traffic Dial 控制到某区域端点组的流量比例；Endpoint Weight 控制同一组内不同端点的相对流量。先验证新区域容量、数据和健康检查，再逐步放量。
排除：不要把两个流量控制层级混为一谈，也不要只修改 DNS TTL 来满足快速、可控的 GA 流量迁移目标。
场景 4：在线游戏要把每个玩家连接到指定媒体服务器和端口

应用需要按会话分配逻辑将玩家连接到一个具体的 EC2 服务器及 UDP 端口，而不是由负载均衡器随机分配后端。

正确方向：评估 Custom Routing Accelerator，并由应用根据端口映射把用户分配到具体子网目的地。
分析：Custom Routing 可将外部 Listener 端口映射到 VPC 子网中的特定私有 IP 和端口，适合由应用逻辑控制目标的实时游戏 / 媒体工作负载。
排除：Standard Accelerator 面向健康端点间的常规流量分配；Custom Routing 不提供 Standard 的健康检查自动故障切换，应用需处理目的地健康。
场景 5：不改变客户端 IP 白名单，但后端看到的来源地址需要核实

迁移到 Global Accelerator 后，安全团队要求后端继续按照客户端原始 IP 做访问控制和审计。

正确方向：先确认所用 Standard 端点类型和配置是否支持客户端 IP 保留，再配置端点与安全组并验证实际源地址。
分析：客户端 IP 保留并非所有 endpoint 的通用默认行为。应按 AWS 的 endpoint requirements 检查端点类型、区域支持和资源配置，并用日志 / 测试流量验证。
排除：不能仅因使用 GA 的静态 IP，就推断后端一定看到用户原始 IP；也不能把 GA 的入口 IP 当作用户地址。
场景 6：区域灾备演练中主区域故障，但备用区域没有准备数据

团队计划将主区域流量拨盘调至零，切到备用区域；检查发现备用应用虽然运行，但数据库尚未复制完成。

正确方向：先建立并验证数据复制 / 恢复、应用依赖和备用容量，再通过健康检查与 Traffic Dial 执行流量切换。
分析：GA 管理网络入口和流量路由，不会复制或保证数据库一致性。健康端点也不能说明数据已经满足 RPO / RTO。
排除：仅调整 GA 流量拨盘会把用户送到可能返回旧数据或错误的应用；必须将数据层灾备作为切换前置条件。

十二、快速自测

先独立作答，再点击选项查看解析。

1. 全球 UDP 游戏客户端要求固定公网入口，并且应用需要按会话连接指定后端服务器与端口，应优先评估哪种方案？
正确答案：B。Custom Routing 提供固定入口并按端口映射到子网里的特定目的地，适合会话必须指定后端的应用。它不负责 Standard 的健康检查自动故障切换。
2. 一个 Web 应用需要缓存静态图片、减少源站请求并在边缘执行请求处理，应选择什么？
正确答案：B。CloudFront 支持 HTTP(S) 内容分发与边缘缓存；GA 提供全球网络路径加速但不缓存应用对象。
3. 需要先将 10% 用户切到新 Region，稳定后逐步提高该区域流量；应使用哪项 GA 控制？
正确答案：A。Traffic Dial 用于区域 Endpoint Group 流量比例；Endpoint Weight 用于同一端点组内的端点相对分配。切流前还要确认新区域健康、数据与容量就绪。
