一、ELB 组件与请求路径

Elastic Load Balancing 将进入流量分发到一个或多个健康目标。负载均衡器对外提供入口，Listener 接收协议/端口上的连接，规则选择 Target Group，健康检查决定目标是否接收新流量。

组件职责容易混淆的边界
Load Balancer跨启用的可用区提供受管入口与负载分配能力。创建 LB 不会自动保证后端应用有足够健康副本。
Listener监听协议和端口，例如 ALB HTTPS:443、NLB TCP:443。TLS 证书和 TLS 终止通常配置在 TLS/HTTPS Listener。
Listener RuleALB 可按 Host、Path、Header、Query 等条件转发、重定向或返回固定响应。NLB 不提供 HTTP 层内容路由规则。
Target Group定义目标类型、端口、健康检查和流量属性；Listener 将请求转发给目标组。目标组健康与应用自身业务健康不是同一监控维度。
Health Check周期性判定目标是否可接收新流量；失败目标会从正常转发中排除。检查路径、协议、端口、响应码与安全组需与应用匹配。
流量控制顺序：先由 LB 的 Listener 接收连接；ALB 再按规则选目标组，NLB 依传输层 Listener 转发，GWLB 负责透明送往网络虚拟设备。不要把 Target Group、Listener 与 Auto Scaling Group 当成同一资源。

二、ALB / NLB / GWLB 选型

维度Application Load Balancer (ALB)Network Load Balancer (NLB)Gateway Load Balancer (GWLB)
层级 / 协议第 7 层 HTTP / HTTPS；支持 WebSocket、HTTP/2 等应用协议特性。第 4 层 TCP、UDP、TLS 等传输流量。第 3 层透明网络流量入口，通过 GENEVE 封装与安全设备通信。
主要能力Host/Path/Header 路由、重定向、固定响应、原生 HTTP 路由。超低延迟、高连接速率、静态地址、保留客户端源 IP 的场景。插入、扩展与管理第三方虚拟安全设备集群。
目标类型Instance、IP、Lambda。Instance、IP、ALB（作为 NLB 后端的特定架构）。作为 Gateway Load Balancer Endpoint 后的虚拟 appliance。
静态地址DNS 名称为入口；通常不提供可固定的每 AZ 公网 IP。可为每个启用 AZ 配置静态 IP；面向公网时可关联 EIP。通过 GWLB Endpoint 和路由实现透明插入，不作为通用公网静态入口选项。
常见场景Web/API、微服务路由、按 URL 分流、HTTP 认证。非 HTTP 协议、大量 TCP/UDP 连接、固定 IP 白名单。防火墙、入侵检测、流量检查等网络虚拟设备。
不擅长任意 TCP/UDP 协议负载平衡。按 HTTP 路径/主机名执行路由。作为应用 Web 入口提供第 7 层规则。

常见目标类型注意事项

  • ALB 的 ip 目标适用于容器任务、私有 IP 或可路由的地址；Fargate awsvpc 通常注册任务 ENI 的 IP。
  • Lambda 可作为 ALB 目标处理 HTTP(S) 请求，但需满足目标组与函数资源权限要求。
  • 同一 ALB 可用不同 Listener Rule 将请求路由到不同 Target Group；蓝绿部署可通过权重在目标组间分配流量。
  • GWLB 后端 appliance 需支持相应 GENEVE 封装与健康检查，客户端流量通过 GWLB Endpoint / 路由表透明经过设备。
一眼选型：HTTP 字段/路径路由选 ALB；TCP/UDP 与静态 IP 选 NLB；需要透明插入第三方网络防火墙或检查设备选 GWLB。

三、Listener 与路由

ALB：按应用内容分流

  • Listener Rule 可按 Host header、Path pattern、HTTP header、query string、来源 IP 等条件匹配，并执行转发、重定向或固定响应。
  • 规则按优先级评估，默认规则作为兜底。优先级需避免宽泛规则抢先匹配。
  • 可将请求按权重转发到多个 Target Group，用于渐进发布；会话粘性需另行评估。
  • 一个 ALB 可承载多个站点/API，配合不同 Host/Path 规则和证书，减少重复入口。

NLB：传输层监听

  • Listener 按 TCP、UDP、TLS 等协议和端口接收连接；不检查 HTTP 路径或 Host。
  • 客户端需要固定 IP 时，为各 AZ 配置静态地址/EIP，并让客户端使用稳定入口；多 AZ 仍应同时发布地址并实现容错。
  • 使用 TCP Listener 可将 TLS 流量透传给目标，让目标自行终止；使用 TLS Listener 可在 NLB 终止客户端 TLS。

GWLB：透明流量插入

GWLB 使用 GENEVE 封装向安全 appliance 分发流量，客户端通常通过 Gateway Load Balancer Endpoint 访问。路由表决定哪些流量经过 Endpoint / appliance；仅创建 GWLB 不会自动拦截 VPC 的所有流量。

陷阱：Listener 不是安全组，ALB 规则不能替代 VPC 路由。GWLB 流量插入必须连同 Endpoint、路由表、返回路径和设备健康状态一起设计。

四、Target Group 与健康检查

配置含义排障重点
Target typeInstance、IP 或 Lambda 等后端注册方式；可用类型取决于 LB 与协议。容器 awsvpc 常用 IP；不能把容器 ENI 当 EC2 Instance ID 注册。
Health check protocol / portLB 探测目标的协议与端口。目标 SG 允许来自 LB SG；应用确实在该端口监听。
Health check path / matcherHTTP(S) 检查路径及可接受状态码范围。路径不重定向到需认证页面；应用响应码与 matcher 一致。
Deregistration delay目标注销时的连接排空时间（connection draining）。长请求/任务需要足够排空时间，应用仍应优雅关闭。
Stickiness在配置支持时使会话在一定时间内保持指向同一目标。粘性降低跨目标均匀性，不替代共享会话存储或无状态设计。
Slow start目标恢复健康后逐步增加接收流量，避免尚未预热就接收过多请求。仅适用支持该属性的目标组类型；配合应用启动与缓存预热。

健康目标与部署容量

  • Load Balancer 只把流量送到健康目标；如果所有目标不健康，应排查后端配置与健康检查，而非假设 LB 会修复应用。
  • Auto Scaling Group 可将实例自动注册/注销到关联目标组；ECS Service 可将任务目标注册到目标组。
  • 部署时设置合理的最小健康百分比、最大运行百分比、健康检查宽限和连接排空时间，避免发布期间无可用目标。
  • 多目标组/多服务共用 ALB 时，确保每条规则、Target Group、容器端口和健康检查路径一一对应。

五、跨区负载与可用区

类型默认跨区行为设计注意
ALB负载均衡器级别的跨区负载默认启用；可按 Target Group 属性调整目标组行为。每 AZ 需有健康目标；跨 AZ 流量仍有架构与数据传输成本影响，需核对计费规则。
NLB默认禁用跨区负载；可在 LB 或目标组层按支持方式启用。默认情况下流量分布依赖各 AZ 目标容量；启用跨区有助于不均衡容量，但可能产生跨 AZ 数据传输费用。
GWLB默认禁用跨区负载；可按需要启用。需确保设备集群、流量对称性、状态同步及 AZ 故障处理正确。
  • 至少启用两个 AZ 通常可提高应用入口韧性；确认 LB 子网地址空间充足，避免子网 IP 耗尽影响扩展。
  • 每 AZ 的后端容量应与接收流量相称。NLB/GWLB 默认区内分配时，单 AZ 流量突增或目标分布不均可能导致热点。
  • 跨区负载可以改善容量利用，但不会自动跨区域；跨 Region 灾备需 Route 53、Global Accelerator 或其他区域级架构。
  • 跨区负载均衡设置可能支持在负载均衡器与目标组层级覆盖；变更前检查实际属性与费用影响。
考试判断：题目强调单 AZ 目标不足或流量需分配给其他 AZ 时，检查 NLB/GWLB cross-zone 属性；题目只说多 AZ 部署，并不代表跨区负载均衡一定自动开启。

六、TLS 终止与证书

模式客户端到 LBLB 到目标用途
ALB HTTPS ListenerLB 终止 TLS，Listener 使用 ACM 或导入证书。可使用 HTTP，也可用 HTTPS 与后端建立加密连接。统一证书管理、TLS 解密后按 HTTP 内容路由。
NLB TLS ListenerNLB 终止客户端 TLS，可使用证书进行握手。按 Target Group 协议设置明文 TCP 或重新加密 TLS。保留 L4 负载与 TLS 卸载能力；不提供 HTTP 路由。
NLB TCP ListenerTLS 字节流原样转发，不在 NLB 解密。后端目标自行终止 TLS。需要端到端 TLS 或目标必须处理客户端 TLS 会话。
  • ELB 使用的 ACM 证书应与负载均衡器位于相同 AWS 区域；CloudFront 的证书区域规则不同。
  • 证书绑定在相应 HTTPS/TLS Listener，而不是 Target Group；证书续期和域名覆盖要一并确认。
  • ALB 可按 SNI 在 HTTPS Listener 上配置多个证书，并按 HTTP Host/Path 进一步路由。
  • LB 到后端若使用 HTTPS/TLS，检查目标端口、证书与后端服务 TLS 设置；不要误以为客户端到 LB 加密自动保证到目标也加密。
终止点：需要 ALB 按 HTTP 路径路由时，TLS 必须在 ALB 处解密；要求 TLS 一直由应用处理时，可让 NLB 使用 TCP Listener 透传加密流量。

七、扩展、粘性与部署

  • 负载均衡器根据注册目标和健康状态分发请求；后端副本数由 EC2 Auto Scaling、ECS Service Auto Scaling 等机制管理。
  • ALB/NLB 与目标组可配合多 AZ、Auto Scaling 和健康检查实现目标故障隔离；LB 本身不是应用数据持久化或跨区域灾备方案。
  • 粘性会话适用于短期会话连续性，但会带来热点并降低无状态扩容弹性；优先将会话状态存入共享存储。
  • 滚动或蓝绿部署期间监控 HealthyHostCount、TargetResponseTime、HTTPCode_Target_*、UnHealthyHostCount 与应用自身指标。
  • WAF 主要与 ALB / CloudFront 等支持的应用层入口集成；网络层防火墙 appliance 可通过 GWLB 插入流量路径。
  • 公网入口安全组只允许需要的客户端端口；后端目标安全组应仅允许来自负载均衡器安全组的应用端口。
  • 为固定公网入口地址与全球骨干网接入评估 NLB + Global Accelerator；单纯 ALB DNS 的 IP 会变化，不应硬编码。
排障层次：客户端无法连接 → DNS/Listener/子网/安全组；目标不健康 → Target Group 检查、应用端口与后端 SG；应用返回错误 → 应用日志、规则转发与目标处理逻辑。先定位故障层再修改配置。

八、场景题解析

场景一：按主机名和 URL 路径拆分微服务

一个 HTTPS 域名承载多个应用，希望按 api.example.com 和 /images/* 将请求分别转发到不同服务。

正确方向：使用 ALB HTTPS Listener、Host/Path 条件规则和多个 Target Group；证书绑定到 Listener。

分析思路：需求依赖 HTTP 应用层信息与规则路由，是 ALB 的典型功能。

排除：NLB 不能基于 URL 路径做路由；仅使用 DNS 不能完成单入口内的 HTTP 请求分发。

场景二：合作方要求稳定的公网 IP 白名单

后端是 TCP 服务，客户端只能连接固定公网 IP，且需要跨 AZ 的高可用入口。

正确方向：使用 NLB 并为每个启用 AZ 配置静态 IP/EIP；让客户端使用全部入口并实现故障容错。

分析思路：NLB 支持每 AZ 静态地址，适合 L4 TCP 流量。

排除：ALB 使用 DNS 入口且地址可能变化；硬编码 ALB 当前解析出的 IP 不可靠。

场景三：集中检查 VPC 出站流量

企业希望将多个 VPC 的网络流量透明导入第三方防火墙 appliance 集群，不想让应用逐个配置代理。

正确方向：使用 GWLB 与 Gateway Load Balancer Endpoint，配置路由表将所需流量导向 Endpoint。

分析思路：GWLB 面向透明网络设备插入和扩展，通过 GENEVE 与 appliance 通信。

排除：ALB/NLB 是应用或传输层负载入口，不替代透明的网络 appliance 插入；创建 GWLB 不会自动改写路由。

场景四：只有一个 AZ 的 NLB 目标健康

NLB 已启用两个 AZ，但目标容量集中在一个 AZ；要求任一入口节点都能将请求分配到其他 AZ 的健康目标。

正确方向：检查并启用 NLB 跨区负载均衡，评估跨 AZ 数据传输费用与目标组层级属性。

分析思路：NLB 的 cross-zone 默认关闭，跨区分发需要明确配置。

排除：仅启用两个 LB 子网不等于启用 cross-zone；DNS 轮询也不会保证请求落到健康后端。

场景五：LB 卸载 TLS 后还要求后端加密

Web 层需要在 LB 解密 HTTPS 以执行 Host/Path 路由，但合规要求 LB 到应用服务器之间也必须加密。

正确方向：在 ALB 配置 HTTPS Listener 和 ACM 证书，并将目标组协议配置为 HTTPS，确保后端服务提供对应 TLS 端口。

分析思路：客户端 TLS 与后端链路 TLS 是两个独立连接段，需要分别配置。

排除：HTTPS Listener 仅能证明客户端到 ALB 加密；默认转发到 HTTP 目标不满足端到端链路加密要求。

场景六：部署后所有目标都被判定不健康

ALB 返回 503，Target Group 中目标 unhealthy。应用进程显示运行中。

正确方向：核对健康检查协议、端口、路径、成功码、目标安全组是否允许来自 ALB 的访问，以及应用监听地址。

分析思路：进程运行不意味着健康检查请求能成功；安全组和路径配置常造成目标全部不健康。

排除：增加 Listener 规则或扩大客户端入口 CIDR 不会修复 ALB 到后端的健康检查链路。

十一、快速自测

先独立选择，再点击“查看解析”。

1. 一个入口需按 HTTP Host 和 URL Path 将请求分发到不同微服务，应选哪种负载均衡器？
正确答案：A。ALB 提供 HTTP 层规则；NLB 是传输层，GWLB 用于透明 appliance 流量插入。
2. NLB 前端必须提供每 AZ 固定公网地址，后端是 TCP 服务。优先采用什么？
正确答案：B。NLB 支持传输层协议与每 AZ 静态地址；实际部署仍需设计多 AZ 客户端容错。
3. ALB HTTPS Listener 已配置证书，但要求后端链路也加密。还需做什么？
正确答案：B。客户端到 ALB 和 ALB 到目标是独立连接段，后端 TLS 需单独启用。
