一、Route 53 基础架构

Route 53 是 AWS 托管的全球 DNS 服务，同时提供域名注册、DNS 解析、健康检查和流量路由功能。"53" 来源于 DNS 协议使用的 UDP 53 端口。

托管区（Hosted Zone）

托管区是 Route 53 中存储 DNS 记录的容器，对应一个注册域名（如 example.com）。分为两种类型：

  • Public Hosted Zone（公有托管区）：对全球 DNS 服务器公开解析，任何人都能查询
  • Private Hosted Zone（私有托管区）：仅关联特定 VPC，只有关联 VPC 内的资源可以解析
关键特性：Route 53 使用 Anycast IP 架构，全球有多个边缘节点，DNS 查询会被自动路由到最近的 Route 53 DNS 服务器，实现低延迟解析。

NS 服务器与域名委托

每个公有托管区创建时，Route 53 会分配 4 个 NS 服务器地址（如 ns-1234.awsdns-56.org）。要让 Route 53 接管域名解析，必须在域名注册商处将域名的 NS 记录改为 Route 53 分配的这 4 个地址。

考试陷阱：如果域名已经在其他 DNS 服务商托管，切换到 Route 53 时必须在注册商处更新 NS 服务器，不能只在 Route 53 中创建托管区。否则查询仍会发到旧的 DNS 服务商。

  • S3 静态网站托管的存储桶
  • Global Accelerator
  • API Gateway
  • VPC Endpoints（PrivateLink）
  • 另一个 Route 53 记录

三、路由策略（七种 — Route 53 最大考点）

Route 53 的路由策略决定了 DNS 查询返回哪个 IP 地址。SAP-C02 考试对路由策略的适用场景、限制和陷阱考察极深。

Simple Routing

最基础的路由策略。一个记录集（Set）可以包含多个 IP，但 Route 53 返回哪个不保证（实际上是随机或轮询）。适用于单端点场景。

陷阱：Simple 策略不保证负载均衡顺序，客户端 DNS 缓存也会打乱分配。不要用 Simple 做多服务器负载均衡。

Weighted Routing

为每个记录分配一个权重值（0–255）。Route 53 按权重比例返回记录。权重 0 = 停止返回该记录（配合健康检查实现自动摘除）。

Latency Routing

Route 53 基于 AWS 内部测量的延迟数据，将用户路由到延迟最低的 AWS Region 中的端点。注意：Latency 策略的端点必须在 AWS Region 内，不能是自建数据中心的 IP。

关键限制：Latency 策略只能指向位于 AWS Region 内的资源（如 ELB、EC2 公网 IP）。无法用于 On-Premises 端点。Geoproximity 策略 + Traffic Flow 可以解决这个问题。

Geolocation Routing

根据 DNS 查询来源的 IP 地址地理位置进行路由。支持国家、州/省、大陆级别粒度。

  • 可以创建 "Default" 记录，匹配所有未被显式规则覆盖的地区
  • 适用于：内容本地化（不同国家不同语言/货币）、合规要求（GDPR 数据不出欧盟）、区域特定部署

Geoproximity Routing（含 Traffic Flow）

比 Geolocation 更精细的地理路由。可以设置 偏移量（Bias）：正数表示"扩大范围"（覆盖更多用户），负数表示"缩小范围"。

Geoproximity vs Geolocation：
Geolocation = "你是中国人就用中国站"（硬边界）
Geoproximity = "离我 500km 内的用户用这个端点"（可动态调整）

Geoproximity 策略需要 Route 53 Traffic Flow 才能使用（额外收费）。端点可以是 AWS Region、边缘位置或任意经度/纬度坐标（支持 On-Premises）。

Failover Routing

主备故障切换。必须定义 Primary 和 Secondary 两个记录，Primary 必须关联健康检查。

  • Primary 健康 → Route 53 返回 Primary 的值
  • Primary 不健康 → Route 53 自动切换返回 Secondary 的值
  • Secondary 也可以关联健康检查，但不是必须
场景：Active-Passive 灾难恢复架构（主区域故障自动切到备区域）。
陷阱：Failover 策略的 DNS 切换生效需要时间（TTL + DNS 传播），通常在数十秒到数分钟之间。不要依赖 DNS 级故障切换来实现秒级 RTO。

Multivalue Answer Routing

一次 DNS 查询返回多个 IP 地址（最多 8 个）。客户端通常会随机选择一个来连接。这是 Route 53 提供的"低成本 DNS 级负载均衡"。

  • 如果启用健康检查，Route 53 自动从返回列表中排除不健康的 IP
  • 最多返回 8 个健康的记录
  • 比 Weighted 更简单，但负载分配不精确

四、健康检查机制

健康检查是 Route 53 实现自动故障切换、智能路由的核心能力。Route 53 从全球多个位置（约 15 个）并行发起检查，避免单点误判。

健康检查类型

类型检查方式适用场景
HTTP / HTTPS向指定 URL 发送请求，检查 HTTP 状态码Web 应用健康状态
TCP建立 TCP 连接，不发送 HTTP 请求非 Web 服务（数据库、消息队列等）
CloudWatch Alarm基于 CloudWatch 告警状态判断与其他 AWS 服务集成（如检测 RDS 故障）
Evaluate Target Health（ELB 专用）ELB 自身的健康检查结果Route 53 指向 ELB 时自动同步

关键参数

  • Request Interval：检查频率，10 秒（快速）或 30 秒（标准）
  • Failure Threshold：连续多少次失败才判定不健康，1–3
  • Healthy Threshold：连续多少次成功才判定健康，1–3
  • Inverted Health Check：反转逻辑（例如检查"网站不应该返回 5xx"，收到 5xx 就是健康）
典型陷阱：EC2 实例健康检查失败但 SSH 能连上。原因：Route 53 从全球不同位置发起检查，如果实例的 Security Group 或 NACL 没有允许来自 Route 53 健康检查器的入站流量，检查就会失败。Route 53 不会告诉你具体是 SG 还是 NACL 阻塞了流量。

Evaluate Target Health（核心考点）

当 Route 53 记录指向 ELB 时，启用 Evaluate Target Health = Yes 可以让 Route 53 直接使用 ELB 的健康检查结果。

  • ALB/NLB 健康 → Route 53 继续路由到该 ELB
  • ALB/NLB 不健康 → Route 53 自动停止路由到该 ELB（即使 ELB 还有部分实例健康）
  • 这是实现 "ELB 级别故障切换" 的关键机制
考试陷阱：如果 Route 53 记录指向 ELB，又同时配置了独立的 HTTP 健康检查，Route 53 会将两者的 AND 结果作为最终判断。独立健康检查比 ELB 内部健康检查更严格。

延迟 vs 健康检查的关系

Latency 策略内置了隐式的健康检查。Route 53 在计算延迟时，会先验证端点是否可达。如果某个 Region 的端点不健康，即使它延迟最低，Route 53 也不会将流量路由过去。

五、Public vs Private 托管区

Public Hosted Zone（公有托管区）

  • 对全球 DNS 服务器公开解析
  • 存储面向互联网的 DNS 记录（如 www.example.com → 203.0.113.1）
  • 每个公有托管区自动创建 NS 记录和 SOA 记录（不可删除）
  • 域名注册在 Route 53 或外部注册商均可

Private Hosted Zone（私有托管区）

  • 仅对关联的 VPC 可解析
  • 存储 VPC 内部使用的私有域名（如 db.internal.example.com → 10.0.1.100）
  • 通过 VPC Association 将私有托管区与 VPC 关联
  • 支持跨账号关联（VPC 在 Account A，私有托管区在 Account B）
Private Hosted Zone
internal.example.com
关联
VPC-A (Account A)
关联
VPC-B (Account B)

Private Hosted Zone 跨账号关联

场景：Private Hosted Zone 在 Account A，VPC 在 Account B。

  1. Account B 的 VPC 开启 enableDnsSupport 和 enableDnsHostnames
  2. Account A 授权 Account B 关联自己的私有托管区（通过 CreateVPCAssociationAuthorization API）
  3. Account B 使用授权 ID 将 VPC 关联到 Account A 的私有托管区
替代方案：使用 Centralized DNS（Route 53 Resolver + 共享 VPC）或在同一个 AWS Organizations 组织内使用 AWSServiceRoleForR53Resolver 服务角色简化跨账号操作。

DNS 冲突问题

如果 VPC 同时关联了 Private Hosted Zone 和 DHCP Option Sets 指定了自定义 DNS，或者 VPC 存在冲突的 DNS 域名，解析可能不可预测。最佳实践：

  • VPC 不要自定义 DHCP Option Sets，让 AWS 提供的 AmazonProvidedDNS 处理 Route 53 私有托管区解析
  • 同一 VPC 可以关联多个私有托管区（域名不冲突时）

六、Route 53 Resolver（混合云 DNS 核心）

Route 53 Resolver 是连接 AWS VPC 与本地数据中心 DNS 的桥梁，实现双向 DNS 解析。SAP-C02 中 Direct Connect + Resolver + Private Hosted Zone 是最高频的混合云 DNS 组合题。

Centralized DNS 架构（企业多账号最佳实践）

场景：企业有多个 AWS 账号，统一由中央网络账号管理 DNS 基础设施。
架构：
1. 中央账号创建一个 Shared VPC（通过 RAM）
2. 在 Shared VPC 中部署 Resolver Inbound/Outbound Endpoints
3. 所有业务账号的 VPC 通过 Transit Gateway 连接到 Shared VPC
4. 所有 VPC 的 DNS 查询都汇聚到 Shared VPC 的 Resolver Endpoints

七、Route 53 Traffic Flow

Traffic Flow 是 Route 53 的高级流量管理功能，提供可视化流量图、多种路由策略组合、地理位置与延迟综合决策。需要额外付费。

核心特性

  • 可视化流量树：图形化定义流量如何从 DNS 查询源头流向各端点
  • 策略组合：在同一个流量策略中使用 Geolocation + Latency + Weighted + Failover
  • Geoproximity 支持：Geoproximity 策略只能通过 Traffic Flow 使用
  • 版本管理：流量策略有版本，可以回滚
  • Real-time health data：使用实时延迟和健康数据决策
何时使用 Traffic Flow：当你需要组合多种路由策略（如"欧洲用户 → 法兰克福 Region，但如果法兰克福延迟过高则切到爱尔兰 Region"），或者需要 Geoproximity 精细地理路由时。简单场景用基础路由策略即可。

  • 支持 Route 53 路由策略 + CloudFront 的组合（如 Weighted 路由到两个 CloudFront 分发）

  • Alias 记录指向 ELB 的 DNS 名称
  • 开启 Evaluate Target Health 让 Route 53 使用 ELB 的健康检查结果
  • Failover 场景：Primary ELB + Secondary ELB，ELB 不健康时自动切备

S3 静态网站 + Route 53

  • S3 存储桶命名必须与域名一致（如 www.example.com）
  • Alias 记录指向 S3 静态网站端点
  • 根域名需要 Alias（CNAME 不能用于根域名）
  • 注意：S3 静态网站端点不支持 HTTPS（需 CloudFront 或 ACM）

Global Accelerator + Route 53

  • Alias 记录指向 Global Accelerator 的 DNS 名称
  • Global Accelerator 提供静态 Anycast IP，Route 53 负责 DNS 解析
  • 通常模式：Route 53 Alias → GA → 多 Region 端点

VPC Endpoints（PrivateLink）+ Route 53

  • VPC Interface Endpoint 创建时可以启用 Private DNS Name
  • 启用后，VPC 实例查询 s3.us-east-1.amazonaws.com 会解析到 Endpoint 的私有 IP
  • Route 53 Private Hosted Zone 中可以创建 CNAME/Alias 记录指向 PrivateLink Endpoint
组合场景：混合云架构下，本地应用通过 DX/VPN → Route 53 Resolver Inbound Endpoint → Private Hosted Zone → Alias → S3 Interface Endpoint。这条链路确保数据全程私密传输。

九、场景题解析

SAP-C02 风格场景题，每个都覆盖一个高频考点 + 常见陷阱。

🧩 场景一：全球多区域应用的就近访问

场景描述：一家跨国公司在东京、法兰克福、弗吉尼亚三个 AWS Region 各部署了一套完整的 Web 应用（前面是 ALB）。公司希望用户被自动路由到延迟最低的 Region 的 ALB。但测试发现，部分欧洲用户被路由到了弗吉尼亚，原因不明。架构师应该选择什么路由策略？

分析思路：
需求核心 = "根据延迟自动选择最近的 AWS Region 端点"。Route 53 的 Latency 策略正是为此设计的——它基于 AWS 内部的延迟测量数据，将查询路由到延迟最低的 Region。Latency 策略还会自动进行健康检查，如果某个 Region 的端点不可用则自动排除。
正确答案：使用 Latency Routing 策略，为每个 Region 的 ALB 创建一条记录（Region 选择对应 Region），开启健康检查。

关于"部分欧洲用户被路由到弗吉尼亚"的问题：这通常是因为 Latency 策略的延迟测量数据是基于 AWS 内部骨干网的，而不是终端用户的实际延迟。如果需要更精细控制，可以在 Latency 之外增加 Geolocation 规则（例如欧洲用户强制去法兰克福），或改用 Geoproximity + Traffic Flow。
错误选项排除：
❌ Weighted 策略 → 按比例分流，不考虑延迟
❌ Geolocation 策略 → 按地理位置硬路由，但不考虑同一地区不同用户的实际延迟差异
❌ 直接给 ALB 分配 EIP 让客户端自己测延迟 → 客户端无法知道三个 Region 的 ALB，且 ALB 不支持 EIP（ALB 只有公网 DNS 名称）
❌ 使用 Global Accelerator 替代 Route 53 → GA 提供的是 TCP/UDP 层加速，不解决 DNS 路由问题；通常是 Route 53 → GA → 端点的组合
🧩 场景二：主备区域灾难恢复

场景描述：公司的核心数据库部署在 us-east-1（主）和 us-west-2（备）的 RDS 多可用区实例上。前端应用通过 Route 53 解析 db.example.com 获取数据库连接地址。当 us-east-1 发生自然灾害时，架构师希望流量自动切换到 us-west-2。应该如何配置？

分析思路：
需求 = "主备故障自动切换"。Route 53 Failover 策略的设计目标正是这个场景——Primary 不健康自动切 Secondary。但需要注意 Failover 策略的健康检查应该检查什么。
正确答案：
1. 在 us-east-1 和 us-west-2 各部署 RDS，配置 Cross-Region Read Replica 并在备区域提升为可读实例（或使用 Aurora Global Database）
2. Route 53 创建两条记录：
• Primary：Failover = Primary，值为 us-east-1 RDS 的 Reader Endpoint（不要用 Writer Endpoint，因为 Writer 只能有一个）
• Secondary：Failover = Secondary，值为 us-west-2 RDS 的 Reader Endpoint
3. 为 Primary 配置 TCP 健康检查（数据库端口 3306/5432），或者更好的方式是创建一个 EC2 探针实例检查 RDS 连接性并上报 CloudWatch Alarm，然后用 CloudWatch Alarm 健康检查
4. 当 Primary 健康检查失败（Region 故障），Route 53 自动切换到 Secondary
错误选项排除：
❌ 使用 Simple 策略 + 两个 A 记录 → 没有故障切换功能，Route 53 可能同时返回两个 IP
❌ 使用 Latency 策略 → 不做主动故障切换，只是"选延迟最低的"
❌ 健康检查用 HTTP → RDS 不提供 HTTP 接口，应该用 TCP 或 CloudWatch Alarm
❌ RDS Writer Endpoint 作为 Failover 目标 → Writer 只能有一个，备区域的 RDS 是 Read Replica，只有 Reader Endpoint 可用；切备后需要提升为独立实例
🧩 场景三：VPC 私有域名 + 本地 DNS 互通

场景描述：公司使用 Direct Connect 连接本地数据中心到 AWS VPC。VPC 内部有一个 Private Hosted Zone corp.internal，存储了 RDS、ElastiCache 等服务的私有域名。现在需要让本地数据中心的应用服务器能够解析 corp.internal 域名，同时让 VPC 内的 EC2 能够解析本地 AD 域 onprem.local。如何实现双向 DNS 解析？

分析思路：
这是混合云 DNS 双向解析的经典题目。需要两个方向：On-Prem → AWS（Inbound）和 AWS → On-Prem（Outbound）。Direct Connect 已经提供了网络连通性，缺的是 DNS 层面的转发。Route 53 Resolver 正是为此设计。
正确答案：
方向 1：On-Prem → AWS（本地应用解析 VPC 私有域名）
1. 在 VPC 中创建 Route 53 Resolver Inbound Endpoint（选择公有子网，会创建 ENI，获得私有 IP 如 10.0.1.50）
2. 确保 Inbound Endpoint 所在子网的 路由表 有到 Direct Connect 的路由，且 Security Group 允许来自本地网络的 UDP/TCP 53 流量
3. 在本地 DNS Server（Windows DNS 或 Bind）上配置 Conditional Forwarder：对 corp.internal 的查询转发到 10.0.1.50
4. Inbound Endpoint 会自动查询 Private Hosted Zone 并返回结果

方向 2：AWS → On-Prem（VPC 实例解析本地域名）
1. 在 VPC 中创建 Route 53 Resolver Outbound Endpoint（选择公有子网）
2. 创建 Resolver Rule：指定要转发的域为 onprem.local，目标 DNS Server 为本地 AD 的 IP（如 192.168.1.10）
3. 关联需要解析本地域名的 VPC 到这个 Resolver Rule
4. VPC 实例查询 onprem.local → Outbound Endpoint → Resolver Rule 匹配 → 转发到本地 DNS
错误选项排除：
❌ VPC 中用 DHCP Option Sets 覆盖 DNS → 这会覆盖 VPC 默认 DNS（AmazonProvidedDNS），导致 Private Hosted Zone 解析失效
❌ 使用 VPC Peering 共享 DNS → Peering 是网络层连接，不解决 DNS 转发问题
❌ 在 Direct Connect 上配置 DNS 隧道 → 没有这个功能
❌ 只配置 Inbound Endpoint 不配置 Outbound → 只解决了 On-Prem 查 AWS 的单向需求
🧩 场景四：A/B 测试 + 自动故障切换

场景描述：公司的网站托管在 CloudFront + S3 上，正在进行 A/B 测试版本切换：90% 用户访问现有版本（S3 Bucket A），10% 用户访问新版本（S3 Bucket B）。同时，如果任意一个 Bucket 不可用，需要自动切换到另一个作为故障转移。如何设计 Route 53 配置？

分析思路：
两个需求：1) 按比例分流 → Weighted 策略；2) 自动故障切换 → 健康检查 + Failover 或 Weighted 的 weight=0 技巧。这里 Weighted 策略 + 健康检查组合是最优解。
正确答案：使用 Weighted 路由策略 + 健康检查：
1. 创建两条 Alias 记录（都指向各自 CloudFront 分发）
• 版本 A：Weight = 90，Set ID = "version-A"
• 版本 B：Weight = 10，Set ID = "version-B"
2. 为每条记录配置 Health Check（HTTP 检查 CloudFront 分发的健康端点）
3. 当任意版本的 CloudFront/源 S3 不健康时，Route 53 自动将该版本的权重视为 0，所有流量切到健康的那个版本
4. 如果两个都健康，90/10 分配正常执行
错误选项排除：
❌ Failover 策略 → Failover 是主备模型（一个 Primary 一个 Secondary），无法做 90/10 比例分流
❌ 两个 CNAME 记录 + 简单轮询 → 没有故障切换，也无法精确控制比例
❌ 在 CloudFront 层面做 A/B → CloudFront 不支持基于权重的 A/B，需要用 Lambda@Edge 或 Route 53 在 DNS 层分流
🧩 场景五：根域名指向 CloudFront 的正确方式

场景描述：公司注册了域名 example.com，网站托管在 CloudFront（域名 d12345.cloudfront.net）。架构师想让 example.com 直接访问 CloudFront 网站。他在 Route 53 中为 example.com 创建了 CNAME 记录指向 d12345.cloudfront.net。测试发现 DNS 解析失败。应该如何修复？

分析思路：
DNS 协议规定 根域名（apex domain）不能使用 CNAME 记录。CNAME 会导致根域名的其他记录（如 NS、SOA、MX）冲突。Route 53 提供了 Alias 记录专门解决这个问题——Alias 可以用于根域名，且是 Route 53 内部追踪 AWS 资源的 IP 变化。
正确答案：删除 CNAME 记录，改为创建 Alias 记录：
• 记录名：example.com
• 类型：A - IPv4 address（Route 53 Alias 在类型上显示为 A 或 AAAA）
• Alias 目标：CloudFront 分发对应的 Alias Target（选择 CloudFront，然后选择你的分发）
• Evaluate Target Health：可选开启（检查 CloudFront 健康）

这样 Route 53 会自动追踪 CloudFront 分配的 IP 地址变化（因为 CloudFront 使用 AWS 的 IP 池，会动态变化）。
错误选项排除：
❌ 继续用 CNAME → 根域名 CNAME 是 DNS 协议硬禁止的，不是 Route 53 的问题
❌ 手动把 CloudFront IP 写到 A 记录 → CloudFront IP 会动态变化，下次 IP 变了就断了
❌ 改用 www CNAME 到 CloudFront，根域名跳转到 www → 这是很多网站的做法（www.example.com CNAME → CloudFront，example.com 301 跳转到 www），但不是最优解；直接用 Alias 更干净
🧩 场景六：多账号共享私有托管区

场景描述：企业使用 AWS Organizations 多账号架构。中央 IT 账号（Network Account）管理所有基础设施，在 VPC 中创建了 Private Hosted Zone corp.internal。现在业务账号（App Account）有一个 VPC，需要解析 corp.internal 下的记录。如何让 App Account 的 VPC 能够解析 Network Account 的 Private Hosted Zone？

分析思路：
Private Hosted Zone 可以通过授权机制让其他账号的 VPC 关联。这是跨账号 DNS 共享的标准做法。不需要 VPC Peering，也不需要 Resolver。
正确答案：
1. 确保 App Account 的 VPC 开启了 enableDnsSupport = true 和 enableDnsHostnames = true（默认已开启）
2. 在 Network Account（Private Hosted Zone 所有者）执行：
aws route53 create-vpc-association-authorization --hosted-zone-id ZONE_ID --vpc VPCRegion=us-east-1,VPCId=vpc-xxxxxxxxx --aws-account-id APP_ACCOUNT_ID
3. 在 App Account 执行：
aws route53 associate-vpc-with-hosted-zone --hosted-zone-id ZONE_ID --vpc VPCRegion=us-east-1,VPCId=vpc-yyyyyyyyy
4. 完成后，App Account VPC 内的实例可以直接解析 corp.internal 下的所有记录
错误选项排除：
❌ 为每个业务账号也创建 Private Hosted Zone → 重复维护，需要同步记录，且域名不能相同（Private Hosted Zone 域名全局唯一）
❌ 使用 VPC Peering + DNS → Peering 让 VPC 网络互通，但 DNS 解析仍然需要各自的 Private Hosted Zone 或 Resolver
❌ 在业务账号 VPC 中配置自定义 DNS Server → 如果指向 Network Account 的 VPC IP，仍然需要 Network Account 那边有 Inbound Resolver Endpoint 来响应

十三、快速自测

先独立选择，再点击"查看解析"。概念练习题，不代表真实考试题。

1. 公司使用 Route 53 将根域名 example.com 指向 CloudFront 分发。工程师创建了 CNAME 记录，但 DNS 解析失败。最可能的原因是什么？
正确答案：C。DNS 协议硬规定根域名（apex domain，即不带前缀的域名如 example.com）不能使用 CNAME 记录。CNAME 会导致根域名的 NS、SOA 等必要记录冲突。Route 53 提供 Alias 记录专门解决此问题——Alias 可以用于根域名，且自动追踪 CloudFront/ELB 等 AWS 资源的 IP 变化。
2. 公司在东京、法兰克福、弗吉尼亚三个 Region 各部署了一套应用（前端 ALB）。希望用户自动路由到延迟最低的 Region。但要求欧洲用户尽量留在法兰克福，不要因延迟数据异常被路由到弗吉尼亚。最佳方案是什么？
正确答案：C。需求有两个层次：① 欧洲用户尽量去法兰克福（地理约束）；② 在地理约束内选延迟最低的（延迟优化）。这需要组合 Geolocation + Latency 两种策略。Route 53 Traffic Flow 支持在同一个流量策略中组合多种路由策略。单纯 Latency 无法强制地理边界，单纯 Geolocation 无法做就近优化。
3. VPC-A 在 Account-A，Private Hosted Zone "corp.internal" 也在 Account-A。VPC-B 在 Account-B，需要解析 corp.internal。以下哪步骤不是必需的？
正确答案：D。Private Hosted Zone 的跨账号 VPC 关联不需要 VPC Peering。只要通过 Route 53 的 VPC Association Authorization 授权，两个 VPC 即使完全独立（不 Peering、不 TGW）也能共享同一个 Private Hosted Zone 的 DNS 解析。Peering 解决的是网络层连通性，Private Hosted Zone 关联解决的是 DNS 层可见性。
4. 公司通过 Direct Connect 连接本地数据中心到 AWS。本地应用服务器需要解析 VPC 中 Private Hosted Zone "aws.corp.internal" 的域名。以下哪种配置是正确的？
正确答案：B。Resolver Inbound Endpoint 的功能正是"让 On-Prem DNS 查询能进入 AWS VPC 的 DNS 系统"。本地 DNS Server 需要配置 Conditional Forwarder（条件转发器）——对 aws.corp.internal 域的查询，转发到 Resolver Inbound Endpoint 的私有 IP。Outbound Endpoint 方向相反（让 AWS 查 On-Prem）。选项 D 的 Secondary Zone 不可行，因为 Route 53 不支持作为 Secondary Zone 的主服务器。
5. 公司将 Route 53 记录指向 ALB，开启 Evaluate Target Health = Yes。以下关于此配置的描述，哪项是正确的？
正确答案：C。Evaluate Target Health 让 Route 53 直接使用 ALB/NLB 自身的健康检查结果——Route 53 不独立发起检查，而是读取 ALB 的状态。如果 ALB 的所有实例都不健康（ALB 级别不健康），Route 53 会自动停止路由到该 ALB（配合 Failover 或 Weighted 策略实现故障切换）。它可以和任何路由策略一起使用，不限于 Failover。
