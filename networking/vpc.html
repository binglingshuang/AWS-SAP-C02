一、VPC 基础架构

VPC（Virtual Private Cloud）是 AWS 提供的逻辑隔离网络环境，是所有 AWS 网络架构的基础。

VPC 的本质

VPC 是 Region 级别的逻辑网络隔离边界。一个 Region 内可以创建多个 VPC，每个 VPC 之间默认完全隔离，互不可达。每个 AWS 账户在每个 Region 有一个默认 VPC（CIDR: 172.31.0.0/16）。

CIDR 规划

  • VPC 支持一个主 CIDR（创建时指定）和最多 4 个辅助 CIDR
  • CIDR 范围：/16（最大 65,536 个 IP）到 /28（最小 16 个 IP）
  • 同一 VPC 内的 CIDR 不得重叠；与 Peering 对端 VPC 的 CIDR 不得重叠
  • AWS 在每个子网保留 5 个 IP：网络地址、VPC 路由器、DNS 服务器、未来保留、广播地址
CIDR 陷阱：规划时预留足够空间，VPC 主 CIDR 一旦创建后不可修改。辅助 CIDR 可以后期添加，但不能与主 CIDR 重叠。

子网（Subnet）

子网是 AZ（可用区）级别的资源，一个子网只能属于一个 AZ，但一个 AZ 可以有多个子网。

  • 公有子网：路由表中有指向 IGW 的路由（0.0.0.0/0 → igw-xxxx），实例需分配公有 IP 或 EIP 才能直接通信
  • 私有子网：路由表中没有指向 IGW 的路由，通过 NAT Gateway 访问互联网

Internet Gateway（IGW）

  • 将 VPC 连接到互联网，每个 VPC 只能绑定一个 IGW
  • 高可用设计：IGW 本身是 AWS 托管的高可用组件，无需配置冗余
  • 支持 IPv4 和 IPv6（双向通信）
  • 仅作为路由目标，本身不做 NAT（与 NAT Gateway 区别）

路由表（Route Table）

  • Main Route Table：创建 VPC 时自动生成，所有未显式关联自定义路由表的子网使用此路由表
  • 自定义路由表：可为特定子网单独配置，实现公有/私有子网分离
  • 每条路由由 目标（Destination） 和 目标（Target） 组成
  • 本地路由（local）始终存在，不可修改，确保 VPC 内部通信
# 公有子网路由表示例
Destination        Target
10.0.0.0/16        local          # VPC 内部路由（不可删除）
0.0.0.0/0          igw-0a1b2c3d   # 默认路由指向 IGW → 公有子网

# 私有子网路由表示例
Destination        Target
10.0.0.0/16        local
0.0.0.0/0          nat-0x1y2z3w   # 默认路由指向 NAT Gateway → 私有子网

二、网络安全控制

VPC 提供两层安全控制：Security Group（实例级别）和 Network ACL（子网级别），两者配合使用实现纵深防御。

Security Group（安全组）

安全组是实例（ENI）级别的虚拟防火墙。

  • 有状态（Stateful）：允许入站流量后，对应的出站响应流量自动允许，无需单独配置出站规则
  • 只能配置允许规则：无法显式拒绝某个 IP（需要拒绝时使用 NACL）
  • 默认规则：默认拒绝所有入站流量；默认允许所有出站流量
  • 可以引用其他安全组作为来源（而不仅是 CIDR），适合微服务之间的访问控制
  • 一个实例可绑定最多 5 个安全组（默认配额）
  • 规则变更实时生效，无需重启实例
# Security Group 规则示例（入站）
Type       Protocol  Port Range  Source
HTTP       TCP       80          0.0.0.0/0         # 允许所有 HTTP 入站
HTTPS      TCP       443         0.0.0.0/0         # 允许所有 HTTPS 入站
SSH        TCP       22          10.0.1.0/24       # 仅允许堡垒机子网 SSH
All Traffic  All     All         sg-0abc123def     # 允许来自另一 SG 的所有流量

Network ACL（NACL）

NACL 是子网级别的防火墙，对进出子网的所有流量生效。

  • 无状态（Stateless）：入站和出站规则互相独立，响应流量必须单独配置出站规则
  • 支持允许和拒绝规则：可以显式拒绝特定 IP 或端口
  • 规则按编号顺序评估：从最小编号开始，匹配到第一条规则即停止，不再继续评估
  • 默认 NACL 允许所有进出流量；自定义 NACL 默认拒绝所有流量
  • 每条规则包含：规则编号、类型、协议、端口范围、来源/目标、允许/拒绝
# NACL 入站规则示例（无状态！需要同时配置出站）
Rule #   Type      Protocol  Port     Source          Action
100      HTTP      TCP       80       0.0.0.0/0       ALLOW
110      HTTPS     TCP       443      0.0.0.0/0       ALLOW
120      SSH       TCP       22       203.0.113.0/24  ALLOW
*        ALL       ALL       ALL      0.0.0.0/0       DENY   # 默认拒绝

# NACL 出站规则示例（响应流量使用临时端口 1024-65535）
Rule #   Type      Protocol  Port         Dest            Action
100      HTTP      TCP       80           0.0.0.0/0       ALLOW
110      HTTPS     TCP       443          0.0.0.0/0       ALLOW
120      Custom    TCP       1024-65535   0.0.0.0/0       ALLOW  # 临时端口
*        ALL       ALL       ALL          0.0.0.0/0       DENY
SAP 必考陷阱 — NACL 无状态：NACL 是无状态的，HTTP 请求进来时使用 80 端口，但响应时服务器向客户端发出的数据使用临时端口（Ephemeral Ports，1024–65535）。如果 NACL 出站规则没有允许这些端口，连接将失败。这是 NACL 排错的首要检查点。

三、网络地址转换（NAT）

私有子网中的实例需要访问互联网（如更新软件包、调用外部 API），但又不能被外部主动访问，此时需要 NAT。

NAT Gateway（推荐）

AWS 托管的 NAT 服务，按使用量计费，无需管理底层基础设施。

  • 部署位置：必须部署在公有子网，并绑定一个弹性 IP（EIP）
  • AZ 级别资源：NAT Gateway 仅为同一 AZ 的资源提供路由；私有子网路由应指向同 AZ 的 NAT Gateway
  • 高可用架构：每个 AZ 各部署一个 NAT Gateway，每个 AZ 的私有子网路由表指向本 AZ 的 NAT Gateway
  • 带宽：默认 5 Gbps，自动扩展至 45 Gbps
  • 不支持端口转发：无法将外部流量转发到私有实例
  • 不支持作为堡垒机（Bastion Host）
  • 支持 TCP、UDP、ICMP

高可用关键：如果所有私有子网都指向同一个 AZ 的 NAT Gateway，当该 AZ 故障时，其他 AZ 的实例也失去互联网访问。正确做法是每个 AZ 一个 NAT Gateway，各自独立。

NAT Instance（遗留方案）

使用特殊 AMI（amzn-ami-vpc-nat）的 EC2 实例，手动充当 NAT 设备。

  • 需要关闭 Source/Destination Check（实例默认只处理自己的流量，关闭后才能转发流量）
  • 性能受 EC2 实例规格限制，需手动扩展
  • 可以兼作堡垒机（Bastion Host）
  • 支持端口转发
  • 需要配置安全组和路由
  • SAP-C02 考试中 NAT Instance 通常作为干扰项，除非题目特别强调"作为堡垒机"或"端口转发"

Egress-Only Internet Gateway

  • 专为 IPv6 设计的单向出站网关（IPv4 使用 NAT Gateway）
  • 允许 IPv6 实例主动访问互联网，但外部无法主动连接
  • 高可用（AWS 托管），无需配置冗余
  • 在路由表中配置 ::/0 → eigw-xxxx

四、VPC Endpoints

VPC Endpoints 允许 VPC 内的资源通过 AWS 私有网络访问 AWS 服务，无需经过公共互联网或 NAT Gateway，提升安全性并降低数据传输成本。

Gateway Endpoint

  • 仅支持：S3 和 DynamoDB（SAP 必记）
  • 完全免费（不额外收费）
  • 通过修改路由表来引导流量（而不是在子网中创建 ENI）
  • 不占用 IP 地址，不创建 ENI
  • Region 级别资源，一个 Gateway Endpoint 服务整个 VPC
  • 不支持通过 VPN 或 Direct Connect 从本地访问（因为它只修改路由表，本地网络没有这些路由）
  • 不支持跨 Region 访问
# Gateway Endpoint 路由表（自动添加）
Destination        Target
10.0.0.0/16        local
0.0.0.0/0          nat-0x1y2z3w
pl-xxxxxxxx        vpce-0a1b2c3d    # S3/DynamoDB 前缀列表 → Gateway Endpoint
考试关键：Gateway Endpoint 是免费的首选方案，用于私有子网访问 S3/DynamoDB，无需 NAT Gateway，节省成本。

Interface Endpoint（AWS PrivateLink）

  • 支持大多数 AWS 服务（EC2 API、SSM、STS、CloudWatch、Kinesis、SNS、SQS 等）以及 AWS Marketplace 的第三方服务
  • 在指定子网中创建一个或多个 ENI（弹性网络接口），分配私有 IP
  • 收费：按 ENI 小时数 + 数据处理量计费
  • 可通过 VPN 或 Direct Connect 从本地（On-Premises）访问
  • 支持 VPC Endpoint Policies（通过 IAM 策略控制访问权限）
  • 支持跨账号共享（通过 PrivateLink）
  • 高可用：建议在多个 AZ 创建 ENI
# Interface Endpoint DNS 示例
# 创建后自动生成私有 DNS 名称
vpce-0a1b2c3d-xy5678ab.s3.ap-northeast-1.vpce.amazonaws.com
# 启用 Private DNS 后，访问 s3.amazonaws.com 自动解析到 ENI 私有 IP
SAP 关键陷阱：On-Premises 通过 DX/VPN 访问 S3
• 如果 On-Premises 需要通过 Direct Connect 或 VPN 私有访问 S3，必须使用 Interface Endpoint（PrivateLink），不能用 Gateway Endpoint。
• Gateway Endpoint 只修改 VPC 路由表，本地网络无法利用这条路由。
• Interface Endpoint 创建的 ENI 有私有 IP，本地可以通过 DX/VPN 路由到该 IP。

五、VPC Peering

VPC Peering 在两个 VPC 之间建立私有网络连接，流量通过 AWS 骨干网传输，不经过公共互联网。

核心特性

  • 可跨账号（Cross-Account）和跨Region（Cross-Region Peering）
  • 连接建立后，两端 VPC 内的资源可通过私有 IP 互相访问
  • 需要双方各自更新路由表，并确保安全组/NACL 允许对应流量
  • 一对一连接：一个 Peering 连接只能连接两个 VPC

关键限制（SAP 超高频考点）

🔥 VPC Peering 不可传递（Non-Transitive）
如果 VPC-A 与 VPC-B 有 Peering，VPC-B 与 VPC-C 有 Peering，VPC-A 不能通过 VPC-B 访问 VPC-C。每对 VPC 之间必须单独建立 Peering 连接。这是 SAP-C02 最常考的 VPC 陷阱之一。
VPC-A
⟷
VPC-B
⟷
VPC-C

❌ A 无法通过 B 访问 C！需要 A-C 单独 Peering

  • CIDR 不能重叠：两端 VPC 的 IP 地址范围不得有任何重叠
  • 不支持边缘到边缘路由：不能通过 Peering 共享 VPN、Direct Connect、IGW 或 NAT Gateway
  • 没有带宽上限限制（受底层网络约束）
  • 每个 VPC 默认最多 125 个 Peering 连接（软限制）

配置步骤

  1. 发起方创建 Peering 请求
  2. 接受方接受请求
  3. 双方各自更新路由表（添加对端 CIDR → Peering 连接）
  4. 更新 Security Group 规则（允许来自对端 CIDR 的流量）

Destination        Target
10.0.0.0/16        local       # VPC-A 自身
172.16.0.0/16      pcx-0abc123 # VPC-B CIDR → Peering 连接

# VPC-B 路由表（添加到 VPC-A 的路由）
Destination        Target
172.16.0.0/16      local       # VPC-B 自身
10.0.0.0/16        pcx-0abc123 # VPC-A CIDR → Peering 连接

六、VPC Flow Logs

Flow Logs 捕获 VPC、子网或 ENI 级别的网络流量元数据，是网络排错、安全审计和合规的重要工具。

基本概念

  • 可以在三个层级启用：VPC 级别（捕获所有子网）、子网级别、ENI 级别
  • 目标存储：CloudWatch Logs 或 S3（推荐 S3，成本低）
  • 不是实时的：有几分钟的聚合延迟，不能用于实时入侵检测
  • 只捕获元数据，不捕获内容：只记录 IP 地址、端口、协议、字节数、是否被允许，不记录数据包内容
  • 默认格式为固定字段；自定义格式可选择需要的字段

Flow Log 字段解析

# 默认 Flow Log 格式（14 个字段）
version  account-id  interface-id  srcaddr    dstaddr     srcport  dstport  protocol  packets  bytes  start  end   action  log-status
2        123456789012  eni-0a1b2c3d    10.0.1.5   52.94.133.0  43210    443      6         20       5000   ...    ...   ACCEPT  OK
2        123456789012  eni-0a1b2c3d    10.0.1.5   1.2.3.4      55001    3389     6         1        44     ...    ...   REJECT  OK

# ACCEPT → 流量被 SG/NACL 允许
# REJECT → 流量被 SG/NACL 拒绝
# NODATA → 该时间窗口没有流量
# SKIPDATA → 因容量限制跳过了某些记录

重要字段

字段含义用途
srcaddr源 IP 地址识别访问来源，发现扫描/攻击 IP
dstaddr目标 IP 地址追踪数据流向
srcport / dstport源/目标端口识别服务类型
actionACCEPT 或 REJECT排查 SG/NACL 拦截问题
bytes传输字节数流量分析、异常检测
protocol6=TCP, 17=UDP, 1=ICMP协议过滤

常见使用场景

  • 安全审计：查看 REJECT 记录，找出被拦截的可疑连接
  • 异常流量分析：识别端口扫描、DDoS 攻击来源 IP
  • 合规要求：PCI DSS、HIPAA 等合规框架要求记录网络访问日志
  • 排查连接故障：实例 A 无法连接实例 B，通过 Flow Log 查看流量是 REJECT 还是根本没有到达
  • 数据传输成本分析：分析跨 AZ 或跨 Region 的数据传输量
Flow Logs 不捕获以下流量：Amazon DNS 服务器的流量、DHCP 流量、Windows 激活流量、169.254.169.254（实例元数据服务）的流量、169.254.169.123（NTP 服务）的流量。

七、DNS 解析

VPC DNS 配置控制 VPC 内实例如何解析 AWS 内部域名，以及 Route 53 私有托管区的工作方式。

VPC DNS 两个核心设置

属性含义默认值注意事项
enableDnsSupport启用 AWS 内置 DNS 解析器（169.254.169.253 或 VPC CIDR + 2）✅ 开启关闭后 VPC 内所有 DNS 解析失效
enableDnsHostnames为具有公有 IP 的实例分配公有 DNS 主机名默认 VPC: ✅；自定义 VPC: ❌必须同时开启 enableDnsSupport 才能生效
Interface Endpoint 私有 DNS：使用 Interface Endpoint 时，需要开启 enableDnsSupport 和 enableDnsHostnames，才能使 VPC 内的 DNS 查询自动解析到 Endpoint 的私有 IP（而不是服务的公有 IP）。

Route 53 私有托管区（Private Hosted Zone）

  • 为 VPC 内部提供自定义域名解析（如 db.internal.example.com）
  • 私有托管区只对关联的 VPC 可见，外部无法查询
  • 同一个私有托管区可以关联多个 VPC（包括跨账号的 VPC）
  • VPC 也可以关联多个私有托管区

跨账号 VPC DNS 关联

Account A 的私有托管区需要为 Account B 的 VPC 提供 DNS 解析：

  1. Account A 在私有托管区上创建 VPC 关联授权（Authorization）
  2. Account B 将本账号的 VPC 关联到 Account A 的私有托管区
  3. 关联建立后，Account A 可以删除授权（已关联的不受影响）
# AWS CLI 跨账号私有托管区关联（示例）
# Step 1: Account A 创建授权
aws route53 create-vpc-association-authorization \
  --hosted-zone-id Z1234567890 \
  --vpc VPCRegion=ap-northeast-1,VPCId=vpc-0abc123def

# Step 2: Account B 关联 VPC
aws route53 associate-vpc-with-hosted-zone \
  --hosted-zone-id Z1234567890 \
  --vpc VPCRegion=ap-northeast-1,VPCId=vpc-0xyz987654

DNS 解析层级（完整流程）

  1. 实例向 169.254.169.253（或 VPC 基地址 +2）发送 DNS 查询
  2. Route 53 Resolver 检查解析规则（Resolver Rules）
  3. 如果匹配私有托管区 → 返回私有记录
  4. 如果匹配 Forwarding Rule → 转发到指定 DNS 服务器（如本地 DNS）
  5. 都不匹配 → 转发到公共 DNS 递归解析
Route 53 Resolver Endpoints（混合云 DNS）：
• Inbound Endpoint：本地 DNS 服务器可以将 AWS 域名查询转发到 VPC
• Outbound Endpoint + Forwarding Rule：VPC 内实例可以将本地域名查询转发到本地 DNS 服务器
这是实现混合云统一 DNS 解析的标准方案。

八、高级特性

DHCP Option Sets

控制 VPC 内 DHCP 分配的配置参数。

  • domain-name-servers：指定自定义 DNS 服务器（默认 AmazonProvidedDNS）
  • domain-name：指定实例的域名搜索后缀
  • ntp-servers：指定 NTP 服务器
  • 创建后不可修改；需要修改时，创建新的 DHCP Option Set 并关联到 VPC
  • 典型使用：企业需要实例使用内部 DNS 服务器

弹性 IP（Elastic IP / EIP）

  • 静态的公有 IPv4 地址，与账号关联（而非实例）
  • 可在实例之间移动，实现快速故障切换
  • 绑定到正在运行的实例时免费；实例停止或 EIP 未绑定时收费（每小时约 $0.005）
  • 每个账号默认 5 个 EIP（软限制，可申请提升）

ENI（Elastic Network Interface）

  • 虚拟网络接口，可以独立创建、附加、分离到实例
  • 每个 ENI 可以绑定多个私有 IP（主 IP + 辅助 IP）
  • 每个私有 IP 可以关联一个 EIP
  • 绑定安全组（安全组绑定在 ENI 上，不是实例）
  • 应用场景：多网卡架构（一个 ENI 面向公网，一个 ENI 面向私有管理网络）、故障切换（将 ENI 从故障实例移到备用实例）

VPC Sharing（RAM 资源共享）

  • 使用 AWS Resource Access Manager（RAM） 将 VPC 内的子网共享给同一 Organizations 中的其他账号
  • 资源所有者账号（Owner）创建和管理 VPC 及子网；参与者账号（Participant）在共享子网中创建自己的资源
  • 不同账号的资源共享同一 VPC 底层网络，无需 Peering
  • 典型场景：中央 IT 团队管理网络，各业务团队在共享子网中部署应用
VPC Sharing vs Peering：Sharing 是让多个账号共用同一个 VPC 的子网（一个 VPC，多个账号）；Peering 是连接两个独立的 VPC（两个 VPC，互相访问）。

Traffic Mirroring（流量镜像）

  • 复制 ENI 的入站/出站流量，发送到目标 ENI 或 Network Load Balancer
  • 目标通常是运行 IDS/IPS（入侵检测/防御系统）或深度包检测工具的实例
  • 不影响原始流量（镜像是复制，不是重定向）
  • 可以设置过滤规则（只镜像特定端口/协议）
  • 收费：按处理的流量数据量计费

VPC Reachability Analyzer

  • 无需发送实际流量，即可分析两个端点之间的网络可达性
  • 输出：可达 or 不可达，不可达时指出阻断原因（哪条 SG/NACL 规则、哪个路由表）
  • 典型用途：排查网络配置问题（比 Flow Logs 更直接）

AWS Network Firewall

  • 托管式网络防火墙，部署在 VPC 内，支持有状态和无状态规则
  • 支持基于域名的过滤（防止访问特定域名）、IDS/IPS 规则集
  • 通常部署在专用的 Firewall 子网，所有流量经过防火墙转发
  • 适合需要七层过滤（URL/域名过滤）的场景，NACL 和 SG 只能做四层过滤

九、场景题解析

以下场景题基于 SAP-C02 考试的典型出题模式，包含完整的分析思路和排错逻辑。

🧩 场景一：VPC Peering 传递性问题

场景描述：某公司在 AWS 上有三个 VPC：VPC-A（生产）、VPC-B（共享服务，如 AD、DNS）、VPC-C（开发）。公司已配置 VPC-A ↔ VPC-B Peering 和 VPC-B ↔ VPC-C Peering，并更新了所有路由表。但工程师发现 VPC-A 中的实例仍然无法与 VPC-C 中的实例通信。应如何解决？

分析思路：
这是经典的 VPC Peering 传递性问题。VPC Peering 是非传递的（Non-Transitive）。即使 A-B 有 Peering，B-C 有 Peering，AWS 也不会将 A 到 C 的流量通过 B 转发——这在网络层面就被阻断了，不是路由表或安全组的问题。
正确答案：在 VPC-A 和 VPC-C 之间直接创建一个新的 VPC Peering 连接（pcx-A-C），然后在两端各自添加路由。
如果公司有许多 VPC，考虑使用 Transit Gateway，它原生支持传递路由，且只需一个中心节点。
错误选项排除：
❌ 在 VPC-B 中配置 EC2 作为中间路由器 → 可行但不推荐，增加运维复杂度和单点故障风险
❌ 修改 VPC-B 的路由表使其转发流量 → VPC Peering 本身不支持传递路由，路由表无法解决此问题
❌ 更新安全组规则 → 不是安全组问题，是架构问题
🧩 场景二：On-Premises 通过 Direct Connect 私有访问 S3

场景描述：某金融公司将核心数据存储在 S3，合规要求所有访问 S3 的流量不得经过公共互联网（包括来自本地数据中心的访问）。公司已通过 Direct Connect 连接到 AWS，VPC 内已创建 S3 Gateway Endpoint。但本地服务器访问 S3 仍经过公共互联网，应如何修复？

分析思路：
Gateway Endpoint 的工作原理是在 VPC 路由表中添加前缀列表条目，将目标为 S3 的流量路由到 Endpoint。但 Direct Connect 连接的本地网络无法使用这些路由——本地网络的路由表不受 VPC 路由表管理。
要让本地通过 DX 私密访问 S3，需要一个在 VPC 内有私有 IP 的端点，这样本地才能通过 DX 路由到该私有 IP。
正确答案：在 VPC 中为 S3 创建 Interface Endpoint（PrivateLink），并启用 Private DNS。本地服务器通过 Direct Connect 连接到 VPC，DNS 解析到 Interface Endpoint 的私有 IP，流量全程不经过公网。
错误选项排除：
❌ 使用现有的 Gateway Endpoint → Gateway Endpoint 不能被 DX/VPN 连接的本地网络使用，这是最常见的陷阱
❌ 配置 S3 Transfer Acceleration → 这是加速功能，仍然走公共互联网
❌ 在本地配置 S3 VPC Endpoint DNS → Gateway Endpoint 不生成私有 IP，无法被路由
🧩 场景三：私有子网实例需要访问互联网但不能被外部访问

场景描述：公司将应用服务器部署在私有子网中，实例需要访问互联网以下载安全补丁（apt-get update / yum update）和调用第三方 API。但出于安全要求，实例不能被外部直接访问。架构师应如何设计？

分析思路：
需要单向出站（实例主动发起 → 互联网），阻止外部入站（互联网主动 → 实例）。这是 NAT 的核心功能。私有子网 + NAT Gateway 是标准方案。
正确答案：
1. 在每个 AZ 的公有子网中部署 NAT Gateway（绑定 EIP）
2. 在每个 AZ 的私有子网路由表中添加 0.0.0.0/0 → 本 AZ 的 NAT Gateway
3. 确保 IGW 已附加到 VPC，公有子网路由表有 0.0.0.0/0 → IGW
4. 安全组只配置必要的出站规则（默认允许所有出站，可收紧）
错误选项排除：
❌ 将实例移到公有子网并分配公有 IP → 公有 IP 意味着可被外部直接访问，违反安全要求
❌ 使用 Egress-Only IGW → 这是 IPv6 专用，IPv4 不适用
❌ 只在一个 AZ 部署 NAT Gateway，其他 AZ 共用 → 如果该 AZ 故障，其他 AZ 实例也无法访问互联网（单点故障）
❌ 使用 VPC Gateway Endpoint 代替 NAT → Gateway Endpoint 只服务 S3 和 DynamoDB，不能替代 NAT 进行通用互联网访问
🧩 场景四：跨账号 VPC 共享子网

场景描述：某大型企业采用多账号策略（AWS Organizations）。中央 IT 团队（Account A）负责管理所有网络基础设施；各业务团队（Account B、C、D）各自拥有 AWS 账号，需要在统一的网络环境中部署应用。要求：各账号的资源共享同一底层 VPC，无需配置 Peering，中央 IT 团队统一管控网络，业务团队不能修改 VPC 配置。如何实现？

分析思路：
核心需求：1) 多账号共享同一 VPC 子网；2) 网络控制权在中央团队；3) 业务团队只能使用子网部署资源，不能修改网络。这正是 VPC Sharing（通过 RAM）的设计目标。
正确答案：
使用 AWS Resource Access Manager（RAM） 实现 VPC 共享：
1. Account A（网络所有者）创建 VPC 和子网
2. 通过 RAM 将特定子网共享给 Account B、C、D
3. Account B/C/D 可以在共享子网中创建 EC2、RDS 等资源
4. 子网的路由表、NACL、VPC 配置由 Account A 统一管理，参与者账号无权修改
错误选项排除：
❌ 为每个账号建立 VPC Peering → 多账号 Peering 管理复杂，非传递性限制互相访问，需要配置大量 Peering 和路由
❌ 使用 Transit Gateway 互连各账号 VPC → TGW 连接独立 VPC，每个账号仍有自己的 VPC，网络分散，不是"共享"模型
❌ 将所有资源部署到同一账号 → 违反多账号隔离原则，不符合企业安全要求
🧩 场景五：安全组配置后 ping 不通的排查

场景描述：工程师在 EC2 实例 A（公有子网，已分配公有 IP）的安全组中添加了入站规则：允许来自 0.0.0.0/0 的 All TCP 流量。但从本地工作站 ping 该实例仍然超时，而 curl 测试的 HTTP 端口可以正常连通。原因是什么？

分析思路：
curl HTTP = TCP（端口 80）；ping = ICMP（不是 TCP，也不是 UDP）。
工程师只允许了 "All TCP"，ICMP 协议没有被包含在 TCP 规则中。安全组对协议是精确匹配的，TCP 规则不覆盖 ICMP。
正确答案：在安全组入站规则中单独添加 ICMP - IPv4 类型的规则，允许来自 0.0.0.0/0（或特定 IP）的 ICMP 流量。
由于 SG 是有状态的，出站响应的 ICMP 流量会自动允许，无需添加出站规则。
错误选项排除：
❌ 检查 NACL → 如果 curl 能通，NACL 基本没问题（NACL 是无状态的，如果 NACL 拦截了 TCP 80 的响应，curl 也应该失败）
❌ 检查路由表 → curl 能通说明路由正确
❌ 检查 IAM 权限 → IAM 不控制网络连通性
延伸陷阱：如果 curl 也无法连通，则检查顺序应为：SG入站规则 → NACL入站规则 → NACL出站规则（临时端口）→ 路由表 → 实例操作系统防火墙

  • Flow Logs：记录元数据（不含内容），有延迟，action 字段 ACCEPT/REJECT
  • Traffic Mirroring：复制完整数据包，用于深度检测（IDS/IPS）
  • Route 53 Resolver Inbound/Outbound Endpoint：混合云双向 DNS 解析

十三、快速自测

先独立选择，再点击"查看解析"。概念练习题，不代表真实考试题。

1. 公司需要本地数据中心通过 Direct Connect 私密访问 Amazon S3，不经过公共互联网。VPC 内已存在 S3 Gateway Endpoint。下一步应该做什么？
正确答案：B。Gateway Endpoint 只修改 VPC 路由表，无法被 DX 本地网络使用。Interface Endpoint 在 VPC 内创建 ENI（有私有 IP），本地可通过 DX 路由到该私有 IP 访问 S3。选项 D 的 Public VIF 走公共互联网，不符合"不经过公共互联网"的要求。
2. 公司有 VPC-A、VPC-B、VPC-C 三个 VPC，已配置 A-B 和 B-C 的 Peering，但 A 无法连接 C。在不增加 Transit Gateway 的前提下，最简单的解决方案是什么？
正确答案：B。VPC Peering 是非传递的，无论如何配置路由表和 NACL，流量都不能经 B 转发从 A 到 C。唯一解决方案是直接在 A 和 C 之间建立 Peering。
3. 私有子网中的实例安全组入站规则：允许 TCP 80（HTTP）来自 0.0.0.0/0。但从公有子网的实例向该私有实例发送 HTTP 请求，响应没有收到。该子网的自定义 NACL 配置了：入站规则 100 允许 TCP 80，出站规则 100 允许 TCP 80。问题最可能是什么？
正确答案：B。NACL 是无状态的。HTTP 请求进入时用 80 端口（NACL 入站规则 100 允许），但服务器响应时源端口是 80，目标端口是客户端的临时端口（1024-65535）。NACL 出站规则只允许了 TCP 80，没有允许临时端口范围，响应被拦截。安全组是有状态的，不存在此问题（选项 A 错误）。
4. 企业使用 AWS Organizations 多账号架构。中央 IT 账号（Account A）负责管理所有 VPC 和子网；10 个业务团队账号需要在统一的 VPC 环境中部署资源，且不能修改 VPC/子网配置。最合适的方案是什么？
正确答案：B。RAM VPC Sharing 正是为此场景设计：网络所有者账号通过 RAM 共享子网，参与者账号可以在共享子网中部署资源，但无法修改 VPC/子网配置，满足题目所有要求。选项 A/C 每个账号各自有 VPC，网络分散，管理复杂，不是"统一 VPC 环境"。
5. 公司需要对某个 EC2 实例进行深度入侵检测，要求检测工具能够看到完整的网络数据包内容（而非仅元数据）。应该使用哪个 AWS 服务？
正确答案：C。Flow Logs 只记录流量元数据（IP、端口、action），不含数据包内容（选项 A 错误）。Traffic Mirroring 会将 ENI 的完整数据包复制到目标 ENI 或 NLB，供 IDS/IPS 工具进行深度检测。GuardDuty 是 AWS 托管的威胁检测服务，使用 VPC Flow Logs/DNS logs 等作为数据源，不提供原始数据包。
