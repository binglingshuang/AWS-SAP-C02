一、服务定位与邮件链路

SES 是托管的邮件发送服务，可替代自建 SMTP 服务器，负责接收发送请求并向收件人邮件系统投递。应用可经 SES SMTP 接口或 SES API 发信；SES 也支持以接收规则处理入站邮件。

  • 适合事务型邮件（验证码、订单通知）、营销邮件和应用通知；用模板及 API 可避免维护邮件服务器。
  • SES 负责邮件发送，不是消息队列或完整工作流。需要异步缓冲时，可在应用与 SES 之间组合 SQS / Lambda。
  • 入站邮件是另一条链路：SES 接收规则集匹配邮件并执行 S3、SNS、Lambda 等动作；不要与出站 SMTP 配置混为一谈。
先看题目限制：若题干要求兼容现有 SMTP 客户端，优先使用 SES SMTP 接口；若需要 SES 模板、细粒度 API 功能或结构化发送操作，通常选择 SES API/SDK。

二、SMTP 与 API 发送方式

方式适合场景关键考点
SES SMTP 接口现有邮件客户端、SMTP 库或邮件服务器迁移，需少改应用协议使用 SES SMTP endpoint、区域专用 SMTP 凭证和 TLS；SMTP 凭证不是 AWS Access Key。
SES API / SDK新应用、程序化控制、SES 模板、丰富的请求参数与响应处理通过 IAM 凭证签名调用 API；使用最小权限的执行角色，无需自行管理 SMTP 密码。
SES 控制台验证身份、请求生产访问、查看发送指标及配置服务不是生产应用持续发信的替代接口。
凭证辨析：SMTP 用户名和密码需从 SES 为目标区域生成，不能直接拿 IAM 用户的 Access Key/Secret Access Key 当 SMTP 凭证。使用 SMTP 的程序仍需能通过 TLS 与 SES 通信。

三、Sandbox、配额与区域

  • 新账户在每个 AWS Region 都有独立的 Sandbox 状态。Sandbox 中可测试服务，但收件人通常也必须是已验证地址/域名（或 SES mailbox simulator），并受发送速率和每日配额限制。
  • 正式向普通收件人发信，需为对应区域申请生产访问、移出 Sandbox；生产状态下，收件人通常不必逐个验证，但发件身份仍须验证。
  • 发送配额和速率限制按区域管理；高容量场景应提前申请提升，并监控配额使用和送达信誉。
  • 身份、SMTP 凭证和服务配置具有区域范围。多区域容灾时，需在备用区域重新验证身份、配置 DKIM/事件目标、申请生产访问并验证配额。
常见误区：在一个 Region 验证域名或退出 Sandbox，不代表其他 Region 自动完成。考试通常考“区域隔离”这一原则；具体限额会随账户与服务更新，以控制台和官方文档为准。

四、身份验证与 DNS 认证

机制目的 / 配置易混点
SES Identity验证发件域名或单个邮箱；域名身份一般更适合组织级发送生产环境仍需验证 From / Source / Sender / Return-Path 等发件身份；验证是区域性的。
DKIMSES 提供 DNS 记录（常见 Easy DKIM 为 CNAME），用于对外发邮件做域名签名把 SES 提供的记录发布到 DNS 并等待验证；不是仅设置 SPF 就完成 DKIM。
SPF / Custom MAIL FROM通过 DNS 声明邮件发送授权；自定义 MAIL FROM 可让退信域名与组织域名对齐SPF 验证 MAIL FROM 域，不等于验证 From 显示地址；按 SES 指引配置 MX 与 SPF。
DMARC发布组织策略，要求 SPF 或 DKIM 与可见 From 域对齐，并接收聚合报告先验证 DKIM/SPF 对齐，再逐步制定策略；DMARC 不能替代 SES identity 验证。
选型提示：为组织域名验证 SES identity，再配置 DKIM，并按邮件域名策略设置 SPF/DMARC，可覆盖多个发件地址并改善收件方信任。不要把“域名已验证”误当成所有 DNS 认证都自动完成。

五、SMTP、TLS 与端口

  • SES SMTP 连接应使用 TLS。STARTTLS 先建立 SMTP 会话再升级到 TLS；TLS Wrapper（隐式 TLS）则在连接开始时就进行 TLS 握手，两者不可混为一谈。
  • SES SMTP endpoint 的端口随连接模式而定；常见 STARTTLS 端口为 25、587、2587，TLS Wrapper 常用 465、2465。按所用区域的 SES SMTP endpoint 文档配置。
  • 题干限定“只能使用 SMTP”时，仍可把 SMTP 服务端改为 SES endpoint，并启用 STARTTLS、配置 SES SMTP 凭证；不必改成 SES API。
  • EC2 对外发起 TCP 25 连接可能受默认节流。若应用/网络可调整，考虑 STARTTLS 端口 587/2587；必须使用 25 时，单独申请移除 EC2 端口 25 限制。
考试陷阱：“应用不能用 TLS”与 SES SMTP 的加密要求冲突，必须升级客户端支持 STARTTLS/TLS。TLS Wrapper 不等同 STARTTLS；而 EC2 端口 25 节流是网络出口限制，不是 SES Sandbox 配额。

六、投递、退信与投诉

  • 硬退信、投诉和高发送失败率会损害发送信誉。只向有许可的收件人发送，及时处理退信/投诉，维护名单和退订流程。
  • 利用 SES 账户级 suppression list 抑制已知硬退信或投诉收件人，避免反复发送；抑制列表不是营销订阅或退订管理的完整替代。
  • 共享 IP 池由 SES 管理发送 IP；Dedicated IP 适用于需要较强发送信誉隔离、具有足够稳定发送量并能承担预热和运营工作的场景。
  • Dedicated IP pool 可按发送类型分组，例如隔离营销与事务邮件，降低一种流量的发送行为对另一种流量信誉的影响。
  • 对高发送量、重要通知和多区域场景，监控发送配额、退信、投诉、延迟及账户发送状态，并通过 CloudWatch 告警或 SNS 通知相关团队。
不要过度设计：题目未要求独占 IP、信誉隔离或可预测发送量时，托管共享 IP 通常更省运维；“Dedicated IP”并不自动带来更高送达率，还需要预热与良好名单管理。

七、配置集与事件追踪

Configuration Set（配置集）将一组发送规则应用于邮件，可配置事件目标、指标及 Dedicated IP pool。发送请求需指定配置集，或在已验证身份上配置默认配置集，否则该请求不会自动采用预期的事件发布设置。

目标适用目的典型组合
CloudWatch按事件类型查看聚合指标、创建告警监控发送量、退信量或投诉变化
SNS将特定事件通知给订阅者退信/投诉事件触发运维或应用处理
Amazon Data Firehose输出详细事件记录，交给后续数据目的地Firehose → S3 → Glue Data Catalog / Athena 查询
EventBridge将邮件事件纳入事件驱动的规则、路由与自动化按事件类型筛选并调用目标服务
日志检索题：需要按收件人、主题和发送时间查询详细邮件事件时，启用 SES 配置集事件发布，使用 Firehose 将事件记录存入 S3，再用 Glue Catalog/Athena 查询。CloudWatch 适合指标与告警，不适合作为逐封邮件的任意字段检索库。
事件语义：SEND 表示 SES 已接受发送请求，不等于收件人邮箱已收到；DELIVERY、BOUNCE、COMPLAINT、REJECT、DELIVERY_DELAY、RENDERING_FAILURE 等事件分别描述后续状态。事件记录不包含可重新发送的完整邮件内容。

八、模板邮件与入站邮件

  • SES 模板可保存主题、HTML/文本正文和替换数据；程序根据收件人填充参数，适合确认邮件、通知和个性化事务邮件。
  • 需要使用 SES 模板 API 时，通常由应用调用 SES API/SDK 的模板发送操作；不要假定只接入通用 SMTP 就能获得完整的 SES 模板管理能力。
  • 模板中的用户数据应做正确的 HTML 转义和字段校验；避免把未受信任输入直接拼接到邮件 HTML。
  • 入站邮件使用 SES receipt rule set：配置活动规则集、收件域名的 MX 记录，并按规则写入 S3、发布 SNS 或调用 Lambda 等。执行角色、目标资源策略和 KMS 权限需逐跳核对。
最少运维的模板题：使用 SES 存储模板，由 Lambda 或应用通过 SES API 发送模板邮件；不必自建 SMTP 服务器或自行维护模板渲染基础设施。

九、安全、跨账号与合规

  • SMTP 发送需启用 TLS 并保护 SMTP 凭证；优先使用 Secrets Manager 等受控凭证存储，定期轮换，避免写入源码、镜像或日志。
  • API 调用使用 IAM 执行角色并遵循最小权限；将发送权限限制到必要 SES 操作和身份资源，避免长期 IAM 用户密钥。
  • 跨账号委托发送要同时配置身份资源策略/发送授权，并由委托方使用其允许的凭证调用；仅有调用方 IAM Allow 并不自动赋予对方 SES 身份的发送权限。
  • 若事件写入 SNS、S3、Firehose 或由 Lambda 处理，应逐跳检查目标资源策略、执行角色、KMS Key policy 和加密要求。
  • 邮件可能含个人或交易信息；限制日志和事件数据访问，定义保留期限，并确保收件人同意、退订及数据处理符合组织政策和适用法规。
边界提醒：邮件投递加密（TLS）、SES 发件身份验证、IAM 授权和目标存储加密解决的是不同问题，应按题目要求分别配置。

十一、场景题解析

场景一：迁移遗留 SMTP 应用，不能改用 API

应用只能使用 SMTP，原邮件服务器不支持 TLS，且使用 TCP 25。公司希望退役自建邮件服务器，改由 SES 发送。

优先设计：将 SMTP 目标改为 SES 对应区域的 SMTP endpoint，给客户端增加 STARTTLS 能力，并使用该区域生成的 SES SMTP 凭证。
分析思路：协议仍是 SMTP，只需要兼容 SES 所要求的 TLS 并更换身份凭证。TLS Wrapper 与 STARTTLS 不同；若工作负载运行在 EC2 且 25 端口外发受限，可选用客户端支持的 STARTTLS 端口或申请解除端口 25 节流。
场景二：Sandbox 中无法向真实客户发信

团队已验证发件域名，但测试时只能向已验证邮箱发送，要求启动生产通知。

分析思路：在要发送邮件的 Region 申请 SES Production access，并按当前控制台流程说明发送用途、网站和退信/投诉处理方式。域名验证不等于退出 Sandbox；申请通过后仍需控制发送配额与信誉。
场景三：排查邮件是否送达并按主题检索

运维需要保留详细的邮件事件，并按收件人、主题和发送时间搜索，不只是看成功率统计。

分析思路：创建配置集并将发送请求关联到配置集；用 Amazon Data Firehose 导出事件到 S3，再通过 Glue Catalog 和 Athena 检索。CloudWatch 用于聚合指标与告警，不是逐条邮件事件的查询仓库。
场景四：邮件模板要填充用户数据，且不维护邮件服务器

SaaS 应用需发送个性化确认邮件，模板包含动态客户字段，要求降低运维。

分析思路：在 SES 管理邮件模板，由应用/Lambda 使用 SES API/SDK 的模板发送操作传入参数。无需自建 SMTP 服务器；动态内容需转义并校验。
场景五：投诉和硬退信必须尽快通知团队

业务需要在发生退信或投诉时触发告警，并阻止向这些地址持续发送。

分析思路：通过配置集发布事件到 SNS 并通知订阅者，配合账户级 suppression list 抑制相关收件人；另行维护业务退订与许可记录。
场景六：多区域容灾时备用区发信失败

主区域邮件正常，切换到另一个 Region 后，发件身份未经验证且账户仍在 Sandbox。

分析思路：SES 区域状态彼此独立。提前在备用区验证域名、配置 DNS/DKIM 和事件目标，申请生产访问、准备区域 SMTP 凭证/API 权限并确认可用配额。

十四、快速自测

先独立选择，再点击“查看解析”。

1. 旧应用只能使用 SMTP，不能调用 SES API；应用运行在 EC2，需接入 SES。哪项配置最合适？
正确答案：B。SES SMTP 需要对应区域的 SMTP 凭证和 TLS。IAM Access Key 不能直接作为 SMTP 密码；STARTTLS 与 TLS Wrapper 是不同连接模式。
2. 运维要按收件人、主题和时间查询 SES 发送事件明细。哪种设计最合适？
正确答案：B。配置集事件发布提供逐条事件数据；Firehose/S3/Athena 适合保留和查询明细。CloudWatch 更适合聚合指标和告警。
3. 在主 Region 可发送，灾备 Region 切换后 SES 拒绝给新客户发信。首先应检查什么？
正确答案：B。SES 的身份、Sandbox 状态和配额按区域管理；需预先准备备用区域，不能假设主区域配置自动复制。
