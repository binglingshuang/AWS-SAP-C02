一、事件模型与总线类型

EventBridge 是无服务器事件总线与路由服务。事件发布者把事件送入总线，规则匹配事件内容，再将匹配事件投递到一个或多个目标；发布者不必直接调用每个消费者。

总线类型事件来源与边界典型用途
Default event bus接收 AWS 服务事件；每个账户区域默认存在。响应 AWS 资源状态变化、服务事件和 CloudTrail API 事件（须事件类型支持）。
Custom event bus应用发布自定义业务事件；可通过资源策略控制发布与跨账户访问。领域事件、微服务集成、应用和 AWS 事件的集中路由。
Partner event bus与受支持 SaaS 伙伴集成后接收伙伴事件。第三方 CRM、监控或业务 SaaS 向 AWS 事件驱动系统发送事件。

事件通常包含 source、detail-type、account、region、时间和 detail 等字段。生产者应维护稳定事件契约；消费者可独立订阅事件而不改动生产者到每个下游的点对点连接。

架构价值：总线降低服务间耦合并支持内容路由，但它不是长期任务队列。需要消费者缓冲、拉取速率控制或持久工作队列时，将事件路由到 SQS。

二、事件模式与规则

规则由 Event Pattern（按事件字段匹配）或 Schedule（基于时间触发）驱动，并指定一个或多个目标。事件模式采用 JSON 结构；只写需要匹配的字段即可，其余字段不限制。嵌套对象可匹配 detail 内的业务属性。

模式设计与常见匹配

  • 匹配 source 与 detail-type，先限定事件种类，再匹配 detail 中具体字段。
  • 字符串精确匹配时留意大小写；事件字段缺失、类型不同或字段路径错误都会导致零匹配。
  • 支持数值比较、前缀、存在性等模式运算符；复杂条件可将多个规则拆分，便于分别审计和监控。
  • 通过事件模式测试工具或代表性样例验证规则；修改生产事件契约后也应更新测试。
触发方式行为用途
Event pattern事件到达且匹配模式时触发。状态变化、业务事件、AWS 服务通知。
Scheduled rule按固定速率或 Cron 计划触发。已有规则的简单定时任务；新建时间计划通常优先考虑 EventBridge Scheduler。
同一规则多个目标一个匹配事件可投递到多个目标。对一个事件执行多项动作；目标有独立重试/权限配置。
过滤语义：事件被规则匹配，只代表符合路由条件，不代表目标已成功处理。需要区分“未匹配”和“目标投递失败”，分别监控匹配计数、失败指标和目标端队列/工作流状态。

三、目标与交付语义

常见目标包括 Lambda、Step Functions、SQS、SNS、Kinesis、API Destination 以及其他 AWS 服务。EventBridge 代表规则调用目标，需通过目标执行角色或资源策略获得权限；具体授权模式取决于目标类型。

目标选择适合需求设计注意
Lambda事件到达后执行轻量业务逻辑。允许 EventBridge 调用函数；处理要幂等，函数自身失败与规则投递失败属于不同层次。
SQS缓冲事件、控制消费速率、隔离下游故障。队列资源策略允许事件总线发送；用队列自身 DLQ 与可见性机制处理消费故障。
Step Functions启动多步骤编排。核对状态机执行权限、输入映射与重复启动的业务影响。
API Destination通过连接调用外部 HTTP API。配置 Connection 凭证、限流、重试以及目标端不可用时的失败处置。
多目标同一事件驱动多个独立动作。每个目标的权限和重试策略需单独验证；一个目标成功不代表其他目标已成功。

目标输入可直接传递原事件，也可用 Input、InputPath 或 InputTransformer 提取/转换字段，避免消费者收到不需要的负载。转换后的结构应保持下游契约稳定。

四、跨账号与跨区域

跨账户事件路由通常由来源账户规则把事件发送到目标账户的自定义事件总线。目标总线资源策略允许指定账户或组织调用 PutEvents；来源端规则还需要有权限把事件投递到该总线。两端权限都正确后，目标账户可使用本地规则再路由给消费者。

  1. 在目标账户创建自定义 Event Bus，并配置限制明确的资源策略。
  2. 在来源端配置事件规则及目标总线 ARN，限制事件来源、类型和账户。
  3. 授权规则使用的角色执行跨账户 PutEvents；目标总线资源策略允许该主体。
  4. 目标账户为事件建立本地规则，完成二次过滤和消费路由。
  5. 验证目标账户/区域、资源策略、事件总线 ARN、KMS 或下游目标权限，并监控转发与投递失败。
不要只加一侧权限：来源身份策略与目标总线资源策略共同决定能否跨账号写入。跨区域复制、全球事件汇聚与跨账号授权是不同问题；根据题干分别检查总线 ARN、区域和账户边界。

组织级策略可降低大量账户逐个授权的运维负担，但应配合组织条件、指定总线和最小权限。不要把公共事件总线开放给任意主体。

五、失败处理、归档与重放

EventBridge 对目标投递提供重试机制，可为规则目标配置最大事件年龄与重试次数；最终仍失败的事件可发送到 SQS 或 SNS DLQ。DLQ 只保存无法投递的事件，消费端执行后失败应由目标服务自己的错误处理机制负责。

功能解决的问题边界
Retry policy目标临时不可用时自动重试投递。不保证目标业务执行成功；避免重试窗口与事件有效期冲突。
Target DLQ保留多次投递仍失败的事件供排障。需为 DLQ 配置权限、告警、恢复与重放流程。
Archive按事件模式保存事件一段时间。便于审计、回溯和恢复；需注意保留期、成本和数据治理。
Replay将归档事件重新送入事件总线，按当前规则再次路由。可能重新触发副作用；消费者必须幂等，且要了解重放期间规则变化。

事件总线与目标队列不是同义词：如果业务要求消费者独立积压、严格控制消费速率、较长时间缓冲，使用 SQS 作为目标。EventBridge Archive/Replay 更适合事件留存和重新路由，不替代业务数据库或长期不可变审计仓库。

六、Schema Registry

Schema Registry 可发现或登记事件结构，并为开发者提供 schema 与代码绑定，帮助生产者和消费者理解事件契约。启用 Schema Discovery 可从进入总线的事件中推断结构，降低手工维护模式的负担。

  • 为自定义事件定义稳定的字段名、类型和语义；schema 版本变更需与消费者兼容策略配套。
  • 发现出来的 schema 是结构辅助，不代表数据正确、业务字段含义清楚或消费者一定兼容。
  • 使用代码绑定减少手工解析错误，但仍要处理可选字段、未知字段和版本演进。
  • 按事件源、detail-type 和 schema registry 的组织方式治理，避免相似事件出现互不兼容的重复定义。
考试要点：Schema Registry 用于事件结构发现、目录和代码生成；它不负责事件路由、持久队列、认证授权或工作流编排。

七、计划任务与服务对比

服务核心模式优先选择线索
EventBridge基于事件内容匹配并将事件路由到目标。AWS/应用/SaaS 事件驱动、多账户事件总线、内容过滤。
EventBridge Scheduler一次性或重复计划，支持时区、灵活时间窗口与重试/DLQ。需要规模化定时调用 AWS API、Lambda 或 Step Functions；新计划任务通常优先用 Scheduler。
SNSTopic 发布后向订阅者广播。简单一对多推送；需要订阅过滤或 SNS→SQS Fan-out。
SQS队列缓冲，消费者拉取。任务积压、独立消费速率和失败隔离。
CloudWatch Alarm指标阈值状态变化与告警动作。监控指标达到阈值；告警动作可接入 SNS/EventBridge，但不是通用业务事件总线。

EventBridge 接续了 CloudWatch Events 的事件路由能力并进一步扩展事件总线、SaaS 集成等功能。旧题描述 CloudWatch Events 时，应识别其与 EventBridge 的服务演进关系；定时任务的新设计再比较 Scheduler。

八、安全与监控

  • 用 IAM 身份策略控制发布、创建规则和管理目标；用事件总线资源策略控制跨账号/组织访问。
  • 目标调用权限按目标类型配置：Lambda 资源策略、SQS Queue Policy、目标执行角色等不可互相替代。
  • 限制事件模式、来源账户和资源 ARN，避免无关主体注入伪造事件。
  • 事件可能包含个人信息或业务机密；评估事件负载最小化、日志访问、加密和保留期限。
  • 关注匹配事件数、目标调用失败、受限调用和 DLQ 消息；并结合目标自身指标定位处理失败。
定位分层：无匹配事件先检查模式与事件字段；匹配但未投递检查目标权限、重试与 DLQ；投递成功但业务无结果检查目标执行和应用日志。

九、场景题解析

场景一：多个账号将资源事件汇聚到中央安全账户

企业希望工作负载账户的合规事件进入中央账户统一审计，再由中央账户路由给处理器。

正确方向：中央账户创建自定义 Event Bus 并配置受限资源策略；各来源账户规则将匹配事件转发到目标总线，授权来源角色执行 PutEvents。
分析思路：跨账户传递需要来源端授权和目标资源策略，中央总线可继续使用本地规则分发。
排除：仅在中央账户创建规则不会自动订阅所有账户事件；只给来源角色身份策略但不允许目标总线资源策略也不够。

场景二：只处理特定 S3 对象标签对应的业务事件

多个 AWS 事件进入总线，消费者只需响应特定来源和 detail 中匹配条件的事件。

正确方向：建立 Event Pattern 规则，精确匹配 source、detail-type 和业务字段，再设置目标。
分析思路：事件模式可在路由层过滤，生产者无需直接了解消费者。用代表性 JSON 测试字段路径和类型。
排除：仅配置目标不会自动过滤；Schema Registry 记录结构但不负责路由匹配。

场景三：临时 Lambda 故障导致部分事件投递失败

匹配规则的目标偶发不可用，要求自动重试并保留最终无法投递的事件供排查。

正确方向：为目标配置重试策略与 SQS/SNS DLQ，并为 DLQ 设置告警和恢复流程。
分析思路：重试负责暂时故障，DLQ 捕获终态投递失败。目标已接收后自身处理失败要用 Lambda 等目标的错误处理。
排除：只增加 Lambda 超时时间不处理 EventBridge 到目标的授权/交付失败；事件归档不是投递失败 DLQ。

场景四：事件契约常变导致消费者解析失败

多个团队独立开发事件生产者和消费者，希望发现结构并生成类型绑定，降低字段变化造成的集成错误。

正确方向：采用 EventBridge Schema Registry 与 Schema Discovery，治理版本兼容和事件契约。
分析思路：Registry 帮助发现、记录 schema 并生成代码绑定；仍需制定向后兼容策略和消费者容错。
排除：事件模式只决定路由；DLQ 只能留存失败事件，不能定义结构契约。

场景五：需要在特定时区按计划触发大量任务

业务需要一次性和周期性定时调用工作流，并要求处理错过的触发和失败重试。

正确方向：使用 EventBridge Scheduler 配置时区计划、目标、重试与 DLQ。
分析思路：Scheduler 专为大规模计划任务提供时区和灵活窗口能力；传统定时规则适合已有或简单规则场景。
排除：自建常驻 EC2 Cron 增加运维；Event Pattern 不是时间计划。

场景六：需要重新处理过去一小时的事件

消费者升级后发现业务解析错误，希望从保留事件中重新投递，而不是要求生产者再次生成原事件。

正确方向：按需启用 EventBridge Archive，修复后对相应归档事件执行 Replay，并确保消费者幂等。
分析思路：归档与重放可恢复事件流；重放可能再次触发已经成功的目标，需控制模式与副作用。
排除：DLQ 只存最终投递失败事件；归档不能替代业务数据备份，也不保证重放结果完全等同历史执行。

十二、快速自测

1. 其他账户要向中央账户的自定义总线发送事件，至少需要检查哪两类权限？
正确答案：B。跨账号写入需要来源端有 PutEvents 权限，目标总线资源策略也必须允许。
2. 多个事件生产者格式不统一，团队想发现事件结构并生成类型绑定，选什么？
正确答案：A。Schema Registry 用于结构发现、登记和代码绑定，不负责事件投递失败恢复。
3. 需要按本地时区定期触发工作流并管理失败重试，优先使用什么？
正确答案：B。Scheduler 支持一次性/重复计划与时区等计划任务能力。
