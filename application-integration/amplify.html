一、Amplify 是什么

AWS Amplify 是面向前端和移动开发者的全栈开发平台，由两部分组成：Amplify Hosting（托管与 CI/CD）和 Amplify 后端工具集（Auth、Data、Storage、Functions 等）。它本身不是新的底层服务，而是把 Cognito、AppSync、DynamoDB、S3、Lambda、CloudFront 等编排起来。

一句话：题干出现“加速开发、减少运维、前端/移动、全栈、托管站点、用户登录”时，Amplify 是优先候选。
考试定位：Amplify 不是 CI/CD 流水线工具（CodePipeline 体系），也不是独立的身份服务（身份用 Cognito）。

二、Amplify Hosting

能力说明考试线索
Git 驱动 CI/CD连接 Git 仓库，推送后自动构建并发布。“推送即发布”“前端自动部署”
全球分发由 CloudFront 提供 CDN，内容存放在托管的 S3。用户分布广、需要低延迟
分支与 PR 预览每个分支独立环境，Pull Request 生成预览 URL。评审预览、多环境
SSR 支持支持 Next.js 等 SSR 框架，不局限于纯静态。“服务端渲染的 Web 应用”
自定义域名与 HTTPS可绑定域名，自动管理证书。免运维证书
访问控制与重定向可为非生产分支设置基本密码保护，支持重写和重定向规则。测试环境限制访问
注意：Amplify Hosting 使用的 CloudFront 与 S3 是托管的，不会作为你自己账号里可直接管理的资源出现。需要完全自定义缓存、WAF 或源站行为时，选 S3 + CloudFront 自建。

三、后端能力与 Gen 2

Amplify 后端按“类别”提供能力，前端通过 Amplify 库直接调用。Gen 2 用 TypeScript 代码优先方式定义后端，底层基于 CDK；Gen 1 使用 Amplify CLI 和 Studio，底层基于 CloudFormation。

  • 每个 Git 分支对应一套独立的前端与后端环境（全栈分支部署）。
  • 本地开发可使用云端 sandbox 环境，快速迭代。
  • 可通过 CDK 扩展 Amplify 没有直接封装的 AWS 资源。
  • DataStore 提供离线优先的数据访问与同步，依赖 AppSync 完成云端同步与冲突解决。

七、快速答题技巧

  1. 先看动机词：“refactor / accelerate development / LEAST operational overhead”+ Web 或移动端，优先 Amplify + Cognito + S3。
  2. 看到 lift-and-shift 方案先排除：Application Migration Service + EC2 + ASG 不符合“重构并加速开发”。
  3. 身份类选项：终端用户 = Cognito；员工 = IAM Identity Center；ALB 认证只认 Cognito / OIDC。
  4. 带 “Amplify 用户池 / Amplify 插件 / Amplify hosted UI” 的选项直接怀疑：多半是编造的干扰项。
  5. CI/CD 题：CodePipeline 体系里用 CodeBuild 测试、CodeDeploy 部署、EventBridge+SNS 告警、手动审批阶段，Amplify 不出现。
  6. 需要精细控制 CDN：自定义 WAF、OAC、Lambda@Edge 等，选 S3 + CloudFront，而不是 Amplify Hosting。
  7. 只要 GraphQL：直接选 AppSync，Amplify 只是它的客户端工具链。

八、场景题解析

场景一：本地文件服务器应用迁移，要求快速开发、仅认证用户上传、运维最少（真题）

美国和加拿大用户上传媒体文件，原应用服务器过载、文件服务器反复扩容；愿意重构应用，需加速开发。

正确方向：Amplify 创建并托管静态站点（Amplify Hosting，背后是 CloudFront），S3 存储上传文件，Cognito 认证用户。
分析思路：关键词“重构 + 加速开发 + 最少运维”指向无服务器全托管。前端由 Amplify Hosting 托管并自带 CDN，文件进 S3，认证交给 Cognito，没有服务器要管。
排除：Application Migration Service + EC2 + ASG + ALB 是 lift-and-shift，仍有服务器运维；IAM Identity Center 面向员工，不适合面向公众的应用用户；AppSync + Lambda resolver 上传文件是绕远路，没有托管站点。

场景二：ALB 后的 Fargate 第三方应用，需要对指定用户加 MFA（真题）

Docker 镜像不能改、不能对接外部 IdP，只允许指定用户从互联网访问，必须 MFA。

正确方向：创建 Cognito 用户池，开启 MFA，在 ALB 监听规则中配置 authenticate-cognito 动作。
分析思路：ALB 原生支持 Cognito / OIDC 认证动作，认证发生在 ALB 层，应用不用改。
排除：“Amplify 用户池”是干扰项：Amplify 本身没有独立的用户池，Amplify Auth 底层就是 Cognito，ALB 也不能挂 Amplify hosted UI。IAM 用户和 Identity Center 都不能作为 ALB 监听规则的认证源。

场景三：CodePipeline 之上的 CI/CD，功能开关、测试告警与人工审批（真题）

需要 CodeCommit 源码、自动化单元测试与安全扫描、测试失败告警、动态开关功能、负责人审批后部署。

正确方向：CodeBuild 跑测试与扫描，EventBridge + SNS 告警，CDK 构造配合清单文件控制功能，管道中加手动审批阶段。
分析思路：Amplify 是应用开发框架，不是 CodePipeline 里的 CI/CD 工具。含 “Amplify plugins / user prompts 开关功能” 的选项可直接排除。
排除：Lambda 跑测试并发 SES 通知、Jenkins 混合方案、CodeDeploy 跑单元测试，都偏离各服务本职，属于典型错配。

场景四：React/Next.js 前端要 Git 推送即自动构建发布，并为每个 PR 预览

团队想零运维托管前端，每次推送到分支自动构建，评审时能看到 PR 预览地址，并绑定自定义域名与 HTTPS。

正确方向：Amplify Hosting 连接 Git 仓库，开启分支自动部署与 Pull Request 预览，绑定自定义域名并自动签发证书。
分析思路：这是 Amplify Hosting 的核心卖点：Git 驱动 CI/CD、分支环境、PR 预览、托管证书。支持 SSR（如 Next.js）。
排除：手动 S3 + CloudFront + CodePipeline 能做但配置多，不是“最少运维”；Elastic Beanstalk 面向服务器应用，不是静态/前端托管首选。

场景五：移动/Web 应用需要用户登录、云端数据与文件，且想减少后端编码

初创团队想快速做出带登录、数据存取、图片上传的全栈应用，不想自己搭建各类后端。

正确方向：Amplify（Gen 2）代码即定义后端：Auth（Cognito）、Data（AppSync + DynamoDB）、Storage（S3）、Functions（Lambda）。
分析思路：Amplify 把常见后端服务编排好，前端通过库直接调用；底层仍是标准 AWS 服务，可被 CDK 扩展。
排除：手工拼装 API Gateway + Lambda + Cognito + S3 可行但开发量大，题干强调“加速开发”时不选；仅 AppSync 不含托管站点与认证。

场景六：已有 Amplify 应用，如何为开发、测试、生产分环境

希望开发分支独立后端、生产分支稳定，合并后自动发布。

正确方向：Amplify 全栈分支部署：每个 Git 分支对应独立前端与后端环境；用环境变量区分配置，生产分支可设保护。
分析思路：Gen 2 里每个分支一个独立后端环境，本地开发另有云端 sandbox。
排除：把所有分支共用一个后端会导致开发破坏生产；手工复制栈既费时又易漂移。

十一、快速自测

先独立选择，再点击选项查看解析。

1. 公司要重构上传应用，要求仅登录用户可上传、开发最快、运维最少，选什么？
正确答案：B。重构 + 加速开发 + 最少运维，对应无服务器全托管组合。
2. 不能修改的 Fargate 应用经 ALB 暴露，需 MFA 认证指定用户，如何做？
正确答案：A。ALB 原生支持 Cognito / OIDC 认证；Amplify 没有独立的用户池。
3. CodePipeline 流水线中需要执行单元测试和安全扫描，用什么？
正确答案：B。CodeBuild 负责构建与测试；CodeDeploy 负责部署；Amplify 不是流水线步骤。
