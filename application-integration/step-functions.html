一、状态机与执行模型

Step Functions 将工作流定义为状态机，状态通过 Amazon States Language（ASL）描述。每次执行沿着状态转换推进，可调用 AWS 服务、执行选择/并行逻辑、等待回调，并记录执行历史。

状态机适合跨多个步骤管理执行状态与错误分支，避免用单个大型 Lambda 承担所有编排。它可以直接集成 AWS 服务 API，减少仅为调用 API 而编写的胶水函数。

何时使用：需要可视化多步流程、长时间等待、分支/并行、服务调用重试、人工审批或补偿流程时，优先考虑 Step Functions；简单的一次通知不必建立工作流。

二、Standard vs Express

维度Standard WorkflowExpress Workflow
时长与调用规模长运行流程，执行可持续至多一年；适合低到中等频率编排。短时、高事件率工作流；单次执行最长 5 分钟。
执行语义Exactly-once 工作流执行语义（显式重试仍会再次执行失败状态）；适合需要审计和长流程的场景。异步 Express 为 at-least-once；同步 Express 为 at-most-once 执行语义。异步流程和外部副作用需按重复执行风险设计。
启动方式StartExecution 异步启动。可异步启动，也可使用同步请求-响应调用。
执行历史Step Functions 持久化执行历史，可在控制台逐状态检查。高吞吐执行主要依靠 CloudWatch Logs 观察；配置日志记录级别和保留策略。
典型场景订单履约、审批、长流程、需要详细执行历史。高频短时数据处理、流量驱动编排、需快速响应的短工作流。

Express 的计费与请求率/持续时间有关，Standard 按状态转换等计费；考试应先依据运行时长、频率、工作流功能与执行语义选型，再考虑成本。精确限制和价格应查当前区域官方资料。

易错点：同步 Express 不是通用的“恰好一次业务事务”；调用方超时、服务集成重试和外部副作用仍可能造成重复或不确定结果，需设计幂等和补偿。

三、状态类型与数据流

状态作用常见用途
Task执行工作，可调用 Lambda 或 AWS 服务集成。读写数据库、处理对象、启动任务。
Choice根据输入数据条件选择下一状态。审批结果、订单金额或业务类别分支。
Parallel并行执行多个分支并汇总结果。同时检查库存、风控和地址。
Map对数组项逐条执行处理器；支持 Inline / Distributed 模式。批量文件或数据项处理；Distributed Map 用于大规模并行迭代。
Wait按时间戳、秒数或输入时间等待。延迟重试、等待审批或业务窗口。
Pass透传或转换状态数据，不调用外部工作。简单数据整形或占位。
Succeed / Fail显式成功或失败结束。清晰标记状态机终态。

ASL 的输入输出字段用于控制状态间数据流。JSONPath 工作流常见 InputPath、Parameters、ResultSelector、ResultPath、OutputPath；JSONata 工作流采用相应表达式字段。避免无意把大型输入传递给每个步骤，并校验下游期望的数据形状。

四、服务集成模式

Step Functions 既可调用 Lambda，也能直接集成许多 AWS 服务。集成模式决定状态机是提交请求后继续、等待任务完成，还是暂停至外部回调。

模式状态机行为适用线索
Request Response调用 API 并在响应后继续；不一定等待后端异步任务完成。提交请求、获取 API 响应即可继续。
Run a Job (.sync)启动作业并等待其完成后再继续。批处理作业、容器任务等需等待完成状态。
Wait for Callback (.waitForTaskToken)将任务令牌交给外部系统，状态机暂停直到回调成功/失败。人工审批、第三方异步处理、外部系统通知完成。
Lambda Invoke调用函数并可按同步返回结果编排后续。保留自定义业务计算；优先直接集成可替代的 AWS API。

回调令牌必须由受信任流程安全保管，不能暴露给未授权调用方；设置超时和错误分支，避免执行永久等待。并非所有服务 API 都支持每一种集成模式，需查该服务的优化集成文档。

服务集成减少胶水代码，但不取消目标服务的 IAM、配额、网络和业务错误约束。状态机执行角色应仅允许它实际调用的资源和操作。

五、错误处理与重试

Task 失败可声明 Retry 重试器和 Catch 捕获器。Retry 可按错误名、间隔、退避倍率和最大次数重试；Catch 可将错误结果写入状态数据并转向补偿、人工处理或失败终态。

机制作用注意
Retry对暂时性错误自动重复执行当前状态。非幂等操作可能重复产生副作用；设置合理退避、最大尝试和预算。
Catch处理重试后仍失败或不可重试的错误。按错误类型分流；保留错误信息，避免吞掉失败后误报成功。
TimeoutSeconds限制单个 Task 等待时间。需与 Lambda/API/回调端超时协调；超时并不一定表示外部操作未执行。
HeartbeatSeconds对长运行活动任务检测心跳丢失。仅适用相关任务执行模式；工作人员需定期发送心跳。
Redrive在支持的工作流执行场景中从失败状态恢复执行。恢复仍可能再次调用状态；先检查副作用、输入和修复条件。

Catch 适合实现 Saga 补偿：若后续步骤失败，调用逆向操作释放预留、撤销资源或标记人工介入。分布式事务不会因工作流存在而自动成立，补偿本身也必须可重试、幂等。

六、并行、Map 与回调

  • Parallel：并发启动固定分支，所有分支完成后汇总；分支输出通常作为数组结果。
  • Inline Map：在父执行中处理较小规模数组，适用于常规迭代。
  • Distributed Map：为大规模数据集使用独立子执行，可处理 S3 清单/对象等输入并提高并行度；关注并发、失败阈值、结果写出与成本。
  • Callback：Wait for Task Token 可等待外部任务或人工审批，必须设计令牌超时、身份验证和重复回调处理。
  • 并发保护：并行度需与下游吞吐和配额匹配，避免工作流瞬间放大调用把数据库、API 或 Lambda 打满。
订单/审批流程：Step Functions 负责流程状态与补偿，SQS 负责可持久缓冲和消费者节流；两者可组合，不是互斥产品。

七、执行、监控与安全

  • 为状态机配置执行角色；按状态任务限制 Lambda Invoke、服务 API 和必要资源 ARN。
  • 需要调用状态机时，调用方还需要 StartExecution 等身份权限；执行角色和启动者权限是不同主体。
  • Standard 执行可在控制台查看历史；Express 应配置 CloudWatch Logs，并通过指标、日志和业务追踪观察结果。
  • 选择日志级别并考虑敏感输入/输出；日志记录配置可能包含业务数据，设置访问控制和保留期限。
  • 处理重复启动：为订单等业务键设计幂等执行，明确执行名/输入冲突后的行为。
  • 设置告警监控执行失败、超时、节流和 Map 子执行失败；为持续故障准备告警与人工恢复程序。

八、架构选择与常见陷阱

需求优先考虑原因
长流程、人工审批、审计执行历史Standard Workflow + Callback支持长时间执行和显式等待。
短时高频事件处理Express Workflow高事件率短执行；确认执行语义与日志需求。
简单 AWS API 编排直接服务集成减少 Lambda 胶水代码。
批量处理大量 S3 数据Distributed Map大规模并行子执行和结果管理。
可恢复且需消费者控速Step Functions + SQS工作流编排和队列缓冲分工协作。
  • Standard/Express 的执行语义不可脱离调用模式、服务集成和业务副作用单独理解。
  • Retry 会重新执行状态；不能对非幂等付款/创建资源盲目自动重试。
  • Lambda 不必承担流程编排状态；否则需自行实现重试、等待、分支和审计。
  • Parallel/Map 扩大并发，必须限制下游负载并监控失败。
  • 状态机定义和执行角色均需最小权限；不要为了快速通过而开放全服务权限。

九、场景题解析

场景一：订单流程包含多步、人工审批和数小时等待

订单要依次预留库存、等待人工批准、扣款和创建履约任务，任何一步失败都需可查看状态并执行补偿。

正确方向：使用 Standard Workflow；人工环节采用 callback/task token，配置错误捕获和 Saga 补偿分支。
分析思路：长运行、可视化审计与等待适合 Standard；状态机管理流程，补偿逻辑负责业务回滚。
排除：Express 最长执行时间有限；单个 Lambda 长时间阻塞既难审计也不适合等待人工审批。

场景二：短时高频事件需要快速编排

每秒大量事件都触发不超过数分钟的步骤，成本和高吞吐重要，不需要长时间持久执行。

正确方向：评估 Express Workflow，并选择异步或同步启动模式匹配调用语义；为关键副作用实现幂等。
分析思路：短时高频是 Express 的典型线索；确认最长执行时间、日志和投递语义符合需求。
排除：不能仅因“高频”忽略执行时限或把 Express 视为端到端 exactly-once。

场景三：提交批处理任务后必须等作业完成

状态机启动 AWS Batch 作业，只有作业成功完成才能进入汇总步骤，失败时进入错误处理。

正确方向：采用支持的 Run a Job（.sync）服务集成模式，等待作业完成后再转换状态。
分析思路：Request Response 可能只确认已提交，不等于作业完成；同步作业模式匹配完成依赖。
排除：用固定 Wait 猜测作业耗时既浪费又不可靠；轮询逻辑无需在自定义 Lambda 中重复造轮子。

场景四：审批系统完成后恢复等待中的工作流

工作流暂停等待外部审批应用，审批结束后继续下一状态；需避免未授权方恢复执行。

正确方向：使用 Wait for Callback 将 task token 传给审批后端，通过受控 API 调用 SendTaskSuccess/Failure，并设置任务超时。
分析思路：令牌关联特定等待任务；安全传递和超时防止泄露、重复或永久挂起。
排除：固定长时间 Wait 无法即时响应审批；不能把 task token 暴露给浏览器客户端。

场景五：失败时自动重试，仍失败就补偿已预留资源

预留资源成功但后续扣款失败，系统需有限重试后释放资源并返回明确失败。

正确方向：在扣款 Task 配置有限退避 Retry；使用 Catch 路由到释放资源的补偿 Task，再以 Fail 终止或转人工处理。
分析思路：Retry 处理暂时故障，Catch 负责长期失败路径；补偿不是数据库事务，需可重试且幂等。
排除：无限重试会积压和重复副作用；直接 Succeed 会掩盖扣款失败。

场景六：数百万条 S3 记录要并行处理

每条记录独立处理，处理结果汇总，工作量超过普通 Map 适宜规模。

正确方向：评估 Distributed Map，对大型数据集启动子工作流；控制最大并行度并定义失败阈值和结果输出。
分析思路：Distributed Map 面向大规模并行迭代；下游容量和成本仍需治理。
排除：把所有记录装入单个 Lambda 容易超出内存/运行限制；无限并行会压垮下游。

十二、快速自测

先独立选择，再点击“查看解析”。

1. 工作流需等待人工审批数小时，哪个类型最匹配？
正确答案：A。Standard 支持长流程，Callback 可安全等待外部审批结果。
2. 暂时性 API 错误应短暂退避重试，之后转补偿流程，使用什么？
正确答案：B。Retry 处理临时故障，Catch 负责失败分支与补偿。
3. 对大型 S3 数据集的数百万项进行并行处理，优先考虑哪项？
正确答案：B。Distributed Map 面向大规模迭代，并需配置下游保护与结果处理。
