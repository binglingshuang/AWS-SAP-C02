一、AI 服务能力地图

先读题干中的“数据是什么、要得到什么结果”。专用 AI 服务适合标准任务快速上线；需要自定义模型结构、训练过程或预测目标时，再评估 SageMaker。

业务输入 / 目标优先评估典型能力容易混淆
图片、视频中识别对象或内容Amazon Rekognition标签、场景、内容审核、人脸分析/比较，及视频分析能力。扫描 PDF 表格和表单应选 Textract。
非结构化文本理解Amazon Comprehend情感、实体、关键短语、语言、主题及受支持的 PII 识别。跨语言翻译选 Translate；语音转文字选 Transcribe。
扫描件、表单、发票、表格Amazon TextractOCR、版面、表单键值对、表格及特定文档分析。仅识别图像内容标签选 Rekognition。
文本跨语言转换Amazon Translate神经机器翻译及受支持的术语/自定义能力。不要把它与 Comprehend 的文本分析混为一谈。
文字转自然语音Amazon Polly文本转语音，可生成音频流或文件。语音转文本是 Transcribe，方向相反。
录音、音视频转文字Amazon Transcribe自动语音识别、转录及受支持的说话人/内容处理。Polly 是文本生成语音。
企业文档自然语言搜索Amazon Kendra连接内容来源、索引、相关性排序与自然语言查询。它不是通用对象存储，也不是替代全部数据湖查询。
个性化商品/内容推荐Amazon Personalize以用户、物品和交互数据构建推荐与个性化排名。任意回归/分类目标和自定义算法通常需 SageMaker。
欺诈风险预测Amazon Fraud Detector面向在线欺诈场景的托管检测工作流与模型。先核实服务当前可用性、账号资格及目标区域。
对话机器人、意图和槽位Amazon Lex自然语言理解、对话状态、语音/文本交互及集成。语音合成/转录本身分别由 Polly/Transcribe 提供。
决策口诀：图片找 Rekognition；文档版面和字段找 Textract；读懂文本找 Comprehend；翻译找 Translate；语音方向先分输入/输出；企业知识检索找 Kendra；推荐找 Personalize；自定义训练找 SageMaker。

二、图像与视频：Amazon Rekognition

Rekognition 提供图像和视频分析能力。架构师应把“识别画面内容”“检测不当内容”“比较/搜索人脸”等任务与应用授权、数据保留和合规要求一起设计。

能力方向适合任务设计注意
Labels / Image properties识别对象、场景、活动或图像属性，给图片库建立可检索元数据。识别结果是模型推断，应设置信心阈值并允许人工复核。
Content moderation识别可能不适宜的图像/视频内容，辅助用户上传审核。按风险等级制定阻断、复核和申诉流程；不要把模型分数当作业务政策。
Face analysis / comparison / search在服务支持范围内检测面部特征、比较两张图或在集合中搜索。生物特征数据敏感；需满足合法依据、最小化保留和授权要求。
Video analysis从视频异步检测标签等信息，配合 S3、SNS/SQS 等工作流。异步作业要跟踪状态、处理通知重复及失败重试。

图片分析通常是按需调用托管 API，不需要自行管理推理实例。需对照当前服务 API、配额和区域可用性设计，并仅让调用角色读取必要的 S3 对象。

三、文本与文档：Comprehend 和 Textract

Amazon Comprehend：理解文本

  • 常见 NLP 任务包括情感分析、实体识别、关键短语提取、语言检测、主题建模，以及支持范围内的 PII 识别。
  • 可用于客户反馈分类、工单路由、评论洞察等；有领域术语或标签任务时，评估当前支持的自定义分类/实体能力和训练数据要求。
  • 批处理、实时推理和自定义模型在输入大小、吞吐、成本与部署方式上不同；先按延迟和规模选择 API 模式。
  • Comprehend 返回分析结果，不负责替业务执行审批或自动删除；敏感文本须控制日志、存储和访问。

Amazon Textract：提取文档结构

  • 基础 OCR 识别文字；文档分析还可提取版面、表单键值对和表格等结构化信息。
  • 贷款申请、发票、税务表单等需字段语义时，考虑对应的文档分析 API；费用单据工作流可评估专用的费用/发票分析能力。
  • 扫描质量、旋转、手写、语言、页面数与模板差异都会影响结果。保留置信度检查和人工校验，不把 OCR 结果默认视作无误。
  • 异步分析适合多页文档处理；常见组合是 S3 上传触发事件，再通过队列/工作流协调任务并持久化结果。
容易考反：“图里有什么”偏 Rekognition；“扫描 PDF 里的文字、表格或字段”偏 Textract；“这段文字是什么情绪/实体”偏 Comprehend。

四、翻译与语音：Translate、Polly、Transcribe

服务输入 → 输出典型架构点
Amazon Translate一种语言的文本 → 另一种语言的文本。术语一致性、语言对支持、批处理数据权限和区域性。
Amazon Polly文本 → 合成语音。实时播报可流式播放；静态内容可缓存音频，避免重复请求。
Amazon Transcribe语音/录音 → 文本转录。实时流与批量作业需分别考虑音频输入、延迟、结果存储和作业通知。

语音交互可以组合 Transcribe（用户语音转文本）、Lex（理解意图和管理对话）、业务后端（执行操作）、Polly（响应文本转语音）。若需求只是把固定文本读出来，不必为 Polly 额外搭建自训练模型。

Translate 与 Comprehend 也可组合：先翻译，再对目标语言执行文本分析；但组合会增加延迟、成本和数据处理路径，应确认语言支持与数据驻留要求。

五、企业搜索：Amazon Kendra

Kendra 面向企业内容搜索：内容连接器把文档源接入索引，查询时根据关键词和自然语言问题返回相关文档/片段。重点是知识发现与相关性，而非全文数据仓库查询。

  • 盘点内容源、连接器、身份系统和同步频率；源文件的更新、删除和访问控制需要反映到索引。
  • 启用文档访问控制/用户上下文时，查询身份必须正确传递，避免因索引权限处理错误造成跨用户泄露。
  • 索引容量、文档数量、连接器支持、同步窗口和区域可用性影响成本与方案；企业搜索并不意味着任何文件格式都无需预处理即可被索引。
  • 若问题是对 S3 结构化数据执行 SQL 分析，优先评估 Athena 等分析服务；若要构建生成式问答体验，应单独设计检索、模型调用、引用和访问控制链路。
陷阱：“找到公司知识库中最相关的文档”是 Kendra 风格的问题；“对海量结构化数据执行任意聚合”不是企业搜索索引的职责。

六、推荐与欺诈检测：Personalize、Fraud Detector

Amazon Personalize

  • 针对个性化推荐和排名场景，以用户、物品及交互事件等数据建立推荐解决方案；可用于内容、商品和个性化排序。
  • 效果取决于事件质量、用户/物品元数据、交互量与业务目标。冷启动、长尾物品、实时事件摄取和模型更新都需纳入设计。
  • 若需要完全自定义特征、损失函数、训练框架或任意预测目标，改评估 SageMaker，而不是强行套用推荐产品。

Amazon Fraud Detector

Fraud Detector 是针对欺诈检测用例的托管服务方向，题目可能将其与支付/注册等交易风险识别关联。实际架构前必须确认服务在目标账户和区域的可用状态、准入要求与当前文档；若不满足服务条件，应选择可用的替代方案（例如用 SageMaker 构建并治理自定义检测模型），不能只凭历史题库默认可部署。

欺诈预测应与交易规则、人工调查和申诉机制协作；阈值体现误报与漏报的业务权衡，不能仅以模型分数自动拒绝所有交易。

七、对话机器人：Amazon Lex

Lex 用于构建文本或语音对话体验，识别用户意图、从话语中提取槽位，并在对话中补齐所需信息。典型用例是客服自助、预约或订单查询。

  • Intent 表达用户目标；Utterance 是用户可能的表达；Slot 收集完成任务所需参数；Prompt 用于引导补充信息。
  • 通过 Lambda 等集成执行业务逻辑；对接 API Gateway、联络中心或其他渠道时，明确身份验证、会话状态和超时处理。
  • 语音通道可组合 Transcribe/Polly 能力；Lex 的对话理解与后端业务动作仍需区分。
  • 限制敏感数据进入日志，设计不匹配、重试、转人工与失败兜底流程；机器人不应仅因“会对话”就绕过后端授权校验。
意图到动作：识别意图和参数 → 检查用户身份及业务权限 → 调用受控后端 → 返回结果；模型识别不等同于授权。

八、托管 AI 与自定义 ML 的边界

选择维度托管 AI 服务SageMaker / 自定义方案
问题类型标准化视觉、OCR、NLP、翻译、语音、搜索、推荐或对话能力。业务目标特殊，需自定义特征、标签、算法或预测逻辑。
运维服务商管理底层模型基础设施，客户配置调用、权限和数据流程。客户负责数据准备、训练/部署选择、评估与模型运营；平台提供托管工具。
速度与控制更快接入，定制边界由 API 与服务能力决定。控制更强，但需要数据科学、MLOps、成本治理和持续维护。
治理仍需核查区域、配额、数据处理、保留、加密和服务条款。还需治理训练数据、模型工件、端点暴露、漂移和部署版本。

无论选哪种服务，都遵循最小权限、加密、数据最小化、审计和人工复核原则。涉及个人数据、图像或语音时，先确认授权、保留周期、数据区域和日志脱敏，再设计调用链。

九、场景题解析

场景一：扫描的保险申请 PDF 包含表格和表单字段

团队要提取文字、字段和值，减少手工录入。

方向：评估 Textract 的文档分析能力，并按页面/字段结构选择相应 API。
题目目标是从文档版面提取结构，而非识别图片中的物体；结果仍应通过置信度和人工流程校验。
不要用 Rekognition 标签分析来读取表单字段。

场景二：客服想按情感和实体自动整理评论

评论已经是文本，团队不需要自建 NLP 模型。

方向：使用 Comprehend 的情感/实体等文本分析能力。
Comprehend 面向文本理解任务；若还需跨语言，可评估与 Translate 组合。
Polly 是文本转语音，不负责文本情感分类。

场景三：用户上传照片，平台需识别对象并过滤不当内容

希望托管 API 返回标签和审核线索。

方向：使用 Rekognition 对图像执行标签检测与内容审核，并由应用按策略处理结果。
标准图像/视频视觉任务适合专用服务，业务阈值和人工复核需自行定义。
不要把模型输出当作自动授权或合规判定。

场景四：用户说出请求，机器人完成账户余额查询并语音回答

需要识别意图、调用账户系统并播报答案。

方向：Lex 管理对话/意图，受控后端验证身份并查余额，Polly 输出语音；若音频入口需要转录，组合 Transcribe 或 Lex 支持的语音通道。
语音识别、对话理解、业务执行和语音合成是不同职责，必须分别设计权限与错误处理。
Lex 识别了“查余额”不代表用户已经通过账户授权。

场景五：员工用自然语言搜索分散在多个知识库的政策文档

需要按相关性返回受权限保护的文档。

方向：评估 Kendra 连接器与索引，并将源身份/文档访问控制映射到查询身份。
企业内容发现与结构化 SQL 分析是不同问题；索引同步和权限过滤是核心架构要求。
不能只建立共享索引而忽略文档级权限。

场景六：内容平台要根据用户行为推荐下一篇内容

不需要设计新的推荐算法，但需要基于用户互动个性化排序。

方向：用 Personalize 评估推荐方案，确保持续收集质量可靠的交互事件。
推荐是其标准场景；若业务目标/算法需要任意定制，再评估 SageMaker。
Comprehend 可分析文本，但不是个性化推荐引擎。

十二、快速自测

1. OCR 已识别文字，但还要提取扫描表格的行列结构，优先看哪个服务？

Textract 的文档分析能力。

2. 用户说话要转成文字，客服答复要生成语音，服务分别是什么？

Transcribe（语音转文本）和 Polly（文本转语音）。

3. 需要员工对内部文档库做自然语言搜索，应该重点考虑什么并避免什么风险？

评估 Kendra 的连接器、索引与相关性能力，并正确映射源文档权限到查询身份。
