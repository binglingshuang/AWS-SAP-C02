一、定位与核心原则

AWS 架构题通常不是“看你知道哪个服务”，而是看你知道“什么架构在什么需求下合理”。候选答案一般是围绕可用性、成本、安全、弹性和治理之间的 trade-off。

考点关键定义做题提示
RTO恢复时间目标，系统要在多少时间内恢复。业务容忍度越低，越偏向更高冗余和更快切换的方案。
RPO恢复点目标，数据能丢多少时间窗口内的数据。高价值数据通常要求更频繁复制、快照或持续同步。
SLA服务可用性目标，如 99.9% / 99.95% / 99.99%。题目常用 SLA 做“是否须多 AZ / 多 Region”判断。
Trade-off高可用增大成本，严格恢复要求提升复杂度。不要只选“最先进”而忽略成本和运维复杂度。

二、Well-Architected Framework

Well-Architected 不是单一的 AWS 服务，而是一套“评估和改进架构”的框架。SAP-C02 常在多选题里要求你优先判断“最缺失的工程能力”。

支柱核心关注点典型动作
Operational Excellence自动化、日志、变更管理、可观测性CloudFormation、CodePipeline、CloudWatch、AWS Config
Security最小权限、审计、加密、身份隔离IAM、KMS、Organizations、GuardDuty
Reliability故障恢复、自动修复、容错、冗余Multi-AZ、Auto Scaling、Health Check、Backups
Performance Efficiency伸缩能力、低延迟、高吞吐、缓存CloudFront、ElastiCache、ECS/EKS、Auto Scaling
Cost Optimization按需、折扣、审计成本Rightsizing、Savings Plans、Spot、S3 Lifecycle
Sustainability降低能源与资源浪费减少无效运行、合理缓存与调度
记忆口诀：“稳定、可审计、能扩展、可运营、能省钱”。

三、灾难恢复与 RTO/RPO

灾难恢复不是“有没有备份”，而是“在故障后如何恢复、恢复到什么程度、需要多长时间”。

策略特点适用场景
Pilot Light核心服务在备用区域已有最少运行能力；恢复时快速拉起其他组件。允许较长恢复时间，但需较快恢复核心业务。
Warm Standby备用环境持续运行一部分服务，恢复时间中等。中高重要业务，接受分钟级切换。
Hot Standby / Active-Active多站点同时运行，切换时间最短，成本最高。金融、支付、关键 SLA。
Backup-centric以快照、备份和恢复为核心，恢复复杂但成本低。非关键业务、离线分析等。

通常题目会按“恢复时间可以接受多久 / 数据能丢多少”来判断：如果要“几分钟恢复、几秒钟切换”就看 Active-Active；如果“本地数据可接受一天损失”则更偏简单备份策略。在考试中，最容易搞混的是：备份本身不等于 DR，DR 还要有恢复流程、切换策略和演练。

考试常见判断：RTO 短 → 更高可用、更多冗余；RPO 低 → 持续复制、增量同步、快照频率高。

四、高可用与 Failover

高可用的核心是“单点故障不影响业务”。最重要的技术点通常是：多 AZ、自动伸缩、健康检查、DNS failover 和无状态化。

模式说明典型服务
Multi-AZ同一区域不同可用区，适合提升可用性。RDS Multi-AZ、ElastiCache、MQ、EFS
Multi-Region跨区域冗余，适合灾难恢复和区域级故障。Route 53 failover、S3 CRR、Global Accelerator
Active/Passive主站点活跃，备用站点冷/温待命。Route 53 health checks + failover
Active/Active多个站点同时服务请求，流量分发和状态管理更复杂。全球业务、高可用分发

一条核心原则：如果实例、接口、数据库或前端节点是有状态且不能无缝替换，就不要“只靠某个单独节点的副本”来解决 HA；要把状态外置、持久化，并在健康检查和路由层做切换。

优先顺序：1）把状态外置；2）做多 AZ；3）做健康检查；4）配置自动扩容；5）再考虑跨区或跨区域切换。

五、多账号与治理边界

大多数企业不是“一个账号承载所有业务”，而是“管理账号 + 安全账号 + 生产/开发/共享服务账号”的组织结构。这样做的目的，是让网络、权限、配置和账单治理互不污染。

  • 组织层级：Root → OU → Account 的结构有助于统一附加策略、环境隔离和账单控制。
  • 权限边界：在多账号环境中，SCP / IAM / 资源策略共同决定“谁在什么账号下能做什么”。
  • 治理能力：Control Tower、Organizations、Config、CloudTrail 让治理变成平台能力，而不是手工操作。
  • 例子：生产账号不允许直接手工创建资源，开发环境不能访问生产日志，安全账号集中接收审计与检测告警。
典型结论：只要题目给出“多个环境、多个账号、共享网络、集中审计”，优先联想到多账号架构与组织治理，而不是把所有资源塞进一个账户。

六、成本优化原则

在 AWS 上，架构题经常出现“保住 SLA，且更便宜”的方案选择。高分答案通常遵循“先对齐需求，再做成本抑制”。

优化方向典型方法适用场景
Right-size按流量与峰值匹配实例大小长时间低负载应用
按使用付费On-Demand / Serverless / Spot波峰波谷、批处理、非关键任务
缓存与削峰CloudFront / ElastiCache / S3 Lifecycle高并发读取、静态内容与热点数据
降低冗余按业务分层决定是否需要多 AZ / 多 Region非核心系统、低频任务
自动化治理Budget、Cost Explorer、Tagging、Lifecycle Rules企业环境与持续运营

常见错误：以为“更高可用就一定是更强的设计”，忽略了“业务真正需要的是 99.95% 还是 99.99%”。对于非关键业务，Pilot Light 或单区方案通常比 Active-Active 更合理。不要为了“架构炫酷”牺牲成本。

七、场景题解析

场景一：政府部门外部服务必须在 30 分钟内恢复

某网站对外服务，要求关键服务在区域级故障中能在 30 分钟内切换到备用区域，且不要求两地同时处理全部流量。

正确方向：优先采用 Warm Standby 或 Pilot Light，把关键数据库和核心应用按备份/复制方案准备在备用区域，并用健康检查 + Route 53 failover 进行切换。

分析思路：要求“恢复较快但不需要全量活跃双活”，因此高成本的 Active-Active 不是第一选择。

排除：只备份但不设计切换流程；或者直接做全双活，成本远高于需求。

场景二：电商平台在促销峰值时需要弹性扩容并控制成本

流量峰值突然放大，尖峰时段资源需求很高，但正常时段很低。

正确方向：采用 Auto Scaling + CloudFront + 弹性缓存 + 服务器端按量资源，并在非关键组件使用 Spot 或更经济的实例类型。

分析思路：这是典型的“成本优化 + Performance Efficiency”优先题，目标是把固定成本压到最低，同时保住尖峰能力。

排除：一贯保持超大实例规模，或者完全采用单一大机型，会浪费成本。

场景三：企业有生产、开发和共享服务三个环境

各环境之间必须能隔离权限、账单和审计流，且不希望管理员在开发账号中直接访问生产凭证。

正确方向：设计为 多账号组织结构：管理账号、共享服务账号、安全账号、开发/测试/生产账号分层，并通过 SCP、IAM role 和 Control Tower 进行治理。

分析思路：题干对“隔离”和“集中治理”要求明显，单账号方案会导致权限混乱和审计困难。

排除：直接把所有资源放一个账号，或者仅靠 IAM 用户管理隔离，无法满足企业治理要求。

场景四：银行类应用要求 99.99% 可用，但不需要把所有地区都同时承载流量

业务非常关键，要求高可用且对恢复时间非常敏感，但预算有限，不能无限扩容。

正确方向：在主区域做 Multi-AZ + 自动恢复，备用区域准备热/冷切换环境，再通过健康检查与 DNS failover 实现最短切换。

分析思路：高可用不是必须双活；关键是“对关键业务按服务分级做最小可接受恢复方式”，同时保持成本可控。

排除：一味追求全量立刻双活，导致资源浪费和复杂度激增。

场景五：企业正在推行 Well-Architected Review

团队发现问题集中在“配置漂移、审计缺失、日志不集中、没有自动化修复手段”。

正确方向：优化 Operational Excellence 与 Security：自动化部署、统一指标、Config 检测、CloudTrail 审计和统一 IAM/Roles。

分析思路：这类题的核心是“架构评审的失分项”，通常不是增加某个高级服务，而是把治理和自动化落实好。

排除：只购买更强的硬件或大幅扩容，无法解决治理漂移问题。

已掌握 0 / 16

  • 架构决策：先看需求，再选可用性、成本和治理的平衡方案。
  • RTO：恢复时间目标，决定是否需要更快切换和更高冗余。
  • RPO：恢复点目标，决定复制频率和备份策略。
  • Well-Architected：稳定、可审计、可扩展、可运维、可省钱。
  • Pilot Light：最少核心能力保活，恢复时快速拉起其余功能。
  • Warm Standby：备用环境持续运行一部分服务，适合中等恢复要求。
  • Active-Active：双活成本最高，适合严格 SLA 和关键业务。
  • Multi-AZ：同区域提升可用性，不等于跨区域灾备。
  • Multi-Region：跨区域 DR / 故障转移的基础。
  • Failover：健康检查 + DNS / 路由切换 + 自动恢复。
  • 多账号：环境、帐单、权限和审计更容易治理。
  • 控制面与数据面：治理能力不能靠“单一账号”隐藏复杂度。
  • 最小权限：架构中安全优先级高于“所有人都能操作”。
  • 成本优化：右配实例、缓存、Spot、按用量和分层设计。
  • 架构不是炫技：需求决定最优方案，不是“最先进”才是正确答案。
  • 最终判断：先看恢复要求，再看成本和治理平衡，最后才选择服务。

十、快速自测

先独立选择，再点击“查看解析”。

1. 某业务要求在区域级故障后 30 分钟恢复核心功能，并接受备用站点仅保留关键服务。最合理的设计是什么？
正确答案：A。在允许中等恢复时间时，Pilot Light 或 Warm Standby 更符合成本与恢复目标平衡。
2. 生产环境必须保证高可用，但预算有限，不希望所有业务都同时双活。最合理的思路是什么？
正确答案：B。高可用并不一定意味着全业务双活；关键是根据 RTO/RPO、业务重要性、成本做分级设计。
3. 企业发现多环境间权限和账单混杂，应该优先考虑什么？
正确答案：A。多账号治理是隔离、审计、权限和账单管理的关键设计模式。
